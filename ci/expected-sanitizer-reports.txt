# Sanitizer reports that are EXPECTED on a given lane, by signature.
#
#   <preset>  <extended regex matching the expected report line>
#
# Consumed by ci/peak-memory-report.sh, which counts sanitizer reports in
# build/<preset>/Testing/Temporary/LastTest.log separately from ctest's exit
# code (a report does not necessarily fail the test that emitted it).
#
# ⚠️⚠️ SINCE #267 ACCEPTANCE ITEM 5, AN ENTRY IN THIS FILE PERMITS A MERGE.
#
# Read the rest of this header with that in mind, because it was written when
# the stakes were lower. `ci/peak-memory-report.sh` used to EXIT 0 always and an
# unexplained report raised a `::warning::`; it now EXITS 1, and the calling
# steps no longer carry `continue-on-error`. So a line here no longer decides
# only whether an annotation is noisy — it decides whether a sanitizer report
# reddens the lane or merges green.
#
# Nothing about the mechanism changed. What changed is the cost of a wrong or
# over-broad entry, and every accepted tradeoff recorded below should be re-read
# as "…and that now permits a merge", not "…and that now costs us a warning".
# The two ASan entries have exactly such a tradeoff; it is restated at each.
#
# ── WHY AN ALLOWLIST EXISTS AT ALL ───────────────────────────────────────────
#
# Because some lanes emit a report BY DESIGN, on every single run, forever.
# Without this file the instrument raises "real defect until disproven" on
# those lanes every run — a permanent false alarm, and a warning that is
# always there is a warning nobody reads. That is how an instrument decays into
# noise, and it would take the genuine signal down with it.
#
# ⚠️ THIS FILE IS KEYED PER PRESET, SO ENUMERATE EVERY PRESET THAT RUNS THE
# CANARY — NOT JUST THE ONE YOU HAPPENED TO LOOK AT. The first version of this
# file listed only `linux-clang-asan` and missed its Tier 3 twin
# `linux-clang-libc++-asan`, which runs the SAME deliberate witness under the
# SAME mechanism. Result: the very instrument this file protects fired a
# permanent unexplained-report warning on that lane on the run that shipped it
# (32024674144, job 95371515426) — the exact decay described above, introduced
# by the fix meant to prevent it. "The asan lane" has more than one spelling.
#
# ── WHY IT MATCHES A SIGNATURE AND NOT A COUNT ───────────────────────────────
#
# ⚠️ A count pin (`asan: expect 1`) FAILS OPEN and was rejected for that reason.
# If the canary stopped firing and a real defect appeared in the same run, the
# count would still read 1 and the instrument would stay silent — the two
# changes cancel. Matching on the report TEXT cannot cancel that way: a new
# finding is a new signature, and a canary that stops firing removes a line that
# was expected.  Same reasoning as `ci/expected-eligible-tests.txt` choosing
# exact equality over a floor.
#
# ⚠️ An entry here NEVER suppresses output. Every matched report line is printed
# with the count either way; the allowlist decides only whether the `::warning::`
# fires. Nothing is hidden — a reader always sees what was found.
#
# ── ADDING AN ENTRY ──────────────────────────────────────────────────────────
#
# An entry is an assertion that a report is deliberate. It needs: the test that
# emits it, the mechanism that makes ctest green anyway, and the run it was
# observed on. If you cannot write those three, it is not expected — it is a
# finding, and this repo's rule is real-defect-until-disproven.

# ── linux-clang-asan ─────────────────────────────────────────────────────────
#
# `CapiSendRecv.InboundHandleUseAfterReturnCaughtUnderAsan` triggers a
# stack-use-after-return ON PURPOSE, to prove ASan catches it — the
# canary-proven-RED discipline.  ASan's default `halt_on_error=1` aborts the
# process, so ctest stays green only because the test is registered as its OWN
# entry with `WILL_FAIL TRUE` under ASan (`tests/capi/CMakeLists.txt:165-175`).
# That split is itself deliberate: a binary-wide `WILL_FAIL` would invert a REAL
# ASan failure in the positive round-trip tests into a pass.
#
# Observed on runs 32003367497 and 32007171995 — exactly 1, both times.
#
# ⚠️ ANCHORED TO THE ADDRESS-SANITIZER ERROR KIND, NOT TO THE TEST NAME: the
# report line is ASan's own, and it does not carry the test name. Consequence,
# stated rather than discovered later: a stack-use-after-return arising ELSEWHERE
# on this lane would also match and be treated as expected. That is a real gap.
# It is accepted here because the alternative — matching a bare
# `AddressSanitizer:` — would allowlist every ASan error class on the lane, which
# is far worse. Narrowing it further needs per-test attribution in LastTest.log,
# which CTest does not make cheap.
#
# ⚠️ #267 RAISED WHAT THAT GAP COSTS, AND IT IS NOW THE GATE'S ONE KNOWN HOLE.
# When this paragraph was written the gap meant a missed WARNING. Since the
# counter fails closed, it means a genuine stack-use-after-return ANYWHERE on
# this lane exits 0 and merges green. Every OTHER ASan error kind on the lane
# still reds it, TSan and UBSan are untouched, and the collision needs the same
# error class — so the hole is narrow. But it is a hole, it is deliberate, and
# `T19b` of ci/test-peak-rss.sh asserts the permitting behaviour as correct.
# Closing it means per-test attribution, which is #266's by-test aggregation
# extended to the ALLOWLIST rather than only to the report — not a bigger regex.
linux-clang-asan    ERROR: AddressSanitizer: stack-use-after-return

# ── linux-clang-libc++-asan (Tier 3) ─────────────────────────────────────────
#
# THE SAME witness, on the Tier 3 libc++ ASan lane. Same three facts:
#
#   test       `CapiSendRecv.InboundHandleUseAfterReturnCaughtUnderAsan`, via the
#              `capi_send_recv_uaf_negative` ctest entry.
#   mechanism  `WILL_FAIL TRUE` is gated on `if(FIXPP_ENABLE_ASAN)`
#              (`tests/capi/CMakeLists.txt:174-176`) — it keys on ASAN BEING ON,
#              not on the standard library, so this lane registers the negative
#              entry identically and ctest stays green.
#   observed   run 32024674144, job 95371515426 (2026-08-17) — exactly 1,
#              signature byte-identical to the Tier 1 lane's.
#
# Same accepted gap as above, and since #267 the same raised cost: anchored to
# the ASan error KIND, not the test name, so an unrelated stack-use-after-return
# on this lane would also be treated as expected — and "treated as expected" now
# means exits 0 and merges green, not merely un-warned. Same reasoning for
# keeping it — the alternative (a bare `AddressSanitizer:`) would allowlist every
# ASan error class on the lane. See the Tier 1 entry for what closing it takes.
linux-clang-libc++-asan    ERROR: AddressSanitizer: stack-use-after-return

#
# In particular `linux-clang-ubsan` has NONE, deliberately. Its 1 report on runs
# 32003367497/32007171995 is a GENUINE finding —
# `tests/capi/public_roundtrip_test.cpp:129` loads an out-of-range enum — filed

# is the failure this file must never become.
#

# like the libc++-asan omission fixed above — a Tier 3 twin warning every run —
# which makes it tempting to "fix" it the same way. DO NOT. Measured on run
# 32024674144 (job 95371515603): 1 report, `ran: 356/356`, ctest green. That is
# #268 reproducing on the libc++ lane, i.e. the finding is NOT libstdc++-specific.
# The asan twin was an enumeration bug in this file; this one is a real defect in
# the code. Same symptom, opposite disposition — the difference is whether the
# report is deliberate, and #268's is not.
