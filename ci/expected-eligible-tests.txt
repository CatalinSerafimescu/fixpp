# Per-lane expected test count for the #229 / #266 peak-memory acceptance.
#
#   <preset>  <expected count>      # `-` = no CI-derived basis recorded yet
#
# ── WHY A PIN AT ALL ─────────────────────────────────────────────────────────
#
# A peak-memory figure is only evidence for `ctest --parallel` if it was taken
# over the workload it claims to describe.  `ctest` exits 0 on a workload of
# ZERO tests, so a green Test step alone does not mean "the suite ran".  The pin
# makes the acceptance HEADING conditional on the run having executed the number
# of tests the recorded basis was taken at.
#
# ⚠️ THE DIRECTION IS SAFE BY CONSTRUCTION, and that is the whole design.  A
# STALE pin degrades a run toward "DIAGNOSTIC ONLY / not evidence"; it can never
# degrade toward a false acceptance.  A mismatch is therefore the DESIGNED
# PROMPT to re-record the basis in ci/ctest-parallelism-probe.md and update the
# line here in the same commit — it is not a broken gate.  Do NOT replace exact
# equality with a floor (`>= 340`): a floor inverts the safe direction and would
# admit a run that silently lost twenty tests as acceptance evidence.
#
# ── TWO CELLS IN ci/test-parallelism-verdict.sh READ THIS FILE ───────────────
#
# Editing a line here can break them, and it has:
#
#   T24 states a count that MATCHES a pin, so it names a number this file holds.
#       Re-record a pin, re-record T24 in the same commit.
#   T25 needs a preset with NO pin at all. It used `windows-msvc-asan` until
#       that lane got its first line below — at which point the cell silently
#       stopped exercising the no-pin path. It now uses `linux-gcc-debug`, the
#       only unpinned preset left; pinning that lane must move the cell, not
#       weaken it.
#
# Named here because this is the file someone edits, and the coupling is
# invisible from it otherwise.
#
# ── WHY IT IS PER-LANE, AND NOT ONE NUMBER ───────────────────────────────────
#
# The counts genuinely DIFFER per lane — some tests are registered only under
# certain build types or sanitizers.  #245's single `expected_eligible=350`
# applied to `linux-clang-tsan` alone, which was correct while the probe ran on
# that one lane.  #267 widens `--parallel` lane by lane and requires a peak
# reading PER LANE, so one constant would be wrong for five of the six, not
# merely stale.
#
# ── WHY THE VALUES MUST BE DERIVED IN CI, NOT LOCALLY ────────────────────────
#
# ⚠️ Local and CI trees do NOT agree, and the previous pin was set from a local
# derivation.  The #229 local sweep (2026-08-16, `main` @ 0b51b1da) counted
# 376 eligible tests on `linux-clang-tsan` and 377 on `linux-clang-debug`; CI on
# the same content ran 361 and 362.  Fifteen tests are registered locally that
# are not registered on a runner.  A value derived on a workstation is therefore
# not a CI basis, however carefully it was measured.
#
# The counts below are read from the CI job logs of ONE `push:main` run —
# run 31737273371, commit `5c56a17e` (Tier 1) — the same run every figure in
# #266/#267/#229's 2026-08-16 comments is taken from.  Our branch changes no
# test registration, so they carry over; the first CI run on this branch is the
# CONFIRMATION, and any lane that renders DIAGNOSTIC ONLY gets its line
# corrected here rather than argued with.
#
# ── #268: +1 ON EVERY LANE ───────────────────────────────────────────────────
#
# `capi_reset_seqnum_policy_range` is a new `add_test` in tests/capi/CMakeLists.txt
# with NO `if()` guard and no label, in a directory every lane includes — so it
# lands in both the `-LE packaging` minimal tier and the full-tier lanes alike.
# Every line below is therefore its previous CI-derived value + 1.
#
# ⚠️ THIS IS ARITHMETIC ON A CI BASIS, NOT A LOCAL DERIVATION — the distinction
# this file's own header insists on. Nothing here was counted on a workstation
# (which the header measures as 15 tests adrift of a runner); a single
# unconditional registration was added to numbers read off CI logs. The first CI
# run on this branch is still the CONFIRMATION, and per the header a mismatch
# renders that lane DIAGNOSTIC ONLY rather than failing it — the safe direction.
#
# ⚠️ #268 also DELETES a gtest case (`PublicRoundtrip.SetResetSeqnumPolicyOutOfRange`),
# and that is deliberately NOT a -1: this project registers each gtest BINARY as
# one ctest entry (`add_test(NAME capi_pure_tests COMMAND capi_pure_tests)` and
# siblings) rather than using `gtest_discover_tests`, so removing a TEST inside a
# binary moves no ctest count. Stated because "+1 -1 = 0" is the plausible wrong
# answer here.
