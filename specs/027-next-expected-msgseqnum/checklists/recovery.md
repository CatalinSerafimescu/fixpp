## Requirement Clarity

- [x] CHK006 Is the proactive-resend range specified as exactly `[X, N-1]` inclusive (not `[X, N]`), with N defined as next-outbound? [Clarity, Spec §FR-003, data-model I-NEX-2] — PASS: FR-003 explicitly states "proactively resend the range `[X, N-1]`"; data-model I-NEX-2 states "The resend range is `[X, N-1]` inclusive — NOT `[X, N]` (N is the next-to-assign, not yet sent)"; research D-5 states "resending `[X, N]` inclusive (off-by-one — N is the *next* to assign, not yet sent)" as an explicitly rejected alternative. Unambiguous.
- [x] CHK007 Is the behind-side post-recovery counter target stated unambiguously as `peer_N` (and explicitly NOT `X_logon+1`)? [Clarity, data-model I-NEX-5/I-NEX-12] — PASS: data-model I-NEX-5 states "After the fill `next_inbound_ == peer_N` (NOT `X_logon + 1` — `set_next_inbound(X_logon+1)` would make the peer's resent frames at `[X, X_logon]` … too-low → fatal disconnect)"; I-NEX-12 names this invariant explicitly and mandates the RED witness asserts `final next_inbound_ == peer_N` with peer_N set ≥1 frame beyond the Logon so the two values diverge; research D-7 derives the formulation-A model and marks `set_next_inbound(X_logon+1)` as "REJECTED — wrong". Unambiguously stated including the negative.
- [x] CHK008 Is the acceptor resend ORDERING specified (resend after the reply Logon's emit, not at the parse point)? [Clarity, Spec §Clarifications "Acceptor resend ordering", contracts C4] — PASS: spec Clarifications Session 2026-06-07 Gate A round 1 Q "Acceptor resend ordering for X<N?" → "AFTER the reply Logon's `store_then_emit` succeeds (`:1766`), not at the 789 parse point"; contracts C4 states "the resend runs AFTER the reply Logon's `store_then_emit` succeeds (`:1766`), not at the parse point (RC#4 ordering)"; plan notes RC#4 ordering; tasks T014 enforces it. Clear ordering requirement.
- [x] CHK009 Are the reused resend semantics specified precisely — application messages with `PossDupFlag(43)=Y`+`OrigSendingTime(122)`, contiguous admin collapsed into `SeqReset`-`GapFill`? [Clarity, Spec §FR-008] — PASS: FR-008 states "original application messages re-sent with `PossDupFlag(43)=Y` and the original `OrigSendingTime(122)`; contiguous administrative ranges collapsed into `SeqReset`-`GapFill`"; data-model I-NEX-3 repeats this; contracts C3 confirms "stored app messages replayed with PossDupFlag(43)=Y+OrigSendingTime(122) at original MsgSeqNum; collapses admin/absent runs into one SeqReset-GapFill". Precisely specified.
- [x] CHK010 Is "both-peers-required" stated as a measurable limitation (no automatic ResendRequest fallback) rather than a vague caveat? [Clarity, Spec §FR-009, L-027-1] — PASS: FR-009 is explicit: "there is NO automatic `ResendRequest` fallback when the knob is enabled.
