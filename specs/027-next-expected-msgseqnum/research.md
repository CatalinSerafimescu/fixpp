# Research — NextExpectedMsgSeqNum(789) fast session resume

Phase 0 grounding. All NEEDS CLARIFICATION resolved (the spec's two deferred axes were settled at `/speckit-clarify` via the reference-engine sweep; the source sweep below settled the integration seams). **Gate A round 1 re-derived the honor/suppression design against the real fixpp FSM — the earlier draft modelled a single inbound-Logon handler + an Active too-high arm that do NOT exist on the reconnect-Logon path. The corrected source model (D-3..D-7, D-10, D-11) is the binding one.**

## D-0: The real two-handler inbound-Logon FSM (the source model the honor design is derived against)

- **Decision**: fixpp has **two structurally distinct inbound-Logon handlers**, both currently fatal-on-too-high with **no AwaitingResend / no ResendRequest on the Logon path**:
  - **Acceptor** `case fsm_state::NotConnected` (`session.cpp:1508`): `interpret_logon` (`:1514`) → `scan_frame_header`/`parse_seqnum` (`:1539/:1540`) → optional `reset_on_logon` reset (`:1562`) → `check_inbound(seq)` (`:1571`, **advances `next_inbound_` on success, fatal→Disconnected on too-low/too-high**) → CompID auth → build reply Logon `reply_seq=peek_outbound()` (`:1744`), `build_logon` (`:1745`) → `assign_outbound` (`:1756`) → `store_then_emit` (`:1766`) → transition Active (`:1779`).
  - **Initiator** `case fsm_state::LogonSent` (`session.cpp:2755`): `interpret_logon` (`:2768`) → `scan_frame_header` (`:2781`) → SendingTime guard → `parse_seqnum` (`:2836`) → `check_inbound(seq)` (`:2842`, **fatal→Disconnected on failure**, `:2843`) → optional received-141 reset (`:2860`) → CompID auth → transition Active. The initiator's OWN Logon was already emitted earlier by `emit_initiator_logon_` (`:601`).
  - The arm at `session.cpp:1968-2009` is the **steady-state Active-path** too-high arm (`case fsm_state::Active`, guard `seq > next_inbound_unsafe() && !reconnect_fsm_.is_awaiting_resend()` @ `:1969`): it enters `AwaitingResend` and emits `ResendRequest(2)`. A reconnect Logon does **not** flow through it.
- **Rationale**: every honor / suppression site must be placed in the two Logon handlers, not in the Active arm. FR-007's "symmetric across both roles" is asserted over two *asymmetric* handlers, so the design enumerates each separately. The Active arm is only a *secondary* suppression site (steady-state gap while the knob is on — D-7).
- **Alternatives considered**: wiring honor into the single `:1968` arm (the original draft — wrong: off the reconnect-Logon path, initiator never reaches it, behind-side fatal at `check_inbound` first).

## D-1: Tag 789 is already in fixpp's FIX 4.4 dictionary + Logon (NO codegen)

- **Decision**: do NOT add tag 789 or touch codegen. `dictionaries/FIX44.xml:6128` defines `<field number='789' name='NextExpectedMsgSeqNum' type='SEQNUM'/>`, and the `Logon` message block (`:278`) lists `<field name='NextExpectedMsgSeqNum' required='N'/>` at `:284`.
- **Rationale**: the **dictionary/codegen need not change**. But inbound Logon processing at this seam does NOT use a generated validator — it uses the hand-written `interpret_logon` (`admin_messages.cpp:167`, an Iter-scan of 8/35/49/56/108) and the hand-written `scan_frame_header` (`session.cpp:1170`, a tag switch at `:1213`). An unknown tag is *tolerated because the hand scans simply ignore tags they don't switch on*, not because a validator passes it. So the work is: **the hand scan must add a `case 789:`** (D-3) and `interpret_logon` continues to tolerate the optional field. FR-010 ("no codegen / no new error slot / no C-ABI") holds.
- **Alternatives considered**: adding 789 to a custom-fields extension (unnecessary — already present); a codegen pass (unnecessary).

## D-2: Single knob, emit+honor, default off (Clarifications Q2)

- **Decision**: one additive `SessionConfig` bool `enable_next_expected_msg_seq_num = false`, controlling BOTH emit and honor.
- **Rationale**: QFcpp `m_sendNextExpectedMsgSeqNum` (`Session.cpp:71` default false) and QFJ `enableNextExpectedMsgSeqNum` (`Session.java:443` default false, setting `EnableNextExpectedMsgSeqNum`) both use a single knob. A primitive bool needs no new header include ⇒ §XV.9 is N/A (contrast 026, which added a chrono include).
- **Alternatives considered**: split emit/honor knobs (no use case; doubles config + test surface; diverges from both engines).

## D-3: Emit — conditional 789 append in the hand-written build_logon + tag-789 capture in the hand scan

- **Decision**: (emit) add an optional `next_expected_seq` parameter to `build_logon` (`admin_messages.cpp:75`); when present, append tag 789 (`render_u32` + `w.append_raw(789, …)`) after the existing `ResetSeqNumFlag(141)` block (`:150-155`). Pass it from the two Logon-build call sites: the initiator path `emit_initiator_logon_` (`session.cpp:601`) and the acceptor reply (`session.cpp:1745`). (capture) add `std::string_view next_expected_msg_seq_num;` to the `FrameHeader` struct (`session.cpp:1152`) and a `case 789:` to the `scan_frame_header` switch (`:1213`).
- **Rationale**: `build_logon` already conditionally appends 141 via `bool reset_seqnum` — 789 is the exact parallel. Both build sites already exist; this is additive. QFcpp emits at the same two points (`generateLogon()` for the initiating Logon, `generateLogon(aLogon)` for the reply). The header scan already captures 7/16/36/43/122/123/141 via `case` arms — 789 is one more.
- **Alternatives considered**: a post-build field injection (fragile — re-frames BodyLength/CheckSum); emitting only on the initiator (breaks FR-007 both-roles).

## D-4: Advertised value + the acceptor-reply off-by-one — RESOLVED (no `+1`)

- **Decision**: the advertised 789 = next-expected-**inbound** = `seqnum_mgr_.next_inbound_unsafe()` at BOTH build sites, **plain (NO `+1`)**.
  - **Initiator** `emit_initiator_logon_` (`:601`): the own Logon is built before any peer Logon is received, so `next_inbound_` has not been advanced for this exchange — `next_inbound_unsafe()` is the correct next-expected.
  - **Acceptor reply** (`:1745`): the inbound Logon was already passed to `check_inbound(seq)` (`:1571`), which **advances `next_inbound_` on success**. So by the reply-build site `next_inbound_unsafe()` is already post-increment = the next seqnum we expect from the peer after this Logon. **No `+1` is needed** — this is exactly where fixpp diverges from QFcpp.
- **Rationale**: QFcpp documents `generateLogon(aLogon)` as `getExpectedTargetNum() + 1` "because incoming Logon did not increment the target SeqNum yet" — but fixpp DOES increment earlier (`check_inbound` @ `:1571` < reply build @ `:1745`). Copying QFcpp's `+1` blind would advertise one too high → the peer would resend a wrong range or trip a false X>N error. Resolved from the increment order in source; RED-witnessed (round-trip: acceptor's advertised 789 == the peer's actual next send).
- **Alternatives considered**: blindly using `next_inbound_unsafe() + 1` at the acceptor (wrong — double-increments); deferring to "pin later" (the fact is knowable now from `:1571` vs `:1745`).

## D-5: Honor — comparison basis + the `replay_outbound_range_` EXTRACTION (RC#2)

- **Decision**: on an inbound Logon carrying `789=X`, with `N = seqnum_mgr_.peek_outbound()`: present-but-invalid X (parse→0) ⇒ Logout+disconnect (D-10, evaluated FIRST); else `X<N` ⇒ resend `[X, N-1]`; `X==N` ⇒ nothing; `X>N` ⇒ error (D-6). The `X<N` resend reuses the resend walk — but **"reuse" is an EXTRACTION, not a free call**: the walk at `session.cpp:2485-2635` is a 150-line inline `if (hdr.msg_type == "2")` block, NOT a callable helper. The design therefore introduces:

  ```
  asio::awaitable<expected_t<void>> replay_outbound_range_(
      seqnum_t begin, seqnum_t requested_end, bool end_is_through_current);
  ```

  **The helper MUST preserve the inline walk's TWO-value end model — a single `(begin, end_inclusive)` signature is WRONG and regresses the shipped 013 ResendRequest caller.** The inline walk carries BOTH:
  - `eff_end` = the clamped store-walk upper bound = `min(requested, our_last)` (`:2552-2553`), used as the per-slot loop bound and the trailing-flush `eff_end+1` NewSeqNo (`:2627`);
  - `rr_end` = the ORIGINAL requested end (raw parsed `EndSeqNo`, `:2487`), used as the `NewSeqNo` basis for the empty/short-store GapFill (`:2558-2559`: `NewSeqNo = (rr_end==0) ? peek_outbound() : (rr_end+1)`).

  A `(begin, end_inclusive=eff_end)` helper would LOSE `rr_end`: peer requests `[10,20]`, store through 5 ⇒ `eff_end=5`; the empty-store branch (`rr_begin=10 > eff_end=5`) needs `NewSeqNo=rr_end+1=21`, but a helper given only `5` would emit `→6` or `→peek_outbound()` — silently mis-filling and corrupting the **shipped 013 ResendRequest path**, not just the new 789 path. So the helper takes `(begin, requested_end, end_is_through_current)` and **owns the resolution internally**: `eff_end = (end_is_through_current || requested_end > our_last) ? our_last : requested_end`; the empty/short-store GapFill NewSeqNo = `end_is_through_current ? peek_outbound() : (requested_end+1)`. What the two callers pass:
  - **789 caller**: `begin = X`, `requested_end = N-1`, `end_is_through_current = true` (N-1 is our current last outbound, so the through-current/`peek_outbound()` NewSeqNo branch is the correct basis when the store is short).
  - **ResendRequest caller**: `begin = rr_begin`, `requested_end = rr_end` (raw parsed `EndSeqNo`), `end_is_through_current = (rr_end == 0)` (the `EndSeqNo=0 ⇒ through-current` flag — the resolution moves INTO the helper, removed from the handler).

  factored from the inline block. What moves into the helper:
  - the two local lambdas `transmit_async` (`:2500`) and `emit_gapfill_async` (`:2525`), and the `is_admin_type` lambda (`:2516`) — now helper-private (or free file-static);
  - the `gapfill_callback_threw` flag (`:2524`) — its semantics (distinguish toAdmin-threw from transport-error) are preserved, surfaced to the caller via the `expected_t` (`app_callback_threw`);
  - the `our_last` clamp via `store_->next_seqnum` (`:2547-2553`) AND the `eff_end`/`rr_end`-NewSeqNo resolution (`:2552-2559`) — both move INTO the helper (per the two-value model above); the `EndSeqNo=0 ⇒ through-current` decision is conveyed by `end_is_through_current`, not re-derived in the caller;
  - the empty-store early GapFill (`:2557-2568`), the per-slot store-walk loop with `CaptureVisitor`/`build_replay_frame` (`:2581-2625`), and the trailing gap flush (`:2626-2633`);
  - the **embedded `record_state_transition_(Disconnected)` + early `co_return`s** (6+ sites): the helper instead returns `std::unexpected(...)` (or a sentinel) and the **caller** owns the FSM transition. The ResendRequest handler (Active) maps a helper failure to its existing Disconnected disposition; the 789 caller (on the Logon path) maps it to Disconnected too. This avoids the helper silently driving FSM transitions that differ by call site.
  - **Invariant-count regression** ([[feedback_half_restructure_symmetric_api]]): exactly ONE walk implementation; both the ResendRequest handler and the 789 path call `replay_outbound_range_`. A grep/structural test asserts the inline `for (seqnum_t k = ...; store_->retrieve` walk body exists in exactly one place.
  - **Required two-value-end tests (both callers)**: explicit-end-beyond-store (peer requests `[10,20]`, store through 5 ⇒ GapFill `NewSeqNo=21`, NOT 6 — guards the shipped 013 regression) AND `EndSeqNo=0`/through-current empty-store (`NewSeqNo=peek_outbound()`), exercised through BOTH the ResendRequest caller and the 789 caller (the 789 caller's `end_is_through_current=true` empty-store case asserts `NewSeqNo=peek_outbound()`; its explicit `requested_end=N-1` short-store case asserts the resend reaches `peer_N`).
- **Rationale**: `peek_outbound()` is exactly QFcpp's `getExpectedSenderNum()`. A second resend implementation would drift; but the existing block is not a function, so the extraction is a first-class design element + task, with its embedded disconnect/throw semantics explicitly re-homed.
- **Alternatives considered**: a fresh resend loop for 789 (drift, duplicate gap-fill logic); leaving the disconnect transitions inside the helper (it would Disconnected from the wrong call-site context); resending `[X, N]` inclusive (off-by-one — N is the *next* to assign, not yet sent); a single `(begin, end_inclusive)` signature with the `EndSeqNo=0`/clamp resolution kept in the caller (REJECTED — loses `rr_end`, regresses the shipped 013 ResendRequest GapFill NewSeqNo for an explicit-end-beyond-store request, see the two-value model above).

## D-6: Too-high (X>N) disposition — Logout(text)+disconnect (Clarifications Q3)

- **Decision**: when `X>N`, `build_logout` with explanatory text (e.g. "NextExpectedMsgSeqNum too high, expecting N but received X") then disconnect; do not enter the established state as in-sync. Applies in BOTH handlers.
- **Rationale**: both engines do exactly this — QFcpp `generateLogout(stream)+disconnect()` (`Session.cpp:230-237`), QFJ `generateLogout("Tag 789 (NextExpectedMsgSeqNum) is higher than expected …")` (`Session.java:2257-2260`). The peer is claiming receipt of messages we never sent — an unrecoverable integrity violation. `build_logout` already exists and is called at `session.cpp:2128` (Active Arm-D) and `:2817` (initiator SendingTime guard).
- **Alternatives considered**: silent disconnect (no diagnostic); session Reject + continue (wrong for an unrecoverable violation); neither matches the engines.

## D-7: Behind-side recovery + suppression — both handlers, NO fallback (Clarifications Q1, RC#1)

- **Decision**: "suppress the ResendRequest" is *necessary but not sufficient* — the behind side must also ACCEPT the peer's proactive resend instead of fatally disconnecting at its own `check_inbound`. When the knob is on and the peer's Logon `MsgSeqNum` is itself too-high:
  - **Acceptor** (`:1571`) and **initiator** (`:2842`): a too-high `check_inbound` result for the peer's Logon `MsgSeqNum = X_logon` MUST NOT fatally Disconnected. **Held-Logon consume model — formulation A (do-NOT-advance):** the handler does NOT take the fatal branch, leaves `next_inbound_` at its current value X (does NOT `set_next_inbound`, does NOT advance for the held too-high Logon's own seqnum — the held Logon is held/ignored for counting purposes), emits NO at-logon `ResendRequest`, and proceeds toward Active. The peer's proactive resend of `[X, peer_N-1]` (driven by OUR advertised 789) is admitted **in-sequence through the existing Active in-sequence path** (`seqnum_manager.cpp:85-87` advances by 1 per PossDup app frame; admin/Logon ranges jump via `apply_inbound_sequence_reset` @ `:2227`), carrying `next_inbound_` forward frame-by-frame to `peer_N`. The held Logon's own seqnum is **consumed by being inside the peer's resend range** (the resend always spans `X_logon`, since `X_logon ≤ peer_N-1`), NOT by a separate count or `set_next_inbound`. After the fill `next_inbound_ == peer_N` and the next live frame (seq `peer_N`) is in-sequence.
    - **Why NOT `set_next_inbound(X_logon+1)` (the wrong intuition):** that would make the peer's resent frames at `[X, X_logon]` arrive too-low (`< X_logon+1`) → fatal too-low (`seqnum_manager.cpp:67-70`) → breaks the feature. The correct target is `peer_N`, reached by in-sequence admission, NOT `X_logon+1`.
    - **FSM expression — Active in-sequence path, NOT an explicit AwaitingResend entry:** because `next_inbound_` is left at X, the resent `[X, peer_N-1]` frames are in-sequence relative to the un-advanced counter, so they flow through the ordinary in-sequence admit — `enter_awaiting_resend` is NOT engaged on the Logon path. AwaitingResend (`:2213-2217` gap-close exit / Arm A too-low admit `:2169-2204`) is needed only if the peer interleaves a too-low PossDup, which 021/022 Arm A already handles independent of 789; engaging it here for the in-sequence fill is unnecessary and would interact with the `:2213-2217` gap-close exit and the Active arm's `!is_awaiting_resend()` guard @ `:1969`. The behind-side handler therefore relies purely on the in-sequence Active path; it does not set `outstanding_end`.
  - **Active arm** (`:1968-2009`): when the knob is on, the steady-state too-high arm still exists (it is the recovery-of-last-resort for a lost proactive resend — D-11), but at logon the gap is closed by 789, so a knob-on reconnect should not normally reach it for the at-logon range.
  - There is NO automatic fallback to `ResendRequest` when the peer doesn't support 789 — operators MUST enable 789 on both ends (limitation L-027-1). All suppression/tolerance is gated strictly on the knob; the default path is byte-identical (013 recovery intact).
- **Rationale**: neither QFcpp nor QFJ has an automatic fallback — when the knob is set, the too-high path does `resendRange`+queue (admits the fill) instead of `doTargetTooHigh` (the ResendRequest path). The original draft only suppressed the (wrong, Active) arm and never specified how the behind side admits the fill — leaving it to fatally disconnect at `check_inbound` BEFORE any resend, doing the opposite of the feature's purpose.
- **Alternatives considered**: a timer-based fallback (divergent, complex); suppressing only the emit but still calling fatal `check_inbound` (the behind side disconnects on the peer's Logon — non-functional); **`set_next_inbound(X_logon+1)` to "consume" the held Logon (REJECTED — wrong)**: this advances past the peer's own resend range, so the peer's resent frames at `[X, X_logon]` arrive too-low and fatally disconnect — the opposite of formulation A. The correct post-recovery counter is `peer_N` (reached by in-sequence admission), not `X_logon+1` (which only coincidentally equals `peer_N` when there were zero post-Logon app frames). RED-witness `final next_inbound_ == peer_N` (data-model I-NEX-12).

## D-8: Interaction with the 024 ResetSeqNumFlag(141) knobs — cause-dependent (RC#3)

- **Decision**: the advertised 789 is read from the live `seqnum_mgr_` at the build site, so it is **cause-dependent** (mirrors the 024 reset split, `session.cpp:1562` before vs `:1718` after `check_inbound`):
  - initiator reset Logon (`emit_initiator_logon_`, reset @ `:559` BEFORE build) ⇒ advertise **1**;
  - acceptor reply under `reset_on_logon` (reset @ `:1562` BEFORE `check_inbound(1)` which advances to 2) ⇒ advertise **2**;
  - acceptor reply under 013-only received-141 (reset @ `:1718` AFTER `check_inbound`, before build) ⇒ advertise **1**.
- **Rationale**: `[FIX-SL §4.5.2]` — after a reset both sides restart at 1, but fixpp's advertised value reflects the *post-`check_inbound`* counter at the build site, which the 024 cause-dependent split makes 1 or 2. A blanket "advertise 1" is affirmatively wrong for the `reset_on_logon` acceptor case (it advertises 2). RED-witness all three.
- **Alternatives considered**: special-casing 789 to force 1 under reset (wrong — would diverge from the counter the peer actually advances to); a single blanket rule (the original draft — wrong for one of two reset causes).

## D-9: Scope boundary — orthogonal to 025 hydrate-on-open

- **Decision**: 027 is the *Logon-time* advertise/honor mechanism only; it reads the in-memory `seqnum_mgr_` state. It does NOT add store→manager hydration at open() — that is the parked 025 dependency (cross-restart continuity). 789 fast-resume operates within a live reconnect where the seqnum state is already in memory.
- **Rationale**: keeps this a thin G3 slice; the cross-restart persistence is a separate, riskier 008-boundary slice (the G3 capstone, [[project_025_refresh_on_logon_bundling_plan]]).
- **Alternatives considered**: bundling hydration here (out of scope — that's 025).

## D-10: Invalid inbound 789 — Logout+disconnect, evaluated before X<N (RC#3)

- **Decision**: `parse_seqnum` (`session.cpp:1266`) returns **0** for empty, non-digit, AND overflow. The honor logic adds an explicit present-but-invalid branch: `if (789 present AND parse(789)==0) ⇒ Logout("NextExpectedMsgSeqNum invalid")+disconnect`, evaluated BEFORE the `X<N` compare.
- **Rationale**: without this branch, a malformed `789=garbage` yields X=0, `0 < N` is true, and the `replay_outbound_range_` clamp `begin>0?begin:1` (`:2560`) would replay `[1, N-1]` — the entire session history, a **remote-triggerable amplification**. An unparseable next-expected is as unrecoverable as an impossible one (X>N), so parity with D-6 is the natural disposition. RED witnesses: `789=` (empty), `789=abc`, overflow.
- **Alternatives considered**: documented-ignore (a hostile peer could keep us advertising while never recovering — but the amplification is the worse risk, so fail-closed); clamping X to 1 (still replays full history).

## D-11: Lost proactive resend — recovery-of-last-resort via the Active arm (New-P2#1)

- **Decision**: 789 suppresses the *at-logon* `ResendRequest` only, NOT the steady-state Active too-high arm (`:1968-2009`). If the peer's proactive resend frames are lost after the Logon exchange, the residual gap is detected by the next inbound frame on the Active path, which still issues a `ResendRequest`. The session therefore self-heals via the Active path rather than wedging.
- **Rationale**: distinguishes "suppressed at logon" from "suppressed forever". This makes the both-peers-required limitation (L-027-1) about the *fast-path*, not a permanent loss-of-recovery. If a future change ever suppresses the Active arm too, that becomes L-027-2 (a genuine never-recover hole) — documented so the distinction is not silently lost.
- **Alternatives considered**: suppress the Active arm too (would create a permanent gap on resend loss — rejected); a dedicated 789 retry timer (out of scope, divergent).

## D-12: Bidirectional simultaneous resend — no deadlock / no double recovery (New-P1#3)

- **Decision**: at reconnect both sides may advertise 789 and both resend. The analysis **rests explicitly on the D-7 / I-NEX-5 held-Logon counter model (formulation A) + the Active-transition ordering**: (a) the acceptor's resend is emitted AFTER its reply Logon `store_then_emit` (`:1766`); the initiator's resend follows its own already-sent Logon. (b) Each side's resend is transmit-only (`replay_outbound_range_` does not advance the LOCAL live OUTBOUND counter, frames not re-stored — preserved from the walk's existing semantics), so neither side's own resend perturbs its own sequencing. (c) Because each side leaves its INBOUND counter at X (formulation A — does NOT `set_next_inbound` for the peer's too-high Logon), the peer's resent `[X, peer_N-1]` frames arrive **in-sequence** and advance that counter one-by-one to `peer_N`; each side recognises them as in-sequence fill (PossDup app / GapFill admin), NOT as a fresh too-high gap — so it does NOT re-trigger recovery (no double recovery, FR-004), and there is no double-count (the held Logon's seqnum is consumed once, by being inside the resend range). (d) **Transition-ordering assumption (made explicit):** the peer's resend frames flow through the Active in-sequence path, which requires the local handler to have already transitioned to Active. The behind-side handler does NOT take the fatal `check_inbound` and proceeds to Active on the same Logon; a peer resend frame cannot be admitted by the `NotConnected`/`LogonSent` Logon-only handler (it is a non-Logon frame there). The resent frames carry seqnums within `[X, peer_N-1]` (≤ what each side expects after admitting the fill, since the counter is left at X), so once Active they are in-sequence, not too-high, and do not race a fresh `check_inbound` fatal. If transport were to deliver a resend frame before the local Active transition, it is a non-Logon frame in a Logon-only handler — handled by that handler's existing guards (not the resend-admit path); the witness exercises the post-Active interleave that the feature relies on.
- **Rationale**: 789 is symmetric and a bidirectional gap is the normal reconnect case; without this analysis each side's resend could be mis-read as a new gap → double recovery (the exact FR-004 violation the feature forbids). RED witness: a bidirectional-gap round-trip recovers both directions with zero `ResendRequest` and no duplicate delivery.
- **Alternatives considered**: serialising the two resends (unnecessary — transmit-only + behind-side tolerance already make it safe).
