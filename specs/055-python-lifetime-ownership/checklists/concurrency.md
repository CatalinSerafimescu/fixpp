# Concurrency, GIL & Reentrancy Requirements Checklist: Python bindings ownership / lifetime layer (PY-004)

**Purpose**: Validate that the threading/GIL/reentrancy REQUIREMENTS (GIL-protected state, concurrent-close race, `_in_callback` reentrancy detection, deadlock-avoidance, sub-interpreter rejection) are complete, unambiguous, consistent, and measurable. Tests requirements writing, not code.
**Created**: 2026-06-27
**Feature**: [spec.md](../spec.md) · [data-model.md](../data-model.md) · [contracts/python-lifetime-api.md](../contracts/python-lifetime-api.md)

## Requirement Completeness

- [x] CHK001 Is it required that ALL lifetime/ownership/marker state is GIL-protected rather than OS-thread-keyed (no `threading.local`, no thread-id assumptions)? [Completeness, Spec §FR-016, data-model E-6/E-7] — PASS: FR-016 requires the state to be "correct regardless of which engine worker thread runs a callback — it is protected by the GIL, not keyed to an OS thread id (`[2m §1.3]` director rule 4)"; data-model E-7 states "GIL-protected (lives on the Python `Session`, not `threading.local`)."
- [x] CHK002 Is reentrancy detection required for ALL THREE blocking APIs — `session.send`, `session.close`, and `engine.close`(→`engine_destroy`)? [Completeness, Spec §FR-017, SC-007] — PASS: FR-017 explicitly enumerates all three: "`session.send` / `session.close` / `engine.close`/destroy"; SC-007 states "100% of blocking-API calls (send / close / engine_destroy)"; contracts C-6 lists all three check sites.
- [x] CHK003 Are requirements defined for BOTH setting the `_in_callback` marker (on callback entry, under GIL) AND clearing it (before GIL release on exit)? [Completeness, data-model E-7] — PASS: data-model E-7 explicitly covers both: "**Set** True by the trampoline on callback entry (under GIL); **cleared** before GIL release on exit — unconditionally, including on the exception-exit path" (SPEC-FIXED text now present; see CHK022).
- [x] CHK004 Is the `Engine.close()` all-sessions `_in_callback` preflight specified as a distinct gate from the per-`Session` `close()` step-0 backstop? [Completeness, contracts C-3 step 1 + Session step 0] — PASS: C-3 Engine.close() step 1 names the preflight explicitly as "BEFORE any C-ABI or any session close" and describes it as the "primary gate"; Session.close() step 0 is labeled "the **per-session backstop**"; the composition-without-double-raise rationale is stated in step 0.
- [x] CHK005 Are sub-interpreter rejection requirements specified at the construction boundary — raising `SubInterpreterRejected` (1201) BEFORE any native engine is created? [Completeness, Spec §FR-018, contracts C-7] — PASS: FR-018 requires detection "at construction"; C-1 Engine `__init__` comment says "rejects sub-interpreter -> SubInterpreterRejected (1201)"; contracts C-7 (sub-interpreter guard) states the check fires "at `Engine.__init__` before any native resource is acquired".

## Ambiguities & Gaps

- [x] CHK022 Does the spec define whether the `_in_callback` marker is correctly cleared when the callback raises a Python exception (the `PyErr_Print` exit path), so a post-exception blocking call is not falsely flagged? [Gap, Exception Flow, data-model E-7, Application E-4] — SPEC-FIXED: FR-017 Trampoline exit discipline added to spec.md: "On callback return the new OO trampoline MUST perform BOTH (a) arm the inbound `Message._dead` sentinel (FR-004) AND (b) clear `Session._in_callback`, unconditionally before the single GIL release — including on the `PyErr_Print` exception-exit path. The trampoline MUST NOT take an early return on a raising callback that skips either postcondition." data-model E-7 mirrored with "cleared … unconditionally, including on the callback exception-exit path (`PyErr_Print` / `PyErr_Occurred`; the OO trampoline MUST NOT early-return …)". Advisor confirmed the exception-path hole also covers the `_dead` arming (L-053-1 UAF half), so ONE clause closes both postconditions.
- [x] CHK023 Is the behavior specified when `send`/`close` is called from a NON-callback thread while a callback is in-flight on another thread (the per-session marker is set) — is that intentionally a reentrancy raise, or a distinct case? [Ambiguity, Spec §FR-016/FR-017] — DD-DECIDED §6.5: `[2m §6.5]` (line 1201) explicitly names all three APIs — `Session.send / Session.close / Engine.close` — as checking `self._in_callback` directly. Line 1203 names the general "`_in_callback` check race" (generic heading, Engine.close used as the example) and renders the verdict "Acceptable in practice" for GIL-bounded false-positives. A cross-thread `session.send()` observing `_in_callback == True` during a GIL-release window inside a mid-callback is exactly this race on the send API; the same "Acceptable in practice" judgment from §6.5 applies. The design chose a session-local, non-thread-keyed marker (§6.5 lines 1199-1200) and explicitly listed send as one of the three checking APIs, accepting the false-positive cost for all three. Settled by the design doc — not an unspecified gap. `[2m §6.5]` is the frozen-authority traceability ref.
- [x] CHK024 Does the spec define a deterministic outcome for `engine.close()` racing a child `session.close()` invoked concurrently (ordering / idempotency under the GIL)? [Gap, Spec §FR-007/FR-008, SC-001] — WAIVED: The GIL serialises all Python-side state mutations; whichever of `engine.close()` / `session.close()` acquires the GIL first closes that session; the other sees `_dead=True` and no-ops (FR-008 idempotency). The outcome is deterministic under the GIL, and FR-008 idempotency + the `_dead` guard cover both orderings. Adding an explicit race-ordering specification would be over-specification — the GIL is the ordering mechanism. Item is tagged `[Gap]`, not Completeness/Clarity/Consistency; WAIVED.
