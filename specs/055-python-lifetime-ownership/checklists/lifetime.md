# Lifetime & Memory-Safety Requirements Checklist: Python bindings ownership / lifetime layer (PY-004)

**Purpose**: Validate that the lifetime/ownership/memory-safety REQUIREMENTS (sentinel, ordered close-flow, ownership graph, callback-leak release, flyweight invalidation) are complete, unambiguous, consistent, and measurable — before implementation. Tests the requirements writing, not the code.
**Created**: 2026-06-27
**Feature**: [spec.md](../spec.md) · [data-model.md](../data-model.md) · [contracts/python-lifetime-api.md](../contracts/python-lifetime-api.md)

## Requirement Completeness

- [x] CHK001 Is the pre-call liveness-check requirement specified for *every* wrapper method that would touch the C-ABI, across all five wrapper types (Engine/Session/Message/Application/Dictionary)? [Completeness, Spec §FR-002, data-model E-6] — PASS: FR-002 requires the check "before making any C-ABI call" for every handle-bearing wrapper; data-model E-6 cross-cuts all five types; contracts C-2 restates the "every method" rule explicitly.
- [x] CHK002 Are the arming sources of the liveness sentinel enumerated for every path that invalidates a handle (parent `close()` walk, inbound-callback return)? [Completeness, Spec §FR-003/FR-004, data-model E-6] — PASS: FR-003 names the `_dead`-flag path; FR-004 names the inbound-callback-return path (closes L-053-1); data-model E-6 "Arming" paragraph enumerates both: "owning parent's close-flow … or, for inbound `Message`, by the trampoline at `fromApp` return."
- [x] CHK003 Are both the strong-reference (child→parent UP) and weak-reference (parent→child DOWN) directions of the ownership graph each explicitly required? [Completeness, Spec §FR-005/FR-006] — PASS: FR-005 requires strong-ref UP ("a `Message` keeps its parent `Session` alive"); FR-006 requires weak-ref DOWN via WeakSet ("parent can invalidate all live children on close").
- [x] CHK004 Is the ordered close sequence (invalidate children → release application ref → native close/destroy) fully enumerated as discrete steps for BOTH `Engine.close()` and `Session.close()`? [Completeness, Spec §FR-007, contracts C-3] — PASS: contracts C-3 provides explicit numbered steps for both Engine.close() (steps 1-5) and Session.close() (steps 0-6); FR-007 states the three-phase ordering; data-model E-1/E-2 lifecycle prose mirrors both sequences.
- [x] CHK005 Are requirements defined for releasing the binding-owned callback reference on BOTH session close AND callback re-registration? [Completeness, Spec §FR-011, contracts C-4] — PASS: FR-011 requires release "when the session is closed OR when a different callback is registered in its place"; contracts C-4 "Re-registration" paragraph specifies reassignment releases the prior callable reference.
- [x] CHK006 Is the two-flavour Message distinction (inbound flyweight vs outbound/clone) specified for all three concerns: ownership, finalisation, and invalidation? [Completeness, Spec §FR-012, data-model E-3] — PASS: FR-012 requires both flavours, distinguishing ownership (engine-owned vs Python-owned), finalisation (`__del__` no-op vs `fixpp_msg_destroy`), and invalidation timing (trampoline-at-return vs Session.close()); data-model E-3 lifecycle sections repeat all three concerns per flavour.
- [x] CHK007 Is the engine-destroy-last ordering ("engine destroys its native handle only after all its sessions are closed") explicitly required? [Completeness, Spec §FR-007, contracts C-3] — PASS: FR-007 states "the engine destroys its native handle only after all its sessions are closed"; C-3 Engine.close() step 4 calls `fixpp_engine_destroy` only after the child-session walk (steps 1–3).

## Requirement Clarity

- [x] CHK008 Is "marked invalid when the callback returns / before the dispatch window closes" pinned to a specific lifecycle point (armed before GIL release at callback return)? [Clarity, Spec §FR-004, data-model E-3] — PASS: FR-004 says "before the dispatch window closes"; data-model E-3 lifecycle (inbound flyweight) says "`_dead=True` armed before GIL release on callback return"; FR-017 Trampoline exit discipline (SPEC-FIXED) now explicitly requires arming unconditionally before the single GIL release including on the exception path.
- [x] CHK009 Is "binding-owned reference" defined precisely enough to distinguish the binding's `_application` ref from the user's external references? [Clarity, Spec §FR-011, SC-002, contracts C-4] — PASS: FR-011 uses the phrase "binding-owned reference" and explicitly contrasts it with the user's external references ("the user remains free to hold their own external references; the guarantee is over the binding's reference"); SC-002 witness drops external refs first to isolate binding-owned leak; C-4 "Two distinct references" paragraph enumerates the distinction.
- [x] CHK010 Is the ordering constraint "arm `_dead` FIRST, before any GIL-releasing teardown" stated unambiguously for both the Session and Engine close-flows? [Clarity, contracts C-3, Spec §SC-001] — PASS: contracts C-3 Session.close() step 1 uses the exact phrase "arm `self._dead = True` FIRST — before the native close (NEW-P2a)"; Engine.close() step 2 uses "Arm `self._dead = True` FIRST — before any GIL-releasing teardown"; SC-001 close-race note states the symmetry explicitly.
- [x] CHK011 Is it unambiguous that the C-ABI registration `userdata` is the INCREF'd `Session` (NOT the callable), and that it is released only at/after the native close? [Clarity, contracts C-4, data-model E-2] — PASS: C-4 opens "the trampoline's `userdata` is the **owning Python `Session` wrapper** (INCREF'd at registration … NOT the bare callable)"; data-model E-2 `_application` field notes "userdata=Session … released AT/AFTER `fixpp_session_close` (after dispatch stops) — never before"; C-3 step 5 releases userdata only after step 4 (native close).
- [x] CHK012 Is the "private unguarded close/destroy helper" requirement (teardown must not route through `_dead`-guarded public methods) stated clearly enough to implement without re-entering the sentinel? [Clarity, contracts C-3 steps 3-4] — PASS: C-3 Engine.close() step 3 says "call a **private unguarded close helper** for that child session" and adds the parenthetical rationale ("the engine's own `_dead` is already armed, so the teardown path must not route through public `_dead`-guarded engine methods"); step 4 calls "a private unguarded engine-destroy helper … directly".

## Requirement Consistency

- [x] CHK013 Do the close-flow steps in contracts C-3 match the lifecycle prose in data-model E-1/E-2 (reentrancy fail-fast → arm `_dead` first → invalidate children → drop `_application` → native close → release userdata)? [Consistency, contracts C-3 ↔ data-model E-1/E-2] — PASS: data-model E-2 lifecycle lists exactly this order (reentrancy fail-fast FIRST, then arm `_dead` FIRST, then walk `_messages`, drop `_application`, `fixpp_session_close`, release userdata); C-3 steps 0-6 match step-for-step; Engine (E-1 lifecycle) matches C-3 Engine.close() steps 1-5.
- [x] CHK014 Is the "strong-ref UP / weak-ref DOWN" graph described consistently across Spec §FR-005/FR-006, data-model E-1..E-3, and contracts C-3? [Consistency] — PASS: FR-005 ("strong-reference graph"), FR-006 ("weak references … parent can invalidate"), data-model E-1 ("strong-ref'd UP by each child Session"), E-2 ("strong ref UP"), E-3 ("strong ref UP") and contracts C-3 all use the same directional terminology and WeakSet for the DOWN direction; no contradictions found.
- [x] CHK015 Does the SC-001 concurrent-close characterization (both wrappers arm `_dead` first before native teardown) align with the FR-007 ordered-close requirement and the C-3 step ordering? [Consistency, Spec §SC-001 ↔ FR-007 ↔ contracts C-3] — PASS: SC-001 explicitly states the concurrent-close safety characterization is "stated symmetrically for session and engine wrappers"; FR-007 requires the ordered close sequence; C-3 Session.close() step 1 and Engine.close() step 2 both arm `_dead` first; no contradiction.
- [x] CHK016 Is the callback-ownership model (`userdata`=Session, `_application`=callable, release-on-close/re-register) described without contradiction between Spec §FR-011, data-model E-2, and contracts C-4? [Consistency] — PASS: all three use the same model — `userdata`=INCREF'd Session (never the callable), `_application`=Python-owned callable ref dropped on close/re-registration; C-4 "Two distinct references" paragraph formalizes the distinction; no contradiction between FR-011, E-2, and C-4.

## Acceptance Criteria Quality & Measurability

- [x] CHK017 Is SC-001's "100% of post-close accesses raise `ObjectLifetime`" scoped with an explicit, testable boundary (the non-concurrent-close case) so the criterion is objectively pass/fail? [Measurability, Spec §SC-001] — PASS: SC-001 explicitly scopes its 100% guarantee to "the single-threaded / happens-after-close-completes case" and separately characterizes the concurrent-close edge as best-effort wrapper-side check + native tombstone fallback; boundary is measurable.
- [x] CHK018 Does SC-002 specify the exact observable witness (callback `weakref` dead after `gc.collect()`, with the caller's external strong refs dropped FIRST) that makes "no binding-owned ref leaks" measurable and discriminating? [Measurability, Spec §SC-002, contracts C-4] — PASS: SC-002 text includes "after the caller's external strong references are dropped" and the witness is "callback's `weakref` becoming dead after `gc.collect()`"; US2 Independent Test further spells out "del the caller's own external strong reference … so the binding's `_application` ref is the only surviving one."
- [x] CHK019 Are the acceptance seams (#3 session-outlives-engine, #8 message-outlives-session) each defined precisely enough to map to a single pass/fail observation under ASan? [Acceptance Criteria, Spec §US1 Independent Test] — PASS: US1 Independent Test names seam #8 (keep inbound Message past callback / past session.close, read a field) and seam #3 (keep Session past engine.close, call send); each maps to a single raise-or-ASan-finding check; acceptance scenario AC1-AC3 further tighten the expected exceptions and error codes.

## Scenario & Edge-Case Coverage

- [x] CHK020 Are idempotency requirements for a second `close()` (including a `with`-exit after an explicit close) specified as a no-op — explicitly not an error or double-free? [Coverage, Edge Case, Spec §FR-008] — PASS: FR-008 states "close() MUST be idempotent — a second close … is a no-op, never a double-free or error"; C-3 closing note "close() is idempotent (a second call … is a no-op — guarded by `_dead`/`_was_explicitly_closed`)".
- [x] CHK021 Are requirements defined for the Application↔Session reference cycle being collectable (broken on explicit close; otherwise left to the cycle collector)? [Coverage, Edge Case, Spec Edge Cases] — PASS: Spec Edge Cases section explicitly states "Application↔Session reference cycle: … the cycle must be collectable (broken on explicit close; otherwise left to the cycle collector)"; data-model E-2 relationships note "collectable cycle"; C-3 step 3 breaks it by dropping `_application`.
- [x] CHK022 Is the GC-without-explicit-close behavior specified (DeprecationWarning + best-effort native cleanup, with finalisation order unspecified)? [Coverage, Spec §FR-010] — PASS: FR-010 requires DeprecationWarning and best-effort cleanup on GC; FR-010 explicitly states "Finalisation order within a GC cycle is unspecified"; C-3 closing note "cross-module `__del__` order at interpreter shutdown is NOT relied upon"; data-model E-1/E-2 `__del__` = "best-effort + DeprecationWarning if not explicitly closed."
- [x] CHK023 Are requirements defined so an outbound-vs-inbound Message mix-up neither double-frees nor leaks (inbound `__del__` no-op; outbound frees its handle, idempotently)? [Coverage, Edge Case, Spec §FR-012, data-model E-3] — PASS: FR-012 requires the two flavours to be "distinguished so neither double-frees nor leaks"; data-model E-3 `_is_inbound` field drives `__del__` (no-op inbound vs `fixpp_msg_destroy` outbound); lifecycle prose for both flavours is explicit; no underspecification.
- [x] CHK024 Is the inbound `set_*` rejection path (`CapiError` code=4 via `_is_inbound`, a distinct path from `_dead`) specified? [Coverage, data-model E-3, contracts C-1] — PASS: data-model E-3 Validation/invariants states "`set_*` on an inbound message short-circuits to `CapiError(code=4)` (`_is_inbound` flag, `[2m §1.3]` rule (1)) — distinct path from `_dead`"; contracts C-1 Message class comment notes "inbound -> CapiError(code=4)".

## Ambiguities & Gaps

- [x] CHK025 Does the spec define that a weakly-tracked child already GC'd is safely skipped during the parent's invalidation walk (WeakSet semantics relied upon)? [Gap, Spec §FR-006] — WAIVED: FR-006 requires WeakSet for child tracking; the safe-skipping-of-dead-weak-refs is a guaranteed stdlib invariant of `weakref.WeakSet` iteration (Python language semantics, not a spec gap). Recording this as a design assumption is appropriate but not a Completeness defect in the spec text; tagging WAIVED on the not-Completeness leg of the item.
- [x] CHK026 Is the outbound-Message construction Python API (callable signature, e.g. `session.create_message(...)`) specified in the contract, or only the native mechanism (`fixpp_msg_create_outbound`)? [Gap, contracts C-1, research D-11] — SPEC-FIXED: `create_message(self, msg_type: str) -> "Message": ...` added to the Session class in contracts/python-lifetime-api.md C-1 (wraps `fixpp_msg_create_outbound` per message.h:290; outbound flavour, Python-owned handle, `_dead` → `ObjectLifetime`). The native mechanism was confirmed present at message.h:290 and fixpp.i:640; T008 in tasks.md references this addition.
- [x] CHK027 Does the spec specify which Message accessors are in scope for the liveness guard vs deferred (callback-surface completeness), so "every accessor checks `_dead`" is bounded? [Ambiguity, contracts C-1, research D-1/D-8] — PASS: contracts C-1 Message class explicitly names `get_string`/`set_string` (with liveness checks) and provides the note "(richer accessors … deferred per D-1/D-8)"; this is adequate: "every accessor checks `_dead`" applies to whichever accessors are in-scope; the deferred-completeness pattern is settled in design D-8 with tasks.md T019 tracking the deferred surface. No Completeness/Clarity gap at the requirements level.
