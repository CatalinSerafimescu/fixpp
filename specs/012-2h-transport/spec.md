## User Scenarios & Testing *(mandatory)*

### User Story 1 — TLS-encrypted FIX session, end-to-end byte stream (Priority: P1)

A FIX engine operator opens an initiator session against a counterparty gateway over TLS. The engine resolves the host, completes the TCP three-way handshake, performs the TLS handshake (consuming the `SslCtxConfig` produced by `011-tls-policy` for the chosen `SecurityProfile`), captures the counterparty's `peer_identity` (parsed from the verified peer cert) by value into the session FSM, and then exchanges FIX frames as a byte stream: inbound bytes flow into `2b`'s `Framer::feed` from `async_read_some` completions; outbound bytes flow from `2b`'s `Writer::commit` post-commit span into `async_write`. The operator never touches OpenSSL directly, never writes a single `SSL_*` call, and never authors a handshake state machine — every part of the wire-side lives behind a small published interface.

**Why this priority**: This is the spine. Without it, none of the upstream work ships — `011-tls-policy` has nowhere to project its validation surface, the session FSM has no Transport to call into, and `2b`'s framing surface has no source of bytes. It is also the only path that proves the cross-doc partitions declared in `[2g §7.1]` (T-039 + T-040 + T-041) actually link cleanly with the consumer side wired up.

**Independent Test**: With a stand-up counterparty (a separate fixpp process or a stub TLS responder) presenting a valid leaf cert pinned in the initiator's `Pinset`, open a session in `mtls_pinned` mode via a freshly-constructed `asio_tls_transport`. Observe: (a) `async_connect` completes with `ConnectInfo` carrying the negotiated remote endpoint; (b) `async_handshake` completes with `handshake_result` carrying `peer_identity`, the captured `Pinset` snapshot, and the negotiated cipher suite; (c) a Logon message issued by the FSM round-trips through `async_write` → counterparty → `async_read_some` and is parsed by `Framer::feed` without any allocation on the read-path completion-handler dispatch.

**Acceptance Scenarios**:

1. **Given** an initiator session config wiring an `asio_tls_transport` and a populated `Pinset`, **When** the FSM calls `async_connect` followed by `async_handshake`, **Then** both awaitables complete with success and `handshake_result.peer_id` carries the verified counterparty identity by value (no `[[clang::lifetimebound]]` dangling).
2. **Given** an in-flight `async_read_some` on a caller-supplied `std::span<std::byte>` aliasing the framer-carry arena, **When** the peer sends a partial frame and then more bytes, **Then** the completion handler fires with a positive byte count, the partial frame is appended to `Framer::feed`, and **zero heap allocations are observed** on the path from completion-handler entry to `Framer::feed` exit per `[const §VIII.5]`.
3. **Given** an outbound frame whose `Writer::commit` span has been finalised and durably stored per `[2e §6.1.4]`, **When** the FSM calls `async_write(bytes)`, **Then** every byte reaches the peer (or, on cancellation, the awaitable completes with `transport_write_cancelled` and the persisted frame is NOT rolled back).
4. **Given** a TLS handshake against a peer presenting a cert that violates the 011 `verify_peer` policy (e.g., RSA-1024 leaf), **When** the OpenSSL `SSL_VERIFY_PEER` callback dispatches into `verify_peer`, **Then** the handshake completes with the exact 011 `tls_*` variant from `[2g §6.6]` (the canonical 15-variant table per `[2g §6.6]:1004`) — 2h does not re-translate or coalesce.
5. **Given** a transport-private failure (DNS resolution failed, TCP connection refused, TLS handshake timeout against an unresponsive peer), **When** the awaitable completes, **Then** it carries a distinct `transport_*_failed` variant — never a generic "transport error" or a thrown exception across the public surface.

### User Story 2 — Bounded reconnect after transient disconnect (Priority: P2)

A FIX engine operator runs a long-lived initiator session against a venue. The venue cycles for a maintenance window of up to ~90 seconds. The session's connection drops; the engine FSM destroys the dead `Transport`, sleeps for the back-off delay computed from the session's `ReconnectPolicy`, MINTS A FRESH `Transport` via the same `TransportFactory`, and calls `async_connect` on the new instance (matching the QuickFIX-cpp / QuickFIX/J / Fix8 fresh-per-attempt pattern per Clarifications 2026-05-27). After the venue recovers, the next attempt succeeds and the session resumes. The back-off schedule is exponential with jitter so 10⁵ peer engines reconnecting at the same moment do NOT thunder-herd the recovering venue. If the venue stays down past the policy's `max_attempts` ceiling, the FSM surfaces `transport_reconnect_limit_exceeded` and stops — the operator decides whether to keep trying.

**Why this priority**: This is the only behaviour the `[FIX-SL §4.3.1]` Transport-layer requirements mandate beyond raw TCP. Without a numeric `max_attempts` ceiling in the defaults, a fleet of engines reconnecting after a venue outage cluster their attempts in narrow windows once `max_delay` is hit — a known TCP/TLS thundering-herd amplifier flagged in `[const §XV]`. P2 (not P1) because a one-shot session that loses connectivity can be re-opened by the operator manually; the automated bounded reconnect is what makes 24/7 operation viable.

**Independent Test**: Configure a session with the `ReconnectPolicy::defaults()` envelope. Bring up a stub peer that accepts the first connection, then closes; the FSM should destroy the dead Transport, mint a fresh one via `TransportFactory::make(...)`, and call `async_connect` on the new instance. Verify the wall-clock delays match the documented schedule (100 ms → 200 ms → 400 ms → … capped at 30 s, with ±10 % jitter), the cumulative envelope at `max_attempts = 10` lands in the 73 – 89 s band per design-doc §1.1, and exceeding the ceiling surfaces `transport_reconnect_limit_exceeded`. Repeat with `max_attempts = 0` to verify the opt-in-to-unbounded path.

**Acceptance Scenarios**:

1. **Given** a session with `ReconnectPolicy::defaults()`, **When** a peer drops the connection and the FSM walks the full 10-entry schedule per FR-020, **Then** the engine waits 100 ms / 200 ms / 400 ms / 800 ms / 1.6 s / 3.2 s / 6.4 s / 12.8 s / 25.6 s / 30 s between attempts (±10 % jitter) — the pre-jitter cumulative sum is 81 100 ms and the ±10 % jitter spread widens this to 73 – 89 s wall-clock per design-doc §1.1 corrected numeric (matching SC-002 and the corrected envelope in `[2h §4.4.1]:627`).
2. **Given** a session with `ReconnectPolicy::defaults()`, **When** the 10th attempt also fails, **Then** the FSM surfaces `transport_reconnect_limit_exceeded` and the engine stops reconnecting without further retries.
3. **Given** an operator-supplied `ReconnectPolicy{max_attempts = 0}` (opt-in to unbounded), **When** the peer never recovers, **Then** the engine keeps retrying at the capped `max_delay` indefinitely; no `transport_reconnect_limit_exceeded` surfaces.
4. **Given** reconnects spread across N engines under simulated venue-recovery load, **When** the venue comes back up, **Then** the ±10 % jitter spreads the inbound connection bursts so the venue does not see a synchronised reconnect spike at any single moment.

### User Story 3 — Multi-session acceptor on a single port (Priority: P3)

A FIX engine operator deploys an acceptor (server-side) gateway that accepts inbound sessions from 10² – 10³ counterparties on a single TCP port. The engine wires an `asio_listener` against the bind endpoint and consumes accepted connections from a single `async_accept` loop on a service-strand executor; each accepted connection mints a fresh `Transport` instance handed off to a new session FSM. Acceptor backlog overflow is bounded by the OS / `SO_BACKLOG`; the engine never starves a connecting client by holding the acceptor strand on per-session setup work.

**Why this priority**: This is the only path the `T-005` (multi-session acceptor) catalogue row covers. Initiator-only deployments (the common case for client-side trading engines) do not exercise this surface; acceptor deployments (broker-side, prime-broker-side, exchange-adjacent gateways) need it but represent a smaller share of v1.0 named deployments. P3 because the Transport interface itself is symmetric — the acceptor reuses every contract the initiator path establishes; only the construction half is new.

**Independent Test**: Stand up an `asio_listener` on `0.0.0.0:0` (OS-assigned port). Open 64 concurrent initiator connections from a stub client process. Verify all 64 `async_accept` completions fire, each producing a distinct `Transport` that successfully handshakes and exchanges Logon messages; verify the per-accepted-connection setup work does NOT stall the acceptor strand (the next `async_accept` resumes within the v1.0 target latency band).

**Acceptance Scenarios**:

1. **Given** an `asio_listener` bound to a port with backlog ≥ 64, **When** 64 clients connect concurrently, **Then** 64 distinct `Transport` instances are produced and 64 sessions transition to Active without any accept being dropped.
2. **Given** an `asio_listener` with the `cancel()` API invoked, **When** a client attempts a new connect after the cancel, **Then** the connect is refused at the kernel level (the acceptor stops listening) and the listener's awaitable completes with `transport_accept_cancelled` per `[2h §6.6]:1191`.
3. **Given** the acceptor port's backlog is full and a 65th client connects, **When** the acceptor cannot dequeue fast enough, **Then** the 65th client's connection is **not established** — fixpp does not over-promise availability under saturated accept rates (per `[2h §10 Q7]` deferral). The ordinal is illustrative: which client number first fails to connect is OS-dependent and no ordinal is asserted anywhere in the tree. **Witness, decomposed across what fixpp owns and what the OS owns:** (a) the configured `Endpoint::backlog` is forwarded to `listen()` — `tests/transport/test_listener_acceptor.cpp` cell 11 (`RequestedListenDepthTracksConfiguredBacklogAtAc3AndDefaultDepths`, portable) records the exact value fixpp passes at this scenario's 64 and at the shipped default 128; cell 12 (`KernelRegisteredBacklogTracksConfiguredDepthUpToSomaxconn`, Linux-only, reads back via `NETLINK_SOCK_DIAG`) confirms the OS actually registered it, at the same two depths plus a depth above `somaxconn` to exercise the clamp — cell 12 is the only one of the two seams that catches a clamp applied AT the `listen()` call site while leaving cell 11's recorded expression intact, so on non-Linux platforms that call-site seam is not witnessed by any cell in the tree; (b) a saturated queue bounds completions and that bound tracks the configured depth — cell 10 (`BacklogBoundsConnectionsCompletedWithoutTheApplication`) witnesses this at the depths it probes (its own probe count is its discrimination ceiling, so it cannot itself reach 64 or 128 — that is why (a) is split into its own cells); (c) that the OS applies the *same* saturation mechanism at 64 as at the lower depths cell 10 probes is an OS property fixpp does not own and is **not asserted** anywhere in the tree. T034's sub-requirement 5 is closed on this basis (#332).

   ⚠️ Until 2026-09-01 this AC promised "a TCP RST or connection-refused per OS behaviour". That is **false** as a guarantee and has been deleted rather than re-scoped: **fixpp makes no guarantee about how the OS declines the 65th client** — reset, refused, or left pending, per OS and per configuration. A client that needs prompt rejection must impose its own connect deadline. Operator-visible consequence recorded in `spec/behaviors-and-limitations.md`.

   The identical "TCP RST or connection-refused per OS" phrasing in scenario 2 above is **not** affected — there the listening socket is closed, which really does produce one of those two outcomes — though whether it surfaces at `connect()` or at the first read is host-dependent (cell 9's assertion admits both; which one appears, and at which syscall, is host-dependent); see the measurement note above cell 9's `connection_refused_or_reset` predicate (`test_listener_acceptor.cpp:180-187`). Same boilerplate, two different situations, two different truth values.

### User Story 4 — Deterministic mock-transport test seam (Priority: P3)

A fixpp developer writes a session-FSM test that needs to drive the FSM through Logon → Heartbeat → Resend → Logout transitions without any real TCP socket, OpenSSL handshake, or kernel scheduling jitter. The developer wires a `mock_transport` (a deterministic in-memory `Transport` impl shipped in a public test header) into the session-config under test. Every cancellation contract the production impl honours, the mock honours; an FSM regression that fails on the real wire would also fail in the mock.

**Why this priority**: This is the test-seam goal `[arch §1.1]` mandates; without it, no FSM unit test can run hermetically (every test would need a real TCP loopback) and every cancellation regression would only surface under integration testing. P3 because the spec / surface is intentionally small (the FSM is the test focus, not the transport).

**Independent Test**: In a hermetic test binary that does NOT link OpenSSL or ASIO's networking components (only the awaitable + strand primitives), wire `mock_transport` into a session-FSM under-test and verify: (a) the FSM completes Logon → Heartbeat → Logout transitions deterministically; (b) cancelling an in-flight `async_read_some` produces `transport_read_cancelled` on the awaitable (same variant as the production path); (c) a Script-driven mock that issues `transport_read_eof` after N bytes triggers the FSM's graceful disconnect path identically to a real EOF.

**Acceptance Scenarios**:

1. **Given** a `mock_transport` scripted to deliver a Logon response after the FSM's outbound Logon, **When** the FSM test runs, **Then** the FSM reaches Active deterministically (no timing flakiness, no real socket).
2. **Given** an in-flight `mock_transport::async_read_some`, **When** the test calls `cancel()`, **Then** the awaitable completes with `transport_read_cancelled` — identical variant to the production `asio_tls_transport`.
3. **Given** a `mock_transport` scripted with a `transport_handshake_failed` response, **When** the FSM's session-open path runs, **Then** the FSM observes the exact same `transport_*_failed` variant it would observe from the production `asio_tls_transport` against a misbehaving peer.

### Edge Cases

- **`async_connect` called twice on the same Transport before the first completes or `close()`/`cancel()` returns**: ⚠️ **Amended 2026-09-01 (#339)** — this Edge Case was written as if the guard were a call counter. It is not: it tests the ENTRY STATE, and `async_connect` leaves the Transport in `fresh` for the whole duration of an in-flight attempt. So an OVERLAPPING second call also attempts — it does not get `transport_already_connected`. That variant is returned once the first attempt has SUCCEEDED (state `connected`/`handshaken`), and `transport_already_closed` once the Transport is closed. ⚠️ **And the two attempts are NOT independent** — corrected again 2026-09-01, because the first amendment closed with "the first call is not disturbed", which is also false. asio's composed `async_connect` does `socket_.close(ec)` immediately before each endpoint attempt (vendored asio 1.38, `impl/connect.hpp`), so the second attempt closes the socket out from under the first; the first can then complete with `operation_aborted`, which this transport maps to `transport_connect_timeout` when no cancellation state is set, and the shared connect-epoch counter is advanced by whichever completes first. **Overlapping `async_connect` is therefore unsupported rather than merely redundant** — it is neither refused with 97 nor safely concurrent. `transport_already_connected` is what a SEQUENTIAL second call gets, once the first has SUCCEEDED. The other sites still stating the overlap form — the parent design doc, plan.md/tasks.md's T017 description, and `test_inflight_exclusivity.cpp`'s header, whose cells 3 and 4 are SEQUENTIAL and not the overlap witnesses they are billed as — are tracked in #342, not corrected here. FR-007 carries the full state table.
- **`async_read_some` issued while a previous `async_read_some` is in flight on the same Transport**: returns `transport_read_in_progress` immediately. (API-level exclusivity contract — strand serialisation is defence-in-depth only per design-doc §4.1.)
- **`async_write` issued while a previous `async_write` is in flight on the same Transport**: returns `transport_write_in_progress` immediately.
- **Short write under cancellation** (some bytes sent, some not): the awaitable completes with `transport_write_cancelled`; the FSM treats this as a torn write and disconnects + recovers via `[FIX-SL §4.5.2]` `ResendRequest`. The persisted frame is NOT rolled back per `[2e §6.1.4]`.
- **Partial read under cancellation**: bytes up to the cancellation point are LOST per ASIO's contract; the FSM treats this as a torn read and (under the v1.0 close-on-cancel contract) drives a session disconnect.
- **TLS handshake timeout**: the awaitable completes with `transport_handshake_timeout` once `Transport::Config::tls_handshake_timeout` (30 s default) elapses; partial OpenSSL state is torn down by `SSL_free`.
- **TLS bidirectional close-notify hangs on an unresponsive peer**: `close()` waits up to `Transport::Config::tls_close_timeout` (1 s default) for the peer's close-notify; on timeout the close completes with `transport_read_truncated` per `[2h §6.6]:1182` — not treated as a hard error. (RC#D gate-b/r1: the prior parenthetical "v1.0 treats this as transport_read_eof" was an internal contradiction with SC-006's distinct-named-variant requirement; resolved in favour of SC-006. The 2k logging layer maps `transport_read_truncated` to a `warn`-level log entry per `[2g §7.8]`.)
- **Reconnect against a venue that takes longer than the default envelope**: at `max_attempts = 10`, the cumulative wall-clock budget is ≈ 73 – 89 s (per design-doc §1.1 corrected numeric). Operators that need a longer envelope override `max_attempts` explicitly (no implicit default per `[const §XII.5]`).
- **Pinset rotation lands during an in-flight handshake**: the handshake's `verify_peer` runs against the snapshot captured at handshake start per `[2g §6.5.1]` BINDING CONTRACT; the new pinset is observable only on the next handshake. The captured-at-handshake-start contract applies symmetrically to BOTH initiator-side AND acceptor-side handshakes — each accepted Transport minted by `asio_listener` captures the acceptor's `SslCtxConfig::pinset` snapshot at its own handshake start; mid-rotation does NOT affect any in-flight handshake on either role.
- **Operator wires PSK config (T-012, post-v1)**: the v1.0 default `asio_tls_transport` rejects `SSL_CTX_set_psk_*` configuration with `transport_psk_unsupported`. The `TlsTransport` sub-interface leaves 4 of 5 pure-virtual slots free for a future PSK callback hook without a major-version bump.
- **PMR allocator throws on a cold path** (e.g., DNS-resolver buffer growth, OpenSSL `SSL_CTX` construction under arena exhaustion): routed through `[2a §4.2]` `trap_throw` and surfaces as the appropriate `transport_*` variant — no PMR throw escapes the public surface as a C++ exception.
- **Service-side acceptor saturation**: backlog overflow + cancellation propagation under 10⁵-accepts/sec is NOT benched in v1.0 (per `[2h §10 Q7]` DEFERRED). The v1.0 target deployments are 10² – 10³ sessions per acceptor; behaviour beyond that is post-v1.
- **`Listener::cancel()` invoked AFTER an `async_accept` resumed with a `unique_ptr<Transport>` but BEFORE the consumer code passed it into `Session::open`** (Clarifications 2026-05-27 Q4=A): the held Transport is unaffected — its FD stays open until the consumer destroys the `unique_ptr` or calls `transport.close()`. The listener does NOT track produced Transports and does NOT have the surface to close them. Consumers that need the "close-everything-I-produced" semantics MUST track their own held Transports.
- **IPv6 zone-id host strings** (e.g., `fe80::1%eth0`): admitted by `Endpoint::host` and resolved by `asio::ip::resolver`; full conformance corpus is deferred per `[2h §10 Q6]`.

## Requirements *(mandatory)*

All requirements below are testable. Items tagged "(security)" trace to `[const §XII]` / `[FIXS RC1]`. Items tagged "(durable-before-transmit)" trace to `[2e §6.1.4]`. Items tagged "(cancellation)" trace to `[const §XI.2]` / `[2d §4.7]`.

### Functional Requirements

**Transport pure-virtual surface (T-001 / T-003)**

- **FR-001**: `fixpp::transport::Transport` MUST expose EXACTLY **5 pure-virtual methods** — `async_connect`, `async_read_some`, `async_write`, `cancel`, `close` — AT the `[const §XIV.2]` cap of ≤ 5. No additional methods, no defaulted-virtual headroom. The interface is encryption-agnostic.
- **FR-002**: `async_connect(Endpoint const&)` MUST return `asio::awaitable<core::expected_t<ConnectInfo>>`. `ConnectInfo` is an owning-by-value POD carrying `(remote, local, family)`. On failure, the awaitable surfaces `transport_resolve_failed` / `transport_connect_refused` / `transport_connect_timeout` / `transport_connect_cancelled` per `[2h §6.6]`.
- **FR-003**: `async_read_some(std::span<std::byte> buf [[clang::lifetimebound]])` MUST return `asio::awaitable<core::expected_t<std::size_t>>` and MUST NOT allocate on the read-path completion-handler dispatch per `[const §VIII.5]` — the caller owns the buffer (typically aliasing 2b's framer-carry arena). EOF surfaces as `transport_read_eof`.
- **FR-004**: `async_write(std::span<const std::byte> bytes [[clang::lifetimebound]])` MUST return `asio::awaitable<core::expected_t<std::size_t>>` and behave as a composed write (ASIO `async_write` semantics, NOT `async_write_some`). Caller MUST keep `bytes` alive past awaitable completion.
- **FR-005**: `cancel()` MUST be synchronous, thread-safe (the underlying ASIO `cancellation_signal` is thread-safe), idempotent on already-cancelled / never-issued ops, and MUST NOT close the socket — the FSM may retry a cancelled `async_connect` / `async_read_some` / `async_write`.
- **FR-006**: `close()` MUST be synchronous on the session strand. After `close()` returns, every subsequent `async_*` returns `transport_already_closed`. For TLS transports, `close()` initiates a best-effort bidirectional shutdown bounded by `Transport::Config::tls_close_timeout` (1 s default); a truncated close (peer-side missing close-notify) surfaces as the DISTINCT `transport_read_truncated` variant per SC-006 and `[2h §6.6]:1182` — NOT collapsed to `transport_read_eof`. (RC#D gate-b/r1: prior wording had an internal contradiction with SC-006; the distinct-variant path wins. The 2k logging layer maps `transport_read_truncated` to a `warn`-level log entry per `[2g §7.8]`.) This is NOT treated as a hard error.
- **FR-007**: **In-flight exclusivity (API-level contract).** At most one in-flight `async_read_some` and one in-flight `async_write` per `Transport` instance. A concurrent second call MUST complete IMMEDIATELY with `transport_read_in_progress` or `transport_write_in_progress` per `[2h §6.6]` — strand serialisation is defence-in-depth, not the binding contract. `async_connect` and `async_handshake` are one-shot per Transport lifetime, and the answer is determined by the ENTRY STATE, not by the call index (#339). `async_connect`: `closed` → `transport_already_closed`; `connected`/`handshaken` → `transport_already_connected`; `fresh` → attempts, and a failed attempt stays `fresh` and is retryable. `async_handshake`: `closed` → `transport_already_closed`; `fresh`/`handshaken` → `transport_already_connected`; `connected` → attempts, so a retry after a preflight rejection is a real attempt and not a one-shot rejection. This clause extends `transport_already_closed` to EVERY closed state, which is wider than FR-006's post-`close()` scope, because a TLS handshake that entered the OpenSSL exchange also reaches `closed` — see B-339-1.
- **FR-008**: Every `expected_t<T>`-returning method on the public surface MUST carry `[[nodiscard]]` at the abstract-base declaration site per `[arch §5.5]`.

### Key Entities

- **`Transport`** — abstract plugin interface (5 pure-virtual: `async_connect` / `async_read_some` / `async_write` / `cancel` / `close`). The byte-stream contract; encryption-agnostic.
- **`TlsTransport`** — sub-interface extending `Transport` with 1 additional pure-virtual (`async_handshake`); returns `handshake_result` by value.
- **`ConnectInfo`** — owning-by-value POD carrying negotiated remote / local endpoints + address family. Returned by `async_connect`.
- **`handshake_result`** — owning-by-value POD carrying `peer_identity` (consumed for T-041 binding), the captured `Pinset` snapshot, and the negotiated cipher-suite name. Returned by `async_handshake`.
- **`Endpoint`** — value type for initiator `(host, port)` or acceptor `(bind_addr, bind_port, backlog)`. Auto-detects address family; admits IPv6 zone-id.
- **`Transport::Config`** — per-session-config knobs (max read-window, max write-size, TCP send/recv buffer sizes, TLS handshake / close timeouts, TCP keepalive group).
- **`ReconnectPolicy`** — value type carrying a user-supplied schedule array (per QuickFIX/J pattern) + jitter + max_attempts; `defaults()` materialises the v1.0 thundering-herd-safe envelope (schedule `[100ms, 200ms, …, 30s]` × 10 entries + jitter=0.10 + max_attempts=10); `defaults_quickfix_compat()` returns industry-canonical `{[30s], 0.0, 0}`.
- **`Listener`** — abstract acceptor interface (1 pure-virtual: `async_accept`).
- **`asio_tls_transport`** — the v1.0 reference `TlsTransport` impl over ASIO + OpenSSL.
- **`asio_listener`** — the v1.0 reference `Listener` impl over `asio::ip::tcp::acceptor`.
- **`TransportFactory`** — `[arch §6]` rule-4 factory producing `Transport` instances; `unique_ptr`-owned per `[2e §4.4]` precedent.
- **`mock_transport`** — public-test-header deterministic in-memory `Transport` impl driving FSM-under-test; honours every cancellation contract the production impl does.
- **`error::transport_*` variants** — named error envelope per `[2h §6.6]:1167-1204` (22 variants); coalesce into `FIXPP_ERR_TRANSPORT_*` C-ABI groups (delegated to 2i). The 15 `tls_*` variants from `[2g §6.6]:986-1004` surface unchanged through this layer.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can stand up a TLS-encrypted FIX session against a counterparty (full TCP connect → TLS handshake → Logon round-trip) using **only** configuration (factories + `Endpoint` + `SecurityProfile` + `Pinset`) — **zero in-process code changes** to 011-tls-policy, 2b, 2e, 2d, or the session Phase-4 module are required to wire 2h in.
- **SC-002**: A reconnect cycle against a venue that drops the connection and recovers within ≤ 90 s completes within the default `ReconnectPolicy` cumulative wall-clock envelope of **73 – 89 s** (per design-doc §1.1 corrected numeric, ±10 % jitter); no thundering-herd burst against the recovering venue across a fleet of 10⁵ concurrently-reconnecting peer engines.
- **SC-003**: **100 %** of in-flight `async_connect` / `async_read_some` / `async_write` / `async_handshake` calls cancelled via `cancel()` complete with the matching `transport_*_cancelled` variant within the cancellation-deadline budget; **zero** in-flight closures / pinned PMR arenas / OpenSSL `SSL_*` state leak across cancellation boundaries (verified by ASan + LSan + the **dual allocation guard**: `counting_resource` PMR-routed allocation counting AND mallocnesia LD_PRELOAD interception of global `operator new` / `malloc` per `[[feedback_tracking_pmr_resource_false_pass]]` — both gates MUST fire; a single-gate witness is REJECTED per the recurring false-pass mode).
- **SC-004**: Replacing `asio_tls_transport` with `mock_transport` in an FSM test binary requires **ZERO** non-test source changes — the swap is at the `TransportFactory` boundary (per `SessionConfig::transport_factory_override`). FSM tests that detect cancellation-propagation regressions do so under the mock alone, with no real socket and no OpenSSL link dependency.
- **SC-005**: A multi-session acceptor on a single port (`asio_listener`) handles the v1.0 named-deployment target of **10² – 10³ concurrent sessions** without backlog overflow under named-workload accept rates; per-accepted-connection setup work does NOT stall the acceptor strand beyond the `[2h §6.3]` Tier 1 ceiling.
- **SC-006**: Every distinct transport-side failure mode (DNS resolution failed, TCP connection refused, connect timeout, handshake timeout, handshake failed via 011 `verify_peer`, read EOF, read cancelled, write cancelled, short write, TLS close-truncated, reconnect-limit-exceeded, PSK-unsupported, already-connected, already-closed, in-progress-overlap) surfaces as a **distinct, named `transport_*` (or unchanged `tls_*`) variant** the operator can recognise in logs / metrics. **No "transport failed" catch-all** exists in the public surface.
- **SC-007**: An in-flight outbound message persisted via `store(committed_span)` per `[2e §6.1.4]` and then cancelled mid-`async_write` results in `transport_write_cancelled` on the awaitable; the persisted frame is **NOT** rolled back; the session FSM recovers the delivery via `[FIX-SL §4.5.2]` `ResendRequest`. The integration witness exercises end-to-end (writer → message store → transport) without per-test mocks of either side.
- **SC-008**: The 011-tls-policy Gate B F-1 carryover — the `cancellable_dispatch` recipe witness for `file_cert_source::load_credentials` — is **GREEN** across all **8 cells** of the test matrix (4 deterministic cases × 2 executor modes — Clarifications 2026-05-27 Q3=C) at this feature's Gate B, with a real `Session*` + `session_executor` fixture wired by this feature. The 4 cases are cached-state fast path (per `[2g §6.4]:927-928`), slot-signalled-BEFORE-pickup (`[2d §6.5]` case 1 → `tls_load_cancelled`), slot-signalled-DURING-execution (`[2d §6.5]` case 2 → `tls_load_cancelled`), and happy path (`[2d §6.5]` case 3 → success); the 2 modes are `per_session_strand` (strand-wrapped) and `direct_executor` (bare attested-serialised).

## Assumptions

This spec codifies the user-visible contract that signed-off design doc `.specify/2h-transport.md` v0.3 (Phase A round 2 converged 2026-05-09) settles. The spec does NOT re-derive design decisions; it states the contract that downstream `/plan` will turn into tasks.

- **Design-doc inheritance**: `.specify/2h-transport.md` v0.3 is the binding upstream. Every §-anchored cite in this spec resolves there or in the inherited docs (constitution v0.2; architecture v0.2; `2a` / `2b` / `2c` / `2d` / `2e` / `2f` / `2g` signed-off).
- **TLS provider**: **OpenSSL on Linux and Windows** per `[const §XII.1]`. No Schannel; no platform-native fallback; no other TLS backend in v1.0.
- **011-tls-policy producer / 2h-transport consumer**: 011 has SHIPPED (closed 2026-05-26 per `[[project_011_tls_policy_closed.md]]`). The published surfaces 2h consumes — `SslCtxConfig`, `verify_peer`, `Pinset::snapshot()`, `peer_identity`, `SecurityProfile`, the 15 `tls_*` error variants per `[2g §6.6]:1004` — are LOCKED. 2h MUST NOT re-derive or re-translate them.
- **011 Gate B F-1 carryover (BINDING for 012 Gate B)**: per `[[project_011_tls_policy_closed.md]]`, the cancellation-seam-#13 full production-path witness was deferred from 011 to 2h's Gate B because constructing it required a real `Session*` + `session_executor` fixture only available once the transport wiring exists. **FR-033 + SC-008 codify this obligation; the spec MUST NOT defer the witness further.** The 011 design anchor `[2g §6.4]:927-928` (cached-state fast-path authorization) is authoritative.
- **2b's framing contract** (the read/write delivery shape): `Framer::feed` consumes `std::span<const std::byte>` per `[2b §4.2]`; `Writer::commit` produces a post-commit span per `[2b §4.5]`. 2h's `async_read_some` and `async_write` map directly.
- **2e's durable-before-transmit invariant** (per `[2e §6.1.4]`): the FSM sequences `Writer::commit → store → async_write`; 2h's `async_write` is purely the wire-side hop. A cancelled `async_write` MUST NOT roll back the persisted frame.
- **2d's threading + clock surface**: per-session strand per `[arch §5.1]` / `[2d §7.6]`; `effective_clock` for every transport-emitted timestamp per `[2d §7.9]`; `session_executor` wrapper per `[2d §4.8]`. Transport callbacks rebind to the session executor on the read-path completion.
- **2f's `async_mutex` is not consumed directly**: 2h references `[2f §4.1.1]` only for the awaitable-API conventions (no `async_mutex` dependency in the transport surface itself).
- **Session FSM (Phase-4 module) — the next feature**: 2h is the FINAL Phase-4 design-doc-driven feature before the session-module Phase-4 spec is drafted. The session FSM consumes `Transport` + `TlsTransport` + `ReconnectPolicy` + `handshake_result` and owns the Logon / Heartbeat / Resend / Reset / Logout transitions + the CompID-to-TLS-identity binding policy half of T-041.
