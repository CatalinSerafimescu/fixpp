## Ambiguities & Conflicts

- [x] CHK044 Does FR-009's "Sub-interface inherits virtually from `Transport`" align with the 5-slot cap accounting — does the virtual-inheritance overhead affect the slot budget (vtable layout)? [Ambiguity, Spec §FR-009] — PASS: `[const §XIV.2]` counts pure-virtual METHOD declarations, not vtable slots. Virtual inheritance does not add pure-virtual method declarations; it changes the vtable layout but not the `= 0` count. The spec's "1 of 5-slot budget" refers to pure-virtual method declarations, which is the right metric per `[const §XIV.2]`. No conflict.
- [x] CHK045 Does FR-023's "ONLY 1 pure-virtual" rule make the abstract `Listener` un-instantiable for `Listener::cancel()` callers — must they downcast or know the concrete type? Is the upcast/downcast pattern documented? [Ambiguity, Spec §FR-023] — DD-DECIDED §6.4.1: the design doc at `[2h §6.4.1]:1124` publishes the engine-scoped Listener cancellation as a SERVICE ROW — the engine-level cancel trigger calls `asio_listener::cancel()` on the concrete impl it owns. The engine was always in possession of the concrete type (it constructed the `asio_listener`); no downcast is needed because the engine stores `unique_ptr<asio_listener>` (or at least knows the concrete type at construction). FR-023 documents this clearly: "cancel is a CONCRETE-IMPL contract on `asio_listener`; the engine holds the concrete type". No ambiguity from the engine perspective; callers who only have a `Listener&` cannot cancel — by design.
- [x] CHK046 Does FR-026's `noexcept make(...)` conflict with the engine-bootstrap-carve-out (`[arch §5.3]` permits constructor throws for engine-scope objects) — is the factory itself bootstrap-scope or runtime-scope? [Ambiguity, Spec §FR-026] — PASS: FR-026 is unambiguous: "The `noexcept` carries per `[2h §4.7]` Codex P2 #6 close; impls MUST trap internal PMR / system throws via `[2a §4.2]` `trap_throw`". The factory `make(...)` is runtime-scope (invoked at every reconnect attempt); the `[arch §5.3]` carve-out applies to the CONSTRUCTOR of `asio_tls_transport` (which may throw at engine bootstrap). The factory wraps the throwing constructor in `expected_t<...>`. No conflict.
- [x] CHK047 Does FR-028's "no mid-session swap of TransportFactory MUST be exposed" leave room for a future-version API to add such a swap — is the prohibition v1.0-only or permanent? [Ambiguity, Spec §FR-028] — WAIVED: FR-028 says "No mid-session swap of `TransportFactory` MUST be exposed" and the design cites `[arch §5.6]` frozen-at-open rule as the rationale. The prohibition is architectural (frozen-at-open IS the design contract); future versions would need to revisit `[arch §5.6]` to add a swap, not just the transport spec. The v1.0 scope boundary is clear. Not tagged Completeness/Clarity/Consistency.
