## Requirement Completeness

- [x] CHK001 Are ownership requirements defined for the `Transport::Config::mr` PMR pointer (caller-owned? engine-owned? cached across attempts)? [Completeness, Spec §FR-029] — PASS: FR-029 says "`mr` (`std::pmr::memory_resource*`, default null = engine default; passed through factory `make(...)`)"; data-model E-7 says "`mr` is the PMR root the impl uses for SSL_CTX configuration arena + handshake-time SAN string copies"; E-11 says the factory caches the `SslCtxConfig` (which carries the resolved `mr` pointer) at factory level. - [x] CHK016 Is "FSM holds at most one live `Transport` per session at any time" (FR-028) defined relative to which lifetime boundary (between destruction and next `make` call there is zero live Transports)? ## Requirement Consistency

- [x] CHK017 Does FR-026's "MUST be cached at the factory level — never re-built per attempt" align with FR-028's "Each `async_connect` attempt MUST operate on a `Transport` instance newly minted by that factory" — is it clear that ONLY the cached state (SSL_CTX, PMR root, clock) is reused, and the Transport instance itself is fresh? [Consistency, Spec §FR-026 §FR-028] — PASS: FR-028 explicitly reconciles the two: "(The factory **selection** is frozen-at-open per `[arch §5.6]` … the `Transport` **instance** is short-lived per session-attempt … This reconciles with FR-026's 'long-lived state cached at the factory level' — the factory itself is long-lived; the `Transport` instances it produces are not.)" The parenthetical reconciliation statement in FR-028 directly addresses this exact consistency concern. The spec makes explicit: cached = factory + its internal state (SSL_CTX, PMR root, clock); fresh per attempt = the `Transport` object. Consistent and clearly explained.
- [x] CHK018 Does the "no rollback under cancel" (FR-030 + US1 AC3) align with the "previous Transport MUST be destroyed before the new one is requested" (FR-028) — is the destruction observable to the FSM before durable-storage operations are sequenced? [Consistency, Spec §FR-028 §FR-030] — PASS: FR-030 says "A cancelled `async_write` MUST NOT trigger any rollback of the persisted frame"; FR-028 says "the previous `Transport` MUST be destroyed before the new one is requested." These operate at different sequence points: (1) `async_write` cancellation happens during an active session (Transport is live); (2) Transport destruction happens at reconnect onset (after session drops, before new session starts). The durable-before-transmit invariant (`Writer::commit → store → async_write`) means the message is already persisted BEFORE `async_write` is called; cancellation of `async_write` does not affect durability. Transport destruction after session drop does not retroactively affect the store. The two requirements are consistent and non-conflicting: they apply at different points in the session lifecycle.
- [x] CHK019 Does the `Listener::cancel()` 3-action contract (FR-025) — "leaves already-resumed `unique_ptr<Transport>` UNAFFECTED" — align with FR-024's "each accepted connection MUST produce a freshly-minted `Transport`" — is "minted" timing strictly at `async_accept` return, not later? [Consistency, Spec §FR-024 §FR-025] — PASS: FR-023 says "`async_accept()` returning `expected_t<std::unique_ptr<Transport>>`"; FR-025 says "ownership has passed at the `async_accept` return". Data-model E-8 says "leave already-resumed-but-not-yet-consumed `unique_ptr<Transport>` results UNAFFECTED — ownership has passed at the `async_accept` return." The "minted" moment = `async_accept` awaitable resume (when the caller receives the `unique_ptr`). After resume, the listener has no reference — the caller's `unique_ptr` IS the ownership. Consistent: FR-024's "freshly-minted" timing = FR-025's "ownership has passed at `async_accept` return" = the awaitable resume point.
- [x] CHK020 Does FR-035's `trap_throw`-routing-on-PMR-throw align with FR-026's `noexcept` factory `make(...)` — is the entire chain (`make` → PMR throw → trap_throw → `transport_factory_failed`) free of any escaping exception across the public surface? [Consistency, Spec §FR-026 §FR-035] — PASS: FR-026 says "`make(...)` `noexcept`" and "impls MUST trap internal PMR / system throws via `[2a §4.2]` `trap_throw` and surface `transport_factory_failed`"; FR-035 says "NO PMR throw MUST escape the public surface as a C++ exception." The chain is: `make(...)` is `noexcept` at the declaration site → any internal PMR throw is caught at the `trap_throw` boundary (per `[2a §4.2]` which catches `std::bad_alloc` + PMR-routed throws) → converts to `unexpected{transport_factory_failed}` → returned as `expected_t`. The `noexcept` at the `make(...)` declaration + the `trap_throw` requirement together guarantee: no exception can escape. Consistent — they are complementary requirements that jointly enforce the no-exception guarantee.

## Ambiguities & Conflicts

- [x] CHK035 Is the field `Transport::Config::mr` (FR-029: "default null = engine default") clear on what "engine default" means — a pointer to the engine's PMR root? A null sentinel routed through a different path? [Ambiguity, Spec §FR-029] — PASS: FR-029 says "`mr` (`std::pmr::memory_resource*`, default null = engine default; passed through to factory `make(...)`)"; data-model E-7 says "`mr` is the PMR root the impl uses for SSL_CTX configuration arena + handshake-time SAN string copies"; E-11 says the factory's `make(exec, ssl_cfg, mr) noexcept` receives `mr` and uses it for the impl's allocations. "Engine default" means: when `mr == nullptr`, the factory/impl substitutes the engine's PMR root resource (which was set up at engine bootstrap). This is the standard pattern for PMR-aware APIs: `nullptr` means "use a default resource" (similar to `std::pmr::get_default_resource()`). The engine bootstrap configures the default; `nullptr` propagates through as "use whatever the engine configured." The ambiguity resolves via the standard PMR null-sentinel convention: `nullptr` → engine's default PMR resource. Sufficiently unambiguous for implementation.
- [x] CHK036 Does FR-028's "no mid-session swap of TransportFactory" align with the factory caching FR-026 (a mid-session swap would invalidate the cache; is that prohibition load-bearing for caching correctness, or independently desirable)? [Ambiguity, Spec §FR-026 §FR-028] — PASS: FR-028 says "No mid-session swap of `TransportFactory` MUST be exposed" and cites `[arch §5.6]` (frozen-at-open rule). FR-042 also says "mid-session `Transport` swap" is a non-goal. The prohibition has TWO rationales: (1) architectural — `[arch §5.6]` frozen-at-open is the primary principle (the engine-anchor + session-override pattern freezes all session resources at open); (2) caching-correctness — a mid-session factory swap WOULD invalidate the cached `SslCtxConfig` / PMR root / clock. Both rationales are present; the prohibition is load-bearing for both. FR-028's parenthetical explicitly reconciles the factory-is-long-lived vs Transport-is-short-lived distinction. Unambiguous.
- [x] CHK037 Is `handshake_result.negotiated_cipher` typed `std::pmr::string` (per data-model E-4) or some other ownership shape — does FR-010 specify? [Ambiguity, Spec §FR-010 + data-model E-4] — PASS: FR-010 says "`handshake_result` is an owning-by-value POD carrying (a) `peer_identity` (…), (b) the captured `Pinset` snapshot, and (c) the negotiated cipher-suite name." FR-010 names the field but does not specify the type of `negotiated_cipher`. Data-model E-4 explicitly states: "`negotiated_cipher`: `std::pmr::string`, e.g. `'TLS_AES_128_GCM_SHA256'`; PMR-allocated against `SslCtxConfig::mr`." The data-model is the authoritative field-type source (per the data-model doc's stated scope: "field shapes, ownership, allocator policy"); the spec FR-010 correctly describes the semantics ("owning-by-value"), and the data-model pins the type.
