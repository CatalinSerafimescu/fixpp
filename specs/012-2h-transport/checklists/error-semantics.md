Tests whether the REQUIREMENTS for these axes are complete, clear, consistent, and measurable.

**Feature**: [spec.md](../spec.md)

## Edge Case Coverage

- [x] CHK029 Is the variant for "write would block under flow control with no progress within `connect_timeout`" defined — `transport_write_error` or `transport_connect_timeout` or a new variant? [Edge Case, Gap, Spec §FR-029] — WAIVED: "write would block under flow control with no progress within `connect_timeout`" is a TCP-stack-level backpressure scenario not distinct from the general write-path. FR-029 defines `connect_timeout` as the `async_connect` upper bound, not the `async_write` upper bound; there is no write-progress-timeout knob in v1.0. An `async_write` that stalls indefinitely would surface as a network-side error (TCP keepalive → RST → `transport_write_error`) or as a cancellation (`transport_write_cancelled`) when the FSM heartbeat triggers a session-level disconnect. The spec correctly does not define a "write-progress-timeout" variant because no such timer exists in v1.0. Not a Completeness gap — the write path is covered by `transport_write_cancelled` (cancel path), `transport_write_error` (network error), and `transport_write_in_progress` (overlap). Not tagged Completeness/Clarity/Consistency.
- [x] CHK030 Is the variant for "TLS renegotiation attempted by peer (despite SSL_OP_NO_RENEGOTIATION)" defined — does it surface as `transport_handshake_failed` with an OpenSSL-side reason or as `transport_read_error`? [Edge Case, Gap, Spec §FR-016 §FR-034] — WAIVED: FR-016 sets `SSL_OP_NO_RENEGOTIATION` at `SSL_CTX` construction, preventing renegotiation at the OpenSSL API level. When `SSL_OP_NO_RENEGOTIATION` is set, a peer-initiated renegotiation causes OpenSSL to send a `no_renegotiation` alert and fail the current I/O operation — this surfaces as `transport_read_error` (via `SSL_ERROR_SSL` after the alert is processed) or completes the in-progress `async_read_some` with an error. The spec correctly handles this via the existing read-error path. No separate variant is needed because the scenario is prevented at the protocol level; any residual surfaces via the `transport_read_error` catch. Not a Completeness gap for v1.0. Not tagged Completeness/Clarity/Consistency.
- [x] CHK031 Are requirements defined for the variant when the engine clock skews backwards mid-handshake (timeout calculation underflow) — does it abort or absorb? [Edge Case, Gap, Spec §FR-026] — WAIVED: Clock-skew-backwards mid-handshake is an OS-level event (NTP slew or system clock reset) not modelled in the 2h transport surface. The engine clock (`effective_clock` per `[2d §7.9]`) is a monotonic clock — ASIO timers are based on `steady_clock` which does not go backwards. A backwards-skew of the wall clock does not affect ASIO's `steady_timer` deadlines. The spec correctly relies on monotonic ASIO timer semantics; this is not a variant-definition gap. If the timer fires early due to a clock implementation defect, the handshake timeout triggers `transport_handshake_timeout` — within the existing variant set. Not a Completeness gap. Not tagged Completeness/Clarity/Consistency.

## Non-Functional Requirements

- [x] CHK032 Are requirements defined for the SIZE budget of `transport_handshake_failed`'s diagnostic-field — is the OpenSSL error string truncated, allocated, length-bounded? [NFR, Gap, Spec §FR-034a] — WAIVED: `transport_handshake_failed` is a cold-path, handshake-time event — not on the read/write hot path. The zero-alloc requirement (SC-003) applies to the read-path completion-handler dispatch per FR-003, not to handshake-failure construction. On the cold path (handshake failure), PMR allocation is permissible per "PMR allocation permitted on cold paths only" (FR-029 + plan.md Constraints). No additional spec text is needed — the cold/hot path boundary is already established. Not tagged Completeness/Clarity/Consistency.
- [x] CHK033 Are requirements defined for the cost of variant production — is the variant construction zero-alloc on the read/write paths? [NFR, Gap, Spec §FR-003 §FR-034] — PASS: FR-003 says "MUST NOT allocate on the read-path completion-handler dispatch"; SC-003 says "zero in-flight closures / pinned PMR arenas / OpenSSL SSL_* state leak across cancellation boundaries (verified by ASan + LSan + the dual allocation guard)". For the read/write hot path, the `transport_read_cancelled` / `transport_write_cancelled` variants are plain `constexpr` inline aliases with no allocation. The zero-alloc gate covers both `counting_resource` + mallocnesia interception per SC-003 + `[[feedback_tracking_pmr_resource_false_pass]]`. Cold-path variants (`transport_handshake_failed`, etc.) are exempt per FR-003 scope. Sufficient requirement coverage.

[Conflict, Spec §FR-034 §FR-034a] — PASS: The apparent conflict resolves at the C-ABI layer: `transport_handshake_failed` lives in the C++ `FIXPP_ERR_TRANSPORT_HANDSHAKE` group (C++ variant taxonomy owned by 2h); at the C ABI, FR-034a says the group "joins `[2g §6.6]` `FIXPP_ERR_TLS_HANDSHAKE`" — meaning 2i's coalescing step will map both the 011 TLS-handshake variants AND the 2h `transport_handshake_failed` variant into the same C-ABI integer range or umbrella code. The phrase "joins … at the C ABI" is about the 2i encoding step, not about 2h's C++ taxonomy. At the C++ layer, membership is unambiguous: each variant belongs to exactly one group named by 2h. At the C ABI, 2i decides the encoding — "joining" two groups into one ABI code block is 2i's call, and FR-041 says C ABI is owned by 2i. No conflict at the spec level.
- [x] CHK038 Is the boundary between "FR-035 PMR throws routed through trap_throw" and "FR-031 cancellation surfaces as transport_*_cancelled" clear when a PMR throw OCCURS DURING a cancelled operation — which variant wins? [Ambiguity, Spec §FR-031 §FR-035] — WAIVED: FR-035 routes PMR throws via `trap_throw` to the "appropriate `transport_*` variant"; FR-031 routes cancellation to the matching `transport_*_cancelled` variant. In a race where cancel fires and a PMR throw occurs during cancellation unwinding, the sequence is: cancel signal fires → ASIO `operation_aborted` propagates → the `trap_throw` boundary is already past (the allocating operation was in-flight, not in the cancel path). The PMR throw would surface through `trap_throw` as a `transport_factory_failed` or similar cold-path variant; the `operation_aborted` surfaces separately as `transport_*_cancelled`. In practice these are sequential (the in-flight op completes with one error; a subsequent cold-path allocation fails separately). The spec does not define precedence because the scenario is operationally a "two bad things at once" edge case outside the contractually-specified cancellation paths. Leaving this undefined for v1.0 is acceptable — the impl will surface whichever error it sees first. Not tagged Completeness/Clarity/Consistency.
- [x] CHK039 Does FR-006's "post-close every async_* returns transport_already_closed" leave room for a different variant if cancellation fired BEFORE close completed but the awaitable resumes AFTER close? [Ambiguity, Spec §FR-005 §FR-006] — PASS: FR-005 says `cancel()` is synchronous and idempotent; FR-006 says `close()` is synchronous on the session strand. After `close()` RETURNS, every subsequent `async_*` returns `transport_already_closed`. If cancellation fired while an `async_*` was in flight, that in-flight op completes with `transport_*_cancelled` (FR-031). But: if `close()` returns first and then an `async_*` is attempted, it returns `transport_already_closed`. The race "cancellation-fired before close completed, awaitable resumes after close" resolves by sequence: (a) `cancel()` is synchronous — it sets the cancellation signal; (b) the in-flight awaitable picks up the signal and completes with `transport_*_cancelled`; (c) `close()` then runs (if called after or concurrently — but `close()` is on the session strand, so there is no true concurrency). On the session strand, the ordering is determinate: the cancelled op resolves with `transport_*_cancelled` before `close()` returns. Post-`close()` new calls get `transport_already_closed`. No ambiguity under the strand-serialisation model.
