## Scope and key recognition

- [ ] CHK001 Is the root-scope refusal stated once and identically? It appears in FR-016 ("a diagnostic that names it as a session key"), research R-9, data-model §A.4, the TOML contract, W-8 and T007 ("dialect_overlay is a session key; set it in [default] or [[session]]"). Is its reason class, `invalid_or_contradictory_selector`, justified against how the loader treats other session-only keys written at root? If the two differ, is the difference recorded? [Consistency, Spec §FR-016, data-model §A.4, research R-9]
- [ ] CHK002 Is the outcome stated for `dialect_overlay` written in a table that is not root, `[default]` or `[[session]]`, for example `[dictionary]` or one of a session's sub-tables? Today `recognize_keys` "applies one key set at every scope". Does the scope-aware change say which other scopes accept, refuse or ignore the key? [Gap, research R-9, data-model §A.4]
- [ ] CHK003 Is `T020_DeferredSetExactCoverage`'s expected set independent of the code it checks? Research R-9 and T007 say "re-derive the set from `kDeferred`". If the test reads `kDeferred` itself, a key removed from `kDeferred` by mistake cannot make it fail. Is it stated that the expected set is written out in the test, or derived by a recipe the reviewer re-runs? [Measurability, research R-9, contracts W-8, tasks T007]
- [ ] CHK004 Is FR-016's "The other deferred TOML keys stay deferred" backed by a stated check beyond `T020_DeferredSetExactCoverage` over the remaining keys? [Traceability, Spec §FR-016, contracts W-8]

## Values and path resolution

- [ ] CHK005 Is relative-path resolution stated for every case? [Clarity, Spec §FR-016, contracts surface.md (TOML), research R-9] The cases:
  - Both origins resolve against the configuration file's directory, which `load_toml_config` takes as `path.parent_path()`.
  - That directory is empty when the configuration path is a bare file name, so resolution falls back to the working directory.
  - Absolute paths are used as given.
  - `~` is not expanded.

  Is each case stated as "as `dictionary.path`", and is that equivalence stated rather than assumed?
- [ ] CHK006 Are the value checks complete, and consistent with `dictionary.path`'s? A non-string is `malformed_value` and an empty string is `empty_required`. Is the outcome stated for a whitespace-only string, a path to a directory, and a TOML array of paths? A user who expects several overlays may write an array, which "one overlay per load" excludes. [Coverage, Spec §FR-016, data-model §A.4, Spec Clarifications (one overlay per load)]
- [ ] CHK007 Is the dependency on `[dictionary] kind = "path"` stated? The overlay step calls `load_any_with_overlay(base path, overlay path, …)`, so it needs a base path. `kind = "version"` is recognised but deferred today. Is "dialect_overlay requires [dictionary]" the right message for that case? Is the dependency recorded for when `kind = "version"` ships? [Dependency, research R-9, data-model §A.4]

## Loading, caching and sharing

- [ ] CHK008 Is the cache key defined: the lexically joined path, its `lexically_normal` form, or the canonical file? Otherwise, two spellings of one file in `[default]` and `session[1]` give two loads, two pointers, and possibly two diagnostics for one failure. Examples are `venue.xml` and `./venue.xml`, or a symlink. [Ambiguity, research R-9, data-model §A.4]
- [ ] CHK009 Is it stated that a merged dictionary reads the base from disk again, apart from `[dictionary]`'s own load? Two consequences follow, and is either recorded? First, if the base file changes between the two reads, a session gets a merged dictionary whose base differs from `engine.dictionaries.front()`. Second, N distinct overlays cost N + 1 base parses at start-up. [Assumption, research R-9, data-model §A.4]
- [ ] CHK010 Is the outcome defined for a `[default]` `dialect_overlay` when there is no `[[session]]`? Is the overlay loaded and checked, or never read? Is a failing file reported in that case? [Gap, Spec §FR-016, research R-9]
- [ ] CHK011 Is the memory resource for the merged dictionary stated, `opts.resource` as for `[dictionary]`? Is its lifetime requirement relative to the returned bundle the same as for the engine dictionary? [Clarity, research R-9]
- [ ] CHK012 FR-015 says each `[[session]]`'s `SessionConfig::dictionary` is set, and the contract says so "when the load succeeds". Are the two consistent? When a load reports any diagnostic, does it return a bundle with the other sessions filled, or no bundle? Is that consistent with the loader collecting every diagnostic in one pass? [Clarity, Spec §FR-015, contracts surface.md (TOML), data-model §A.4]
- [ ] CHK013 Is the Orchestra case through TOML covered? `load_any_with_overlay` accepts an Orchestra `[dictionary]` with a `fixr:repository` overlay, but W-8's fixtures are all QuickFIX XML (T006). Is the Orchestra TOML path stated to be covered by W-4's dispatch witness, or given its own row? [Coverage, contracts W-8, tasks T006, contracts W-4]

## Diagnostics

- [ ] CHK014 Is `LoadDiagnostic::location` specified for each `dialect_overlay` diagnostic? The `key_path` is given per authoring origin. Is the line and column that of the value in `[default]` for an inherited failure, and that of the session's own value otherwise? [Gap, Spec §FR-016, research R-9, data-model §A.4]
- [ ] CHK015 Is the `message` of a failed load specified? FR-007 requires the C++ error to name the conflicting element, and FR-009 the cap, but every overlay failure maps to one reason class, `invalid_or_contradictory_selector`. Does the message carry the loader's text, so an operator can tell a limit from a conflict from a missing file? [Gap, Spec §FR-007, Spec §FR-009, research R-6 (TOML column)]
- [ ] CHK016 Is "reported once per authoring origin" defined in one place for every combination? Do FR-016, research R-9, data-model §A.4 and the TOML contract agree on each of these cases? [Consistency, Spec §FR-016, research R-9, data-model §A.4, contracts surface.md (TOML)]
  - `[default]` alone, inherited by several sessions: one diagnostic.
  - `[default]` and `session[N]` naming one failing file: two.
  - Two sessions each setting the same failing file: one each.
- [ ] CHK017 When `[dictionary]` is absent, is the full set of diagnostics specified? `load_toml_config` already emits `missing_required` at `dictionary`. Is it stated that the overlay step adds its own diagnostic at each origin, so one file reports both? Is it stated that `T020_MissingRequired_Dictionary`'s unchanged assertion still holds once that second diagnostic is added? [Clarity, research R-9, data-model §A.4, contracts W-8]
- [ ] CHK018 Is it stated how TOML reports an allocation failure during the overlay load? Research R-6 maps every row to the same reason class. Is that consistent with what `trap_throw_to_expected` does with a `std::bad_alloc` at its existing sites? Does its rewritten doc state that rule? [Consistency, research R-6, research R-9, tasks T062]

## The filled session dictionary: hosts

- [ ] CHK019 Does the B-098-3 disclosure name every way a host's existing code meets the filled bundle? [Gap, data-model §D (B-098-3), research R-9, Spec Clarifications (merge in the loader)]
  - A host that overwrites `config.dictionary` with `engine.dictionaries.front()` silently discards the overlay.
  - A host that builds `SessionConfig::dict_snapshot` from the engine's base dictionary now fails `open()` on every overlay session, because `Session::open()` refuses a snapshot whose `source()` is not `cfg_.dictionary`.
- [ ] CHK020 Does the release note give the migration as well as the hazard: stop copying the dictionary, or copy it only when `config.dictionary` is null? [Clarity, data-model §D (Release note (098)), plan Risks]
- [ ] CHK021 Is SC-004 measured the way its TOML-only host behaves? AS-1's cell drives `Session::open()` with no host code. Is it stated that `open()` is the observable, not just a non-null `config.dictionary`? Is the unfixed tree's failure stated to be `invalid_session_config`? [Measurability, Spec §SC-004, contracts W-8, tasks T006]
- [ ] CHK022 Is the TOML key's reach stated? The C ABI has no TOML loader, and `src/capi/config.cpp` sets `SessionConfig::dictionary` from a handle. So C and Python hosts cannot use `dialect_overlay` and must call `fixpp_dict_load_from_xml_with_overlay` instead. [Gap, Spec US3, Spec US4, research R-9]
- [ ] CHK023 Is the handling of `tests/session/engine_establishment_timeout_test.cpp` stated as a rule with a stop condition: run it unedited, and edit it only if R-9's change makes its host copy wrong? Is the reasoning that its copy is harmless written so that a reviewer can re-check it? That reasoning is that the file copies the same pointer the bundle already holds for a session without an overlay. [Clarity, plan Risks, tasks T061, research R-9]

## Engine dictionaries, the registry and FIXT

- [ ] CHK024 Is it stated which dictionary a FIXT.1.1 TOML session's overlay applies to? TOML loads one `[dictionary]` (L-097-1), and that is the session's own dictionary. Is it recorded that a FIXT TOML user can overlay only that file, FIXT11.xml or the Orchestra FIX Latest file? Does L-098-1 state this? [Ambiguity, Spec Edge Cases (FIXT.1.1 session), Spec §FR-021, data-model §D (L-098-1)]
- [ ] CHK025 Is FR-021's premise backed by a search that can be re-run? The premise is "today the registry only answers serviceability". The search should cover every reader of `EngineConfig::dictionaries` and of the registry. If any of them parses or validates for a session, the base-only registry would bypass that session's overlay. [Measurability, Spec §FR-021, Spec Edge Cases (FIXT.1.1 session)]
- [ ] CHK026 Does FR-015's "`EngineConfig::dictionaries` keeps holding the base dictionary" match FR-021's statement that the registry is unchanged? Is a witness named that shows the engine's vector holds the same pointer before and after the overlay step? [Consistency, Spec §FR-015, Spec §FR-021, research R-9]
- [ ] CHK027 Is L-097-1's text checked against 098? Its sentence "The TOML resolver loads one `[dictionary]`" stays true for the engine. But a TOML bundle now holds several dictionaries, one per distinct overlay. The spec's references call L-097-1 "read and unchanged", and data-model §G's recipe does not match it. Is the reason it needs no note recorded? [Consistency, Spec Normative References (B&L), data-model §G]
- [ ] CHK028 Is the hand-off to row 6 (fixpp#643) recorded where row 6 will read it? FR-021 records it as an `L-098-*` row "until row 6 settles it". Does that row also say what row 6 must not do: replace the session's own dictionary, for the session's own version, with a registry dictionary? [Completeness, Spec §FR-021, data-model §D (L-098-1)]
