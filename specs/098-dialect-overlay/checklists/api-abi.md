## C++ load entry points

- [ ] CHK001 Is FR-001's "a string form of the same for in-process use" applied the same way on every surface? `XmlLoader` and `OrchestraLoader` gain `load_with_overlay_from_string`, while `dict::load_any_with_overlay` and the C ABI take paths only. Is the missing string form on those two surfaces stated as a decision, or does FR-001 require one there too? [Consistency, Spec §FR-001, research R-8, contracts surface.md]
- [ ] CHK002 Do the throws lists in contracts/surface.md cover the path forms in full? The new bounded overlay reader (research R-5 step 1) and the base read can each fail on a missing, unreadable or non-regular file. Which type does each failure throw, and which C-ABI code follows (200, by the "any other `std::exception`" row)? [Gap, contracts surface.md (xml_loader.hpp), research R-5 step 1, research R-6]
- [ ] CHK003 Is it stated how `policy` reaches research R-5 step 6? Under `unresolved_group_policy::tolerant` the loader leaves a group unregistered, and that changes which groups `finalize` expands standalone. W-1's `tolerant` rows assert that the step counter equals the prediction, so the pre-walk must model the policy too. Is that a stated requirement on the walk, or only implied by the witness? [Gap, contracts surface.md, research R-5 step 6, contracts W-1]
- [ ] CHK004 Do the requirements state the lifetime rule for the `std::string_view` inputs of `load_with_overlay_from_string`: that no view into `base_xml` or `overlay_xml` outlives the call? Is it the same rule `load_from_string` follows? [Gap, contracts surface.md]
- [ ] CHK005 FR-008 holds by construction because "the loaders are stateless". 098 adds a step counter to `LoaderState` / `OrchestraLoaderState`, and a test-facing read seam that returns it. Is it stated that the counter lives only in per-call state and that the seam returns it by value? If not, the structural argument and the contract's "Thread safety as `load`" line need re-deriving. [Assumption, Spec §FR-008, research R-5 (read seam), contracts surface.md]
- [ ] CHK006 Does `dict::load_any_with_overlay` define an error for every format mismatch? The cases are: a QuickFIX-XML base with a `fixr` overlay, the reverse, a base of neither format, and an overlay of neither format. The spec gives the base case "the error `load_any` gives for an unrecognised root", and the contract gives a mismatched overlay `overlay_conflict_error`. Is an overlay whose root is neither format covered? [Completeness, Spec Edge Cases, contracts surface.md (load_any.hpp), contracts W-4]
- [ ] CHK007 FR-001 says the existing `load` / `load_from_string` / `load_any` MUST NOT change, yet 098 changes code they share: the factored pair detection, the counter at the head of `expand_field_list`, and the header-store walk on the `load` path. Is a check named that shows their observable results are unchanged, beyond "the existing dictionary tests stay GREEN"? [Measurability, Spec §FR-001, research R-1, tasks T021]

## Error types and what they carry

- [ ] CHK008 Is the class hierarchy of the two new errors stated, with its consequence for Orchestra callers? `overlay_conflict_error` and `overlay_limit_error` derive from `xml_parse_error`, not from `orchestra_parse_error`. A `catch (orchestra_parse_error const&)` around an Orchestra overlay load therefore misses an overlay conflict. One such conflict is the second-partner `lengthId` case, which the base `load` reports as `orchestra_parse_error`. [Clarity, research R-6, contracts surface.md (orchestra_loader.hpp)]
- [ ] CHK009 Can a caller tell an internal model drift from a user-caused limit by the step-counter refusal's public type? Both are `overlay_limit_error`, both map to 201 at the C ABI and in Python, and only the test seam exposes the origin. Is it stated that the C, Python and TOML surfaces report drift as "limit exceeded", and is that disclosure recorded? [Ambiguity, research R-5 (the step counter), research R-6, contracts surface.md]
- [ ] CHK010 Is the content of `what()` a requirement on the API, or only a witness assertion? FR-007 requires the conflicting element to be named, FR-009 the cap, and research R-3 both base occurrences of a repeated key. Which parts of the message are a stable contract, and which are free text? [Measurability, Spec §FR-007, Spec §FR-009, research R-3, research R-6]
- [ ] CHK011 Is `xml_oom_error`'s place stated the same way in the C++ throws list, the C-ABI catch order and the TOML column? It derives from `std::bad_alloc`, not from `xml_parse_error`, so it escapes a `catch (xml_parse_error const&)`. [Consistency, contracts surface.md, research R-6]

## `table_view::is_header_tag` and the declared header store

- [ ] CHK012 Is the tag's type conversion on the send path specified? `is_send_header_tag` takes a `std::uint32_t` tag, and the new `table_view::is_header_tag` takes `std::uint16_t`. In the classification `is_send_header_tag(tag) || inbound_tv_->is_header_tag(tag)`, a tag above 65535 would narrow onto a lower tag. Does the requirement say how such a tag is classified, so that it cannot alias a declared header tag? [Gap, research R-7 (Decision), data-model §A.3, contracts surface.md (table_view.hpp)]
- [ ] CHK013 FR-022 says "The dictionary MUST expose that header membership". Data-model §B lists only `table_view::is_header_tag` as public, while T056 edits `include/fixpp/dict/dictionary.hpp`. Is any new public `Dictionary` member named with its signature, or is it stated that `Dictionary` gains none? [Consistency, Spec §FR-022, data-model §B, tasks T056]
- [ ] CHK014 Is `is_header_tag`'s answer specified for each dictionary shape? The shapes are a FIX 5.0 QuickFIX-XML file whose `<header>` is empty (always false), FIXT11, an Orchestra dictionary (component 1024 with its group members), and a tag that is a member of a group in the header. Does the contract's one-line comment ("QuickFIX `<header>` expansion, Orchestra component 1024 expansion") match data-model §A.3's "fields, component members, NumInGroup tags and group members"? [Clarity, data-model §A.3, contracts surface.md, research R-7]
- [ ] CHK015 Is the layout growth disclosed as a C++ change that needs a consumer rebuild? `table_view` and the metadata handle each gain the header store. Is "no size or trait pin exists" backed by a search a reviewer can re-run? The new `table_view_builder` forwarder fills `header_bits_`. Does `tests/dictionary/table_view_seal_compile_test.cpp` (its "SEAL LEAK" / "PROBE BLIND" pairs) gain a probe showing that `table_view` itself still exposes no mutator? [Completeness, data-model §A.3, research R-7]

## C ABI 1.13: `fixpp_dict_load_from_xml_with_overlay`

- [ ] CHK019 Does the doc block's list of 201 causes match the C++ throws? The contract says 201 means "exceeds a cap or the expansion budget, carries a DOCTYPE, or would push a side table past 16 bits". The step-counter refusal is also an `overlay_limit_error`, so it also maps to 201, but the list does not name it. The list also enumerates causes in a shipped comment, which goes stale when a cap is added. [Conflict, contracts surface.md (C ABI), research R-6]
- [ ] CHK020 Is the difference between the two sibling C loaders disclosed for a host that moves from one to the other? `fixpp_dict_load_from_xml` maps every failure to `FIXPP_ERR_CAPI_CONFIG_INVALID` (10, `CapiError` in Python). The new function maps a missing or malformed base to `FIXPP_ERR_DICT_CONFIG` (200, `ValidatorError`). Is that stated in the doc block or in B-098-6? [Consistency, research R-6, data-model §D (B-098-6)]
- [ ] CHK021 Is NULL handling defined for each of the three arguments, and for an empty string? The doc block says "a NULL argument; *out_dict = NULL when out_dict is not NULL". Is that consistent with `fixpp_dict_load_from_xml`'s wording ("if path or out_dict is NULL")? Is an empty `base_path` or `overlay_path` stated to be a load failure (200), not `FIXPP_ERR_NULL_HANDLE`? [Clarity, contracts surface.md (C ABI), research R-6]
- [ ] CHK022 Is it stated that the C ABI loses FR-007's detail? The function returns only a code, and the C ABI has no last-error text, so a C or Python host cannot learn which element conflicted or which cap was passed. Is that recorded as a property of the surface (B-098-6 or an `L-098-*` row), or is FR-007 stated to be C++-only? [Gap, Spec §FR-007, Spec §FR-013, data-model §D]
- [ ] CHK023 Are the C++-only capabilities recorded as not offered at the C ABI, each with its reason? They are `unresolved_group_policy::tolerant`, the string form and the memory resource. `load_any.hpp` justifies the existing C function's lack of `policy` by the 1.5.0 freeze, and that reason does not cover a function added at 1.13. [Gap, research R-12, contracts surface.md, Spec §FR-013]
- [ ] CHK024 Are the path encoding and the resolution of relative paths stated for `base_path` and `overlay_path`? That means how `std::filesystem::path{const char*}` reads the bytes on MSVC and on Linux, and that relative paths resolve against the process working directory. Is each stated to be the same as for `fixpp_dict_load_from_xml`? [Gap, research R-6, research R-12]
- [ ] CHK025 Is the reentrancy token justified? `Reentrancy: single-thread.` matches the sibling loader, but the loaders are stateless and the merge holds no shared state. Is the choice between single-thread and thread-safe recorded against `[const §X.5]`, with `tools/check_capi_reentrancy.sh` named as its check? [Consistency, const §X.5, research R-12, contracts W-9]
- [ ] CHK026 Is the ownership and failure contract stated in full? On success the handle is owning and released with `fixpp_dict_destroy`, and `fixpp_session_config_set_dictionary` copies it. On every failure `*out_dict` is NULL, including when the handle's own allocation fails (202). Does the requirement also say what happens to a non-NULL `*out_dict` passed in? [Completeness, data-model §C, contracts surface.md (C ABI)]
