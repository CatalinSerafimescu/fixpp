## `fixpp_msg_remove_tag` & Index Bounds — Completeness & Clarity

- [x] CHK001 Does the spec state that the refusal **narrows the published idempotence guarantee** (*"absent returns OK"*), so an absent tag with a builder open no longer returns OK? Or is that consequence left to `contracts/msg-remove-tag.md` §1? FR-003 covers only the no-builder case. [Completeness, FR-001, FR-003, Spec §Edge Cases] — PASS: US1 Acceptance Scenario 1 already states the refusal fires "for any tag" while a builder is open (which includes an absent one), and the Edge Cases bullet "A refusal that is safe to refuse" explicitly names the absent-tag-with-builder-open case and says it is refused anyway. `spec.md` §User Story 1 Acceptance Scenario 1, §Edge Cases.
- [x] CHK002 Is "any group builder is open" defined over the whole builder stack, including a **nested** builder and several simultaneous top-level builders, within FR-001 itself rather than only in Edge Cases? [Clarity, FR-001, FR-002, Spec §Edge Cases] — PASS: FR-001's "**any** group builder is open" is already a universal quantifier over the whole builder stack — it does not carve out nesting or count by construction. The Edge Cases bullet "Several builders open at once" adds rationale for why several top-level builders don't need a case split; it does not widen FR-001's scope beyond what "any" already covers. `spec.md` FR-001, §Edge Cases.
- [x] CHK003 Does the spec require that every open builder remain **usable** after a refusal (add-entry, set, group-end still succeed), as a stated post-condition distinct from the byte-identical payload? A payload match alone does not separate a refusal from a partial operation. [Completeness, FR-001, SC-001] — SPEC-FIXED: FR-001 now states the post-condition directly — "Every open builder MUST remain usable after the refusal — its add-entry, field-set and group-end calls continue to succeed — as a post-condition distinct from SC-001's byte-identical committed payload." `spec.md` FR-001.
- [x] CHK004 FR-004 says *"three reachability classes exist … the classes are the requirement"* but does not name them. Are the classes stated in the spec, so the requirement can be evaluated without the contract — including that immediate dereferences of a resolver result are a **propagation** obligation and not a subscript? [Completeness, FR-004] — SPEC-FIXED: FR-004 now names all three classes verbatim, matching `contracts/msg-index-bounds.md` §2.1, including that class (3) "becomes a new null-dereference site unless the resolver's failure is propagated through it" (a propagation obligation, not a subscript). `spec.md` FR-004.
- [x] CHK005 Is the arrangement by which SC-003's out-of-range index is produced specified? The Edge Cases state the refusal is **expected to be unreachable** through the C ABI once FR-001 lands. Does SC-003 say whether its observable is reached through the public surface or through an internal arrangement? [Measurability, Conflict, SC-003, Spec §Edge Cases] — SPEC-FIXED: SC-003 now states "Reached through an arrangement that presents an out-of-range index directly, since FR-001's guard is expected to make the public path unreachable once it lands", resolving the apparent conflict with the Edge Cases unreachability claim without prescribing which of `plan.md`'s open implementation shapes (resolver-body checks vs. a caller-side check) the arrangement must bypass — that choice is left open per `plan.md` §"What Phase 0 deliberately leaves open". `spec.md` SC-003.

## `fixpp_msg_clone` — Consistency & Measurability

- [x] CHK006 Are **both** allocation-failure routes specified with their codes? US3 scenario 2 says an allocation failure yields `FIXPP_ERR_UNKNOWN`. The clone contract preserves `std::bad_alloc` during clone construction as `FIXPP_ERR_CAPI_CONFIG_INVALID`, an arm the spec never mentions. As written, a reader expects one out-of-memory code where there are two. [Ambiguity, Conflict, FR-006, FR-008, Spec §US3] — SPEC-FIXED: a new Edge Cases bullet, "Two distinct out-of-memory arms on the clone path, not one", now names both routes and their codes and states the second is preserved, not widened, by FR-008. `spec.md` §Edge Cases.
- [x] CHK007 FR-006 and SC-005 state the codes as a fan of **three**. The clone contract defines the code as *"`translate()`'s current image … a condition plus a function, not a closed list"*. Is the spec's list presented as exhaustive, and is that consistent with the contract's definition? [Consistency, FR-006, SC-005] — SPEC-FIXED: FR-006 now states the three are "the re-parse failure routes reachable **today**... not a closed list this feature owns — a future route added to that switch translates through the same mechanism without further change here", matching the contract's "condition plus a function" framing. `spec.md` FR-006.
- [x] CHK008 Is FR-008's abort limb given an acceptance criterion that stays meaningful **if no injectable non-`bad_alloc` seam exists**? The quickstart registers that set as possibly empty. Does the spec say what discharges FR-008 in that case, and is the fatal log's content or destination specified enough to be matched? [Measurability, FR-008] — SPEC-FIXED: the "A non-allocation exception on the clone path" Edge Cases bullet now states the disposition-if-untestable — "the declaration and ledger row still stand on the shape of the code... rather than on a demonstrated trigger, and any resulting uncovered line is dispositioned per `[const §IX.1]` at implementation time." (The fatal log's exact content/destination is left to the shipped idiom it must match — `src/capi/session.cpp`'s `std::fputs`/`std::abort()` — a code-shape fact appropriately owned by the contract.) `spec.md` §Edge Cases.
- [x] CHK009 Does the spec require that the **source** handle is unchanged and still usable after a refused clone, and that `*clone_out` is NULL on every refusal arm? SC-004 says *"no handle"*, which is not the same statement. [Completeness, FR-005, SC-004] — SPEC-FIXED: FR-005 now states "On this and every other refusal arm, `*clone_out` MUST be set to `NULL` and the **source** handle MUST remain unchanged and usable — no clone was constructed and nothing was consumed from it." `spec.md` FR-005.

## Session-Config Byte Floor — Completeness, Edge Cases & Measurability

- [x] CHK012 Is the C++ error for FR-012's refusal at session open named in the spec? `error::invalid_session_config` appears only in the contract, and FR-012 names no error at all. [Completeness, FR-012] — SPEC-FIXED: FR-012 now ends "...before any message is emitted, returning `core::error::invalid_session_config`." `spec.md` FR-012.
- [x] CHK013 Is SC-007's observable specified in a form a caller can see? The contract records that both engine sites which open a session **discard** the error, so *"opening it fails"* may have no caller-visible code. Is *"never emits a frame"* the stated criterion, and by what observation? [Measurability, SC-007] — PASS: US2 Acceptance Scenario 2 already ties "opening fails" directly to `Session::open()`'s own return ("the open fails before any message is emitted"), which is testable by a C++ caller invoking `Session::open()` directly and observing no frame on a mock transport. The contract's point (§7) is that the two **production** engine call sites discard that result — a fact about production wiring, not about SC-007's own testability. `spec.md` §User Story 2 Acceptance Scenario 2, SC-007.
- [x] CHK014 Is the refusal of `fixpp_session_config_set_comp_ids` specified as **atomic across both arguments**, so a valid sender with an invalid target stores neither? FR-011's *"leave the configuration unchanged"* can be read either way. [Clarity, FR-011, SC-006] — SPEC-FIXED: FR-011 now states "For `set_comp_ids`, the refusal MUST be **atomic across both arguments**: a valid sender paired with an invalid target MUST leave neither stored." Verified against source: `src/capi/config.cpp`'s current body assigns `sender_comp_id` then `target_comp_id` sequentially with no atomicity today, so this is a real implementation obligation, not a restatement. `spec.md` FR-011.
- [x] CHK015 Does the spec state that the two setters are the **only** C-ABI route by which CompIDs and BeginString enter a session configuration? The C-ABI half of FR-011's protection rests on that assumption. [Assumption, Coverage, FR-011] — SPEC-FIXED: a new Assumptions bullet states the condition and its re-derivation recipe ("re-derive by searching `src/capi/` for writes to those members; a new route appears as a write outside the two setters"), verified against source with a control: `grep -rn "sender_comp_id\|target_comp_id\|begin_string" src/capi/` returns writes only at the two setters in `config.cpp`, against a different-pattern control (`store_factory\|heartbeat`) positive on the same corpus, so the negative is a measurement. `spec.md` §Assumptions.
- [x] CHK016 Is the treatment of an embedded **NUL** stated? It is inside the floor's `< 0x20` range, but a C string cannot carry it past the setter. Is the reason stated why SC-008 exercises SOH *"(not NUL)"*, and what a reader should expect from NUL on each surface? [Edge Case, Clarity, FR-011, SC-008] — SPEC-FIXED: SC-008 now states the reason — "NUL is excluded because a C string cannot carry an embedded NUL to this call at all — the byte scan never sees it — so SOH is the byte that exercises the floor." `spec.md` SC-008.
- [x] CHK017 Are bytes the floor deliberately **accepts** — `0x7F` and bytes `≥ 0x80` — stated as accepted, rather than inferred from *"widening … is out of scope"*? [Edge Case, FR-013, Spec §Explicitly out of scope] — SPEC-FIXED: a new Edge Cases bullet states directly that "Bytes `0x7F` and every byte `≥ 0x80` are deliberately accepted by the floor, not merely untested." `spec.md` §Edge Cases.
- [x] CHK018 Is there a requirement that the **existing credential refusal** (username/password at session open) is behaviourally unchanged when its function-local rule is replaced by FR-013's single definition? FR-013 fixes the *charset*, not the credential guard's observable behaviour. [Coverage, Gap, FR-013] — SPEC-FIXED: FR-013 now states "Replacing the credential guard's existing function-local lambda with a call to this one definition MUST NOT change the credential refusal's observable behaviour — its return code and refusal condition stay exactly as shipped." `spec.md` FR-013.
