**Purpose**: "Unit tests for English" — validate that the REQUIREMENTS for the logging-leg TOML loader are complete, clear, consistent, measurable, and cover the highest-risk surfaces, BEFORE implementation. Tests the spec/plan/research wording, not the (not-yet-written) code.

## Fail-Closed & Zero-Side-Effects (US2 / FR-014 / FR-015 / SC-003)

- [x] CHK001 Is the ordering requirement "validate + preflight, then construct the live Logger only on a clean whole-file accumulator" stated unambiguously, with the construction step named as the SOLE side-effectful step? [Clarity, Spec §FR-015 / research §D-7] — PASS: FR-015 "A live logger…MUST be constructed only at the very end of a load whose whole-file diagnostic accumulator is empty"; research D-7 step 3 names it "the SOLE side-effectful step."
- [x] CHK002 Is "nothing is left opened on a failed load" decomposed into objectively-checkable post-conditions (no sink file opened, no directory created, no drain thread started)? [Measurability, Spec §FR-015 / §SC-003] — PASS: FR-015 "no sink files are opened and no drain thread is started; nothing is left partially configured"; SC-003 adds "no directory is created" as a third named post-condition, all three objectively checkable.
- [x] CHK003 Are the requirements explicit that a per-session logger error suppresses construction of an EARLIER session's (and the engine's) logger (whole-file scope, not per-session)? [Completeness, research §D-7 N-2 / data-model §E-5] — PASS: research D-7 N-2 "a later session's error still suppresses construction of an earlier session's logger"; data-model E-5 "a later session's error suppresses construction of an earlier session's logger (N-2)"; construction is "a single final pass over the whole set."
- [x] CHK004 Is the prohibition on silent no-op-logger substitution stated as a requirement (not merely implied), and is "no-op logger" defined? [Clarity, Spec §US2 / §FR-001] — PASS: US2 "the loader never silently falls back to a no-op output"; Glossary defines "fail-closed" as "never silently substitutes a default, a no-op output, or a partial configuration"; FR-003 + data-model E-1 define null-logger as the engine no-op, distinguishing it from silent substitution.
- [x] CHK005 Is the named inherited-017 TOCTOU limitation (ctor silently disables a sink whose open() fails post-preflight) documented as an explicit, bounded limitation rather than left as an unstated gap? [Completeness, research §D-7 / Spec §FR-015] — PASS: FR-015 carries an explicit "Known limitation (inherited from the 017 logger)" paragraph naming the TOCTOU window; research D-7 "Named limitation" paragraph provides identical coverage with the future-option tightening noted as not-required.

## Side-Effect-Free Load-Time Resource Preflight (FR-014)

- [x] CHK006 Is "side-effect-free" preflight quantified by the exact operations allowed (stat/access only; no mkdir; no probe file write)? [Measurability, Spec §FR-014 / data-model §validation-summary] — PASS: FR-014 "a stat/access check — the preflight MUST NOT create the directory or write a probe file"; data-model validation-summary "stat/access only, no mkdir, no probe file"; research D-7 step 2 repeats the same constraint verbatim.
- [x] CHK007 Are the three preflight checks each specified with their pass/fail condition: file-sink directory already-exists-and-writable, OTLP cert readable+PEM-magic, OTLP endpoint present/non-empty? [Completeness, Spec §FR-014 / data-model §E-4] — PASS: FR-014 enumerates all three checks with named fail conditions; data-model E-4 repeats each check with pass/fail mapping per sink type.
- [x] CHK008 Is the boundary between load-time validation (PEM-magic only) and deferred sink-open() work (full CA-bundle parse) stated unambiguously, with the rationale for not doing the full parse at load? [Clarity, research §D-4] — PASS: FR-014 "leading-`-----BEGIN`/PEM-magic validation — the full CA-bundle parse happens later at sink open()"; research D-4 explains the rationale: no cheap public CA-PEM parse primitive exists (`make_file_cert_source` is client-identity-only; the private `load_ca_bundle` is inaccessible), with the future-tightening option noted.
- [x] CHK009 Is each preflight failure mapped to a specific reason_class (dir/cert → invalid_or_contradictory_selector; endpoint → missing/empty_required) so the requirement is testable per-key? [Measurability, data-model §validation-summary] — PASS: data-model validation-summary maps every preflight failure to an exact reason_class: dir-not-exist/not-writable → `invalid_or_contradictory_selector`; cert unreadable/non-PEM → `invalid_or_contradictory_selector`; endpoint absent/empty → `missing_required`/`empty_required`. Quickstart failure-table provides key_path examples per case.
- [x] CHK010 Is it specified that FileSink::open() opens the log FILE (not the directory), so the "directory must pre-exist" requirement is internally consistent across spec/research/quickstart? [Consistency, Spec §FR-014 / quickstart §note] — PASS: FR-014 states "`FileSink::open()` creates/opens the live log file, not the directory; the directory must pre-exist"; quickstart note repeats this verbatim; data-model validation-summary and research D-7 each state it — four consistent sites, none contradictory.

## Build-Conditional Sink Symmetry (FR-013)

[Consistency, Spec §FR-013 / research §D-3] — PASS: FR-013 names both cases symmetrically under `invalid_or_contradictory_selector`; research D-3 confirms "build-unavailable, like syslog on non-POSIX — FR-013"; data-model E-4 maps both platform gate (syslog) and build availability (OTLP) to `invalid_or_contradictory_selector`.
- [x] CHK012 Is the distinction between "build/platform-unavailable kind" (invalid_or_contradictory_selector) and "recognized-but-deferred" (recognized_not_yet_supported_step2) stated as a requirement so the two are never conflated? [Clarity, Spec §FR-013 / Clarifications 2026-06-20] — PASS: FR-013 "MUST NOT…conflate it with the recognized-but-deferred reason, or report it as an unknown enum"; Clarifications 2026-06-20 "hard fail-closed config error (the kind is real but unusable on this deployment), never silently skipped and not conflated with the recognized-but-deferred reason."
- [x] CHK013 Is the syslog `facility` closed set fully enumerated (no ellipsis) AND is the build-conditional `#ifdef LOG_*` sub-rule (in-set name whose macro is undefined → invalid_or_contradictory_selector) specified distinctly from the not-in-set rule (→ unknown_enum)? [Completeness, data-model §E-4 / research §D-3] — PASS: data-model E-4 enumerates all 20 facility names explicitly (kern, user, mail, daemon, auth, syslog, lpr, news, uucp, cron, authpriv, ftp, local0–local7) with no ellipsis; two distinct rules stated separately: "name in set but LOG_* undefined → invalid_or_contradictory_selector" and "name not in set → unknown_enum, reporting the legal set." Research D-3 confirms both rules.
- [x] CHK014 Is it required that a build-unavailable sink is NEVER silently skipped or dropped from the chain (loud, not silent)? [Coverage, Spec §FR-013] — PASS: FR-013 "MUST NOT silently skip it, silently drop it from the chain"; data-model E-4 platform gate "never silently dropped"; contracts/observability_config.hpp resolver entry-point comment confirms "#else emits the diagnostic (never silently dropped)."

## Per-Key Collect-ALL Diagnostics (FR-020 / FR-021 / SC-007)

- [x] CHK015 Does the spec require every diagnostic to carry all of {offending key/selector path, reason_class, file location}, and is the reason_class taxonomy enumerated (reusing step-1's 9 values, no new value)? [Completeness, Spec §FR-020 / research §verified-surface] — PASS: FR-020 requires "the specific offending key/selector, the reason class (reusing step 1's taxonomy: unknown key, recognized-but-not-yet-supported, missing required, empty required, malformed value, out-of-range, unknown enum, invalid/contradictory selector, parse error), and the file location" — all three fields required, all 9 values named; verified 9-value count matches load_diagnostic.hpp enum; FR-024 confirms "no new reason_class."
- [x] CHK016 Is "collect-ALL in one pass" stated as a hard requirement (N independent errors → exactly N diagnostics; no fix-one/re-run loop), including logger errors interleaved with establishment errors? [Measurability, Spec §FR-021 / §SC-007] — PASS: FR-021 "MUST collect and report ALL errors found in a single load pass (including logger errors interleaved with establishment errors)…no fix-one / re-run loop"; SC-007 "N independent errors (logger and/or establishment) yields N distinct per-key diagnostics from a single load attempt."
- [x] CHK017 Are the key_path conventions for nested/array selectors specified (e.g., `logger.sinks[1].endpoint`) so diagnostics are unambiguous per sink? [Clarity, quickstart §failure-table / data-model §E-4] — PASS: quickstart failure-table provides concrete examples `logger.sinks[0].kind`, `logger.sinks`, `logger.sinks[1].endpoint`, `logger.capacity`, `logger.sinks[1].cert_source`, `logger.sinks[1].use_grpc` — sufficient to unambiguously derive the convention (dot-path with 0-based bracket indexing for array entries); data-model E-4 uses `logger.capacity` and the contracts use `logger.sinks[i]` consistently.

[Consistency, Spec §SC-007 / §FR-022] — PASS: SC-007 "still-deferred keys…are reported under the distinct deferred reason, not as unknown-key typos"; FR-022 keeps all deferred keys under `recognized_not_yet_supported_step2`, never `unknown_key`; US4 acceptance scenarios confirm `[tracer]`/`[meter]` → distinct "recognized-but-not-yet-supported" reason.

## Credential Redaction (FR-023)

- [x] CHK019 Is the set of sensitive values reachable through a logger selector defined (e.g., credentials embedded in a collector endpoint/header) so redaction scope is unambiguous? [Clarity, Spec §FR-023] — PASS: FR-023 bounds the scope explicitly: "concretely: credentials embedded in an OTLP collector endpoint URL — e.g. the userinfo in `http://user:secret@collector:4318/v1/logs`" and "endpoint userinfo is the only file-reachable credential surface; the redaction scope is bounded to it" — header-based auth excluded because `OtlpLogSinkConfig` carries no header/auth field.
- [x] CHK020 Is the redaction requirement stated to cover BOTH diagnostics AND logs, consistent with step-1's redaction behavior (no drift in the redaction token/placeholder)? [Consistency, Spec §FR-023] — PASS: FR-023 "MUST be redacted from diagnostics and logs, consistent with step 1's redaction behavior." Both surfaces (diagnostics and logs) are explicitly named. The "consistent with step 1's redaction behavior" phrase is the Consistency anchor by-reference — it pins the implementation to the 044 redaction contract without re-specifying the token, which is the correct form for a behavior that belongs to the inherited loader invariant.
- [x] CHK021 Is redaction made objectively verifiable (the diagnostic message must never contain the cleartext secret)? [Measurability, Spec §FR-023] — PASS: FR-023 "MUST be redacted from diagnostics and logs" is a binary, objectively verifiable condition; the US2 independent test ("assert each is rejected, the diagnostic names the correct key and reason") requires inspecting the diagnostic message, so a test that injects a URL with an embedded secret and asserts the raw secret does not appear in the diagnostic text is a direct and implementable verification.

## Cross-Cutting Clarity / Consistency / Edge Cases

- [x] CHK029 Is the composite-selector requirement (logger scalars PLUS an ordered, non-empty `[[logger.sinks]]` array) unambiguous, including the zero-sinks-is-an-error rule and the duplicate-sink-kind-is-valid edge case? - [x] CHK030 Is relative-path resolution specified consistently for ALL path-bearing selectors (file-sink directory, OTLP cert) — against the config-file dir, not the process CWD (matching step-1 FR-016a)? - [x] CHK031 Is the empty-OTLP-endpoint decision (loader is stricter than the sink's silent-drop default → reject as empty_required) documented with rationale, so the requirement is not mistaken for sink default behavior? [Clarity, Spec §Edge-Cases / data-model §E-4] — PASS: Edge-Cases paragraph explains the underlying sink behavior ("records are buffered and silently dropped on flush") and then states the loader decision ("deliberately stricter than the sink default") with rationale ("a file-explicit empty is far more likely a mistake than intent, and the silent-drop sink behavior makes the loud rejection the safe choice"); data-model E-4 OTLP maps `absent/empty → missing_required/empty_required`.
- [x] CHK032 Is the `ring_resource` exclusion (logger buffer allocator stays default; selecting it → deferred arena, never file-set) stated as a requirement so it is not silently mappable? [Completeness, Spec §FR-010 / data-model §E-3] — PASS: FR-010 "MUST NOT configure memory-arena selection (including the logger's buffer memory resource)"; Edge-Cases "A logger ring/buffer memory resource: not file-selectable this step…an attempt to select it is treated as the deferred arena surface (US4)"; data-model E-3 row `ring_resource` "NEVER file-set / deferred arena (FR-010); selecting it → deferred reason."
- [x] CHK033 Is "frozen at load/open" specified (later edits to the file do not affect a running engine until reload-and-reopen), consistent with step-1? [Consistency, Spec §FR-019] — PASS: FR-019 "Configuration MUST remain frozen at load/open; later edits to the source file MUST NOT affect a running engine's logging until an explicit reload-and-reopen"; Edge-Cases "configuration is frozen at load/open exactly as in step 1" — explicitly invokes step-1 consistency.
- [x] CHK034 Are the `capacity` power-of-2 and `on_overflow` closed-enum requirements quantified with their failure reason_class (out_of_range / unknown_enum), and is "no implicit defaults" stated (absent optional → documented default; absent required → error)?
