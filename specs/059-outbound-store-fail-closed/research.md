# Phase 0 Research — Outbound store-failure disposition (059)

All line numbers verified against the reviewed tree (submodule HEAD `9305e69`, the bundle commit), 2026-07-03.

## Grounded facts (the mechanism, re-confirmed)

- **Two independent counters.** The wire counter (`SeqnumManager::next_outbound_`) is advanced by `assign_outbound()` in `send_impl` (`session.cpp:~4478`) **before** `store_then_emit` runs. The store keeps its **own** next-expected counter, advanced only on a fully successful `store()` (`memory_store.hpp:196`; `file_store.cpp` Region 3, skipped on `!io_ok`).
- **The swallow.** `store_then_emit` (`session.cpp:4780-4801`) does `auto store_r = co_await store_->store(...); (void)store_r;` (`:4790`). The store returns `store_io_failure` / `store_seqnum_out_of_order` / `store_capacity_exhausted` as `std::unexpected` — **returned, not thrown** — so the surrounding `try/catch` (which only catches `asio::system_error{operation_aborted}`) never sees them. The frame is then transmitted unconditionally in Step 2 (`:4817-4834`).
- **Retain-before-transmit (I-3).** Step 1 (store) precedes Step 2 (transmit). A `co_return` in the store-failure branch skips the transmit.
- **The asymmetry (S-P2-1).** `persist_inbound_advance_` (`session.cpp:699-709`) and `persist_outbound_advance_` (`:716-726`) each do: `if (!r) { record_state_transition_(fsm_state::Disconnected); co_return std::unexpected(error::store_io_failure); }` — fatal-when-persistent, gated on `store_is_persistent_`. The outbound **frame** store on the send path is the odd one out (logged-then-proceed).
- **`store_is_persistent_`** is set once at `open()` (`session.cpp:1154`) from `cfg_.store_factory->yields_persistent_store()` — `false` for `MemoryStore`, `true` for `FileStore`; null-store path leaves it `false`. Single reliable capture point covering both roles.
- **Rehydrate on reconnect.** `ensure_hydrated_` (`session.cpp:639-693`) early-returns when `hydrated_ && !force` (`:642-645`). It is called on reconnect by **both** roles: initiator via the shared `emit_initiator_logon_` emit point (`:761`) and acceptor via the inbound-Logon handler (`:2062`), each with `force = refresh_on_logon && !bilateral_strict` (default `false`). It re-applies **both** the inbound seed (gated by `apply_inbound_seed`) and the outbound seed via `seqnum_mgr_.hydrate(...)` — which is why forcing it (by clearing the latch) has cross-feature blast radius; see D4.
- **Targeted outbound reseed exists.** `SeqnumManager::set_next_outbound(n)` (`seqnum_manager.hpp:140`) forces the outbound counter only — minted for the 032 initiator restore. `peek_outbound()` reads it synchronously. `reset_to_one()` (`seqnum_manager.hpp:124`) resets **both** counters to 1 — but it is reached **only** via `reset_seqnums_to_one_durable`, which the initiator emit gates on `if (cfg_.reset_on_logon)` (`session.cpp:776-782`). It is **NOT** run under `bilateral_strict`: that policy only forces the outbound `141=Y` flag (`initr_reset_seqnum`, `session.cpp:816-818`) and samples `peek_outbound()` (`:802`) with no preceding reset. **`bilateral_strict` is the production DEFAULT** (`session_config.hpp:231`); `reset_on_logon` defaults `false` (`:251`).
- **The existing transport-failure disposition (the parity anchor for D3).** `store_then_emit` (def `session.cpp:4734`) already fails closed on a *transport-write* failure: Step 2 does `co_return std::unexpected(error::dispatch_aborted)` on a live-write error (`:4820-4822`) and on the config-time `transport_send_` throw (`:4826-4832`). It does **not** call `record_state_transition_` itself — the transition is **caller-owned**. Step 1's store-error swallow (`(void)store_r;`, `:4790`) and the thrown-`operation_aborted` → `dispatch_aborted` (`:4791-4795`) sit in the same coroutine. So the persistent-store-failure fatal path is the *same shape* as the existing transport-failure return: reconcile (best-effort) + `co_return std::unexpected(err)`, **no internal transition**.
- **`store_cancelled` is shutdown-only.** Returned on the `store()` path exclusively when `async_lock()` is cancelled/drained (`memory_store.hpp:145`, `file_store.cpp:1028`) — see D7.

## D1 — Disposition: fatal-when-persistent (Option A), NOT counter-reconcile (Option B)

**Decision.** On `!store_r` in `store_then_emit`: if `store_is_persistent_` → fail closed (best-effort reconcile, **do not transmit**, `co_return std::unexpected(store_r.error())`) — the **same return shape** as the existing transport-write failure (`co_return dispatch_aborted`, `session.cpp:4820-4832`). The `Disconnected` transition is **caller-owned**, exactly as it is for the transport-failure return today (see D3). Else → today's `(void)store_r;` logged-then-proceed.

**Rationale.**
- Symmetric with the already-fatal durable counter-write paths (`persist_*_advance_`) — same durable-write class, now the same disposition. Removes the S-P2-1 asymmetry that is the root of the S-P1-1 freeze.
- Constitutionally mandated: Art. XV §15 forbids silent app/session message loss and names `disconnect-and-recover` (disconnect → `ResendRequest` on reconnect) as the sanctioned mode. The current swallow is precisely the banned silent-desync.
- Because store precedes transmit, fail-closed = **disconnect-before-transmit**: the un-retained seqnum `k` never reaches the wire, so the peer's last-seen (`k-1`) stays consistent with the durable store counter (`k`) — the restart/reconnect desync (blast #2) is eliminated at the source.

**Alternatives rejected.**
- **Option B — reconcile the store counter up to the assigned seq** (accept `k`, advance the store past the un-written bytes). *Rejected:* for the `store_io_failure` sub-case this is actively wrong — it would advance the store's counter over bytes that were never written, so a later `retrieve(k)` returns a hole/garbage while the store *claims* to hold `k`. Reconcile only makes sense for a pure order-check rejection, not a write fault, and the disposition must not depend on distinguishing them (FR-004). Fail-closed is uniformly correct across all three error classes.
- **Option C — keep swallowing but log louder.** *Rejected:* does not fix the freeze or the restart desync; the whole point is that "advertise a retention guarantee you can't honour" is the defect.

## D2 — Error code: propagate the store's own error, no new code

**Decision.** `co_return std::unexpected(store_r.error())` — surface the store's actual error (`store_io_failure` / `store_seqnum_out_of_order` / `store_capacity_exhausted`).

**Rationale.** Symmetric with `persist_*_advance_` (which return `store_io_failure`); preserves the diagnostic distinction for logging; introduces **no new error code** (A-4). The existing `operation_aborted` throw-path keeps returning `dispatch_aborted` unchanged (D5).

**Capture-before-reconcile (NEW-P3).** The fatal branch MUST capture `store_r.error()` into a local **before** the best-effort reconcile read (D4). The reconcile does `co_await store_->next_seqnum(...)` inside the existing `try`; on a shutdown race that read can throw `operation_aborted`, be caught, and pre-empt the intended error with `dispatch_aborted`. Capturing first guarantees the returned code is the store's own error regardless of a reconcile throw.

**Consequence for the narrow-guard caller (see D3 census).** Because the returned code is the store class (not `dispatch_aborted`), the **one** consumer that gates its `Disconnected` transition specifically on `== dispatch_aborted` — `Session::send` (`session.cpp:4046`) — does not fire on it. That single site's guard is broadened to also transition on the store-fatal class `{store_io_failure, store_seqnum_out_of_order, store_capacity_exhausted}`, keeping the app-veto codes (`app_do_not_send` / `app_payload_malformed`, `session.cpp:4468-4470`) non-fatal. This is the one genuinely-new-in-059 call-site edit; every other propagating caller already uses a broad `if (!emit_r)` and needs no change.

**Alternative rejected.** Coercing every store failure to `dispatch_aborted` — loses the diagnostic and conflates cancellation with I/O fault; and would change the returned code at *every* propagating site, not just the one narrow-guard consumer.

## D3 — Location: reconcile + `co_return unexpected` INSIDE `store_then_emit`; the transition is CALLER-owned (transport-failure parity)

**Decision.** Inside `store_then_emit`, on the persistent-fatal branch, do the best-effort reconcile (D4) then `co_return std::unexpected(store_r.error())` — **do NOT** call `record_state_transition_` inside the callee. This is the **exact same disposition** as the existing transport-write failure return (`co_return dispatch_aborted`, `session.cpp:4820-4832`), which likewise does not transition internally. Whatever machinery transitions each caller to `Disconnected` on today's transport-failure return is the *same* machinery that handles the store-failure return. Only the reconcile is callee-owned; the transition is caller-owned.

**Why the original "callee owns `Disconnected`" design was wrong.** Placing `record_state_transition_(Disconnected)` inside `store_then_emit` is NOT caller-independent, and it is unsafe: `record_state_transition_` (`session.cpp:209-250`) fires the application `onLogout` callback **synchronously** on any `Active→!Active` edge (`:234-249`). Firing it deep inside a caller that is mid-inbound-handler (e.g. `:2656`/`:3176`) is a re-entrancy hazard, and several discard-callers then continue past the swallow into a live/other state. The `persist_*_advance_` analogy is **false**: those callers immediately `co_return` on `!r`; the `store_then_emit` discard-callers do not. Mirroring the transport-failure return (no internal transition) dissolves both problems — the store-failure return is byte-identical in shape to a return each caller already handles today.

**Real census (FR-006 / SC-006) — 26 `store_then_emit` call sites, `9305e69`.** This is a **parity check** against the existing transport-failure return, not a new design. Classified by how each site consumes the return:

- **Propagating, broad guard `if (!emit_r) → Disconnected` (9 sites):** `:864` (initiator Logon), `:1781`, `:1825`, `:2496`, `:2820`, `:3379`, `:3542`, `:4615`, `:4673`. These transition on **any** error, including the store class — fail-closed already holds, **no change**.
- **Propagating, narrow guard `== dispatch_aborted` (1 site — the residual):** `Session::send` (`:4046`) consuming `send_impl` (`:4488`), the **primary US1 app-send path**. It transitions only on `dispatch_aborted`, so the store class (D2) misses it and the session would stay `Active`. On a *transport* failure the same site returns `dispatch_aborted` and DOES transition — so this is genuinely new-in-059 for the store class. Resolved by the minimal guard broadening in D2 (add the store-fatal class, keep app-veto non-fatal). No new machinery.
- **Swallow-and-continue (16 sites):** `:2130`, `:2344`, `:2656`, `:2680`, `:2742`, `:2869`, `:2921`, `:2959`, `:2982`, `:3176`, `:3233`, `:3687`, `:4902`, `:4963`, `:5221`, `:5264`. Each `(void)`s the return and continues. Because the store-failure return is the **same shape** as the transport-failure `dispatch_aborted` these sites **already** swallow today, their post-swallow continuation is **unchanged by 059** — a *pre-existing* transport-failure disposition, not something 059 introduces. Examples read from source: `:4963` (`run_logout_phase1`) sets `logout_seen_=true` and transitions to `LogoutSent` (`:4972-4975`) — it does so today on a transport-failed Logout emit; `:2656`/`:2680` swallow, emit a further Logout, then `record_state_transition_(Disconnected)` at `:2685`; `:3176` runs a `fromAdmin` dispatch before its own disconnect. In every case the un-retained frame is **not** transmitted (the fatal branch returns before Step 2) — the data-integrity invariant (INV-059-2) holds regardless of the continuation. Moreover the continuations are data-*safe* under the corrected design: the reconcile (D4) has already set `next_outbound` back to `k`, so a follow-on emit (e.g. the Logout at `:2680`) correctly reuses `k` — no gap, no wire-reuse — which resolves the Opus review's "post-fail-closed emission at k" concern. These are documented as best-effort per FR-006 (**in-scope to document, out-of-scope to fix** — fixing them is fixing the pre-existing transport-failure disposition, a separate concern).

**Consequence for FR-006 / FR-001.** "Fail closed" on the primary US1 send path (`Session::send`) means transition to `Disconnected` (via the broadened guard) + no-transmit + surfaced error. It does **not** literally mean every one of the 16 swallow sites transitions — those are documented best-effort where continuing is safe because the frame never reached the wire and the reconcile (D4) prevents any freeze. The `/tasks` census records each swallow site's actual post-swallow continuation as its explicit disposition.

## D4 — Reconcile-from-durable (FR-007 / US3): targeted outbound-only reseed via `set_next_outbound(durable_k)` — NOT clearing `hydrated_`

**Decision.** In the fatal branch, after capturing `store_r.error()` (D2) and before the `co_return`, **best-effort** reconcile the in-memory outbound wire counter to the durable store counter:
1. `auto dk = co_await store_->next_seqnum(direction_t::outbound, /*increment=*/false)` — read the durable outbound counter (unchanged on a `store_io_failure`; the true value on an out-of-order/capacity failure).
2. if `dk` has a value: `co_await seqnum_mgr_.set_next_outbound(*dk)` — the **existing** outbound-only setter (`seqnum_manager.hpp:140`, minted for the 032 initiator `peer_ack_sent_reset_flag` restore). If the read fails (e.g. cancellation), skip the reconcile — the disconnect still happens (degrades to the safe disconnect-loop).

Do **NOT** clear `hydrated_`.

**Rationale.** After fail-closed the manager sits at `k+1` (assign_outbound already ran) while durable is `k`. A direct outbound-only reseed to the durable value fixes exactly the desync, is fully self-contained in `store_then_emit`, and touches **only** the outbound counter — never inbound, never the Logon-seed path. Rewinding to `k` is safe precisely because seq `k` was never transmitted (D1), and `set_next_outbound` is already a sanctioned restore operation.

**US3 clean-recovery is scoped by reset policy — it is NOT policy-agnostic (RC#2 correction).** `reset_to_one()` is reached **only** via `reset_seqnums_to_one_durable`, gated on `if (cfg_.reset_on_logon)` (`session.cpp:776-782`); it is **NOT** run under `bilateral_strict` (which only forces `141=Y`, `:816-818`). Three cases:
- **Plain (non-reset) persistent session** — the reconcile makes the reconnect resume at `k` **cleanly** (FR-007). This is the scope of US3 clean-recovery.
- **`reset_on_logon`** — the durable reset overrides the outbound counter to 1 before the reconnect Logon; the reconcile is neutral (resume at 1).
- **`bilateral_strict` (the production DEFAULT, `session_config.hpp:231`)** — there is **no** reset. After fail-closing at `k>1` and reconciling `next_outbound = durable_k`, the reconnect Logon carries `34=k` (k>1) **with** `141=Y` — the **pre-existing, DEFERRED L-029-3** malformed-Logon limitation (`spec/behaviors-and-limitations.md:1252-1265`). 059's reconcile is **neutral vs no-reconcile**: without it the manager sits at `k+1` (also non-1, also L-029-3). 059 **neither introduces nor fixes L-029-3**, but it DOES create a new reconnect path that can *reach* L-029-3 (pre-fix the store failure never disconnected, so this reconnect never happened). Under `bilateral_strict`, US3 recovery is therefore **bounded by pre-existing L-029-3**, not clean — a separate tracked item, out of 059 scope. (A new B-/L- note may be warranted; flagged for `/tasks`, not designed here.)

**Why NOT clear `hydrated_` (the rejected first design; advisor-flagged blast radius).** Clearing the one-shot latch forces `ensure_hydrated_` to re-run on the next reconnect **regardless of `force`** — which (a) **bypasses the `bilateral_strict` suppression** `refresh_active = refresh_on_logon && !bilateral_strict` whose absence re-introduces INV-RoL-3 (a non-1 outbound seed into a `bilateral_strict` reset-Logon → malformed Logon), and (b) **re-applies the inbound seed** (gated by `apply_inbound_seed`), pulling unrelated inbound sequencing into a store-failure recovery. The targeted reseed avoids both by construction.

**Alternatives rejected.**
- **Clear `hydrated_` (+ a `bilateral_strict` guard).** *Rejected:* couples the fix to the reconnect re-hydration machinery's per-policy guards and the inbound-seed logic; larger cross-feature blast radius than a one-counter reseed.
- **Compute `k = stamped_seq` instead of reading durable.** *Rejected:* only valid for the `store_io_failure` sub-case; reading the durable counter is uniform across all failure classes (FR-004).

**Verification note (US3 — three honest policy variants).** The reconcile happens at disconnect time, so `peek_outbound() == durable_k` is assertable immediately, before reconnect. W3 MUST cover: (A) **plain persistent** → clean resume at `k`; (B) **`reset_on_logon`** → durable reset overrides to 1 (reconcile neutral); (C) **`bilateral_strict` (default)** → assert 059 does **not worsen** L-029-3 (the reconciled `durable_k` and the un-reconciled `k+1` are both non-1) and that the resulting malformed Logon is the pre-existing L-029-3, **not** a 059 regression — do NOT assert clean recovery. Each variant also asserts **inbound sequencing is unaffected** (the trap the original finding is about — no test combined the conditions). The reconcile itself is done in `store_then_emit` (role-independent), but reconnect **reset** reaches through different sites per role: initiator via the `reset_on_logon` path (`:776`), acceptor via received-`141=Y` / inbound-Logon (`session.cpp:2141`, `:2414`). W3 either adds an acceptor-side witness or records a sourced exclusion for the acceptor path (handed to `/tasks`).

## D7 — `store_cancelled` is cancellation-class: excluded from fail-closed (FR-005 parity)

**Decision.** In the failure branch, `store_cancelled` is handled **before** the persistence gate and keeps today's behaviour (absorb → proceed); it never trips fail-closed or the reconcile. Only the genuine retain-failure classes (`store_io_failure`, `store_seqnum_out_of_order`, `store_capacity_exhausted`) fail closed on a persistent store.

**Rationale.** `store_cancelled` is returned **only** when the store's `async_lock()` is cancelled/drained — the shutdown path (`memory_store.hpp:145`, `file_store.cpp:1028`; FileStore explicitly "does NOT surface `store_cancelled` under graceful close", `file_store.hpp:171`). It is the *returned* twin of the *thrown* `operation_aborted` that D5/FR-005 deliberately excludes. Failing closed + reconciling on a normal drain would be wrong (spurious disconnect/counter-rewind during shutdown). Excluding it cannot mask a genuine retain failure because it is unreachable off the cancellation path (source-verified: two `store()`-path return sites, both `!async_lock()`).

## D5 — Preserve the `operation_aborted` cancellation path verbatim (FR-005)

**Decision.** Leave the existing `try { ... } catch (const asio::system_error& e) { if (operation_aborted) co_return dispatch_aborted; ... }` exactly as-is. The new logic is a check on the **returned** `store_r` (a non-throwing value), placed where `(void)store_r;` is today — inside the `try`, before Step 2. A `co_return` from inside the `try` is well-formed.

**Rationale.** Cancellation (shutdown) is not a durable retain failure and must keep its current `dispatch_aborted` disposition; conflating them would spuriously trip the fatal path during normal close. `feedback_reset_cancellation_state_wipes_pre_entry_cancel` and the F5 drift history (`feedback_async_mutex_us3_asio_cancel_and_subagent_seams`) both warn against disturbing this window.

## D6 — Test infrastructure

**Decision.** Two mechanisms, each matched to the leg it proves:

1. **FileStore `store()`-pwrite fault-injection seam (new).** A `FIXPP_TEST_HOOKS`-gated hook (an `std::atomic<bool>` "fail next store pwrite" arm, mirroring `g_force_abort_after_reset_lambda` / `g_post_rename_reopen_fail_hook`) forces one `raw_pwrite_all` in `store()` to return `false` → `io_ok=false` → `store_io_failure`. This is the **only** way to drive the real durable path incl. the on-disk counter and the restart-recovers-below-peer-last-seen leg (SC-001 blast #2, SC-002 restart). Compiled unconditionally with the declaration gated in `file_store.hpp` (the established pattern: a gated *increment/call* would be unreachable from library-linked tests — `feedback_ci_gate_observes_not_asserts...` cousin).
2. **Bounded MemoryStore at capacity (no new infra).** `store_capacity_exhausted` is naturally reachable by filling a bounded MemoryStore — this drives the **volatile-unchanged** arm (US2 / FR-003 / SC-003) without any mock.

**Rationale.** The FileStore seam is load-bearing for the P1 flagship blast (durable counter + restart). The volatile arm needs no mock. This keeps the infra minimal and avoids a general-purpose mock store whose fidelity would itself need review.

**Alternatives considered.**
- **A general GoogleMock `MessageStore`.** *Deferred/rejected as primary:* useful to isolate `store_then_emit`'s branch from disk, but it cannot exercise the durable on-disk counter / restart leg, which is the whole P1 amplification. If a pure-unit isolation of the disposition branch is wanted, a minimal fake persistent store (yields_persistent_store()==true, arm-to-fail) may be added at `/tasks` — decided there, not a plan blocker.
- **`errno`/`ENOSPC` real-disk injection (e.g. tmpfs size cap).** *Rejected:* flaky, platform-specific, slow; the in-code seam is deterministic and matches the repo's established fault-injection idiom.

**RED-first mandate.** Per `feedback_fail_placeholder_red_test` + `feedback_sanitizer_canary_must_be_proven_red`, the SC-001 cascade witness is run against **current `main`** (pre-fix) and must FAIL (post-`k` loss + stuck durable counter + restart-below), captured as evidence, before the fix makes it GREEN.
