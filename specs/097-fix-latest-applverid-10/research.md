# Research: 097 — FIX Latest is ApplVerID 10

All source references are to fixpp `origin/main` `23895374` (this branch's base). Re-derive any of them
with the recipe given; do not trust a line number after the first implementation commit.

## R-1 — The wire value and the enumerator

- **Decision**: `application_version::vlatest = 9` (the next value after `v50sp2 = 8`), wire value `"10"`.
- **Rationale**: FIX Session Layer with Errata (Nov 2020) §11.2 lists `FIXLatest = 10`; the vendored
  `dictionaries/orchestra/OrchestraFIXLatest.xml` defines code `FIXLatest`, `value="10"`. Appending keeps
  every existing enumerator's value, so `version_profile` (4 bytes, `static_assert` in
  `version_profile.hpp` and `tests/dictionary/version_profile_test.cpp`) and any stored value are
  unchanged. The C++ index and the wire value differ, as they already do for every member (the
  `resolve_application_version` comment's I-13 note).
- **Alternatives rejected**: a composite `(v50sp2, ApplExtID 303)` key (no QuickFIX engine reads
  1407/1156 — parent `research/findings/v1-row4b-applverid-10-sweep-2026-10-29.md` Q3); renaming or
  renumbering existing members (a break for nothing).
- **Recipe**: `grep -n "enum class application_version" -A14 include/fixpp/dict/version_profile.hpp`.

## R-2 — Parse is length-dispatched today

- **Decision**: `resolve_application_version` gains a two-character arm accepting exactly `"10"`.
- **Rationale**: today it switches on one character (`'2'`..`'9'`) and refuses everything else with
  `dict_unknown_appl_ver_id` (`src/dictionary/version_profile.cpp`). `"10 "`, `"010"`, `"1O"`, `"11"`
  must keep that error (spec Edge Cases). `tests/dictionary/version_profile_test.cpp` and
  `tests/dictionary/reify_dispatch_test.cpp` each assert `"10"` is refused today: both are rewritten
  (they are the RED for FR-001).
- **Recipe**: `grep -rn '"10"' tests/dictionary/version_profile_test.cpp tests/dictionary/reify_dispatch_test.cpp`.

## R-3 — The registry

- **Decision**: one slot per application version (`kTableSize` 9 → 10); `session_to_application(vlatest)`
  → `vlatest`; the FR-010 collision check and its `std::abort` are deleted, not left as dead code.
- **Rationale**: with distinct slots no two distinct session versions map to one slot, so the check can
  never fire; an unreachable abort is a claim the code would no longer back. Two dictionaries with the
  same session version keep last-writer-wins (unchanged, not FR-010's case).
- **One-way fallback (spec FR-006, owner Q1 second ruling)** is the one rule added to `get`: an empty
  v50sp2 slot answers from the vlatest slot; nothing else falls back. It keeps the shipped answer pinned by
  `OrchestraFR010Guard.SingleDictConfigsSucceed`'s FIX-Latest-alone arm, so that arm stays unchanged and
  becomes FR-006's characterization pin. `OrchestraVersionIdentity.DistinctVLatestMapsToV50SP2`
  (`tests/dictionary/orchestra_loader_test.cpp`) asserts the mapping and is rewritten to `vlatest`.
- **Why not strict** (owner's first ruling, withdrawn): only direct C++ can register two dictionaries —
  TOML loads exactly one (`src/config/selector_resolver.cpp`, one `push_back` into
  `engine.dictionaries`) and the C API fills none (`src/capi/config.cpp` sets `SessionConfig::dictionary`
  only). Strict would have moved every TOML FIX Latest FIXT session from `"9"` to `"10"`, a wire change
  peers react to (spec Clarifications Q1). The remaining config-surface gap is `L-097-1`.
- **Layout**: `version_registry` grows by one `shared_ptr` slot, and `Engine`, which holds it by value,
  grows with it (B-097-2). No size pin exists for either: `git grep -n -E
  'sizeof\((fixpp::)?(dict::)?version_registry|sizeof\((fixpp::)?(session::)?Engine\b' -- include src
  tests tools bindings` is empty. Re-run it at the implementation head; the full build of T070 is the
  backstop for a pin the pattern misses.
- **Recipe**: `grep -n "kTableSize\|FR-010\|case session_version::vlatest" include/fixpp/dict/version_registry.hpp src/dictionary/version_registry.cpp`.

## R-4 — The generated tiers: two different mappings, both corrected

- **Finding**: two codegen tables map vlatest to v50sp2, and they are not the same table.
  - `tools/codegen/fixpp-codegen/ir.cpp`'s `kCodegenVersions` `.a` sets `VersionIR::application`, which
    **nothing reads** (`grep -rn "\.application\b" tools/codegen src` finds only the assignment). It changes
    no generated byte.
  - `tools/codegen/fixpp-codegen/gen_util.hpp`'s `app_version_enum("vlatest") → "v50sp2"` writes every
    `fixpp::vlatest` typed class's static `version_v` (`emit_messages.cpp`, `emit_reify.cpp`). Its comment
    says it exists because `application_version::vlatest` does not exist.
- **Decision**: correct both. `.a = vlatest`; `app_version_enum("vlatest")` returns `"vlatest"` (the
  guard, its `ns == "vlatest"` → `"v50sp2"` branch, is deleted, since the enumerator now exists). Its
  other mappings are unchanged: `vt11` → `Unknown`, and every other namespace verbatim. The vlatest
  typed classes then report FIX Latest, agreeing with the dispatch arm's handle (R-5).
- **The `ir.cpp` change has no witness.** Nothing reads `VersionIR::application`, so no test can turn
  RED for `.a`. It is a data-and-comment correction, checked by review of T045's diff, not by a
  witness.
- **Consequence**: the checked-in golden `specs/076-fix-latest-typed-codegen/contracts/golden/vlatest_Messages.golden.hpp`
  changes on exactly the `application_version::v50sp2;` lines that belong to vlatest classes, and
  `tests/codegen/vlatest_compile_smoke_test.cpp`'s `which() == v50sp2` assertion flips. The golden is a
  test oracle, regenerated in place (precedent: 077 regenerated v44's builder golden); the diff must be
  exactly those lines, `v50sp2` → `vlatest`, and nothing else (quickstart §3).
- **Alternative rejected**: leaving `app_version_enum` alone. A `fixpp::vlatest::owning_X::which()` that
  reads FIX50SP2 while `reify()` hands back a handle reading FIX Latest is the same false premise one
  layer down, and FR-012(c) names it.
- **Recipe**: `grep -c "application_version::v50sp2;" specs/076-fix-latest-typed-codegen/contracts/golden/vlatest_Messages.golden.hpp`.

## R-5 — The dispatch arm

- **Decision**: `emit_dispatch.cpp`'s `kAppVersions` gains `{ns = "vlatest", av = vlatest}`.
- **Rationale (measured)**: the generated `_dispatch/reify_dispatch_application.hpp` includes only
  `core/error.hpp`, `dict/reify.hpp`, `dict/version_profile.hpp`, `wire/message_view_contract.hpp`; every
  arm returns `detail::owning_message_handle_from_frame(rmv_app, view, mr)`, a hand-written,
  version-independent factory (`src/dictionary/reify.cpp`). No `fixpp::vlatest` header and no new link is
  needed. The arm's case label and `rmv_app.application` are both written from `av.ns`, so the enumerator
  must be spelled `vlatest`. One codegen invocation sees every version's IR (`main.cpp` builds `all`, then
  emits dispatch once).
- **Under `FIXPP_CODEGEN_FIX_LATEST=OFF` (Gate A round 1, O097-003)**: the vlatest IR is absent. The
  emitter MUST then **skip the outer `case` for a `kAppVersions` row whose IR is absent**, so `vlatest`
  falls to the outer `default`, which already returns `dict_reify_unknown_msg_type`. This matches spec
  Clarifications Q2 ("there is no arm"). An earlier draft of this section said the arm was "still
  emitted with no MsgType switch". That shape is expected not to build: the Gate A round-1 review
  derived this from source plus a scratch TU, not from a real OFF build, and mutant M-9c is what
  observes it in the real build. With `ir == nullptr` the emitter today
  writes the `const resolved_message_version rmv_app{…}` local, the empty-MsgType early return and the
  trailing fail-loud return, but neither switch, so `rmv_app` is never read. clang and gcc warn
  `-Wunused-variable` on it, and the base preset sets `FIXPP_WERROR=ON`. The generated header is a
  plain (non-SYSTEM) include of `fixpp_dict_dispatch_bridge`, which gets `-Wall -Wextra -Werror` like
  every target under `src/`. Re-derive: `grep -n "rmv_app\|ir != nullptr\|has_one_char" tools/codegen/fixpp-codegen/emit_dispatch.cpp`.
  The outer switch keeps its `default:`, so omitting an enumerator's `case` raises no `-Wswitch`.
  Witness: contracts W-9(c) (spec US3 scenario 4).
- **Anchor**: `tests/codegen/vlatest_dispatch_exclusion_test.cpp` is rewritten; what it asserts after
  097, and how each half is shown RED, is contracts W-9 (not restated here).
- **Recipe**: `grep -n "#include\|owning_message_handle_from_frame" build/linux-clang-debug/_codegen/include/fixpp/_dispatch/reify_dispatch_application.hpp | head`.

## R-6 — Session paths need no code change

- **Finding (corrected at Gate A round 1, G097-011)**: the three session paths are different, and
  `grep -n "app_version_registry_->get\|resolve_application_version" src/session/session.cpp` names
  them:
  - **`open()`** looks up the session's already-typed configured default (`registry.get` only, no
    parse);
  - **the acceptor's inbound-Logon check** parses the peer's 1137 with `resolve_application_version`,
    then calls `registry.get` (serviceability);
  - **the initiator's Logon-ack handling** parses the peer's 1137 and records it as the negotiated
    version, with no registry lookup.

  R-2 changes the acceptor's and the initiator's parse. R-3 changes the answer at `open()` and at the
  acceptor. The one-way fallback therefore reaches `open()` and acceptor admission, never initiator
  recording. None of the call sites is edited.
- **Outbound Logon**: `admin_messages.cpp` renders `default_appl_ver_id` through `render_appl_ver_id` (the
  only exhaustive `switch` over `application_version` in the tree — `-Wswitch` forces its new case).
- **Inbound 1407 / 1156 (corrected at Gate A round 1, G097-003 / RC-1; wording corrected at T003a
  round 1, OA097-004)**: no session code uses either tag to resolve a version or select a dictionary
  (`grep -rn "1407" src include` is empty; `grep -rn "1156" src include` finds only the send-header
  tag list in `src/session/session.cpp`, the FIXT framing table, and comments). An
  earlier draft said that because `dictionaries/FIXT11.xml` defines both, "a dictionary-driven check
  does not reject them". As a general statement that is false. Inbound validation uses the session's
  own `SessionConfig::dictionary`: the validator is built from `cfg_.dictionary->as_table_view()`, and
  the validate-first gate (`grep -n "validate_inbound_messages && validator_" src/session/session.cpp`)
  runs before `interpret_logon` and before the 1137 check. `include/fixpp/wire/validator.hpp` rejects a
  tag that is neither valid for the MsgType nor a FIXT framing tag (`wire_unexpected_tag`). The framing
  table (`src/dictionary/fixt_framing_table.hpp`) is installed only for v50/v50sp1/v50sp2 dictionaries.
  It whitelists header 1156 but no Logon body tag.

  So FIXT11.xml is consulted only when the integrator chose it as the session dictionary. The outcome,
  by session dictionary:

  | Session dictionary (validation on) | Logon with 1407 | Header 1156 |
  |---|---|---|
  | `FIXT11.xml` | accepted (declared in Logon) | accepted (declared in header) |
  | Orchestra FIX Latest | accepted (Logon fieldRef 1407) | accepted (StandardHeader expanded into every message) |
  | `FIX50SP2.xml` | n/a: it defines no Logon, so every validated Logon is rejected today | accepted (081 framing surface) |
  | FIX4.x-shaped with 1137 injected (`fix44_dictionary_with_1137()` in `tests/support/validation_test_dictionary.hpp`, moved there from `tests/session/engine_reset_unit_stop_test.cpp` at T068 F3) | rejected (`wire_unexpected_tag`) | rejected |

  Owner ruling (spec Clarifications, Gate A round 1): **no new rule**. The table is today's behaviour
  and stays so. B-097-3 discloses it. QuickFIX/Go with its shipped FIXT11.xml behaves like the last row
  for 1407 (findings file Q4). W-7 pins the FIXT11.xml, Orchestra and FIX4.x-shaped rows, each with a
  control arm. For the FIX50SP2 framing row it cites 081's existing validator-level witness.
- **Emission**: fixpp originates no 1407 (`grep -rn "1407" src include` is empty), no 1156 and no header
  1128. But `is_send_header_tag` in `src/session/session.cpp` lists 1128 and 1156, and
  `build_send_frame_` moves an application payload's own 1128 or 1156 into the header and sends it. So
  the claim is about session-originated frames only, and that is what SC-005's oracle counts on captured
  frames (contracts W-8).

## R-8 — Constitution: MINOR, v4.2 → v4.3

- **Decision**: amend Article I §1 (FIX Latest bullet; post-1.0 milestone line) and annotate Article
  XVIII §2's v1.2 bullet; record in a Sync Impact Report; Article XX §4 MINOR (a factual correction,
  with Article I's post-1.0 residue restated to match Article XVIII §2; not a banned pattern or a
  perf-budget tightening); no `CHANGELOG.md` entry. Text: data-model §E.
- **Rationale**: Article I §1 currently states "wire application version `v50sp2` via
  `session_to_application`; no distinct ApplVerID" and keeps "ApplExtID(1156)=303 differentiation and
  session negotiation" post-1.0. After 097 the first is false and the second is answered. FIX Latest is
  identified by ApplVerID 10 and negotiated by DefaultApplVerID(1137) like any version, when that value
  is `10` (the value the session reads from its peer; data-model §A). A FIX Latest dictionary session
  configured `"9"`, with a peer that sends `9` too, negotiates FIX50SP2 (the fallback). The
  residue is the canonical sentence (data-model §E.0):

  For FIX Latest, only the EP-level field back-port into the legacy dictionaries and Extension Pack negotiation (DefaultApplExtID(1407) / ApplExtID(1156), which fixpp does not use to resolve a version or select a dictionary) remain post-1.0, both in the Article XVIII §2 v1.2 milestone.
- **Why one sentence (Gate A round 2, RC-A)**: round 1 rewrote each residue locus from the clause it
  replaced, so Article I dropped the field back-port and Article XVIII §2 dropped Extension Pack
  negotiation. One sentence, pasted verbatim and counted at each locus (quickstart §4.2), cannot drift
  that way. It follows the current Article XVIII §2 v1.2 bullet, which already holds the field
  back-port and the only roadmap text about 1156.
- **§XVIII.1/§XVIII.5 (Gate A round 1, G097-006)**: read and unchanged; the argument goes into the
  Sync Impact Report (data-model §E.4). FIX Latest negotiation by DefaultApplVerID is S-025's v1.0
  mechanism (the FIXT.1.1 session layer, inside §XVIII.1's scope) with one more value. It is not a
  post-1.0 protocol shipped early (§XVIII.5). The post-1.0 list narrows by amendment (§XVIII.4,
  Article XX), which this is.

## R-11 — The parse under a fuzzer (`[const §VII.7]`; analyze D1)

- **Finding**: T018's two-character arm makes `resolve_application_version`
  (`src/dictionary/version_profile.cpp`) parser-touching code in `[const §VII.7]`'s sense: it parses the
  peer's DefaultApplVerID(1137) on the acceptor and initiator paths, and a header ApplVerID(1128) in
  `dict::reify`. No harness reaches the function: `grep -ln "resolve_application_version\|1137"
  tests/fuzz/*.cpp` is empty (the same grep without the `*.cpp` filter does hit corpus files, so the
  pattern can match). The nearest harness, `tests/fuzz/fuzz_session_recovery_admin_parse.cpp`, sets
  `cfg.begin_string = "FIX.4.2"` (`grep -n begin_string` in it), so the acceptor's FIXT DefaultApplVerID
  block, which parses 1137 and looks it up in the registry, never runs there.
- **Decision**: a new harness, contracts W-12. 033's precedent (its plan's `VII.7` row and its task T036)
  extended an existing harness's corpus; 033 held that the harness reached its new scanner arms (see the
  lead below). Here no harness reaches the function, so a corpus extension would cover nothing.
- **Where the ten minutes run**: CI's `linux-clang-asan` lane builds the fuzz targets and replays every
  corpus as a ctest (`fixpp_add_fuzz_replay` in `cmake/Helpers.cmake`, `-runs=0`). No workflow runs a
  timed campaign (`git grep -n -e '-max_total_time' -- .github` is empty). The ten-minute run
  `[const §VII.7]` asks for is therefore `/speckit-verify` Step 7 with `--fuzz-duration=600`. That gap
  predates 097; it is reported to the owner, not fixed here.
- **Pre-existing lead, not fixed by 097**: 033's T036 and its verify record
  (`.specify/decisions/033-fixt-fix50sp2-session-verify.md`) say that `fuzz_session_recovery_admin_parse`
  drives the `case 1137:/553:/554:` arms 033 added to the inbound Logon scanner. That claim was not
  checked against the harness's configuration. With `begin_string = "FIX.4.2"`, the FIXT
  DefaultApplVerID block does not run, so at most the scanner's tag walk is reached. Recorded as a lead
  for the owner; 097 does not change that harness.
