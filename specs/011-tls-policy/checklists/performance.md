# Performance Requirements Quality Checklist: 011 — TLS Policy Core

**Purpose**: Validate the quality (completeness, clarity, consistency, measurability) of the **latency / allocation / throughput** requirements written in `spec.md`. This checklist tests whether the perf requirements are quantified, platform-conditioned, hot-vs-cold-path-distinguished, and bench-gateable — NOT whether the benches actually pass (that's `/speckit-verify` T053).
**Created**: 2026-05-24
**Feature**: [spec.md](../spec.md)
**Scope**: `Pinset::find` / `Pinset::snapshot` p99 ceilings; `verify_peer` envelope vs DoS-reject latency; zero-alloc hot-path; cold-path PMR permission; platform-conditional ceiling rules; regression bounds.

## Requirement Completeness

- [x] CHK001 Is the `Pinset::find` p99 ceiling stated for BOTH the lock-free floor (`libstdc++ ≥ 16` / `libc++`) AND the internal-mutex fallback (`libstdc++ ≤ 15`) — not just one? [Completeness, Spec §SC-007] — PASS: SC-007 states "≤ 130 ns p99 on the lock-free libstdc++ ≥ 16 / libc++ floor; ≤ 200 ns p99 on the libstdc++ ≤ 15 internal-mutex fallback per [2g §6.3]". Both platform-conditional ceilings are explicitly named.
- [x] CHK002 Is the `Pinset::snapshot` acquisition latency requirement specified separately from the `find` requirement (different operations, different bounds)? [Gap, Spec §SC-007] — DD-DECIDED §6.3: [2g §6.3] specifies `Pinset::snapshot()` separately at "≤ 30 ns p99 on the lock-free floor; ≤ 100 ns p99 on the libstdc++ ≤ 15 fallback path." SC-007 in the spec names the combined `find` ceiling (snapshot_acquire + linear_scan_16). T021 (bench_pinset_snapshot_acquire.cpp) and T022 (bench_pinset_find.cpp) are separate bench tasks, separating the two operations at implementation level. The design-doc anchor mandates the separate bench; the spec-level SC-007 references the combined find ceiling because that is the end-user-visible latency. The separation at bench level is the design-doc's domain.
- [x] CHK003 Is the `verify_peer` p99 ceiling specified — both the in-envelope happy-path bound AND a separate DoS-reject fast-path bound? [Gap, Spec §FR-019 / §FR-020] — DD-DECIDED §6.3: [2g §6.3] specifies both: `verify_peer(...)` happy-path "≤ 50 µs p99" and DoS-bound entry checks "≤ 1 µs p99". The spec FR-019 establishes the DoS cap semantics but does not repeat the µs ceilings as SC-level items — those are locked in the design-doc Tier 1 table. Tasks T018 (alloc guard) and the bench matrix handle this. A Measurability/Coverage concern, not Completeness — the ceilings exist in the signed-off design-doc anchor.
- [x] CHK004 Is the zero-allocation hot-path scope specified by named operations (not just "the hot path") — i.e., `Pinset::find`, `Pinset::snapshot`, `verify_peer`? [Completeness, Spec §FR-007] — PASS: FR-007 states "Pinset reads on the TLS handshake hot path MUST be lock-free and MUST allocate zero per [const §VIII.5]." FR-023 states "The zero-allocation invariant applies to the hot-path `Pinset::find` only." Key Entities names `Pinset::find` as the hot-path operation. `[2g §6.1]` defines the hot path as: `Pinset::snapshot()` (captured once at handshake start), `Pinset::find(...)`, and `verify_peer(...)` — all three are named. The spec FR-007 names the Pinset read operations; FR-023 names `Pinset::find` explicitly as the hot-path scope boundary. Named operations are present.
- [x] CHK005 Are the cold-path operations where PMR allocation IS permitted (`load_credentials` file I/O + parse + chain build) named explicitly? [Completeness, Spec §FR-023] — PASS: FR-023 states "PMR allocation MUST be permitted on the cold-path `load_credentials` (file I/O + parse + chain build)." The cold-path operation is named by method name (`load_credentials`) and activity description (file I/O + parse + chain build). Explicit.
- [x] CHK006 Is the platform tuple to record at bench time (compiler / stdlib / stdlib-version / cpu-supports-cmpxchg16b) specified — so a result can be compared against the right ceiling? [Gap, Spec §SC-007] — DD-DECIDED §6.3: [2g §6.3] states "The §9 seam #4 records the platform-bench tuple so CI knows which ceiling applies on the runner." Tasks.md T021 bench states "record platform tuple (compiler / stdlib / stdlib-version / cpu-supports-cmpxchg16b) and select ceiling at runtime." The platform tuple is mandated at the design-doc + tasks level; SC-007 in the spec references the ceiling but delegates the platform-tuple recording to the bench tasks per [2g §6.3].

## Requirement Clarity

- [x] CHK007 Is "imperceptible at session-open time" (SC-007 prose) backed by a concrete bound — i.e., is the human-language phrase ALSO quantified as a numeric ceiling? [Clarity, Spec §SC-007] — PASS: SC-007 contains the human-language phrase "imperceptible at session-open time" immediately preceded by the numeric ceiling: "≤ 130 ns p99 on the lock-free libstdc++ ≥ 16 / libc++ floor; ≤ 200 ns p99 on the libstdc++ ≤ 15 internal-mutex fallback per [2g §6.3]". The phrase elaborates the numeric ceiling, not the other way around. Both are in the same SC text. The numeric ceiling governs; the phrase is explanatory.
- [x] CHK008 Is "zero allocation on the hot path" quantified by enforcement gate (e.g., `counting_resource` + mallocnesia LD_PRELOAD dual-gate per `[[feedback_tracking_pmr_resource_false_pass]]`) — i.e., is the verification mechanism named? [Clarity, Spec §FR-007] — PASS: FR-007 states the constraint; `contracts/pinset.hpp` assertion 7 states "find allocates 0 bytes on the hot path; verified via tests/perf/test_tls_handshake_alloc_guard.cpp with counting_resource + mallocnesia LD_PRELOAD dual-gate (FR-007 / [[reference_mallocnesia_path]] / [[feedback_tracking_pmr_resource_false_pass]])." Tasks.md T018 specifies the dual gate explicitly: "(a) `counting_resource` (PMR routing) AND (b) mallocnesia LD_PRELOAD (global-malloc interception)". The verification mechanism is named in the contract oracle and tasks.md.
- [x] CHK009 Is "lock-free" defined by the criterion that determines which ceiling applies (which standard-library version → lock-free vs internal-mutex `std::atomic<std::shared_ptr<T>>`)? [Clarity, Spec §SC-007] — PASS: SC-007 defines "lock-free" by the platform criterion: "lock-free libstdc++ ≥ 16 / libc++ floor" vs "libstdc++ ≤ 15 internal-mutex fallback." [2g §6.3] (cited in SC-007) elaborates: "≤ 30 ns p99 on platforms where the implementation is genuinely lock-free (libstdc++ ≥ 16 with `__atomic_shared_ptr`; libc++ on x86_64 with `cmpxchg16b`); ≤ 100 ns p99 on platforms where the implementation falls back to an internal mutex (libstdc++ ≤ 15 on glibc)." The criterion (stdlib version / implementation) is fully defined.
- [x] CHK010 Is the "DoS bound is the whole point of the cap" framing for the fast-reject path made measurable (e.g., explicit p99 ceiling for the rejection short-circuit)? [Clarity, Spec §FR-019] — DD-DECIDED §6.3: FR-019 establishes the semantic purpose (DoS cap — refuse before parsing) but does not repeat the ≤ 1 µs p99 ceiling. [2g §6.3] defines "verify_peer — DoS-bound entry checks: ≤ 1 µs p99" with rationale "three integer comparisons + one ASN.1 length read; sub-microsecond by construction." The spec FR-019 correctly describes the semantic ("refused *before* parsing"); the design-doc anchor is the latency ceiling authority per the per-doc Tier 1 table precedent.
- [x] CHK011 Is the regression budget (≤ ±5% per `[const §VIII.2]`) stated as a normative bound, not just an inherited assumption? [Clarity, Spec §FR-007] — DD-DECIDED §VIII.2: [const §VIII.2] states the ≤ ±5% regression budget as a constitution-level requirement. [2g §6.3] states "CI flags > 5% regression on the hot-path rows." FR-007 cites "[const §VIII.5]" but not the regression budget explicitly. The regression budget is a constitutional requirement ([const §VIII.2]) that governs ALL performance-sensitive modules; repeating it in FR-007 would be redundant and the precedent in 2d/2e/2f design docs shows it is treated as inherited. The budget is normative at the constitution level.

## Requirement Consistency

- [x] CHK012 Does the `Pinset::find` ceiling cited in SC-007 (≤ 130 ns p99 lock-free / ≤ 200 ns p99 fallback) match the design-doc anchor `[2g §6.3]` cited in SC-007? [Consistency, Spec §SC-007] — PASS: SC-007 states "≤ 130 ns p99 on the lock-free libstdc++ ≥ 16 / libc++ floor; ≤ 200 ns p99 on the libstdc++ ≤ 15 internal-mutex fallback per [2g §6.3]". [2g §6.3] table row for `Pinset::find(sha256)` states "≤ 130 ns p99 at max_pins = 16 on the lock-free floor; ≤ 200 ns p99 on the libstdc++ ≤ 15 fallback path." Values match exactly. Consistent.
- [x] CHK013 Are the hot-path zero-alloc rule (FR-007) and cold-path PMR-permitted rule (FR-023) consistent with each other — i.e., is the boundary unambiguous (no operation falls into both categories)? [Consistency, Spec §FR-007 / §FR-023] — PASS: FR-007 bounds the hot path ("Pinset reads on the TLS handshake hot path"). FR-023 bounds the cold path ("`load_credentials` (file I/O + parse + chain build)"). The boundary is at the handshake hot-path entry: `Pinset::find`, `Pinset::snapshot`, `verify_peer` = hot. `load_credentials` I/O + parse + chain build = cold. No operation falls into both — the Assertions section and [2g §6.1] confirm the boundary. The two FRs partition the space without overlap.
- [x] CHK014 Is the PMR-throw-routed-to-`error::tls_*` requirement (FR-024) consistent with the cold-path-PMR-permitted rule (FR-023) — i.e., does the spec say the cold path MAY throw but MUST route to a named variant? [Consistency, Spec §FR-023 / §FR-024] — PASS: FR-023 permits PMR allocation on the cold path. FR-024 states "PMR-thrown exceptions MUST be routed through `[2a §4.2]` `trap_throw` and surface as `error::tls_*` variants." Edge Cases confirms the specific variant: "PMR allocator throws during cold-path `load_credentials`: routed through `[2a §4.2]` `trap_throw`; surfaces as `error::tls_cert_load_failed`." The two FRs are consistent: allocation is permitted (FR-023) AND throws from that allocation must be routed (FR-024). No contradiction.
- [x] CHK015 Are the `max_pins = 16` (FR-010) and `Pinset::find` p99 ceiling (SC-007) consistent — i.e., is the ceiling stated AT `max_pins = 16`, not at an arbitrary set size? [Consistency, Spec §FR-010 / §SC-007] — PASS: FR-010 states "`Pinset::Config::max_pins` MUST default to 16." SC-007 states the ceiling "at max_pins = 16" (the design-doc [2g §6.3] row for find states "at max_pins = 16"). The ceiling is explicitly conditioned on the max_pins = 16 v1.0 cap, not an arbitrary set size. Consistent.

## Scenario Coverage

- [x] CHK019 Is the high-load case (`Pinset` at `max_pins = 16` with continuous rotation) covered by a stated requirement — i.e., does the spec require the p99 ceiling to hold during concurrent `add`/`remove`? [Coverage, Spec §SC-007 / §FR-009] — PASS: SC-007 states the ceiling "at max_pins = 16" conditioning the ceiling on the cap. FR-009 requires rotation to be mid-session-mutable without affecting in-flight handshakes. T013 (stress test: thread A runs add/remove loop; thread B runs find loop under TSan) witnesses concurrent rotation + find correctness. The design-doc [2g §6.3] row for `add`/`remove` gives a separate soft ceiling (≤ 5 µs p99 at max_pins = 16). The hot-path `find` ceiling is stated to hold under the operational cap; the rotation rate is operationally vanishing (30-90 days) per §1.1.
- [x] CHK020 Are degradation-under-stress requirements specified for the `verify_peer` DoS-reject path (peer presenting an oversized cert / oversized SAN / 1024-bit RSA) — i.e., is the fast-reject path's latency bound stated under adversarial input? [Coverage, Spec §FR-019] — DD-DECIDED §6.3: FR-019 establishes the semantic (refused before parsing for oversized cert; refused via integer check for oversized SAN and RSA upper bound). [2g §6.3] provides the fast-reject ceiling: "verify_peer — DoS-bound entry checks: ≤ 1 µs p99; three integer comparisons + one ASN.1 length read; sub-microsecond by construction." The fast-reject bound is mandated at the design-doc level; spec FR-019 covers the mechanism. T018 witnesses zero-alloc under adversarial input paths.
- [x] CHK021 Is the "no perf claim for the cold path" stance made explicit (or implicit by absence) — i.e., is it clear that `load_credentials` carries no SC-level latency ceiling? [Coverage, Spec §FR-023] — PASS: FR-023 states "PMR allocation MUST be permitted on the cold-path `load_credentials` (file I/O + parse + chain build). The zero-allocation invariant applies to the hot-path `Pinset::find` only." There is no SC for `load_credentials` latency in the spec. [2g §6.3] states "cert_source::load_credentials — cold path: ≤ 50 ms (soft) per call" with "allowed disk I/O" and "no [const §VIII.5] applicability" — the soft ceiling is advisory, not a gate-level requirement. The explicit absence of a hard SC for `load_credentials` makes the "no perf claim" stance clear.
