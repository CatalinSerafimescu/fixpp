# Concurrency & Cancellation Requirements Quality Checklist: 011 — TLS Policy Core

**Purpose**: Validate the quality (completeness, clarity, consistency, coverage) of the **concurrency, cancellation, and lifetime** requirements in `spec.md`. This checklist tests whether the cross-thread / cross-coroutine contracts are specified at the right level — atomic transitions, mid-rotation snapshot semantics, ASIO cancellation paths, off-strand binding — NOT whether the implementation actually races (that's TSan + the bench matrix in `/speckit-verify` T053).
**Created**: 2026-05-24
**Feature**: [spec.md](../spec.md)
**Scope**: ASIO cancellation contract; pre-I/O reap; snapshot-vs-rotation atomicity; `pin_view` lifetime; `shared_mutex` writer / lock-free reader rationale; `async_signer_ref` off-strand binding; per-counterparty `Pinset` sharing semantics; mid-session-mutable carve-out.

## Requirement Clarity

- [x] CHK008 Is "atomic" in "both sessions transition atomically" (US1 Independent Test) defined unambiguously — i.e., is the granule of atomicity specified (per-handshake-`find` call, not per-`add`/`remove` operation)? [Clarity, Spec §US1 / §FR-009] — PASS: US1 AC2 defines "atomic" as per-handshake `find()` call: "the validation result matches whichever pinset was current when the handshake's `find()` ran (no torn read)." FR-009 clarifies: "A rotation landing during an in-flight handshake MUST NOT affect that handshake; the new pinset is picked up at the *next* handshake." The granule is the handshake's `find()` snapshot capture, not the `add()`/`remove()` operation. Edge Cases confirms "no torn read" as a separate concept from `add`/`remove` atomicity. Clear.
- [x] CHK009 Is the `std::shared_mutex` writer + `atomic<shared_ptr<const pin_snapshot>>` reader rationale traceable to a cited consolidated inheritance pin (`[2g §6.5.2]`) — and is the rationale stated as "cite-and-stop" (not re-derived in this spec)? [Clarity, Spec §FR-007 / §FR-009] — PASS: FR-007 states "Pinset reads on the TLS handshake hot path MUST be lock-free" citing "[const §VIII.5]". Data-model E-5 states: "Mutex choice: `std::shared_mutex` writer + lock-free reader (atomic `shared_ptr<const pin_snapshot>` load/store). Consolidated rationale lives ONLY at `[2g §6.5.2]` (NEW-P2-6 close — the bundle MUST NOT re-derive the rationale at multiple sites; cite `[2g §6.5.2]` and stop)." The spec's data-model correctly cites-and-stops at `[2g §6.5.2]` without re-deriving. `contracts/pinset.hpp` repeats the citation pattern.
- [x] CHK010 Is "no torn read" defined precisely — i.e., does the spec specify whether a `find()` mid-rotation observes the pre-rotation OR post-rotation snapshot (never a hybrid)? [Clarity, Spec §US1 AC2, §FR-009, §Edge Cases] — PASS: US1 AC2: "the validation result matches whichever pinset was current when the handshake's `find()` ran (no torn read)." Edge Cases: "There is no atomic-swap shortcut and no torn read." FR-020a step 9 cites `[2g §6.5.1]` BINDING CONTRACT: "scan `cfg.pinset_snapshot` for `peer_chain[0].sha256()` per `[2g §6.5.1]` — NEVER call `cfg.pinset->find/contains/snapshot` mid-verification." The "no torn read" means: find() loads the snapshot atomically (one acquire-load); the loaded snapshot is either pre-rotation or post-rotation, never a mix. Precise.
- [x] CHK011 Is "off the session strand" (SC-008) defined with the verification mechanism — thread-id sampling INSIDE the dispatched coroutine per `[[feedback_asio_post_resume_bounces_to_spawn_executor]]` (NOT after `co_await asio::post(other_exec, use_awaitable)`)? [Clarity, Spec §SC-008] — PASS: SC-008 states "in a trace or test harness." T027 (tasks.md) provides the precise mechanism: "sample `std::this_thread::get_id()` INSIDE the dispatched coroutine (per `[[feedback_asio_post_resume_bounces_to_spawn_executor]]` — `co_await asio::post` does NOT pin the resume to the other executor; use nested `asio::co_spawn(other_exec, fn, use_awaitable)` and put the sampling inside `fn`)." The ASIO footgun is acknowledged and the correct verification pattern (nested co_spawn + sampling INSIDE fn) is specified at task level.
- [x] CHK012 Is the writer-holds-mutex-only-during-publication invariant explicit at FR-level — i.e., does the requirement state that readers NEVER block on the writer? [Clarity, Spec §FR-007 / §FR-009] — DD-DECIDED §6.5.2: FR-007 states "Pinset reads on the TLS handshake hot path MUST be lock-free." "Lock-free" by definition means readers never block on a mutex. [2g §6.5.2] consolidated rationale states: "The READER path is lock-free. Pinset::find / Pinset::snapshot do an acquire-load on `std::atomic<std::shared_ptr<const pin_snapshot>>` and never touch `writer_`. Readers do not contend with writers." The spec's FR-007 "lock-free" requirement implies readers-never-block; the explicit statement is the design-doc's domain per the cite-and-stop rule.
- [x] CHK013 Is the per-counterparty `Pinset` sharing semantic ("rotation atomically across both on the next handshake") clear about what "next handshake" means under concurrent in-flight handshakes? [Clarity, Spec §FR-009a / §US1 Independent Test] — PASS: FR-009 defines "next handshake" as: "A rotation landing during an in-flight handshake MUST NOT affect that handshake; the new pinset is picked up at the *next* handshake." US1 AC2 provides the concrete witness: "a handshake captured mid-rotation completes against whichever set was current when the handshake's `find()` ran." For concurrent in-flight handshakes sharing one Pinset: each handshake captures its snapshot at its own `find()` invocation; handshakes starting before the rotation observe the pre-rotation snapshot; handshakes starting after observe the post-rotation snapshot. "Next" = the next handshake whose snapshot capture occurs after the rotation's release-store completes. Clear from FR-009 + US1 combined.

## Requirement Consistency

- [x] CHK014 Is the cancellation-completes-with-`expected_t::unexpected{tls_load_cancelled}` (FR-021) consistent with the US2 AC3 statement ("completes with `unexpected{tls_load_cancelled}` (not by throwing)")? [Consistency, Spec §FR-021 / §US2 AC3] — PASS: FR-021 states "Cancellation MUST complete with `expected_t::unexpected{tls_load_cancelled}` (no thrown exception)." US2 AC3: "When cancellation propagates, Then the awaitable completes with `unexpected{tls_load_cancelled}` (not by throwing)." Both use identical completion mode (`unexpected{tls_load_cancelled}`), both exclude throwing. Consistent.
- [x] CHK015 Is the "mid-session-mutable" carve-out (FR-009 / FR-016) consistent across — i.e., does only `Pinset` get the carve-out, with `SecurityProfile`, `cert_source`, and `CipherPolicy` ALL frozen at session open? [Consistency, Spec §FR-009 / §FR-015 / §FR-016] — PASS: FR-009 grants the carve-out to Pinset ("mid-session-mutable per the [arch §5.6] carve-out"). FR-015 freezes SecurityProfile. FR-016 freezes cert_source and states "The `Pinset` is the ONLY mid-session-mutable TLS surface." CipherPolicy is compile-time constant by design (FR-011). FR-027 prohibits mid-session cert_source swap and mid-handshake pinset rotation. The carve-out is exclusive to Pinset; all other surfaces are frozen. Consistent across all four entities.
- [x] CHK016 Is the "no atomic-swap or 'set' shortcut" rule (FR-006) consistent with the `add` / `remove` separate-operations rule — i.e., does the spec rule out a hypothetical `Pinset::replace(old_fp, Certificate const&)` API? [Consistency, Spec §FR-006] — PASS: FR-006 states "There MUST be NO atomic-swap or 'set' shortcut per `[2g §6.5]` invariant 3." This rules out any API (including a hypothetical `Pinset::replace`) that combines add and remove in a single atomic step. The `add`/`remove` separate-operations rule is the only published API shape. `contracts/pinset.hpp` assertion 6 confirms: "NO atomic-swap / bulk-set API exists on Pinset (FR-006 / 2g §6.5 invariant 3)." Consistent.
- [x] CHK017 Is the FR-009a "per-counterparty `shared_ptr<Pinset>`" recommendation consistent with the FR-009 "rotation MUST be mid-session-mutable" requirement — i.e., does cross-session sharing inherit the atomicity contract correctly? [Consistency, Spec §FR-009 / §FR-009a] — PASS: FR-009 establishes rotation is mid-session-mutable (the Pinset's `add`/`remove` operations are thread-safe by design per [2d §7.5]). FR-009a says the same `shared_ptr<Pinset>` is shared across sessions for the same counterparty. When the shared Pinset is rotated, the atomic snapshot publication (release-store) makes the new snapshot visible to all concurrent `find()` calls on any session's next handshake. Cross-session sharing inherits the atomicity contract because the contract is in the Pinset itself (atomic snapshot pointer), not in any per-session locking. US1 Independent Test explicitly witnesses this. Consistent.
