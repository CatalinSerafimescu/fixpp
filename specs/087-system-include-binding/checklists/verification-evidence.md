## Requirement Completeness — what must be recorded

- [x] CHK045 - Is the recording obligation for each red specified as **exit status + asserted token + first diagnostic line**, with the reason an exit status alone is insufficient? [Completeness, Contract §5 preamble] — PASS: §5's preamble requires all three and gives the reason ("it does not identify which C-1/C-2 branch fired, so it does not discharge the branch the row exists to exercise"). `quickstart.md` §4 restates it operationally and adds the concrete trap: `> file` discards the exit status.
- [x] CHK046 - Is every **induction class** defined in prose, and does the count in the prose agree with the classes the table actually uses? [Completeness, Consistency, Contract §5, quickstart §4] — PASS: §5 defines all **four** (expectation-side, package-side, invocation, reply-side) with the rows each covers, and its box records that the prose said "two" until Gate A round 2 and that the round-2 review itself counted three — both undercounts preserved rather than quietly replaced, "because the class list is what tells an implementer which induction means each row permits". `quickstart.md` §4 carries the same four.
- [x] CHK047 - For each row that mutates the tree, is the **exact mutation** written out rather than described by a keyword flip whose meaning is ambiguous? [Completeness, Contract §5 demonstration-#2 and -#8 boxes] — PASS: #2's box gives the shipped state at `src/capi/CMakeLists.txt:97-99` and `:112-115`, the exact diff, what is **not** touched, and why "flip `PRIVATE` → `PUBLIC`" is not the same edit (086 paid an implement round on that). #8's box gives the diff plus its `git show cb397284` provenance, and states which of two readings of "revert" the row induces — because there the ambiguity decides the **asserted token**.
- [x] CHK048 - Where a mutation's expected magnitude has never been measured, is the expectation stated **qualitatively** with the reason no figure is given? [Completeness, Clarity, Contract §5 demonstration-#2 box] — PASS: the "Why no count" paragraph proves the reverted set is *not* the umbrella's 7-entry set (it retains `include/capi`, which the umbrella set does not contain), states that its cardinality has never been measured, and refuses to supply a replacement figure because "substituting a second inferred number would reproduce the defect this box exists to remove". `tasks.md` T016 carries the prohibition forward.
- [x] CHK049 - Is the fault-injection **seam** specified — against what artifact a reply-side mutation is applied — given the sub-build is wiped and reconfigured on every run? [Completeness, Contract §5 reply-side class, `run_consumer_witness.cmake:46`] — PASS: §5's reply-side class requires `cp -r` of a **real** reply directory and mutation of the **copy**, and states why it is the only realisable seam: `:46`'s `file(REMOVE_RECURSE …)` regenerates the reply before any persistent tree edit could reach it. It adds the trap explicitly — "remove an entry from the observed side" is **not** achievable by editing the tree, and an implementer who tries ends up editing the *expectation*, which is row #1 with the sign flipped.
- [x] CHK050 - Are requirements stated for the arguments a **direct** comparator invocation must be given, including any the enclosing CMake run would otherwise have supplied? [Completeness, Contract C-6.1, quickstart §4 closing paragraph, `tasks.md` T005a] — PASS: C-6.1's tuple carries `install-prefix` explicitly (added by the Gate A fixer for exactly this reason — a standalone `cmake -P` inherits no CMake variables), and `quickstart.md` §4's closing paragraph requires it for rows 3–6a with the consequence of omitting it. T005a resolves it to the concrete path.
- [x] CHK051 - Is there a requirement that every fault-inducing demonstration run against the **shipped** script rather than a re-implementation? [Completeness, Contract C-6.5] — PASS: C-6.5 states it as a MUST with the reason ("a red produced by a bespoke harness proves nothing about the shipped path"), and every §5 row that induces a fault names `compare_system_includes.cmake` explicitly.
- [x] CHK052 - Are the evidence-durability requirements stated — a durable location rather than `/tmp`, and capture of the real exit code rather than a redirect that discards it? [Completeness, quickstart §0/§4] — PASS: §0 sets `FIXPP_087_EVIDENCE=~/fixpp-087-evidence` and marks it "DURABLE, not /tmp"; §4 requires the "**real exit status** (`> file` discards it)". `tasks.md` T002 carries the durable-directory task and each red task names its evidence file.

## Requirement Clarity — each row's asserted token is determinate

- [x] CHK053 - Does each demonstration row state the **complete** token set it asserts, rather than a single token where more than one fires? [Clarity, Measurability, Contract §5 rows 4 and 8, C-1] — PASS: §5's preamble states that the table asserts the **complete token set** each row produces; row 8 asserts `LEAK` **and** `DROP` from one mutation, and row 4 asserts `RECLASSIFIED` "**and that token alone**" with the reason no other accompanies it. Both are the rows where a single-token reading would be wrong.
- [x] CHK054 - Is the rule governing multi-token reporting stated, with the scope of what may and may not co-occur? [Clarity, Contract §3, C-1] — PASS: §3 confines the multi-token permission to C-1's three and keeps `MISSING_REPLY` / `INPUT_ERROR` / `LEG_ERROR` as **exclusive pre-comparison terminations** that can neither accompany a C-1 token nor each other. Its box records that the previous "the six tokens are mutually exclusive" rule was falsified in **both** halves by §5 on the same page.
- [x] CHK055 - For the row whose token set depends on the comparison's **staging**, is the staging stated as normative rather than as an implementation note? [Clarity, Contract C-1, §5 row 4, data-model I2] — PASS: C-1 says "**The staging is normative**, not an implementation note", and gives the failure it prevents: under an unstaged reading of I2's `(path, isSystem)` canonicalisation, a flipped `isSystem` lands in both residual set differences *and* the classification test — three tokens from one cause with no rule ordering them. §5 row 4 and I2's box both point back at it.
- [x] CHK056 - Are the sub-cases of any multi-part row **enumerated and each marked mandatory**, so discharging one is not read as discharging the row? [Clarity, Contract §5 row 6a, quickstart §4] — **SPEC-FIXED**: row 6a was correct (four **mandatory** sub-cases, with 6a(ii) explicitly "not discharged by *(i)*"), but rows **5** and **7** merely enumerated theirs — "and, as a second sub-case…", "as a second sub-case…" — without requiring both. That is the same shape that left 6a's missing-leg case undemonstrated until Gate A round 2: an implementer discharges the first, ticks the row, and leaves the second unproven. Both rows now say **two mandatory sub-cases** and state what each independently exercises (row 5: a directory that exists but holds no reply for this leg vs no directory at all — §2a says the *second* is the realistic failure; row 7: R7 guard #3 vs guard #4). `quickstart.md` and `tasks.md` T020/T023 already treated both as required, so no downstream sweep was needed. **Triggers a `/speckit-analyze` re-run.**
- [x] CHK057 - Is generator-specific diagnostic phrasing tied to the generator actually in use, with the alternative named as *not* applicable? [Clarity, Contract C-6.3, §5 row 7, Spec §Edge Cases] — PASS: C-6.3 and §5 row 7 both give Ninja's `ninja: error: unknown target '<name>'` as **measured in 086** and state that the Makefile generators' "No rule to make target" phrasing never appears in this project. `spec.md` §Edge Cases carries the general rule that anything matched textually is verified against the generator in use rather than assumed.
- [x] CHK058 - Is the same-run evidence obligation clear about **what produces it** — a gate output vs a follow-up read by the demonstrator? [Clarity, Spec §FR-007a, Contract §2b, quickstart §4 box] — PASS: §2b states it is discharged "**by the gate, not by the demonstrator**", and explains why the alternative is unsound — a manual read of a surviving work directory would satisfy the letter while depending on an incidental property (`:46` wipes at the *start*) that no requirement pins. `quickstart.md` §4's box records that it said to read the reply yourself until Gate A round 2 and that the manual read is now a cross-check, not the discharge.
