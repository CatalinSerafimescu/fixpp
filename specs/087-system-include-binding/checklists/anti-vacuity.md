# Anti-Vacuity Requirements Checklist: 087 system include binding

**Purpose**: Unit tests for the *requirements writing* on this feature's declared identity — that the gate
cannot report success having observed nothing. All four of Gate A's decisive catches sat on this axis, inside
the feature's own gate, so the requirements here are load-bearing rather than aspirational.
**Created**: 2026-08-05 · **Audited**: 2026-08-05 (pipeline step 9)
**Feature**: [spec.md](../spec.md) §US2 · [research.md](../research.md) R7 · [contracts/system-include-interface.md](../contracts/system-include-interface.md) §6
**Audience**: Gate B reviewer. Depth: formal release gate.

> These items test whether the **requirements are written well**, not whether the gate works. "Is the guard
> specified?" — not "does the guard fire?".

## Requirement Completeness — the guards

- [x] CHK021 - Is every anti-vacuity guard **enumerated**, with a count stated, rather than described as a general posture? [Completeness, research R7] — PASS: R7 states "**six** independent guards" and lists them 1–6. Its header records the enumeration's own history (three at first draft; two added at Gate A round 1 and not swept until round 2; guard 6 from contract §6), so the count is auditable rather than asserted.
- [x] CHK022 - Does each guard state **what makes it mechanised** — the specific clause that enforces it — rather than asserting that it is? [Completeness, Measurability, research R7 guards 1–6] — PASS: each guard names its enforcing clause — #1 C-6.4's empty-expectation rejection ("that rejection is what makes this guard *mechanised rather than declared*"), #2 FR-005, #3 FR-006 via `_required_targets`, #4 C-6.1/C-6.3 with §5 row 7's second sub-case, #5 C-6.4 with §5 row 6a, #6 FR-014 with §6/§6a.
- [x] CHK023 - Are requirements stated for the case where the observation is **present and parses but yields zero entries**, distinctly from the case where the input is absent? [Completeness, data-model I3, Contract C-2 box] — PASS: C-2's box states that reply *existence and parse* is all C-2 checks, that a populated-but-empty observation passes it, and that what rejects ∅ is the non-empty expectation (I3) failing "by arithmetic" as a `DROP`. I3 says the same and adds "the two guards are easy to conflate", which is precisely why both state it.
- [x] CHK024 - Is there a requirement covering an expectation that is non-empty **as declared in the tree** but reaches the comparator **empty** — and is the guard for it specified as a mechanism rather than a note? [Completeness, Contract C-6.4, data-model I3, research R7 guard 1] — PASS: C-6.4's fourth `LEG_ERROR` cause requires `compare` to reject an empty `expectation` argument at argument-validation time, with a "Why it is a mechanism and not a note" paragraph naming the failure it prevents (a mis-spelled `${FIXPP_087_EXPECTED_*}` composed with a zero-entry observation comparing ∅ against ∅ and reporting green). Added at Gate A instance 2 round 1, where the cause was named in C-2 and defined nowhere.
- [x] CHK025 - Are requirements stated for the gate's carrier being **deleted**, distinctly from the comparator script being deleted while the carrier survives? [Completeness, Contract C-6.3 / §5 row 7, Spec §US2 scenario 3] — PASS: §5 row 7 now states **two mandatory sub-cases** with distinct expected failures (Ninja's unknown-target error vs the target's own command failing), and C-6.3 requires the by-name entry that makes both fail. US2 acceptance scenario 3 is the spec-level statement.
- [x] CHK026 - Is there a requirement that the comparison have a **standalone, separately-invocable identity**, with the reason an inline block would be deletable without anything noticing? [Completeness, Contract C-6, plan §Structure Decision] — PASS: C-6's preamble quotes 086's own finding ("*the gate can be removed without anything noticing is the same defect class as the gate cannot fail*", `run_consumer_witness.cmake:99-106`) and forbids an inline block; `plan.md`'s Structure Decision restates it and adds why reusing an 086 target is also insufficient. This was Gate A i1r1's root cause #1.
- [x] CHK027 - Are requirements stated for the vacuity path that sits **outside** the gate entirely — a lane on which the witness stops registering — and is it bound to every workflow that runs the witness? [Completeness, Coverage, Spec §FR-014, §SC-008, Contract §6/§6a] — PASS: FR-014 and SC-008 are both written **unqualified by tier**; §6a gives four independent reasons for all three workflows (single `LABELS consumer` at `CMakeLists.txt:421`; `FIXPP_BUILD_CODEGEN_TOOL` default ON overridden nowhere; the witness executes on all of them; narrowing would be strictly narrower than the spec).
- [x] CHK028 - Are the invariants that are **review-time only** labelled as such, so none is read as enforced by the gate? [Clarity, Contract C-4, data-model I4, research R7 "one last turtle"] — PASS: C-4 carries an explicit box ("C-4 is a review-time invariant only, and so is `data-model.md` I4"); I4 says the same and states that US3's Independent Test is a human inspection; R7's closing box discloses the carrier's own `leg-set` invocation line as review-enforced. I3 is explicitly contrasted as *not* review-time-only, which is the distinction that makes the labelling meaningful.
- [x] CHK029 - Is the residual set of unclosable vacuity paths **enumerated** rather than implied by a claim of singularity ("the last path")? [Clarity, Completeness, Contract §6 box] — PASS: §6's box enumerates both residuals (the carrier's own `leg-set` invocation line; the computed-expectation prohibition) and records that the section read "**One** path remains… **the last** vacuity path" until Gate A instance 2 round 1, noting "this project has twice found real defects behind exhaustiveness claims".
- [x] CHK030 - Is the distinction between "the gate cannot fail" and "the gate can be removed without anything noticing" stated as **one defect class with two shapes**, so a requirement closing one is not read as closing the other? [Clarity, Contract C-6, research R7 guards 3–4] — PASS: C-6 states them as the same defect class explicitly, and R7 separates the two shapes into distinct guards — #3 (by-name requirement, target deleted) and #4 (script deleted, target survives) — each with its own demonstration sub-case.
- [x] CHK031 - Is `E2.present` (reply existence and parse) clearly separated from the non-empty-expectation arithmetic, given the two are easy to conflate? [Clarity, data-model E2/I3, Contract C-2 box] — PASS: I3 states it in the strongest available form — "**This, not `E2.present`, is what catches** a reply that exists and parses but yields zero include entries" — and E2's validation clause scopes `present` to reply existence and parse only.
- [x] CHK032 - Is it unambiguous **which mode** of the comparator owns each fault cause, so no cause is named in one clause and defined in none? [Clarity, Contract C-2, C-6.4] — PASS: C-6.4 assigns the three leg faults to `leg-set` and the empty-expectation fault to `compare`, and its "Which mode induces which sub-case" paragraph maps each §5 row 6a sub-case to the mode that induces it. C-2 delegates the whole cause list to C-6.4 and says so. This is exactly the defect (a cause named once and carried nowhere) that Gate A instance 2 round 1 closed.
