# ABI-Boundary Requirements Checklist: 087 system include binding

**Purpose**: Unit tests for the *requirements writing* around the C-ABI consumption boundary this feature
binds — the fourth usage requirement `$<LINK_ONLY:>` withholds, and the 086 scope limit it closes.
**Created**: 2026-08-05 · **Audited**: 2026-08-05 (pipeline step 9)
**Feature**: [spec.md](../spec.md) · [contracts/system-include-interface.md](../contracts/system-include-interface.md)
**Audience**: Gate B reviewer. Depth: formal release gate.

> These items test whether the **requirements are written well** — complete, unambiguous, consistent,
> measurable — not whether the implementation works. Implementation behaviour is asserted by contract §5's
> demonstrations and `tasks.md`, not here.

## Requirement Completeness

- [x] CHK001 - Are the expected include sets for **both** bound targets enumerated member-by-member with a stated rationale per member, rather than given only as a count? [Completeness, Contract §1, data-model E3] — PASS: Contract §1's table gives both sets with counts; `data-model.md` E3 carries a "why it is there" column per member (`include/capi` = 086's C-ABI root, `fixpp::capi`'s only `$<INSTALL_INTERFACE:>`; `include/service-iface` = service's own declaration; `include/capi` on the service leg = inherited through the link).
- [x] CHK002 - Are requirements stated for the second leg (`fixpp::service`) as an independently declared obligation, with the reason it is **not** implied by the C-ABI leg? [Completeness, Spec §FR-001a, §Clarifications] — PASS: FR-001a states it as a separate MUST with its own expectation; §Clarifications Q2 gives the reason as a **measurement** from 086 (`src/service/CMakeLists.txt` declares its own `$<INSTALL_INTERFACE:>`), not an inference.
- [x] CHK003 - Is the treatment of compiler- and SDK-supplied include roots specified as a **measured** fact with its measurement cited, rather than as an assumption about what the instrument reports? [Completeness, Contract §1a, research R2/R6] — PASS: Contract §1a states the mechanism per platform (compiler's own search path on Linux; `INCLUDE` from `vcvars64.bat` on MSVC) and closes with "*(Measured, not assumed — R2 and R6.)*". This is what makes the closed-set expectation cheap rather than a maintenance burden.
- [x] CHK004 - Is the prefix-relative comparison rule specified **together with** what happens to an observed entry that falls outside the prefix? [Completeness, Contract C-3, data-model I1] — PASS: C-3 and I1 both state that an out-of-prefix entry stays in canonical absolute form, cannot match the closed prefix-relative expectation, and is therefore classified `LEAK`. The consequence is stated, not left to inference.
- [x] CHK005 - Are requirements stated for the disposition on a platform where the instrument is unavailable, **decided in advance** rather than left to implementation time? [Completeness, Spec §FR-010, §FR-010a] — PASS: FR-010a fixes the disposition up front (scope out with a recorded reason; fail loudly or be visibly absent on the excluded platform) and explicitly forbids an implementation-time choice to let the gate no-op. The rationale names 086's post-sign-off round as the reason for deciding early.
- [x] CHK006 - Does the amendment set distinguish artifacts to be **corrected** from historical records to be **appended to**, so provenance is preserved rather than rewritten? [Completeness, Contract §4a row 5] — PASS: §4a row 5 is marked "provenance-preserving only", mandates a dated parenthetical append and forbids rewriting; rows 6 and 7 carry the same marker for the two consumer-harness records. Row 5's closing note says the universal wording is deliberately not narrowed to "current normative artifacts".
- [x] CHK007 - Are requirements explicit that no C-ABI header, symbol set or version-script change occurs — i.e. that this feature *asserts* an existing boundary rather than moving it? [Completeness, Spec §Out of Scope, plan Articles IX §5 / X §1] — PASS: §Out of Scope names all three; §Assumptions adds "no production C/C++ source changes"; `plan.md`'s IX §5 row states `include/fix/**` is byte-unchanged and X §1/§2 states the feature asserts an existing property without moving the surface.

## Requirement Clarity

- [x] CHK008 - Is the comparison form (exact set equality vs containment vs deny-list) stated **once** with the rationale for rejecting each alternative, rather than restated divergently across artifacts? [Clarity, Spec §FR-003a, §Clarifications] — PASS: §Clarifications Q1 carries the rationale for rejecting both alternatives (containment is blind to a **drop**, which is half of what C-3 claims; a deny-list only catches leaks it was told about). FR-003a, contract C-1 and `data-model.md` I2 restate the *decision* consistently and defer to C-1 as the authority — restatement in agreement, not divergence.
- [x] CHK009 - Is it unambiguous that `isSystem` classification is **part of the compared value** and never discarded, including which side of the comparison it is matched within? [Clarity, Spec §FR-003a, data-model I2, Contract C-1] — PASS: C-1 stage 1 is explicit that `path` alone is the match key and `isSystem` is compared *within* a matched pair, never part of the key. I2 carries the same with a box explaining why the staging is part of the invariant.
- [x] CHK010 - Does the spec make clear **which install prefix** the comparison uses at gate time, distinctly from any prefix used for a manual reproduction of the measurement? [Clarity, Contract C-3] — PASS: as a *requirement* the rule is unambiguous — every §5 reply-side row and `quickstart.md` §4's closing paragraph require "the same install prefix the original configure used". The gap was operational, not in the requirement text: no artifact resolved that rule to a path, while `tasks.md` T004 introduced a different concrete prefix. Closed at `/speckit-analyze` by new task **T005a**, which pins the driver's stage, sub-build and reply directory and records that a wrong prefix degenerates the comparison to all-`LEAK` + all-`DROP` *without erroring*.
- [x] CHK011 - Is the directional hazard — reverting the capi leg reds **both** legs — written as an inherited **measurement** rather than as a hypothesis? [Clarity, Spec §FR-007a, 086 FR-011e] — PASS: FR-007a states the mechanism (`fixpp_service` links `fixpp_capi`) and tags it "*Inherited from 086 FR-011e, which established this hazard by measurement*"; §Clarifications repeats "inherited, not hypothetical".
- [x] CHK012 - Are the requirements for amending 086's C-3 bounded, stating exactly which legs become bound and by what instrument, and explicitly **not** generalising 086's reachability matrix? [Clarity, Contract §4, §4a "must not claim"] — PASS: §4a's closing "What the amendments must **not** claim" paragraph states that 086's §1 reachability matrix still covers system include directories only at its two named header boundaries, that 087 binds the *include set of the two consumer targets* only, and that each amendment names its legs and instrument and leaves the matrix scope note intact.
- [x] CHK013 - Is the constitutional basis for treating this feature as ABI-adjacent stated with its citation, rather than inherited silently from 086's disposition? [Clarity, Traceability, plan Article X §6, Spec §Normative References] — PASS: `spec.md` §Normative References cites `[const §IV.2]` (`.specify/constitution.md:141`) as what makes an unenforced C-ABI include boundary a defect rather than tidiness, and `[const §X.6]` (`:225`) for the four controls; `plan.md`'s X §6 row states the reasoning explicitly ("the property asserted *is* the C-ABI consumption boundary") rather than citing 086 alone.

## Requirement Consistency

- [x] CHK014 - Is the FR-011 amendment set defined in **exactly one** place, with every other artifact citing that definition rather than restating the list? [Consistency, Spec §FR-011, Contract §4a] — PASS **with a recorded residual**: §4a is declared the single definition, and `plan.md`'s Article VI row plus SC-007 cite it rather than restating. `spec.md` FR-011 does name the **count** ("seven") and three of the seven paths — deliberately, with "§4a is the authority" stated in the same sentence — so it is the one site that goes stale if the table grows. Residual closed by an explicit sweep obligation added to **T036**: if §4a's row count changes, FR-011 is swept in the same commit.
- [x] CHK015 - Are the requirements consistent that entry **ordering is not asserted**, and is that recorded as a limitation rather than silently ignored? [Consistency, Contract §1a, data-model I2, Spec §Assumptions] — PASS: contract §1a records order as a recorded limitation, not closed; I2 states entry order is not part of the compared value and that `research.md`'s observed order is a measurement note; `spec.md` §Assumptions states order-insensitivity as the default *with* ordering effects called out rather than ignored. All three agree.
- [x] CHK016 - Is the toolchain-scope argument stated **per toolchain**, each carried by the workflow and step that actually decides it — rather than by one cite that reaches only some of them? [Consistency, Coverage, Contract §1 table] — PASS: contract §1's per-toolchain table maps clang, gcc, libc++ and MSVC each to its matrix and to the `ctest` step(s) that run the witness. The box below it records that the previous single cite (`tier1.yml:511-513`) reached gcc and **did not reach libc++ at all**, and why the mapping is now stated per toolchain. Corrected at Gate A round 2.
- [x] CHK017 - Is the claim "unmeasured toolchains are covered because CI executes the same gate" made explicitly **conditional** on the thing that makes it true, rather than asserted unconditionally? [Consistency, Contract §1, §6] — PASS: §1 states "That argument holds only once each of those steps carries FR-014's registration-count assertion (§6)", with the reason (`ctest -L` exits 0 when it selects nothing) and the observation that libc++ sits on the one workflow with no count assertion today. This is also given as the substantive reason §6 prescribes all three workflows.
- [x] CHK018 - Do the spec's Key Entities and `data-model.md`'s entities describe the same set of things under the same names? [Consistency, Spec §Key Entities, data-model E1–E4] — **SPEC-FIXED**: they did not. `spec.md` said "**Allowed** expectation" where the data model says "**Declared** expectation" (E3), and Key Entities omitted **E4, the per-leg result file**, entirely — E4 was added to the data model at Gate A instance 2 and never swept into the summary. That is this feature's own recorded recurring root cause: *round-N additions swept into the artifacts that do the work but not into those that summarise it*. `spec.md` §Key Entities now lists E1–E4 under the data model's names with a dated note. **Triggers a `/speckit-analyze` re-run.**

## Acceptance Criteria Quality

- [x] CHK019 - Can the bound property's headline success criterion be **objectively measured** — zero unexpected entries, zero missing entries, zero classification mismatches — without interpretation? [Measurability, Spec §SC-001] — PASS: SC-001 is stated as exact set equality with all three counts at zero. Each of the three is independently observable through a named diagnostic token (`LEAK` / `DROP` / `RECLASSIFIED`), so a failure identifies which count is non-zero rather than reporting a bare inequality.
