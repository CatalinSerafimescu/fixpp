# Phase 0 Research: ResetOn{Logon,Logout,Disconnect} Lifecycle Knobs (024, S-017)

All NEEDS CLARIFICATION resolved (none remained after `/speckit-clarify` 2026-06-06). Decisions are grounded in a source sweep of fixpp + the two live interop targets QuickFIX-cpp v1.16.0 and QuickFIX-J 3.0.1.

## D1 — `ResetOnLogon` is coupled to `ResetSeqNumFlag(141)`, NOT wire-independent

- **Decision**: On the **initiator**, enabling `reset_on_logon` (or `reset_on_logout`/`reset_on_disconnect`) makes the outbound Logon carry `ResetSeqNumFlag(141)=Y` once the logon-time reset has put both seqnums at `{1,1}`. The local reset and the wire announcement are the *same* event.
- **Rationale**: Both interop targets do exactly this and agree:
  - QuickFIX-cpp `Session::generateLogon` (`Session.cpp:677-685`): `refresh()` → `reset()` (if `m_resetOnLogon`) → `if (shouldSendReset()) logon.setField(ResetSeqNumFlag(true))`. `shouldSendReset()` (`:1037`) = `beginString >= FIX41 && (m_resetOnLogon||m_resetOnLogout||m_resetOnDisconnect) && nextSender==1 && nextTarget==1`.
  - QuickFIX-J `Session.generateLogon` (`Session.java:2083-2090`): `if (refreshOnLogon) … ; if (resetOnLogon) reset(); if (isResetNeeded()) logon.setBoolean(ResetSeqNumFlag.FIELD, true);`. `isResetNeeded()` (`:919`) = `(resetOnLogon||resetOnLogout||resetOnDisconnect) && seqnums==1`.
  - A purely-local reset (fixpp at 1, peer unchanged) would desync immediately → the peer detects a too-low seqnum and rejects/ResendRequests. Announcing via `141=Y` is the only interop-correct behavior.
- **fixpp mapping**: fixpp emits `141=Y` today only when `reset_seqnum_policy_field == bilateral_strict` (`session.cpp:523-526`). This feature extends the emission predicate to `send_reset_flag || ((cfg_.reset_on_logon || cfg_.reset_on_logout || cfg_.reset_on_disconnect) && seqnums=={1,1})`, after a `co_await reset_to_one()` — the OR-of-three exactly matching QFcpp `shouldSendReset()` (`:1037`) and QFJ `isResetNeeded()` (`:919`). The `reset_on_logout`/`reset_on_disconnect` arms are load-bearing: such a session that reset to `{1,1}` at a **prior teardown** opens its next Logon at `{1,1}` and MUST announce that reset with `141=Y` (QuickFIX does; a single-knob `reset_on_logon`-only predicate would desync a `reset_on_logout`/`reset_on_disconnect` session against a live QuickFIX peer). The existing `013` `reset_seqnum_policy_field` continues to govern **validation** of the peer's `141` echo (emission vs echo-validation are orthogonal axes).
- **Alternatives rejected**: (a) keep decoupled / local-only (the spec input's framing) — diverges from both interop targets and desyncs a live peer; (b) acceptor-only reset — asymmetric, QuickFIX resets in both roles.

## D2 — Reuse the existing `013` reset primitive via a 024 durable-reset helper with explicit per-site error disposition

- **Decision**: The reset is **two** operations, not one: `SeqnumManager::reset_to_one()` (`seqnum_manager.hpp:113`) mutates only the live counters under the mutex; persistence is a **separate** `co_await store_->reset()` call (the `013` acceptor path at `session.cpp:1589-1592` discards the store-reset result: `(void)store_rst_r; // store_io_failure → logged-then-proceed (I-07)`). 024 specifies a single helper `reset_seqnums_to_one_durable(disposition)` that `co_await`s `reset_to_one()` **then** `store_->reset()`, with the store-failure disposition keyed on the **trigger cause** (NOT the trigger location) — because the existing 013 received-`141` reset on the acceptor must keep its current I-07 behavior even when the knobs are off (FR-001 zero regression):
  - **Knob-driven Logon reset** (`reset_on_logon == true`, initiator `open()` / acceptor inbound-Logon): **fatal** — a `store_->reset()` failure MUST **prevent reaching `Active`** (propagate the error). A non-durable reset that does not survive a restart would silently re-desync, defeating FR-008's "a subsequent open observes `{1,1}`".
  - **013-only received-`141` reset** (knobs off, acceptor `hdr.reset_seqnum_flag=="Y"`): **logged-then-proceed (I-07)** — UNCHANGED from today's `session.cpp:1589-1592`. With all 024 knobs off, a tolerated store failure on a peer-`141` receipt MUST still let the session reach `Active` exactly as it does today; the 024 fatal disposition MUST NOT touch this path.
  - **Teardown path** (`close()` logout/disconnect): **logged-then-proceed** (I-07) — the session is already terminating, so a `store_->reset()` failure does not abort teardown; the contract states this explicitly rather than implying durability it does not enforce.
  - **Logon-path overlap** (`reset_on_logon && peer_sent_reset` on the acceptor): the reset is called **once** with the **stricter (knob → fatal)** disposition (see D3 single-combined-decision). The 013-only I-07 path applies only when the knob is OFF.
- **Rationale**: `reset_to_one()` sets both `next_inbound_`/`next_outbound_` to `seqnum_min` (1); calling it onto an already-`{1,1}` state is a value no-op for the counters. But `MessageStore::reset()` (`message_store.hpp:133`) is **not** a no-op — `FileStore::reset()` (`file_store.cpp`) does a full atomic-rename + fdatasync + dir-fsync on every call regardless of the current counter value (see D-idempotency in D3 / FR-009). The helper centralizes both ops so the per-site disposition and the single-fire teardown guard live in one place.
- **Alternatives rejected**: a new dedicated knob-reset primitive — needless duplication; the existing `reset_to_one()` + `store_->reset()` pair already does "both counters → 1 + persist", the helper just couples them with defined error handling.

## D3 — The three wiring sites are existing FSM transition points (no new states)

- **Decision**: Wire the triggers at the existing transition points fixpp **actually converges on**, adding no new `fsm_state` value or transition-matrix entry:
  - **`ResetOnLogon` initiator** → `Session::open()` initiator arm (`session.cpp:519-561`): `reset_seqnums_to_one_durable()` **before** `peek_outbound()` (`:522`), then the extended OR-of-three `141` flag into `build_logon`.
  - **`ResetOnLogon` acceptor** → inbound-Logon handler (`session.cpp:1437-1584`): a **single combined pre-validation decision** `need_logon_reset = reset_on_logon || peer_sent_reset` (`peer_sent_reset` = `hdr.reset_seqnum_flag=="Y"`) drives **one** `reset_seqnums_to_one_durable()` call **BEFORE `check_inbound(seq)` (`:1437`)** with the **stricter applicable disposition** (knob present → fatal; 013-only received-`141` with knob off → I-07, per D2). This is NOT the existing `141`-receipt reset at `:1584` relocated — it is one combined reset placed before validation. The existing `141`-receipt reset runs *after* `check_inbound`, and in the handshake (LogonReceived) state a too-low **or** too-high sequence is **fatal** (`:1438-1441` → `record_state_transition_(Disconnected)`), so a knob/`141` reset placed after `check_inbound` cannot rescue a fresh peer Logon `34=1` when local `next_inbound_ > 1` — the session disconnects first. Moving the decision before `check_inbound` so the fresh `{1,1}` space admits `34=1` means the existing `:1584` `141`-receipt reset is **subsumed** by the combined pre-validation reset (it does not run a second store-reset I/O). (QFcpp/QFJ `nextLogon` honor the received `141`/`ResetOnLogon` reset before validating the incoming target seqnum — same ordering.) `FileStore::reset()` is non-idempotent I/O (full atomic-rename + fdatasync + dir-fsync every call), so the combined single-decision is what guarantees **exactly one** `store_->reset()` for `reset_on_logon && inbound 141=Y`; the reply Logon mirrors `141=Y` (existing path). **Superseded — see FR-007 / C2.2 + the /speckit-verify regression finding: the acceptor is a cause-dependent split, not a single combined pre-`check_inbound` decision.**
  - **`ResetOnDisconnect`** → `Session::close()` convergence (`session.cpp:823-1025`), **before** the SeqnumManager async-mutex drain (`~:1002`) so `reset_to_one()` does not hit a drained mutex (which returns `session_already_closed` and silently no-ops): fires on **ANY** `close()` (graceful, terminal, and abnormal read-pump EOF/error → `close(terminal)`).
  - **`ResetOnLogout`** → fires when a Logout occurred in **EITHER direction** before teardown — NOT keyed on `close_mode::graceful` alone. A **locally-initiated** Logout traverses `close(close_mode::graceful)` (`:880`), but a **peer-initiated** Logout (inbound `35=5`) does **NOT** call `close()` at all: it transitions inline to `Disconnected` (`session.cpp:~2095-2174`), and teardown then arrives via read-pump EOF → `close(close_mode::terminal)` (`engine.cpp:506`). So `close_mode::graceful` reaches only the local-initiate half of FR-004. The `reset_on_logout` reset MUST therefore be keyed on a dedicated **`logout_seen_`** flag set ONLY where a real Logout is observed — NOT derived from `onLogout_fired_`. `record_state_transition_` (`session.cpp:175-191`) sets `onLogout_fired_` on **ANY** `Active→!Active` transition (incl. an abnormal terminal close / fatal with no Logout in either direction — see the in-source comment "terminal close or fatal"), so it is a *left-Active* predicate, not a *logout-seen* predicate; keying `reset_on_logout` off it would fire the reset on a raw disconnect and collapse it into `reset_on_disconnect` (contradicts C4.2). Set `logout_seen_` at exactly two sites: (a) the local graceful-Logout-**sent** path (`close(close_mode::graceful)` `:880` / the generateLogout site), and (b) when an inbound `Logout (35=5)` is observed in `Active`/`LogonReceived`/`LogoutSent` (the peer-Logout transition `~:2095`, before its `record_state_transition_(Disconnected)`). The teardown reset in `close()` fires when (`(logout_seen_ && reset_on_logout) || reset_on_disconnect`).
- **Single-fire teardown guard**: `close()` MUST guard the durable reset with a "reset already done this teardown" flag so a double-trigger (`reset_on_logout` + `reset_on_disconnect`, or a graceful Logout that then disconnects) does **at most one** `store_->reset()` I/O cycle — `FileStore::reset()` is NOT a no-op (full atomic-rename + fdatasync + dir-fsync every call), so without the guard the double-trigger performs two durable rewrites. (FR-009 / D-idempotency.)
- **Rationale**: `close()` is the unified teardown convergence for graceful, terminal, and abnormal drops — so a single `reset_on_disconnect` placement there catches "any disconnect incl. abnormal drop" (FR-005) without touching the read pump. But `reset_on_logout` is role-sensitive: QuickFIX's `nextLogout` is invoked on **both** sent-and-received Logout, whereas fixpp's `close(graceful)` is only the local-initiate path — hence the "logout seen (either direction)" keying rather than `close_mode`. QuickFIX placement reference: `ResetOnLogout` in `nextLogout` before `disconnect()` (QFcpp `Session.cpp:325-327`, QFJ `:1484`), `ResetOnDisconnect` in `disconnect()` (QFcpp `:638`, QFJ `:2161`).
- **Alternatives rejected**: (a) keying `reset_on_logout` on `close_mode::graceful` alone — structurally misses every peer-initiated Logout (half of FR-004); (b) the acceptor reset around the existing `:1584` `141`-receipt site — runs after `check_inbound`, so a fresh `34=1` disconnects first.

## D4 — Default `false` ⇒ pure no-op (zero regression)

- **Decision**: `reset_on_logon`/`reset_on_logout`/`reset_on_disconnect` all default `false`. With all off, the only changed predicate (`open()`'s `141` flag) reduces to today's `send_reset_flag` (policy-driven), and the `close()`/inbound-Logon paths take no reset branch — byte/semantics-identical to the pre-feature baseline, including the `013` `bilateral_strict` flow.
- **Rationale**: [const §XII.5] no-implicit-default + the project's additive-knob precedent (021 `redeliver_poss_dup`, 022 `allow_pos_dup`). The default matches QuickFIX (`N` for all three).

## D5 — Config-key naming mirrors QuickFIX exactly

- **Decision**: C++ `SessionConfig` fields are house snake_case (`reset_on_logon`, `reset_on_logout`, `reset_on_disconnect`); the `008` `cfg_loader` translation keys are the literal QuickFIX/J keys (`ResetOnLogon`/`ResetOnLogout`/`ResetOnDisconnect`).
- **Rationale**: 1:1 QuickFIX-config mapping (same precedent as 022's `AllowPosDup` → `allow_pos_dup`); operators porting a QuickFIX `.cfg` get the knobs for free.

## D6 — `RefreshOnLogon` (S-018) descoped — fixpp's manager is not store-seeded

- **Decision**: `RefreshOnLogon` is OUT of this slice; S-018 stays `backlog`.
- **Rationale**: fixpp's `SeqnumManager` is **never** seeded from the store at `open()` — the manager always starts at 1 (`session.cpp:1423` comment "seqnum_mgr_ starts at 1"; the sole `set_next_inbound` caller is the inbound `SequenceReset` handler `:3663`, not a store-hydrate; `open()`'s store resolution `:700-711` mints the store but never reads its counters into the manager). The `FileStore` persists `CounterPayload` durably, but nothing reloads it into the live manager. A meaningful `RefreshOnLogon` ("reload seqnums from the store at Logon") presupposes a store→manager hydrate-on-open path that does not exist — building it is a larger architecture-touching change at the `008` store-as-authority boundary (a likely Gate-A escalation). Keeping it out preserves G3's small-slice discipline ([[feedback_phase_implementer_sonnet_runaway_scope]]).
- **Follow-up**: tracked as L-024-1 + an S-018 catalogue gap-note; the future store-hydrate slice owns both persist-and-reload-on-open and `RefreshOnLogon`.

## Open risks carried into design

- **R1 — `reset_to_one()` ordering in `open()`**: must precede `peek_outbound()` (`:522`) or the initial Logon carries a stale seqnum. Pinned by a witness asserting the emitted Logon's `MsgSeqNum==1` after a seeded non-1 state.
- **R2 — policy × knob matrix**: `reset_on_logon` must log on cleanly under every `reset_seqnum_policy_field` (`bilateral_strict`/`bilateral_lenient`/`unilateral`) — knob-driven `141=Y` emission + policy-driven echo validation must compose without wedging. Pinned by a per-policy witness.
- **R3 — abnormal-drop arm**: `ResetOnDisconnect` must fire on a raw transport drop (no Logout), not only graceful close. Pinned by a witness that drives a read-pump EOF and asserts the persisted counters are 1.
- **R4 — close-drain ordering**: the teardown reset must run **before** the SeqnumManager async-mutex drain (`~:1002`) — `reset_to_one()` `co_await`s `mutex_.async_lock()`, which on a drained mutex returns `session_already_closed` and silently no-ops; placing the reset after the drain would defeat it. The `store_->reset()` awaitable must complete before `state_ = closed_drained` (`:1025`) and must not deadlock the close drain. Verified under TSan; witnessed by asserting the persisted counter is `1` after an abnormal drop AND that the live reset actually succeeded (not a swallowed `session_already_closed`).
- **R5 — peer-initiated Logout teardown wiring**: a peer Logout never enters `close(graceful)`; the `logout_seen` flag MUST be set at the peer-Logout-received transition (`:~2095-2174`) so the `reset_on_logout` reset fires for the received half of FR-004. Pinned by `ResetOnLogout_PeerInitiated_Resets`.
