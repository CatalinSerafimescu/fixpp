# Feature Specification: ResetOn{Logon,Logout,Disconnect} Sequence-Number Lifecycle Knobs

**Feature Branch**: `024-reset-refresh-on-logon`
**Created**: 2026-06-06
**Status**: Draft
**Input**: User description: "G3 slice 3 (S-017): per-session ResetOn* sequence-number lifecycle config knobs — ResetOnLogon, ResetOnLogout, ResetOnDisconnect. Distinct from the existing ResetSeqNumFlag(141) wire-flag policy; additive SessionConfig bool knobs, default off = QuickFIX-compatible no-op. Grounded vs live interop targets QuickFIX-cpp v1.16.0 and QuickFIX-J 3.0.1. (RefreshOnLogon / S-018 deferred to its own slice — see Clarifications.)"

## Context & Background

This is the third slice of interop gate **G3** (after `021`/`022`, which completed catalogue row **S-010**). It adds the three QuickFIX-canonical per-session **sequence-number reset knobs** that reset sequence numbers on session lifecycle events, completing catalogue row **S-017** (`ResetOnLogon/Logout/Disconnect`), flipping it `backlog → done`.

`RefreshOnLogon` (catalogue **S-018**) was **descoped from this slice** (Clarifications 2026-06-06): a Phase-0 grounding pass found fixpp's `SeqnumManager` is never seeded from the message store at `open()` (the manager always starts at 1; the `FileStore` persists counters but nothing reloads them into the live manager). A meaningful `RefreshOnLogon` ("reload seqnums from the store at Logon") therefore presupposes a store→manager hydrate-on-open path that fixpp does not have today — a larger, architecture-touching change at the `008` store-as-authority boundary. It is deferred to its own follow-up slice; **S-018 stays `backlog`**.

These knobs are **distinct** from the `ResetSeqNumFlag(141)` *wire-flag* policy already shipped in `013` (`SessionConfig::reset_seqnum_policy_field`, the `bilateral_strict`/`bilateral_lenient`/`unilateral` matrix). The `141` policy governs how the engine *validates* a **mutual, on-the-wire** sequence reset negotiated with the peer during the Logon handshake. The knobs in this feature are **local operator policies** that reset the engine's own sequence-number state at lifecycle transitions; their relationship to a `141=Y` handshake (the initiator *announces* a reset via `141=Y`) is resolved in Clarifications.

The three knobs (QuickFIX default for all three = `N`/off):

- **`ResetOnLogon` (S-017)** — when on, reset both the inbound (next-expected) and outbound (next-to-send) sequence numbers to 1 when the session logs on (initiator: at its outbound Logon; acceptor: when it processes the inbound Logon).
- **`ResetOnLogout` (S-017)** — when on, reset both sequence numbers to 1 when the session logs out (Logout sent or received → terminal).
- **`ResetOnDisconnect` (S-017)** — when on, reset both sequence numbers to 1 on **any** transport disconnect/teardown, not only a graceful Logout.

Scope is FIX 4.4 session-layer only (interop matrix option (a)). `RefreshOnLogon` (S-018), `CheckCompID=N`, `validateSequenceNumbers=N`, `MaxLatency/CheckLatency`, and `NextExpectedMsgSeqNum(789)` are **separate later G3 slices**, explicitly out of scope here.

## Clarifications

### Session 2026-06-06

- Q: How should `ResetOnLogon` relate to `ResetSeqNumFlag(141)` on the wire (the spec input framed the knobs as "independent of 141")? → A: **Follow the QuickFIX coupling — the knobs are NOT wire-independent on the initiator.** The reference sweep (QuickFIX-cpp `Session.cpp:677-685` `generateLogon` + `shouldSendReset()` at `:1037`; QuickFIX-J `Session.java:2083-2090` `generateLogon` + `isResetNeeded()` at `:919`) shows **both** live interop targets agree exactly: at Logon the initiator does `refresh()` (if `RefreshOnLogon`) → `reset()` (if `ResetOnLogon`) → then, because any reset knob is on **and** both sequence numbers are now `{1,1}`, the outbound Logon **carries `ResetSeqNumFlag(141)=Y`**. So enabling `ResetOnLogon` (or `ResetOnLogout`/`ResetOnDisconnect`) makes the initiator *announce* the reset on the wire — a purely-local reset would desync the peer. fixpp wires this onto its **existing `013` reset primitive and `reset_seqnum_policy_field`**: the knob-driven reset emits `141=Y`, and the `013` policy (`bilateral_strict`/`bilateral_lenient`/`unilateral`) then governs how the peer's `141` echo is validated. On the acceptor (inbound-Logon) path the knob reset and the received-`141=Y` reset are collapsed into ONE combined pre-validation decision — `need_logon_reset = reset_on_logon || peer_sent_reset` → a single `reset_seqnums_to_one_durable()` before `check_inbound`, with the stricter applicable disposition (knob-driven → fatal; 013-only received-`141` → I-07 logged-then-proceed). The sequence-number **result** is `{1,1}` regardless, but the durable `MessageStore::reset()` fires **exactly once** (it is not a value no-op — `FileStore::reset()` does full fsync I/O every call; see FR-009 / contract C2.2).
- Q: Config-key naming for the knobs (008 `cfg_loader` QuickFIX-config parity)? → A: **Mirror QuickFIX exactly for NAMING.** The QuickFIX/J config-key spellings — `ResetOnLogon`, `ResetOnLogout`, `ResetOnDisconnect` — inform the field naming so a future `cfg_loader` mapping is 1:1. **This slice does NOT parse those keys in the `008` `cfg_loader`**: the current loader (`src/session/quickfix_compat/cfg_loader.cpp`) extracts only `FileStorePath`/`SenderCompID`/`TargetCompID` and parses no bool knobs. This slice delivers the C++ `SessionConfig` bool fields ONLY (house snake_case `reset_on_logon`/`reset_on_logout`/`reset_on_disconnect`, each defaulting to `false`); wiring the three cfg-keys into the `cfg_loader` is an explicit out-of-scope follow-up.
- Q: Scope — should this slice also deliver `RefreshOnLogon` (S-018)? → A: **No — descope `RefreshOnLogon` to its own later slice; 024 = S-017 ResetOn* only.** Phase-0 grounding (`session.cpp:1423` comment "seqnum_mgr_ starts at 1"; the sole `set_next_inbound` caller is the inbound `SequenceReset` handler at `:3663`, not a store-hydrate) confirmed fixpp's `SeqnumManager` is **never** seeded from the store at `open()`. `RefreshOnLogon` presupposes a store→manager hydrate-on-open path that does not exist, so it would require new plumbing at the `008` store-authority boundary (a likely Gate-A escalation and a much larger slice) — exactly the runaway-scope trap G3's small-slice discipline avoids. `ResetOnLogon/Logout/Disconnect` are a clean wire-in onto the existing `013` `reset_to_one()` primitive. **S-017 → done this slice; S-018 stays `backlog`.**

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Reset sequence numbers at Logon (Priority: P1)

An operator configures a session with `ResetOnLogon` on so that every new connection starts the FIX dialogue from `MsgSeqNum = 1` in both directions, regardless of any persisted sequence state. When the session logs on, fixpp resets both its next-expected (inbound) and next-to-send (outbound) sequence numbers to 1, persists that reset, and proceeds with a fresh sequence space — no spurious gap detection, no ResendRequest for the pre-reset range.

**Why this priority**: `ResetOnLogon` is the most widely-used of the three knobs (the canonical "every session starts at 1" deployment, common with counterparties that do not persist sequence state across the trading day). It is also the knob with the most subtle interaction surface (gap recovery, the `141` handshake), so it carries the highest correctness value and is implemented first.

**Independent Test**: Construct a session whose persisted next-expected and next-to-send sequence numbers are both > 1, with `ResetOnLogon` on; drive a Logon; assert both sequence numbers are 1 immediately after logon completes, the reset is persisted to the store, the session reaches `Active`, and no ResendRequest is emitted for the pre-reset range.

**Acceptance Scenarios**:

1. **Given** a session with `ResetOnLogon` on whose persisted next-expected = M and next-to-send = N (M, N > 1), **When** the session logs on, **Then** both the next-expected and next-to-send sequence numbers are reset to 1, the reset is persisted, and the session reaches `Active`.
2. **Given** a session with `ResetOnLogon` **off** (default), **When** the session logs on, **Then** no reset branch runs and the persisted sequence numbers are not rewritten (behavior byte/semantics-identical to today's sessions; note fixpp does not hydrate the live manager from the store at `open()` — the off case neither resets nor reloads, consistent with the `RefreshOnLogon` descope).
3. **Given** a session with `ResetOnLogon` on, **When** it logs on after a prior disconnect that left an apparent inbound gap, **Then** the reset suppresses the gap (sequence space starts fresh at 1) and **no** ResendRequest is issued for the pre-reset range.
4. **Given** a session with `ResetOnLogon` on, the behavior holds whether fixpp is the **initiator** (reset at outbound Logon — which therefore carries `ResetSeqNumFlag(141)=Y`, validated against the `013` `reset_seqnum_policy_field`) or the **acceptor** (reset on processing the inbound Logon, idempotent with any received `141=Y`).

---

### User Story 2 — Reset sequence numbers at Logout and at Disconnect (Priority: P2)

An operator configures `ResetOnLogout` and/or `ResetOnDisconnect` so the session's persisted sequence state returns to 1 when the session ends — either via a graceful Logout exchange (`ResetOnLogout`) or via any transport teardown including abnormal disconnects (`ResetOnDisconnect`). The next time the session is opened, it begins from a clean sequence space.

**Why this priority**: These teardown-time resets are the complement of `ResetOnLogon` and share the same single reset primitive, but they are lower-frequency in practice and have a narrower interaction surface (they fire at terminal/teardown, after the wire dialogue is over). Sequenced after US1.

**Independent Test**: Drive a session to `Active` with non-1 sequence numbers; trigger a graceful Logout (for `ResetOnLogout`) and, separately, an abrupt transport disconnect (for `ResetOnDisconnect`); assert the persisted sequence numbers are 1 after each teardown when the respective knob is on, and unchanged when off.

**Acceptance Scenarios**:

1. **Given** a session with `ResetOnLogout` on, **When** the session logs out (Logout sent **or** received → terminal), **Then** both sequence numbers are reset to 1 and the reset is persisted.
2. **Given** a session with `ResetOnDisconnect` on, **When** the transport is torn down by **any** disconnect (graceful Logout *or* an abnormal connection drop), **Then** both sequence numbers are reset to 1 and the reset is persisted.
3. **Given** a session with both `ResetOnLogout` and `ResetOnDisconnect` on, **When** a graceful Logout is followed by the consequent disconnect, **Then** the durable reset fires **at most once** per teardown (collapsed by the single-fire guard — the sequence-number result is already `{1,1}`, but the durable `MessageStore::reset()` is not a value no-op and must not run twice; see FR-009).
4. **Given** a session with both teardown knobs **off** (default), **When** the session ends by Logout or disconnect, **Then** the persisted sequence numbers are preserved (today's behavior).

### Edge Cases

- **`ResetOnLogon` drives `141=Y` on the initiator** (Clarifications): with `ResetOnLogon` on, the initiator's outbound Logon carries `ResetSeqNumFlag(141)=Y` (seqnums `{1,1}` after the reset); the local reset and the wire announcement are the *same* event, and the `013` policy validates the peer's echo. The local reset and a received `141=Y` MUST resolve to a **single** `{1,1}` reset — never a double-reset, never a direction left inconsistent.
- **`ResetOnLogon` and gap recovery**: a reset at Logon starts a fresh sequence space, so there is no pre-reset gap to recover; fixpp MUST NOT issue a ResendRequest for sequence numbers below the reset point.
- **`ResetOnDisconnect` on an abnormal drop (no Logout)**: the reset MUST still fire on a raw connection loss, not only on a graceful Logout (this is what distinguishes it from `ResetOnLogout`).
- **Reset idempotency**: applying a reset onto an already-`{1,1}` sequence state is a no-op; overlapping triggers (e.g. `ResetOnLogout` + `ResetOnDisconnect` on the same teardown) reset at most once observably.
- **All three knobs off (default)**: a session is behavior-identical to today's — no lifecycle reset; existing `013` `ResetSeqNumFlag(141)` behavior and every merged session are unaffected.
- **Both roles**: every knob's behavior MUST hold whether fixpp is the initiator or the acceptor.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `SessionConfig` MUST expose three additive per-session boolean knobs — `ResetOnLogon`, `ResetOnLogout`, `ResetOnDisconnect` — each defaulting to **off** (no-implicit-default per `[const §XII.5]`: each default is explicit and documented). With all three off, a session MUST be behavior-identical to today's (zero regression to existing `013` `ResetSeqNumFlag(141)` behavior and all merged sessions).
- **FR-002**: When `ResetOnLogon` is on, the session MUST reset both its next-expected (inbound) and next-to-send (outbound) sequence numbers to 1 at Logon — for the **initiator** when its Logon is sent/accepted, for the **acceptor** when it processes the inbound Logon — and MUST persist the reset to the message store before proceeding with the dialogue. On the **acceptor**, the reset (live manager + store) MUST run **before** inbound-Logon sequence validation (`check_inbound`), because in the handshake state a too-low sequence is fatal (disconnect); a reset that ran after `check_inbound` would let a fresh peer Logon `34=1` disconnect first when the local next-expected is > 1.
- **FR-003**: When `ResetOnLogon` is on, the logon-time reset MUST run **before** inbound-Logon sequence validation (`check_inbound`) so the fresh `{1,1}` space admits the peer's `34=1` Logon without a pre-reset gap. **Initiator**: the reset in `open()` precedes any inbound, so no pre-reset gap exists and no ResendRequest is emitted. **Acceptor**: the pre-validation reset (the reset MUST precede `check_inbound`, see FR-002) makes `check_inbound` see `next_inbound_==1`, so a fresh peer Logon `34=1` is admitted with **no too-low disconnect** and no ResendRequest — there is no ResendRequest path in the acceptor handshake state (a gap there is fatal), so "gap suppression" on the acceptor means "the pre-validation reset prevents the too-low disconnect," not "a ResendRequest is suppressed."
- **FR-004**: When `ResetOnLogout` is on, the session MUST reset both sequence numbers to 1 and persist the reset when it logs out (Logout sent or received → terminal).
- **FR-005**: When `ResetOnDisconnect` is on, the session MUST reset both sequence numbers to 1 and persist the reset on **any** transport disconnect/teardown, including an abnormal connection drop with no graceful Logout.
- **FR-006**: A config-knob reset MUST share the **same single reset primitive** as the existing `013` `ResetSeqNumFlag(141)` handshake reset (no parallel seqnum path). When both a knob reset and a `141=Y` handshake reset apply to the same Logon, the sequence space MUST be reset **once** (idempotent onto `{1,1}` — no double-reset, no direction left inconsistent).
- **FR-007**: Per the Clarifications coupling decision, the **initiator**'s outbound-Logon `ResetSeqNumFlag(141)=Y` emission predicate MUST be `send_reset_flag || ((reset_on_logon || reset_on_logout || reset_on_disconnect) && seqnums == {1,1})` — i.e. all three reset knobs OR together, gated on both sequence numbers being `{1,1}` (matching QuickFIX-cpp `shouldSendReset()` `Session.cpp:1037` and QuickFIX-J `isResetNeeded()` `Session.java:919`, which both OR the three knobs). The `reset_on_logout`/`reset_on_disconnect` arms matter because a session with one of those knobs that reset to `{1,1}` at a **prior teardown** MUST announce that reset with `141=Y` on its **next** initiator Logon — QuickFIX does, so omitting it desyncs the peer (which sees `34=1` with no `141=Y` and may reject/ResendRequest). The existing `013` `reset_seqnum_policy_field` MUST then govern validation of the peer's `141` echo (`bilateral_strict` requires the echo; `bilateral_lenient`/`unilateral` per `013`). The **acceptor** MUST reset on a received `141=Y` (per `013`) and when `ResetOnLogon` is on — collapsed into ONE combined pre-validation decision (`need_logon_reset = reset_on_logon || peer_sent_reset`) so the result is a single `{1,1}` with exactly one observable `store_->reset()` I/O (`FileStore::reset()` being non-idempotent I/O).
- **FR-008**: Every reset MUST go through the existing `SeqnumManager` + `MessageStore` reset/persist primitives — no new sequence-number storage, no new error slot, and no new codegen are introduced; the reset MUST be durable (persisted) so a subsequent open observes the reset value.
- **FR-009**: A reset applied onto an already-`{1,1}` sequence state leaves the sequence-number **result** unchanged. Note the durable store reset (`MessageStore::reset()`) is **not** a value no-op — `FileStore::reset()` performs a full atomic-rename + fdatasync + dir-fsync on every call regardless of the current counter value. Therefore overlapping lifecycle triggers on a single teardown (e.g. `ResetOnLogout` + `ResetOnDisconnect`) MUST be guarded by a **single-fire** flag (a "reset already done this teardown" guard in `close()`) so the durable reset fires **at most once** per teardown — not merely "the sequence result is idempotent." The witness MUST assert exactly one observable store-reset per teardown.
- **FR-010**: All three knobs MUST behave identically whether fixpp is the initiator or the acceptor, and MUST interop cleanly with live QuickFIX-cpp v1.16.0 and QuickFIX-J 3.0.1 counterparties in both roles.
- **FR-011**: This feature MUST complete catalogue row **S-017** (`ResetOnLogon/Logout/Disconnect`), flipping it `backlog → done`. Catalogue row **S-018** (`RefreshOnLogon`) is explicitly **out of scope** and stays `backlog` (see Clarifications — deferred pending a store→manager hydrate-on-open path).

### Key Entities

- **Lifecycle reset knob** (`ResetOnLogon` / `ResetOnLogout` / `ResetOnDisconnect`): an additive `SessionConfig` boolean (default off) naming a lifecycle event at which the session resets both its inbound and outbound sequence numbers to 1 via the existing reset primitive, persisting the reset. On the initiator, an enabled reset knob makes the outbound Logon carry `ResetSeqNumFlag(141)=Y` (the wire announcement of the reset; see FR-007).
- **Durable reset helper** (`reset_seqnums_to_one_durable(disposition)`, this feature): wraps the existing two operations — `SeqnumManager::reset_to_one()` (mutates live counters) **then** `MessageStore::reset()` (durable persist) — with a store-failure disposition keyed on the **trigger cause**, NOT the trigger location: a **knob-driven** Logon reset (`reset_on_logon == true`) is **fatal** (a store-reset failure prevents reaching `Active` — propagate); the existing **013-only received-`141`** reset (all 024 knobs off) keeps its current **logged-then-proceed (I-07)** disposition UNCHANGED so all-off is byte/semantics-identical (FR-001); the **teardown** path is logged-then-proceed (I-07). On the acceptor Logon path the knob reset and the received-`141` reset are collapsed into ONE combined pre-validation decision (`need_logon_reset = reset_on_logon || peer_sent_reset`) with the stricter applicable disposition. The underlying `reset_to_one()` + `MessageStore::reset()` pair is the existing `013` `ResetSeqNumFlag(141)` handshake primitive; this feature adds new *triggers* + the durable-helper coupling, not a new seqnum path. Note `MessageStore::reset()` (`FileStore::reset()`) is NOT a value no-op — it does full atomic-rename + fdatasync + dir-fsync on every call — so the acceptor Logon overlap (single combined decision) and teardown double-triggers (single-fire guard) each collapse to one observable store reset (FR-009).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: With `ResetOnLogon` on, 100% of Logons from a session with non-1 persisted sequence numbers leave both sequence numbers at 1 (persisted), reach `Active`, and emit no ResendRequest for the pre-reset range.
- **SC-002**: With `ResetOnLogout` on, 100% of logouts, and with `ResetOnDisconnect` on, 100% of disconnects (graceful or abnormal), leave the persisted sequence numbers at 1.
- **SC-003**: With all three knobs off, a session's wire behavior and persisted sequence state are byte/semantics-identical to the pre-feature baseline (zero regression), including the existing `013` `ResetSeqNumFlag(141)` flows.
- **SC-004**: An initiator with `ResetOnLogon` (or `ResetOnLogout`/`ResetOnDisconnect`) on emits `ResetSeqNumFlag(141)=Y` on its outbound Logon in 100% of cases where seqnums are `{1,1}`, and a reset coincident with a received `141=Y` resets the sequence space exactly once (no double-reset, no inconsistent direction).
- **SC-005**: fixpp interops cleanly with QuickFIX-cpp v1.16.0 and QuickFIX-J 3.0.1 across the three-knob scenarios in both initiator and acceptor roles (live interop cells green under normal + sanitizer builds), and catalogue row S-017 is flipped `done`.

## Assumptions

- **FIX 4.4 session-only scope** (interop matrix option (a)). `RefreshOnLogon` (S-018), `CheckCompID=N`, `validateSequenceNumbers=N`, `MaxLatency/CheckLatency`, `NextExpectedMsgSeqNum(789)`, FIXT.1.1 / FIX 5.0 SP2 routing are separate later slices and out of scope here.
- **`RefreshOnLogon` (S-018) descoped** (resolved by Clarifications) — fixpp's `SeqnumManager` is never seeded from the message store at `open()` (always starts at 1; `FileStore` persists counters but nothing reloads them into the live manager). A meaningful refresh needs a store→manager hydrate-on-open path fixpp lacks, which would be a larger architecture-touching change at the `008` store boundary. Deferred to its own slice; **S-018 stays `backlog`**.
- **Coupled to `ResetSeqNumFlag(141)`, NOT independent** (resolved by Clarifications) — the `013` `reset_seqnum_policy_field` (wire-handshake *validation* policy) is unchanged, but the reset knobs are wired onto the **same `013` reset primitive** and, on the initiator, **drive `141=Y` emission** when seqnums are `{1,1}` (both QuickFIX-cpp and QuickFIX-J do this; a purely-local reset would desync the peer). The `013` policy then validates the peer's `141` echo. The C++ `SessionConfig` fields are house snake_case (default `false`); their naming mirrors the QuickFIX cfg-keys (`ResetOnLogon`/`ResetOnLogout`/`ResetOnDisconnect`) so a future `cfg_loader` mapping is 1:1, but **this slice does not add those keys to the `008` `cfg_loader`** (it parses only `FileStorePath`/`SenderCompID`/`TargetCompID` today) — cfg-key parsing is a follow-up.
- **Existing machinery is reused** — the `SeqnumManager::reset_to_one()`, the `MessageStore::reset()`, the `005`/`009` Logon-complete / Logout-terminal / disconnect FSM transition points, and the `013` reset primitive (with its `141=Y` emission path) already exist. This feature adds three additive `SessionConfig` booleans (default off) and wires them as triggers at the existing transition points. **No new persistent store, codegen, error slot, or wire field is anticipated** (the `141` field is already emitted by `013`).
- **No-implicit-default** (`[const §XII.5]`): all three knobs default to off (QuickFIX-compatible), making the feature a pure-additive no-op for every existing session unless an operator opts in.
- **Tests-grounded** — each knob ships RED-first witnesses asserting its named post-condition directly (sequence number == 1 after the event when on; unchanged when off; initiator emits `141=Y`), per `[[feedback_witness_asserts_named_postcondition_not_proxy]]`. Each knob is independently testable.
