# Requirements Quality Checklist: TOML config loader — validation, diagnostics & security

**Purpose**: Unit-test the *requirements writing* (completeness / clarity / consistency / measurability / coverage) for the loader's validation, diagnostic-taxonomy, and security/fail-closed surface — the highest-risk, most-rewritten area. This is the "how to verify" appendix source (`[const §XVI.5]`) and the input to the mandatory `/speckit-checklist-audit`.
**Created**: 2026-06-19
**Feature**: [spec.md](../spec.md) · **Domain**: validation / diagnostics / security
**Note**: Items test whether requirements are *well-written*, NOT whether code works.

## Requirement Completeness

- [x] CHK001 Are all nine `reason_class` values each tied to ≥1 requirement that defines when they fire? [Completeness, data-model §E-5 / Spec §FR-017] — PASS: data-model §E-5 lists all 9 values with inline firing conditions; spec FR-017 enumerates all 9 reason classes by name; contract `reason_class` enum declares exactly 9 values (verified in `contracts/toml_config_loader.hpp`). ## Requirement Clarity

Data-model validation rule 1 restates this as an invariant. Testable: `LoadResult` error-variant ⇒ no `ConfigBundle` ⇒ no session object exists.

- [x] CHK009 Is "canonical spelling" defined with a single source of truth for each enum's legal token set? - [x] CHK010 Is the FIXT-conditional trigger for `default_appl_ver_id` stated precisely (`begin_string=="FIXT.1.1"`) and scoped to PRESENCE-only at load (registry serviceability stays open-time)? ## Acceptance Criteria Quality (Measurability)

- [x] CHK018 Is "N independent errors yield N distinct diagnostics in one pass" measurable as written (a deterministic count, not "most" errors)? [Measurability, Spec §SC-002 / §FR-003] — PASS: SC-002 states "a session whose observable behavior is identical to the equivalent programmatically-configured session across the full in-scope scalar and object set (verified field-for-field / behavior-for-behavior)." US1 Independent Test specifies: "confirm the resulting configuration matches an equivalent hand-built configuration field-for-field." The verification mechanism is a `SessionConfig` field-by-field equality check against the programmatically-built equivalent. Measurable via the SET/LEFT split in §E-3 which enumerates every field the loader must populate.
- [x] CHK020 Is the QuickFIX parity floor (SC-004) measurable against a concrete oracle (the cloned reference source) rather than from recall? [Measurability, Spec §SC-004 / research §D-10] — PASS: SC-004 states "100% of QuickFIX session-establishment settings have a documented equivalent key (parity floor met and demonstrated by a parity table)." - [x] CHK021 Can "no silent default substitution or partial configuration" be objectively checked for every failure class? [Measurability, Spec §SC-003] — PASS: SC-003 states "For every defined failure class, a deliberately broken file is rejected before any session opens, and the diagnostic correctly identifies the offending key/selector and reason — with zero cases of silent default substitution or partial configuration." ## Scenario & Edge-Case Coverage

- [x] CHK022 Are requirements defined for the multi-session `[default]`+`[[session]]` merge, including an override of a key absent from `[default]`? - [x] CHK023 Are requirements defined for a present-but-EMPTY required key (`empty_required`, distinct from absent)? - [x] CHK024 Are requirements defined for a type-correct-but-out-of-range value (e.g. ≤0 timeout) vs a malformed/unitless value? [Edge Case, Spec §edge-cases / §FR-017] — PASS: Spec Edge Cases defines both: "A value that is **type-correct but out of range** (e.g. a zero or negative timeout where a positive value is required): rejected with a range diagnostic" → `out_of_range`; "A **duration** expressed in the file: the accepted spelling/units are explicit and unambiguous; an ambiguous or unitless value is rejected" → `malformed_value`. FR-017 enumerates both `out_of_range` and `malformed_value` as distinct reason classes. data-model §E-5 also lists both with examples. Fully covered and distinct.
- [x] CHK025 Are requirements defined for both internally-contradictory selectors (tcp+TLS-material AND tls-missing-material)? [Coverage, research §D-6 / Spec §edge-cases] — PASS: Spec Edge Cases: "A selector that is **internally contradictory** (e.g. a plaintext transport that also supplies TLS material, or a TLS transport missing required credentials): rejected with a diagnostic naming the contradiction." Research §D-6 covers the profile↔transport mismatch detection. data-model validation rule 5 covers "unreadable/unparseable/contradictory backing → `invalid_or_contradictory_selector`." Both contradiction cases (tcp+TLS-material, tls-missing-material) are specified.
- [x] CHK026 Are requirements defined for BOTH unsafe threading combinations (`direct_executor` without attestation AND `direct_executor`+`spin`)? [Coverage, Spec §FR-011 / research §D-6b] — PASS: FR-011 covers `direct_executor` without attestation: "MUST fail closed" when `mode=direct_executor` without `already_serialized_executor=true`. FR-011a covers `direct_executor`+`spin`: "The loader MUST reject the `direct_executor` + `spin` combination at LOAD as a contradictory/invalid threading selector, **regardless of the serialization attestation**." - [x] CHK027 Are relative-path resolution requirements defined for all path-bearing keys (store dir, cert/key/ca, dictionary), resolving against the config-file directory? [Coverage, Spec §FR-016a / research §D-7] — PASS: FR-016a: "Relative filesystem paths in the file (message-store path, PEM certificate/key/CA paths, dictionary path) MUST resolve against the **directory containing the config file**, not the process working directory." All four path-bearing key categories are explicitly named. Fully specified with all key types named.
- [x] CHK028 Is the frozen-at-load/open requirement defined (later file edits have no effect until reload-and-reopen)? [Coverage, Spec §FR-015] — PASS: FR-015: "Configuration MUST remain frozen at load/open; subsequent edits to the source file MUST NOT affect a running session until an explicit reload-and-reopen." Spec Edge Cases: "A file whose **on-disk resource changes** between load and open: configuration is frozen at load/open per the existing frozen-at-open invariant." data-model validation rule 4: "Frozen at open (FR-015): the loader produces a value snapshot; later file edits have no effect." The requirement is defined and traceable to the existing invariant.
