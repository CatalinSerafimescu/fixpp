## `extra_paths`: values and resolution

- [ ] CHK001 Does "resolved and loaded as `path` is" pin every rule that applies to `path`: the base directory, format detection through `dict::load_any`, and a non-regular file? A reviewer has to be able to compare the two without reading the loader. [Clarity, Spec §FR-017, contracts surface.md (TOML), research R-12]
- [ ] CHK002 Is `extra_paths = []` specified, and is it stated to behave as an absent key, so that W-14's "bundle identical" reaches it? [Edge Case, Gap, contracts surface.md (TOML), contracts W-14]
- [ ] CHK003 Is an entry that repeats `path`, or another entry, specified: loaded twice, de-duplicated, or refused? NFR-003 counts distinct dictionaries by pointer, so two loads of one file are two walks. [Edge Case, Gap, Spec §FR-017, Spec §NFR-003]
- [ ] CHK004 What answers when an extra has the same version as `path`, or as another extra? E-1a's "last writer wins" moves the registry slot, and FR-017 says the session dictionary stays the `path` file. Is the resulting split stated per session? [Consistency, Spec §FR-002, Spec §FR-017, data-model E-1a]
- [ ] CHK005 Is every `kind` case specified for a `[dictionary]` that also carries `extra_paths`? "`kind` other than `path` is refused as today" can be read as the whole table being refused, or only `kind`, with the key then ignored. [Clarity, contracts surface.md (TOML)]
- [ ] CHK006 W-14 has a T shape from TOML, so `path` may name `FIXT11.xml` and `engine.dictionaries.front()` may be a dictionary with no application version. Is it stated that nothing reading `front()` assumes an application dictionary? [Assumption, contracts W-14, research R-12]
- [ ] CHK007 One TOML file can carry FIXT and non-FIXT sessions over one `[dictionary]`. Is it stated that `extra_paths` leaves a non-FIXT session's route and validation unchanged, and is that part of SC-005's claim? [Coverage, Spec §FR-017, Spec §SC-005]
- [ ] CHK008 Does the bundle show the whole TOML for US5 scenario 3? The surface's snippet has `[dictionary]` only, and the scenario also needs `begin_string`, `default_appl_ver_id` and `validate_inbound_messages` on the session. Is it stated that those keys already exist and take the values this feature expects, FIX Latest's among them? [Completeness, Spec US5, contracts surface.md (TOML)]

## `register_session` and `open()` refusals

- [ ] CHK017 Do FR-004, ruling 2, US3 scenario 5 and surface.md give registration the same scope? FR-004's first sentence speaks of "no transport dictionary", while E-9's shared check also refuses no default and a slot miss on a validating config. - [ ] CHK021 Is it stated which error `register_session` returns for a config that is both a duplicate `SessionId` and fails the check, so the ending is one? [Edge Case, Gap, Spec §FR-004, data-model E-9]
- [ ] CHK022 Do the requirements say whether a host can learn which clause refused it, by a message or a log line? All four clauses return one `invalid_session_config`. [Clarity, Spec §FR-004, data-model E-9]
- [ ] CHK023 Is "before any observable effect" defined per caller, as a measurable list? W-8 has `never_opened` and no registry entry. Are the reader snapshot, published endpoints and a build already performed on a retry covered? [Measurability, Spec §FR-004, contracts W-8]
