- [x] CHK007 Is "clean teardown" / "no leaked work" quantified (named sanitizer matrix + second-stop no-op), not left qualitative? - [x] CHK008 Is the read-pump guarantee "in arrival order, on the session strand, exactly once" expressed as objectively-testable acceptance criteria? - [x] CHK009 Is the backpressure model (natural — synchronous `co_await on_inbound_frame`, NO inbound queue) stated, so "continuously read" cannot be misread as buffering/queueing? [Ambiguity, Spec §FR-004] — PASS: spec §US2 "Why this priority" note explicitly states: "Scope note: 015 has no user sink for inbound *application* messages." US2 Independent Test note states the read-pump "delivers every frame to `Session::on_inbound_frame`." research.md R3 states "Backpressure is natural — the pump co_awaits on_inbound_frame synchronously and does not read the next chunk until the session has consumed the current frame, so there is no unbounded inbound queue." realized-behavior C2 shows the code structure with the natural co_await backpressure and states "Backpressure is natural — the pump does not read the next chunk until on_inbound_frame completes; there is no inbound queue." The no-queue model is stated in the design contracts. While spec.md FR-004 says "continuously read," the Clarifications section and US2 together establish the no-queue model unambiguously.
- [x] CHK010 Is the distinction between the acceptor attach primitive (sets `live_peer_id_` + rebinds outbound, NO FSM transition) and the initiator-only `install_reconnected_transport` (re-enters `LogonSent`) stated as a requirement constraint, not only design narrative? [Clarity, Spec §Clarifications] — PASS: spec §Clarifications (Gate A round 1) bullet 2: "Attach uses a **new acceptor-specific primitive** (design-named `attach_accepted_transport`) that sets `live_peer_id_` + rebinds outbound **without** an FSM transition — NOT `install_reconnected_transport`, which re-enters `LogonSent` (initiator-only)." FR-005 normative: "the accept loop runs `async_handshake` and harvests `handshake_result.peer_id`, then resolve the matching session and feed the live byte stream into it." data-model E-2 (requirements design record) states the NOT constraint explicitly: "NOT `install_reconnected_transport` — that re-enters `LogonSent` (initiator-only) and would mis-drive the acceptor." This is a requirement constraint (not just narrative), and it is stated in the normative Clarifications section as a "resolved decision."

## Requirement Consistency

- [x] CHK011 Is the "no new disposition" requirement (FR-012) consistent with the read-pump EOF/read-error behavior (pump stops; session uses its existing disconnect handling) so no new state is implied? [Consistency, Spec §FR-012/§US2 AC2] — PASS: FR-012: "The engine MUST NOT alter the established disposition rules: the open-path acceptor Logon failure stays terminal fail-CLOSED (013); the initiator reconnect-path authorization failure stays retry-to-cap (014). 015 adds no new disposition." These are fully consistent — no new state/disposition is implied anywhere.
- [x] CHK012 Do the idempotent-stop requirement (FR-011) and the SC-005 second-stop-no-op outcome reference one mechanism (the `stopped` flag) without divergent wording? - [x] CHK013 Is the "no engine-owned worker threads / caller drives the executor" model consistent across FR-001, FR-003, and the Assumptions, with no requirement implying an internal thread? [Consistency, Spec §FR-001/§FR-003/§Assumptions] — PASS: FR-001: "The engine MUST run on a **caller-supplied asio executor** (e.g. an `io_context`) and MUST NOT own or spawn worker threads; the caller drives the executor." FR-003: "launched on the caller-supplied executor" — no thread spawning implied. §Assumptions: "the engine binds to a caller-supplied asio executor (e.g. an io_context) and owns no worker threads; start() is non-blocking (launches loops and returns); stop() is idempotent and cancellation-safe."
