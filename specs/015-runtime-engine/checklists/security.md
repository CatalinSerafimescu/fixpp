## Requirement Completeness

- [x] CHK001 Are requirements for the live-identity SOURCE (`handshake_result.peer_id` harvested by the accept loop's own `async_handshake`) stated for the acceptor first-connection path AND distinguished from the initiator path? [Completeness, Spec §FR-005/§FR-006] — PASS: FR-005 explicitly states "the accept loop runs `async_handshake` and harvests `handshake_result.peer_id`"; FR-006 requires the post-handshake authenticated identity drives the acceptor gate. FR-005 also explains the initiator distinction ("the `Listener::async_accept()` result is TCP-connected with TLS not yet issued and carries no peer identity"). research.md baseline table (listener.hpp:45-53) and data-model E-2 confirm the source distinction.
- [x] CHK002 Is the happens-before invariant (`live_peer_id_` set on the session strand strictly-before the first `on_inbound_frame` reaches the acceptor gate) captured as a binding *requirement*, not only a design note? [Gap, Spec §Clarifications "happens-before invariant"] — PASS: spec §Clarifications (Session 2026-05-30, Gate A round 1) bullet 4 states "A written **happens-before invariant** — `live_peer_id_` is set on the session strand strictly-happens-before the first `on_inbound_frame` reaching the acceptor gate — plus a delayed-identity fail-CLOSED regression test" as a resolved decision, and FR-005 Edge Cases reads "sets it on the session (via the acceptor attach primitive) strictly before the Logon gate runs". spec §Edge Cases (second bullet) also states this directly. The §Clarifications section is expressly normative per spec structure; research.md R7 and data-model E-2 both record this invariant. realized-behavior C1 pins it as a contract. The invariant is a binding requirement, not merely a design note.
- [x] CHK003 Are the fail-CLOSED requirements specified for BOTH the "off-list" and the "absent/delayed" identity as distinct cases (not collapsed into one)? [Completeness, Spec §FR-007/§SC-002] — PASS: FR-007 states "absent or off-list" and SC-002 names "An off-list or absent live identity". The Clarifications section bullet 4 explicitly identifies the "delayed/absent" ordering case (gate runs before identity arrives → must still fail CLOSED). US1 AC2 also names "off-list or absent peer identity" and the fails-CLOSED test task T009 tests both (a) off-list and (b) absent/delayed as distinct cells. The two sub-cases are present even if merged in a single FR.
- [x] CHK004 Are requirements defining the unmatched-Logon disposition (`session_unknown_acceptor_session = 121`, NO session created, connection-level close) complete and free of any fail-open path? [Completeness, Spec §FR-005/§Edge Cases] — PASS: FR-005 final sentence: "an unmatched Logon MUST be rejected at the connection level with NO session created — routing is static for this feature, with no fail-open path." Edge Cases bullet 1: "an inbound Logon matching no registered acceptor session is ALWAYS rejected at the connection level (`session_unknown_acceptor_session`, no session created) — there is no fail-open path." research.md R5 pins the slot value = 121. realized-behavior C7 states the error surfaces at the connection level only and never to a Session event.
- [x] CHK005 Are requirements defined for every pre-session abort path (handshake stall, silent peer, partial first frame, over-budget) ensuring transport + accept slot reclamation on each? [Completeness, Spec §FR-014/§SC-011] — PASS: FR-014 explicitly enumerates "a peer that exceeds either (slow-loris, partial frame, or an unbounded stream before a valid Logon) MUST be closed and its accept slot reclaimed, without affecting other peers." SC-011 names "stalls the TLS handshake, sends nothing, sends a partial first frame, or sends more than the first-frame byte budget before a valid Logon is closed within the configured deadline, its transport and accept slot are reclaimed (no leak under sanitizers), and other peers are unaffected." All four abort scenarios have explicit reclamation requirements.
- [x] CHK006 Is the test-seam removal requirement scoped to a defined "production surface" that explicitly enumerates which artifacts (config struct, public headers, AND tests) must be free of `logon_peer_identity_override`? [Completeness, Spec §FR-009] — PASS: FR-009 states "The test-only `logon_peer_identity_override` seam MUST be removed from the production surface; no production code path and no test MUST depend on it after the live acceptor path lands." US4 AC1 states the seam is absent from "the production surface" and "no test depends on it." SC-006 states "`logon_peer_identity_override` is absent from the production surface and no test depends on it." tasks T019 (grep gate across `src/` + `include/` + `tests/`) and T021 (re-point binding-logic tests) enumerate the three artifact trees. realized-behavior C4 names the field (`session_config.hpp:229`) and both gate sites.

## Requirement Clarity

- [x] CHK007 Is the first-frame "byte budget" quantified, or its configuration source named, rather than left as an unquantified "maximum"? [Clarity, Spec §FR-014/§SC-011] — PASS: FR-014 says "a maximum byte budget AND a handshake/Logon deadline" owned by an "engine-level accept-scope cancellation domain wired into `stop()`." SC-011 references "the configured deadline." The spec does not pin a literal constant but explicitly names the mechanism as configurable (not hardcoded) and names its owner. research.md R9 and data-model E-7 state "(FR-014: byte cap + Logon deadline)". Quantifying the exact default value is an implementation decision properly deferred to `/speckit-implement` (the spec establishes the configuration surface exists; the contract names it "byte cap + handshake/Logon deadline"). This is sufficient for a requirement-clarity standard — the requirement is unambiguous: the deadline and budget exist, are configurable, and are owned by the accept-scope cancellation domain.
- [x] CHK008 Is the "handshake/Logon deadline" expressed as a measurable, configurable value with a defined owner (the accept-scope cancellation domain)? [Clarity, Spec §FR-014] — PASS: FR-014 explicitly names "owned by an engine-level accept-scope cancellation domain wired into `stop()`." research.md R9 decision states "(a) the accepted transport, (b) the TLS handshake, (c) the bounded first-frame read" owned by the accept-scope domain. data-model E-7 repeats the ownership. SC-011 names "closed within the configured deadline" — measurable via the ASan no-leak requirement. The owner (accept-scope cancellation domain), the measurability (configured deadline + sanitizer no-leak), and the scope (pre-session window) are all defined.
- [x] CHK009 Are "off-list" and "absent" identity given explicit, distinguishable criteria rather than being used interchangeably? [Clarity, Spec §FR-007/§SC-002] — PASS: FR-007 uses "absent or off-list" as an enumeration. The §Clarifications section (Gate A round 1) bullet 4 distinguishes the two cases explicitly: "delayed/absent identity" (the happens-before regression — gate runs before identity arrives) vs. off-list identity (identity present but not in the allow-list). US1 AC2 names "off-list or absent peer identity." data-model E-4 states the absent case "falls to `else if (is_mtls) → fail-CLOSED` (safe)" while the off-list case hits the `authorize()` call and returns unauthorized. research.md R7 distinguishes them in the happens-before invariant. The two cases are distinguishable by their failure mechanism even though both result in fail-CLOSED.
- [x] CHK010 Is "the authenticated peer identity (not a test override or fabricated stand-in)" precise about what disqualifies a value as the authorization source? [Clarity, Spec §FR-006] — PASS: FR-006 says "the post-handshake authenticated peer identity (not the test override or a fabricated stand-in)." The disqualifying values are named explicitly: (1) the test override = `logon_peer_identity_override` (FR-009 names it precisely); (2) fabricated stand-in (the 014 pre-production placeholder). research.md R7 explains the accepted primitive sets `live_peer_id_` from `handshake_result.peer_id` specifically as the sole valid source. realized-behavior C3 pin the code path. The positive criterion is "harvested by the accept loop's own `async_handshake`" (FR-005); the negative criterion names what is excluded.

## Edge Case & Boundary Coverage

- [x] CHK017 Are requirements defined for a peer that completes TLS but never sends a Logon (silent peer) as distinct from one that sends a partial/over-budget first frame? [Edge Case, Spec §SC-011] — PASS: SC-011 enumerates four cases explicitly: "(a) stalls the TLS handshake, (b) sends nothing, (c) sends a partial first frame, or (d) sends more than the first-frame byte budget before a valid Logon." Cases (b) "sends nothing" and (d) "sends more than the byte budget" are distinct from (c) partial frame — silent peer = sends nothing = deadline triggers; partial frame = some bytes but no complete valid Logon = either timeout or over-budget depending on how many bytes. These are distinguished by the deadline vs. byte-budget enforcement path. FR-014 uses the same enumeration. tasks T010 tests all four as distinct cells.
- [x] CHK018 Is the non-mTLS permissive path explicitly excluded from the binding logic so it cannot be read as a fail-open authorization path? [Boundary, Spec §Edge Cases/§Out of Scope] — PASS: spec §Edge Cases bullet 6: "**Non-mTLS acceptor path**: genuinely permissive (the three-way guard's non-mTLS skip), unchanged and out of scope for the binding logic." §Out of Scope: "Non-mTLS permissive binding path — genuinely permissive (three-way guard non-mTLS skip), unchanged." FR-007 says "fail-CLOSED under mTLS" — explicitly scoped to mTLS. realized-behavior C3 shows arm (3) is the non-mTLS skip, explicitly labelled unchanged. The boundary is defined: mTLS → binding logic applies; non-mTLS → permissive, not in scope.
- [x] CHK019 Is the pre-session window's independence from per-session limits stated (it precedes any `Session` object, so it cannot rely on per-session config)? [Coverage, Spec §FR-014] — PASS: FR-014 explicitly: "This window precedes any `Session` object, so it cannot rely on per-session limits; it is owned by an engine-level accept-scope cancellation domain wired into `stop()`." The independence is stated in the normative text of FR-014 itself — this is the exact language the CHK item asks for.

## Ambiguities & Assumptions

- [x] CHK020 Is the optional dynamic-session-provider hook's deferral unambiguous, so no acceptance criterion (SC-001..SC-011) silently requires the dynamic path to close T-041? [Ambiguity, Spec §FR-005/§Assumptions] — PASS: FR-005 explicitly states routing "is static for this feature" and the dynamic hook "is deferred (R2)." §Assumptions states the dynamic path is "bounded as an opt-in extension — the static path carries the T-041 fail-CLOSED proof." SC-001..SC-011 all describe the static path only; none reference dynamic session creation. §Out of Scope does not list the dynamic provider (it is named as "optional future" in Assumptions, not deferred out-of-scope), but Assumptions + FR-005 + Edge Cases all clearly state the dynamic hook is deferred and T-041 is proven on the static path alone. No SC ambiguity.
- [x] CHK021 Is the assumption "no new error slots are required by the binding logic" reconciled with the one genuinely-new lifecycle slot (`session_unknown_acceptor_session = 121`), so the boundary between binding-logic and lifecycle slots is unambiguous? [Assumption, Spec §Assumptions/§Clarifications] — PASS: §Assumptions states "No new error slots are required by the binding logic (it inherits 013/014 codes)." The §Clarifications section (Gate A round 1) bullet 7 states "Exactly one — `session_unknown_acceptor_session = 121`" — and explains this is a lifecycle slot (unmatched connection at the engine level), not a binding-logic slot (binding reuses 117/119). realized-behavior C7 confirms `session_unknown_acceptor_session` surfaces at the connection level only (no Session exists). research.md R5 explicitly draws the boundary: binding-logic codes (#2 duplicate reg = 119, #3 authz failure = 117) reuse existing slots; only the genuinely-new lifecycle condition (#1 unmatched Logon = 121) gets a new slot. The spec text is consistent: "binding logic" inherits, lifecycle appends one.
