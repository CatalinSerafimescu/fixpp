# Recovery-Interaction Requirements Checklist: Persistent seqnum hydrate

**Purpose**: Validate that the requirements governing how the resumed seqnum state interacts with the Logon-path seqnum gate, the received-reset (`141=Y`) / `reset_on_logon` arms, the `789` next-expected advertisement, and the post-GapFill recovery precondition are complete, clear, and non-contradictory. This is the RC-1 surface the round-1 design could not satisfy.
**Created**: 2026-06-09
**Feature**: [spec.md](../spec.md) · [contracts/seqnum-hydrate.md](../contracts/seqnum-hydrate.md) · [research.md](../research.md)

## Logon-Gate vs Steady-State Gate (the RC-1 model)

- [x] CHK001 Does the spec distinguish the **Logon-path** seqnum gate (acceptor `NotConnected` `:1596` / initiator `LogonSent` `:2841`, which fatals on too-high with NO ResendRequest arm unless 789) from the steady-state Active gate (which enters AwaitingResend)? Is this distinction stated as a requirement constraint, not buried in rationale? [Clarity, FR-009 / research §RC-1 / spec Edge Cases] — PASS: FR-009 states the Logon-path gate constraint as a requirement: "Recovery of a too-high peer Logon without a fatal is bounded by the Logon-path gate: it succeeds via the existing 013/027 sub-protocol only when enable_next_expected_msg_seq_num is enabled or the peer Logon announces a reset"; spec Edge Cases §"Counterparty ahead after restart" explicitly states "the post-restart peer Logon is validated by the Logon-path seqnum gate (acceptor NotConnected / initiator LogonSent), which fatals on too-high unless enable_next_expected_msg_seq_num (789) is enabled — there is no ResendRequest arm on the Logon path (only the steady-state Active path enters AwaitingResend)". Stated as a requirement constraint with the line anchors (:1596/:2841), not buried in rationale.
- [x] CHK002 Is the requirement that a resumed (hydrated) `next_inbound` MUST NOT pre-empt a peer reset Logon into a too-low fatal at `:1615` stated explicitly, with the failing-without-it scenario named? [Completeness, FR-010 / INV-H5 / W9b] — PASS: FR-010 states "The existing inbound ResetSeqNumFlag(141) handling and the 024 acceptor cause-dependent reset split MUST be preserved — hydrate establishes the resume baseline but MUST NOT mask, reorder, or suppress the received-reset path"; spec Edge Cases §"Counterparty resets (141=Y)" states "the resumed next_inbound MUST NOT pre-empt a peer reset Logon into a too-low fatal (FR-010)"; INV-H5 states "hydrate never lets a resumed next_inbound pre-empt a peer reset Logon and fatal it as too-low"; research D-6 names the failing scenario: "a hydrated next_inbound=37 makes a peer reset Logon 34=1,141=Y return session_seqnum_too_low at :1596 and the handler disconnects at :1615 — before the 013-only received-141 reset arm at :1760 can run". Both the requirement and the failure scenario are named.
- [x] CHK003 Is the inbound-seed **withhold-on-reset-Logon** condition specified precisely — withhold when the header pre-scan shows `141=Y` OR `reset_on_logon`, apply otherwise — and is the placement requirement (after the pre-scan `:1585-1587`, before `check_inbound` `:1596`) stated consistently across spec/plan/contract? [Consistency, C2.4 / C2.5 / research D-6] — PASS: C2.4 specifies "Apply the inbound seed only on the non-reset Logon branch — when the header pre-scan shows the peer is announcing a reset (141=Y) or reset_on_logon is set, the inbound seed is withheld so check_inbound sees the construction value (1) in-sequence"; C2.5 pins the placement: "acceptor: in the NotConnected inbound-Logon case, after the peer_sent_reset / reset_on_logon header pre-scan (:1585-1587) so the inbound-seed decision (C2.4) is made against the announced reset, and before check_inbound (:1596)"; research D-6 repeats the same placement. Consistent across contract/research/plan; spec Edge Cases also repeats it. The withhold condition (141=Y OR reset_on_logon) is explicit.
- [x] CHK004 Is the asymmetry of the hydrate split stated (outbound seed applied UNCONDITIONALLY since it only feeds `34=`/never a gate; inbound seed CONDITIONAL on the non-reset branch)? [Clarity, C2.4 / INV-H5] — PASS: C2.4 states "hydrate the outbound counter unconditionally (co_await seqnum_mgr_.hydrate(…) writes outbound; it only feeds the Logon's 34=, never a validation gate). Apply the inbound seed only on the non-reset Logon branch"; research D-6 repeats "Outbound is hydrated normally (it only feeds the reply/initiator Logon's 34=, never a validation gate — no precedence hazard)". INV-H5 ties the outbound/inbound split to the precedence rule. The asymmetry and its rationale are stated clearly.

## Post-GapFill / Peer-Ahead Recovery Precondition

- [x] CHK005 Is the lower-bound recovery precondition stated WITHOUT over-claim — i.e. a too-high peer Logon recovers non-fatally ONLY when `enable_next_expected_msg_seq_num` (789) is on OR the peer Logon announces a reset; otherwise it fatals on the Logon gate and recovers by reconnect (L-029-1)? [Clarity, SC-004 / FR-009 / [[feedback_witness_asserts_named_postcondition_not_proxy]]] — PASS: SC-004 precisely states "A resumed session whose counterparty is ahead recovers without a fatal when enable_next_expected_msg_seq_num is enabled or the peer Logon announces a reset … The complementary knob-off case (peer Logon too-high → fatal on the Logon gate → recover by reconnect, L-029-1) is verified as its own documented disposition, NOT asserted to recover-in-place"; FR-009 repeats the bounded claim; spec US2 AS3 includes the NOTE about the Logon-path fatal with knob off. The SC-004 wording explicitly prohibits over-claiming in the witness. No over-claim detected.
- [x] CHK006 Does the acceptance criterion forbid naming the knob-OFF path "recovers via ResendRequest" (the Logon gate has no ResendRequest arm), requiring the knob-off case to assert its own Disconnected-then-reconnect disposition? [Measurability, SC-004 / W5 / spec US2 AS3] — PASS: SC-004 states "The witness MUST assert the actual precondition; it MUST NOT claim 'recovers via ResendRequest' for the knob-off path"; W5 in data-model.md states "Do NOT let the witness name claim 'recovers via ResendRequest' for the knob-off path. (SC-004, L-029-1, RC-1/New-1, [[feedback_witness_asserts_named_postcondition_not_proxy]])"; T009 in tasks.md repeats: "Do NOT name the knob-off path 'recovers via ResendRequest' — the Logon gate has no ResendRequest arm". The prohibition is stated three times with the correct justification (no ResendRequest arm on the Logon path).
- [x] CHK007 Is L-029-1 (post-GapFill restart ⇒ bounded redundant ResendRequest when 789/reset available, else Logon fatal + reconnect) specified as a documented, recovery-correct limitation — not a silent skip? [Completeness, L-029-1 / data-model W5] — PASS: spec Edge Cases §"Counterparty ahead after restart" documents L-029-1 explicitly as a documented case: "a knob-off restart-after-GapFill can fatal on the Logon and recover by reconnect (documented L-029-1)"; W5 in data-model.md states "Restart: assert the lower-bound recovery is non-fatal only with enable_next_expected_msg_seq_num ON (or a peer reset Logon) — and assert that knob-OFF restart-after-GapFill whose peer Logon is too-high fatals on the Logon gate (the documented L-029-1 case, its own assertion)"; plan §VI delta specifies adding L-029-1 to behaviors-and-limitations.md. Named as a limitation, not a silent skip.
- [x] CHK008 Is the clean-restart (no-gap) case — resumed at N+1, peer continues from N+1, peer Logon in-sequence — covered as a requirement distinct from the gap case, so W4 is not the only inbound-resume scenario? [Coverage, spec US2 AS / W4] — PASS: spec US2 AS2 covers the clean-restart case: "Given a persistent store whose inbound counter reflects five accepted inbound messages, When the session restarts and re-opens, Then the in-memory next-expected-inbound resumes at the persisted value (6), not 1." W4 in data-model.md covers the acceptor clean-resume: "store {in=37,out=42} → acceptor cold open → peer Logon 34=37 is in-seq (not too-high fatal), reply samples 34=42 (FR-009, both-roles)". The gap case is US2 AS3/W5. Both scenarios are distinctly covered.

## 789 (Next-Expected) Interaction

- [x] CHK009 Is the requirement that a hydrated initiator with the 789 knob on advertises `789 = <hydrated next_inbound>` (the true resumed position, not 1) stated, with the source of the value (the hydrated manager) identified? [Completeness, C2.7 / spec Assumptions §027/789 / W11] — PASS: C2.7 states "the hydrated next_inbound feeds the initiator initr_next_expected (789, :603) and the acceptor reply 789 — a hydrated initiator with the knob on advertises 789 = <hydrated next_inbound>"; spec §Assumptions §027/789 states "a hydrated initiator with enable_next_expected_msg_seq_num enabled advertises 789 = <hydrated next_inbound> (the true resumed inbound position)"; W11 specifies: "persisted {in=37,out=42} + enable_next_expected_msg_seq_num=true → the initiator Logon advertises 789=37 (hydrated next_inbound, not 1)". Source of value is the hydrated manager (next_inbound_unsafe() at :605, verified in source). Complete.
- [x] CHK010 Is the requirement that a resumed session does NOT emit a spurious `141=Y` (because `seqnums_at_one` is false once hydrated) stated and tied to the `seqnums_at_one` condition? [Clarity, C2.7 / W11] — PASS: C2.7 states "`seqnums_at_one` (:596) is false on a resumed session so no spurious 141=Y is emitted"; spec §Assumptions §027/789 states "`seqnums_at_one` is false on a resumed session, so no spurious 141=Y is emitted"; W11 asserts "does NOT carry 141=Y (seqnums_at_one false on a resumed session)". The seqnums_at_one condition is confirmed to be the predicate at :596-597 in the live source (verified). The requirement is tied to the specific condition and line anchor.
- [x] CHK011 Is the ordering between hydrate and the 789 sampling specified (hydrate completes before the initiator `789`/acceptor reply `789` is sampled) so the advertisement reflects the resumed value? [Consistency, FR-004 / C2.7] — PASS: research New-3 specifies the ordering: "With ensure_hydrated_() at the top of emit_initiator_logon_() (before the reset block at :558), the hydrated counters feed two :596-606 predicates"; C2.7 places ensure_hydrated_() call at the top of emit_initiator_logon_(), which is before the :603-606 789 sampling (verified in live source: ensure_hydrated_ call site is the spec's first line before :558); FR-004 states "The hydrate MUST complete before any outbound message's sequence number is sampled and before the inbound validation gate runs". Ordering is specified and consistent with the live code structure.

## Received-Reset / reset_on_logon Precedence (non-regression)

- [x] CHK012 Is the requirement that the existing `141`/024 cause-dependent reset split is PRESERVED (hydrate must not mask, reorder, or suppress the received-reset path) stated as a hard non-regression requirement? [Completeness, FR-010 / INV-H5] — PASS: FR-010 states "The existing inbound ResetSeqNumFlag(141) handling and the 024 acceptor cause-dependent reset split MUST be preserved — hydrate establishes the resume baseline but MUST NOT mask, reorder, or suppress the received-reset path"; spec Edge Cases §"Counterparty resets (141=Y)" states "the existing 013/024 received-reset handling still owns this; hydrate must not mask or reorder it"; tasks.md T011 explicitly includes "Confirm the 013/024 received-141 + reset_on_logon reset paths remain UNTOUCHED (FR-010)". Stated as a hard non-regression requirement with "MUST NOT" language.
- [x] CHK013 Is the outbound precedence specified (outbound hydrate runs BEFORE the `024 reset_on_logon` block, so a configured reset still wins and resets outbound to 1)? [Consistency, INV-H5 / W9a] — PASS: C2.6 states "the outbound hydrate runs before reset_on_logon (024); the inbound seed is conditioned on / runs after the Logon-gate reset decision so the 013 received-141 reset (:1760) and the reset_on_logon reset (:1587) still win"; INV-H5 states "the outbound hydrate runs before reset_on_logon (024 reset wins, initiator)"; W9a specifies: "reset_on_logon=true + persisted {37,42} → outbound resets to 1 (reset wins, INV-H5)". The live code at :558 shows reset_on_logon block is the first thing in emit_initiator_logon_() — the spec mandates ensure_hydrated_() runs before :558. Consistent across contract/invariant/witness.
- [x] CHK014 For the acceptor reset-Logon case, is the post-state of `next_inbound` after withhold specified ("per existing 013 policy") rather than left undefined, so the witness has a definite expected value? [Ambiguity, W9b / C2.6] — PASS: W9b in data-model.md specifies: "acceptor cold-hydrated {in=37,…}, peer Logon 34=1,141=Y, reset_on_logon=false → the inbound seed is withheld so check_inbound(1) is in-sequence, the received-141 reset wins, manager ends per existing 013 policy"; C2.4 states "the existing reset arm owns the post-state (RC-1)"; research D-6 states "the existing reset path owns the post-state". While "per existing 013 policy" defers to 013 rather than enumerating the exact final value, it is sufficient: the witness has a definite test criterion ("assert the session does NOT fatal as too-low at :1615" — W9b's primary assertion), and the post-state is per the 013 received-141 path which is a fixed, tested, existing behavior. Not ambiguous for the witness.
