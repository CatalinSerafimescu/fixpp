# Durability Requirements Checklist: Persistent seqnum hydrate

**Purpose**: Validate that the durability/persistence requirements (the durable inbound write, the lower-bound invariant, the crash-ordering semantic, the failure disposition, and the non-persistent no-op floor) are complete, clear, consistent, and measurable — BEFORE a high-risk store↔session boundary slice (008 drew 5 P1s).
**Created**: 2026-06-09
**Feature**: [spec.md](../spec.md) · [data-model.md](../data-model.md) · [contracts/seqnum-hydrate.md](../contracts/seqnum-hydrate.md)

## Persistence Semantics (lower bound & ordering)

- [x] CHK001 Is the INV-H1 lower-bound invariant (`persisted_next_inbound ≤ manager.next_inbound`, always) stated as an always-holds requirement, with every place it could be violated enumerated (GapFill jump, fatal-after-advance, persist failure)? [Completeness, INV-H1 / data-model §Invariants] — PASS: INV-H1 is stated as an always-holds invariant in data-model.md §Invariants ("store.next_inbound ≤ manager.next_inbound at all times"); the three violation-candidate sites are enumerated: GapFill jump (→ no-persist, D-5), fatal-after-advance exits (data-model §35=4 note: "Fatal-after-advance exits do not persist because the session terminates; INV-H1 keeps the durable counter a safe lower bound"), and persist failure (→ fatal disconnect, D-3). FR-007 and spec Edge Cases both reference INV-H1 by name. Complete and consistent.
- [x] CHK002 Is "deliver-then-persist" specified precisely enough to distinguish the in-memory `check_inbound` advance (BEFORE delivery, the gate, unchanged) from the durable write (AFTER the callback)? [Clarity, FR-002 / INV-H2 / C4] — PASS: FR-002 states the inbound store-write MUST occur "after the application callback (fromApp/fromAdmin) for that message returns"; C4 explicitly states "The in-memory check_inbound gate (advance-before-deliver) — unchanged"; INV-H2 in data-model.md states "the durable inbound advance for message S happens strictly after the fromApp/fromAdmin callback for S returns". Two-phase distinction is unambiguous across spec/contract/data-model.
- [x] CHK003 Can the D-2 ordering ("after the application callback returns") be objectively verified, and is the observation point (durable value sampled *inside* `fromApp`/`fromAdmin` for msg S equals S, not S+1) specified rather than left to the implementer? [Measurability, W3 / INV-H2] — PASS: W3 in data-model.md specifies exactly: "a callback-observing app/store records the durable next_inbound observed inside fromApp for msg S and asserts it is still S — persist strictly after the callback returns (INV-H2/FR-002)"; W3 in tasks.md T008 names the same observation point. The measurement methodology (callback-observing store/app) is specified, not left to the implementer.
- [x] CHK004 Is the at-least-once consequence (crash mid-delivery ⇒ re-deliver on restart, deduped by PossDup/ResendRequest; never silently skipped) stated as a requirement, not only as rationale? [Completeness, FR-002 / spec Edge Cases] — PASS: FR-002 states "so a crash mid-delivery re-delivers the message on restart (recovered by the standard PossDup/ResendRequest path) rather than silently skipping it"; the spec Edge Cases §"Crash mid-delivery" repeats it as a requirement-style statement; FR-007 also states "the in-flight message whose persist failed MAY be replayed (at-least-once, INV-H2 — deduped by PossDup); the guarantee is that the durable counter never advances ahead of true, so no inbound is ever skipped". Stated as requirement in three places.
- [x] CHK005 Is the counter-only nature of the inbound persist (no inbound frame body retained — fixpp never resends inbound) explicitly required and distinguished from the outbound store-with-body? [Clarity, plan §Summary / C3.0] — PASS: plan §Summary states "counter-only, no inbound frame retention (fixpp never resends inbound), matching QFcpp's incrNextTargetMsgSeqNum"; C3.0 names the helper and specifies "co_await store_->next_seqnum(direction_t::inbound, increment=true) when store_is_persistent_" — no frame body; research D-4 explicitly rejects "store(seq, frame, inbound)" as "heavier (frame body)". Distinction is clear and grounded.
- [x] CHK006 Is the decision NOT to persist a `SequenceReset`-GapFill absolute jump (the store has no absolute set; the jump is `set_next_inbound`, not `+1`) stated as a requirement with its INV-H1 justification, rather than an incidental implementation choice? [Completeness, D-5 / INV-H1 / C3.4] — PASS: C3.4 item 3 states "Absolute NewSeqNo jump via apply_inbound_sequence_reset → NO-PERSIST (INV-H1 / D-5 — the jump is via set_next_inbound, not a +1; the durable counter stays ≤ the manager. No code at the jump site touches store_)"; data-model.md matrix row for "Absolute NewSeqNo jump" states "NO-PERSIST (D-5 / INV-H1 lower bound)"; research D-5 names this a deliberate decision with INV-H1 justification. Stated as a requirement with full justification.

## Hydrate-on-Open Lifecycle

- [x] CHK012 Is "hydrate-on-open" bounded to **cold open, one-shot** (mutates the manager at most once per session lifetime; reconnect never re-hydrates) as an explicit requirement, with the regression it prevents (re-hydrate regressing a live manager to the store lower bound) named? [Completeness, INV-H3 / D-6] — PASS: INV-H3 states "ensure_hydrated_ mutates the manager at most once per session lifetime, on the first counter touch; reconnects never re-hydrate"; C4 states "Reconnect behavior — no re-hydrate (one-shot)"; research D-6 names the regression: "One-shot ⇒ reconnect skips — re-hydrating a live session regresses the manager to the store's lower-bound value (the 025 Gate-A New-1 corruption)". FR-003 also states "This hydrate is always-on whenever a persistent store is configured (D-1); no config flag gates it" (implying cold-open scope). Complete.
- [x] CHK013 Is the latch-after-success semantic (`hydrated_` set ONLY after both reads + `hydrate()` succeed; a transient read failure stays retryable on the next reconnect) specified, distinct from a pre-latched flag that would make a transient failure sticky? [Clarity, INV-H6 / D-9 / C2.1] — PASS: INV-H6 states "`hydrated_` is set only after both reads + `hydrate()` succeed; a transient read failure leaves `hydrated_ == false` so the next reconnect retries (D-9). Re-entrancy is guarded by `hydrating_`, cleared on failure"; C2.1 says "`hydrated_ = true` is set only after both reads + `hydrate()` succeed — not before the awaits. On any failure, clear `hydrating_` and leave `hydrated_ == false`"; research D-9 cites the rejected alternative "hydrated_ = true before the reads (Codex P2#5: sticky failure)". The distinction is explicit with the rejected alternative named.
- [x] CHK014 Is the hydrate-before-first-use ordering requirement (outbound counter loaded before any outbound seqnum is sampled; inbound seed before the inbound validation gate) stated with both directions, and is it testable as a happens-before, not just a call-count? [Measurability, FR-004 / W8 / data-model W8] — PASS: FR-004 states "The hydrate MUST complete before any outbound message's sequence number is sampled and before the inbound validation gate runs". W8 in data-model.md mandates "hydrate completes-before the first check_inbound on both roles" and requires observable-state assertion ("read next_inbound_unsafe() at the moment the first inbound Logon reaches the gate and assert it already equals the hydrated value, so a coincidental ordering in a 1-thread harness cannot pass it"). The [[feedback_single_threaded_harness_masks_strand_races]] citation makes the measurability requirement explicit. Both directions covered, testable as happens-before.
- [x] CHK015 Is the empty/never-written persistent store case specified as a no-op hydrate to `1` (NOT an error), with the WIRE-level byte-identity caveat (one open-time read accepted) called out? [Edge Case, spec Edge Cases / FR-005] — PASS: spec Edge Cases §"Empty / never-written persistent store" states "hydrate reads back the construction-default (1) — no-op, no error"; spec US3 AS2 states "persistent store that has never been written → hydrate is a no-op leaving counters at 1 — not an error"; FR-005 clarifies "An empty/first-run persistent store performs the open-time read and hydrates a no-op 1 — see FR-003; the byte-identity guarantee for that case is at the WIRE level with the one-time open-time read accepted, not zero reads." The caveat is explicitly distinguished from the memory-store zero-reads guarantee.

## Failure Disposition

- [x] CHK016 Is the inbound persist-write failure disposition (D-3 fatal → Disconnected, reusing the existing store-failure disposition, no new error slot) stated as a requirement, with the reconnect-rehydrates-last-durable-value recovery path named? [Completeness, FR-007 / D-3] — PASS: FR-007 states "An inbound store-write failure MUST be fatal → disconnect (D-3), reusing the existing store-failure disposition (no new error slot). On reconnect, hydrate reads the last successfully-persisted value (a lower bound — INV-H1, never ahead of the true position) and the 013 recovery sub-protocol resyncs any gap"; FR-011 reaffirms "no new error slot". C3.3 in contracts states the same. research D-3 provides the rationale with reference to QFcpp IOException. Both the requirement and the recovery path are named.
- [x] CHK017 Is the hydrate READ-failure disposition (fatal → Disconnected, NO partial seed — manager mutated only after BOTH reads succeed) specified and distinguished from the persist-WRITE failure? [Clarity, FR-006 / SC-005 / C2.3] — PASS: FR-006 addresses read failure ("A store-read failure during hydrate MUST be treated as a fatal session error → disconnect, reusing the existing store-failure disposition (no new error slot)"); C2.3 distinguishes it: "A read failure → hydrating_ = false; record_state_transition_(Disconnected) + std::unexpected(err) (FR-006); no partial seed — the manager is mutated only after BOTH reads succeed, and hydrated_ is NOT set"; SC-005 names the split witness "(split: first-read-fails and second-read-fails-after-first-succeeds, proving no partial seed)"; W14 is labeled "Hydrate read-failure fatal, no partial seed" distinct from W6 (write failure). Clearly distinguished.
- [x] CHK018 For the persist-failure witness, does the spec require asserting the durable counter is the last-persisted lower bound (NOT "manager unchanged", since `check_inbound` advanced before delivery ⇒ at-least-once replay)? [Measurability, SC-006 / W6 / [[feedback_witness_asserts_named_postcondition_not_proxy]]] — PASS: SC-006 explicitly states "The test MUST NOT assert 'manager unchanged' — the in-memory check_inbound advanced before delivery, so the in-flight message may be replayed on reconnect (at-least-once), never skipped"; W6 in data-model.md states "durable counter stays the last-persisted lower bound (NOT 'manager unchanged' — in-memory advanced pre-delivery, so the in-flight msg may replay at-least-once, never skipped)"; T008 in tasks.md repeats this prohibition. The anti-proxy requirement is stated explicitly and references [[feedback_witness_asserts_named_postcondition_not_proxy]].

## Non-Persistent No-Op (byte-identity floor)

- [x] CHK019 Is the non-persistent discriminator requirement keyed to a captured-at-open `store_is_persistent_` bool (from a factory accessor) rather than `store_ == nullptr`, so a configured MEMORY store (non-null) still skips the read? Is the reason (a memory store's counter read posts/locks/allocates) stated? [Clarity, FR-005 / D-10 / INV-H4] — PASS: FR-005 states "Because a configured memory store is non-null and its counter read posts/locks/allocates, the no-read guarantee is keyed to a non-persistent discriminator captured at open (not to store_ == nullptr), so a memory store skips the hydrate read entirely"; C2.2 specifies "`store_is_persistent_` is a single bool captured at `open()` inside the `if (cfg_.store_factory)` branch (session.cpp:779) from the new `MessageStoreFactory::yields_persistent_store()` accessor"; data-model.md entity table states "A configured MemoryStore is non-null but discriminated non-persistent at open(), so it skips the read". The reason (posts/locks/allocs) is stated with a code reference (memory_store.hpp:359). Fully specified.
- [x] CHK020 Is the byte-identity guarantee for the non-persistent path quantified as "zero added store read AND zero added allocation on the open path", and is the binding measurement basis (mallocnesia LD_PRELOAD, not a PMR counter alone) named? [Measurability, SC-003 / INV-H4] — PASS: SC-003 states "the open path performs zero added store reads and zero added allocations (verified under the existing no-heap/allocation discipline — the memory store is discriminated non-persistent and its counter read is skipped, not paid)"; T012 in tasks.md states "the BINDING no-heap gate is the mallocnesia LD_PRELOAD interceptor tools/mallocnesia/libmallocnesia.so wrapping the session binary — a PMR counting_resource alone is a false-pass since non-PMR std::vector/global-new escapes it, [[feedback_tracking_pmr_resource_false_pass]]"; plan §VIII.5 also cites mallocnesia as the measurement. The binding basis is named and the false-pass risk is documented.
