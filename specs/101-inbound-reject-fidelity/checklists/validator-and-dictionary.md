## The defined-tag store (FR-002, research D1)

- [ ] CHK001 D1 fills the store from "the merged field store". For a FIXT application route and for a route plus `extra`, is it stated which field lists go into the store: the application dictionary's, the transport dictionary's, `extra`'s? A tag that only FIXT11 defines, such as a FIXT-only header tag in an application frame judged by the route's table, must not answer 373=0. [Clarity, research D1, Spec §FR-002]
- [ ] CHK002 `tag_defined` takes a `std::uint16_t`. Is it stated what the validator does with a wire tag above 65535? Either it is unreachable because the parser already answers `wire_invalid_tag_number`, or a narrowing conversion could alias it to a defined tag. [Edge Case, Gap, data-model "table_view", research D1]
- [ ] CHK003 D1's census of hand-built population operations is "at round 1", re-derived at tasks. Is there a requirement, beyond the mutation cells, that a population operation added later calls `mark_defined`? Without one, a new operation would make its tags answer 373=0 with nothing noticing. [Coverage, research D1]
- [ ] CHK004 D1's rationale takes QuickFIX's "defined" from the dictionary's field list (`m_fields`), not from what messages reach. Is it stated that a field declared under `<fields>` and referenced by no message counts as defined, so it answers 373=2? [Clarity, research D1 "Rationale"]
- [ ] CHK005 A 098 overlay can add a field without adding any message that reaches it. Is it stated that such a field is defined, so it answers 373=2 and not 373=0, and that a peer therefore sees a different 373 depending on whether the operator loaded an overlay? [Coverage, research D1, Spec §FR-002]
- [ ] CHK006 Is "Orchestra's fields" tied to a named source element, so that the dictionary-built fill for FIX Latest can be checked against the tag recipe in research Supersessions (`<fixr:field id=…>`)? [Clarity, research D1, research "Supersessions (by name)"]

## The MsgType check (FR-001, research D2)

- [ ] CHK007 FR-001 places the check "after the header-order check and before the field walk". The Survey's validator order also has 092's failed-build fault scan ahead of Step 0, and 099's FIXT envelope and 1128 arms. Is the check's position stated against those, so that it is clear which result answers first for an unknown MsgType that also carries an unknown 1128? [Clarity, Spec §FR-001, research "Survey"]
- [ ] CHK008 On a FIXT session the check uses "the dictionary the frame is validated with" (Edge Cases). Is the ending stated for each case: an application frame whose 1128 099 refuses, and one whose resolved version lacks the MsgType? Is it stated which refusal wins when both apply? [Coverage, Spec "Edge Cases", research D2]
- [ ] CHK009 On a hand-built table, a MsgType is defined only by `add_valid(_tag)` or `add_required(_tag)`. Is the consequence stated for a table that names application messages but no admin messages: every Heartbeat would then draw 373=11? Is that intended for hand-built validating sessions? [Edge Case, research D2]
- [ ] CHK010 D2 says that header and framing operations do not define a MsgType. It also says that on a dictionary-built table every declared message gets its header tags as valid. Is it stated that the second statement comes from the dictionary-built fill calling `add_valid`, and not from the header operation itself, so that the two sentences cannot be read as contradicting each other? [Consistency, research D2, data-model "table_view"]
- [ ] CHK011 Does "one `valid_.find` per message, as today" also hold on the FIXT envelope arm, or does that arm do its own lookup? The plan's performance goal states the count. [Clarity, research D2, plan "Technical Context"]

## Error slots and the C ABI (research D2, plan "Constitution Check")

- [ ] CHK016 Both new slots map to `FIXPP_ERR_WIRE_CONFORMANCE`, as `wire_unexpected_tag` does, while `wire_invalid_tag_number` maps to `FIXPP_ERR_WIRE_INVALID_FRAME`. Is it stated that a C caller cannot tell an undefined MsgType, an undefined tag and a tag not in this message apart, and that this is intended? [Clarity, data-model "core::error", plan "Constitution Check"]
- [ ] CHK017 Are the two slots' message strings (`core::error_message`, `to_string`) specified, either as text or by the rule the neighbouring slots follow? Tasks T022's completeness test pins them, so the bundle should define what it pins. [Gap, data-model "core::error", tasks T022]
- [ ] CHK018 Is it stated where else the new slots must appear: Python's error mirror, the logging of an error name, and any table the repo-wide census of tasks T018 finds? Or is T018's classification the only place this is decided? [Coverage, tasks T018]
- [ ] CHK019 Is `wire_invalid_tag_number`'s contract (a malformed tag, no 371) worded the same way in the Clarifications, data-model "core::error" and D10's correction of the `reject_reason_map.hpp` comment? [Consistency, Spec "Clarifications", data-model "core::error", research D10]
- [ ] CHK020 "No C-ABI version step" rests on `core::error` being a C++ enum that the C surface reaches only through `translate`. Is that premise stated, and is it stated that `AbiSymbolGolden.ErrorEnumUnchanged` moves its sentinel without the C enum changing? [Assumption, plan "Constitution Check", research D9]
- [ ] CHK021 Tasks T030 adds a forwarder on `table_view_builder` so that `Dictionary::build_table_view` can fill the store. Is its visibility stated: public API on an installed header, or internal? If public, is it covered by the B-rows? [Gap, tasks T030, research D1]
