[Completeness, Spec §FR-002 / Key Entities] — PASS: FR-002 enumerates per-handle lifecycle discipline; data-model E-1 provides a per-row ownership table (engine: caller-owns; session: engine-owns; msg: session-arena; dict: caller-owns; store: non-owning observer); Key Entities section calls out each handle individually.
- [x] CHK002 Does the spec require the complete published `fixpp_error_t` per-domain block layout (all `[2i §4.3]` ranges + the codes defined now), not only Feature-A-reachable codes? [Completeness, Spec §FR-006 / Assumptions] — PASS: FR-006 explicitly states "full master enum published now (all domains, all reserved ranges)"; Assumptions confirm "full block layout shipped even for Feature-B-deferred codes"; data-model E-2 documents every numeric block with its range, origin, and provisional vs master values.
- [x] CHK003 Are requirements present for BOTH version tracks (C-ABI surface vs C++ library) AND their decoupling? [Completeness, Spec §FR-015 / SC-001] — PASS: FR-015 specifies both tracks ("C-ABI SemVer is an independent track from the C++ library version"); SC-001 is the scenario requiring both `fixpp_version()` (C-ABI) and `fixpp_library_version()` (C++) to be exported as distinct functions; `[arch §9.2]` cited as authority.
- [x] CHK004 Is the set of in-repo sites that must move in lockstep for the decimal renumber enumerated as a requirement (header, impl, contract copy, C/oracle tests), not deferred to implementation discretion? [Completeness, Spec §FR-011] — PASS: FR-011 enumerates the lockstep sites (header `#define`, translate() switch, error_codes_v1.txt, C-oracle test constants, contract copy); T002 and T012 in tasks.md encode this as discrete verifiable tasks with per-site checks.
- [x] CHK005 Is the "from-consumer" direction (unknown codes from older consumers tolerated as opaque pass-through) specified in addition to the return-path downgrade? [Completeness, Spec §FR-009 / Edge Cases] — PASS: FR-009 covers both directions: "engine downgrades future codes to FIXPP_ERR_UNKNOWN(2) when returning to an older consumer" AND "codes from an older consumer are treated as opaque pass-through (no rejection)"; Edge Cases section adds an explicit scenario for each direction.
- [x] CHK006 Is there a requirement that the audit record is born complete (every published code, including those whose producing functions arrive in later features)? [Completeness, Spec §FR-012 / Assumptions] — PASS: FR-012 states "error_codes_v1.txt MUST be complete at first publish — every code in the master enum (including Feature-B-deferred codes) gets an entry with its introducing_minor ordinal"; Assumptions confirm this explicitly.

## Requirement Clarity & Measurability

- [x] CHK007 Is the "unknown error" sentinel quantified with its exact numeric value (2) everywhere it is referenced (downgrade target AND out-of-range strerror)? [Clarity, Spec §FR-008/FR-009] — PASS: FR-008 states "strerror on an unrecognised/out-of-range input returns the string for FIXPP_ERR_UNKNOWN (2)"; FR-009 states "translate_for_consumer maps future codes to FIXPP_ERR_UNKNOWN (2)"; data-model E-2 shows the sentinel block with numeric value 2 explicitly.
- [x] CHK008 Is the quantity the downgrade keys on unambiguous — the published ABI **minor** ordinal, explicitly distinct from the major/GA freeze? [Ambiguity, Spec §FR-009/FR-017] — PASS: FR-009 uses "consumer_minor" as the key parameter throughout and explicitly states this is the ABI minor version, not the library major; FR-017 distinguishes "ABI minor bump" from "major GA freeze"; D-3 in research.md confirms: "downgrade keys on introducing_minor ordinal in error_codes_v1.txt".
- [x] CHK009 Is "zero allocation" for `fixpp_strerror`/`fixpp_version` specified measurably (no global-heap allocation), so it is objectively verifiable? [Measurability, Spec §FR-007 / SC-002] — PASS: FR-007 states "fixpp_strerror, fixpp_version, fixpp_library_version MUST NOT allocate from the global heap (zero-alloc)"; SC-002 is a scenario that tests this with a counting allocator; `[const §XV §1]` provides the authority.
- [x] CHK010 Are the reentrancy classes enumerated as a closed set of exactly three, with "exactly one per public symbol" stated measurably (0 unannotated, 0 double-classed)? [Measurability, Spec §FR-014 / SC-005] — PASS: FR-014 states "exactly three reentrancy classes (FIXPP_THREAD_SAFE / FIXPP_SINGLE_THREAD / FIXPP_REQUIRES_SESSION_LOCK) and each public C ABI symbol MUST carry exactly one annotation"; SC-005 is a scenario that grep-counts annotations and fails on zero or >1; `[2i §4.10]` (confirmed at line 1168) provides the authoritative three-class taxonomy.
- [x] CHK011 Is "no C++ symbol leakage" expressed as an objectively checkable criterion (only `extern "C"` `fixpp_*` exported, verified by the nm/visibility gate)? [Measurability, Spec §FR-004 / SC-003] — PASS: FR-004 states "shared-library export MUST contain no C++ mangled symbols; all exports are extern "C" fixpp_* names"; SC-003 is a scenario that uses `nm -D` and fails on any `_ZN`-prefixed symbol; tooling-and-abi.md specifies the nm gate as part of the CI pipeline.
- [x] CHK012 Is the underlying representation of `fixpp_error_t` fixed unambiguously (`int32_t`, `#define` constants — explicitly NOT a C `enum`)? [Clarity, Spec §FR-006] — PASS: FR-006 states "fixpp_error_t is typedef int32_t; constants are #define macros, NOT a C enum"; data-model E-2 header states "typedef int32_t fixpp_error_t; all domain constants are #defines"; error-surface.md contract shows the typedef explicitly; `[2i §4.3]` (confirmed at line 473) gives the authoritative rationale.
- [x] CHK013 Are the occupancy gate's two checks specified distinctly enough to be independently verifiable (header `#define` layout vs sibling variant-row counts) with the requirement that they are never compared to each other? [Clarity/Measurability, Spec §FR-013] — PASS: FR-013 explicitly names "Check A: header #define block layout" and "Check B: sibling variant-row count comparison" as distinct checks; data-model E-6 describes each check independently; tooling-and-abi.md contract for check_capi_occupancy.sh encodes both with discrete exit-code semantics and the explicit note that the two check results are never compared to each other.
- [x] CHK014 Is the criterion for a "compatible" surface stated measurably (equality of the major component) vs "incompatible" (major mismatch)? [Measurability, Spec §US1-AC3 / §FR-010] — PASS: US1-AC3 defines "compatible: major == consumer_major" and "incompatible: major != consumer_major"; FR-010 states "a major-version mismatch MUST return FIXPP_ERR_VERSION_MAJOR_MISMATCH and is an objectively checkable integer comparison"; Edge Cases section covers the mismatch scenario explicitly.

## Requirement Consistency

- [x] CHK015 Is SC-007 consistent with FR-019 and the stated invisibility of the decimal renumber to the nm gate (symbol-set delta only; renumber verified separately)? [Consistency, Spec §SC-007/FR-019] — PASS: SC-007 explicitly states "the nm/ABI-golden gate checks the set of exported symbols, not the numeric values of #defines; the decimal renumber is invisible to this gate"; FR-019 consistently states "symbol-set delta only (3 new symbols)"; no cross-contradiction.
- [x] CHK016 Do the handle-ownership requirements (FR-002) align with the Key-Entities description, with no residual "uniform destroy" wording surviving in either place? [Consistency, Spec §FR-002 / Key Entities] — PASS: FR-002 and Key Entities both use per-handle ownership rules; handle-catalogue.md contract also specifies per-handle discipline (engine: caller destroys; session: engine-owned; msg: session-arena, no explicit destroy; dict: caller destroys; store: non-owning, never destroyed by caller); no uniform-destroy wording found in either section.
- [x] CHK017 Is the version value (stay 0.x → 0.2.0) stated consistently across FR-018, the version FRs, and the Assumptions? [Consistency, Spec §FR-018 / Assumptions] — PASS: FR-018 states "version 0.2.0 for this feature; [2i §4.5]'s literal 1.0.0 is the documented GA end-state, not a directive"; Clarifications section reconciles the discrepancy with [2i §4.5] explicitly; Assumptions state "pre-1.0, 0.x; stability binds only at MAJOR==1 per [const §X.4]"; version-surface.md contract pins 0.2.0 for all three macros; consistent throughout.
- [x] CHK018 Is the unpublished-groups decision (session/log/otel/app → UNKNOWN now) consistent with the "full enum now" assumption, with no contradictory claim that `[2i §4.3]` publishes a session block? [Consistency, Spec Assumptions / §FR-006] — PASS: Assumptions explicitly state "session_*/log_*/otel_*/app_* groups are NOT published as #define blocks in this feature — they map to FIXPP_ERR_UNKNOWN(2) and are documented as L-049-2"; FR-006 states "full master enum" but data-model E-2 correctly shows those ranges as reserved-comment-only (not #defines); no claim that [2i §4.3] publishes a session block; research.md L-049-2 records the limitation.

## Scenario & Edge-Case Coverage

- [x] CHK019 Are requirements defined for the out-of-range / undefined `strerror` input (returns "unknown", no crash, no allocation)? [Coverage/Edge Case, Spec §FR-008] — PASS: FR-008 states "fixpp_strerror(code) where code is not in any published block MUST return a non-null, static string equivalent to FIXPP_ERR_UNKNOWN's string; no crash, no allocation"; Edge Cases section enumerates this as a scenario with exact expected output; error-surface.md contract confirms "totality rule: every input returns a valid static C string".
- [x] CHK020 Are requirements defined for distinguishing a null handle from a previously-valid-but-destroyed/corrupted handle (two distinct codes)? [Coverage, Spec §FR-003 / Edge Cases] — PASS: FR-003 specifies two distinct error codes: "FIXPP_ERR_NULL_HANDLE (null pointer) and FIXPP_ERR_INVALID_HANDLE (non-null but already-freed/invalid)"; Edge Cases section enumerates both scenarios with distinct expected return codes; handle-catalogue.md contract confirms the two-code design.
- [x] CHK021 Is the major-version-mismatch case covered by a requirement for a distinct reserved code, separate from the per-call "unknown" downgrade? [Coverage, Spec §FR-010 / Edge Cases] — PASS: FR-010 defines FIXPP_ERR_VERSION_MAJOR_MISMATCH as a dedicated code for engine-create major-version mismatch, distinct from FIXPP_ERR_UNKNOWN(2) which is for per-call downgrade; Edge Cases section covers both scenarios; data-model E-2 shows these two codes in different numeric blocks.
- [x] CHK022 Is the numeric-slot-drift scenario covered by a requirement that the occupancy/audit gate fails deterministically on re-use or re-definition? [Coverage, Spec §SC-004 / Edge Cases] — PASS: SC-004 is a scenario that covers numeric-slot re-use and re-definition; FR-013 (occupancy gate) states "shall fail deterministically if a slot is reused or redefined"; tooling-and-abi.md describes the check_capi_occupancy.sh two-check structure that enforces this deterministically.
- [x] CHK023 Is the forward-compat scenario (newer engine emits a code the consumer's minor predates) covered with a defined, testable outcome? [Coverage, Spec §FR-009 / SC-006] — PASS: FR-009 defines the outcome: "translate_for_consumer(code, consumer_minor) returns FIXPP_ERR_UNKNOWN(2) when code.introducing_minor > consumer_minor"; SC-006 is a scenario with specific test parameters (an in-range code that postdates the consumer's minor must be downgraded); testable via the oracle table in data-model E-3-test.
