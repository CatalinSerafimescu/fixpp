## Requirement Clarity

- [x] CHK010 Is "atomic swap" (FR-033) precisely specified — `std::atomic<std::shared_ptr<cert_source>>::store(...)` with which `memory_order`? Is the FSM-side load `memory_order_acquire`? [Clarity, Spec §FR-033] — DD-DECIDED: C++ `std::atomic<std::shared_ptr<T>>::store()` defaults to `memory_order_seq_cst` and `load()` defaults to `memory_order_seq_cst`. The sequentially-consistent default is correct and sufficient for this pattern (one writer on operator thread, one reader on session strand); no weaker ordering is needed. The spec names the atomic type (`std::atomic<std::shared_ptr<cert_source>> cert_source_slot_`) which implies the default memory order; explicit `memory_order` annotation is an implementation detail, not a spec-level requirement.
- [x] CHK011 Is "deferred until in-flight handshake completes" (FR-033) clear about WHICH handshakes are "in-flight" — only the current single one already past `TransportFactory::make`, or all handshakes that called `make` BEFORE `reload_credentials` returned? [Clarity, Spec §FR-033] — PASS: FR-033 is explicit: "any in-flight handshake that already captured a `std::shared_ptr<cert_source>` BY VALUE COPY before the swap." A handshake is "in-flight" from the moment `drive_reconnect_attempt()` calls `factory_->cert_source_snapshot()` until the TLS handshake completes. Any number of such handshakes (N concurrent sessions) that captured the old snapshot before `reload_credentials` returned are all in-flight — they all run on the old cert_source. Specified.
- [x] CHK012 Is the "BY VALUE COPY" capture point (FR-033) specified at an EXACT FSM-side line — at `drive_reconnect_attempt` entry? at `factory_->cert_source_snapshot()`? immediately before `make(...)`? [Clarity, Spec §FR-033, §A.6] — PASS: FR-033 specifies: "subsequent FSM-driven `drive_reconnect_attempt()` calls read the atomic via `load()`, build an `SslCtxConfig` from the snapshot, and pass it by-value into `TransportFactory::make(exec, ssl_cfg, mr)`." The capture point is `factory_->cert_source_snapshot()` within `drive_reconnect_attempt()` — explicitly named. Specified.
- [x] CHK013 Is "Worst-case rotation latency ≈ one in-flight HANDSHAKE duration" (FR-033) measuring a single handshake, or the longest-pending across N concurrent sessions? [Clarity, Spec §FR-033] — PASS: FR-033 says "Worst-case rotation latency = one-handshake duration (typically 50-500 ms — the in-flight HANDSHAKE window, NOT an in-flight `make()` window)." This is the duration of ONE TLS handshake. With N concurrent sessions, each in-flight handshake independently holds its old cert_source until completion; the rotation is visible to ALL sessions simultaneously after the atomic store (each session's NEXT reconnect observes the new cert). The "worst case" is that the LAST in-flight handshake takes the full duration. The spec specifies this correctly for the single-session case; N-session worst case is not explicitly stated but implied by the "any in-flight handshake" language.
- [x] CHK014 Is FR-031's "next `TransportFactory::make(...)` call" precise — only FSM-driven reconnect, or could it include an operator-driven path (e.g., `add_session`)? [Clarity, Spec §FR-031] — SPEC-FIXED: FR-031 was silent on trigger. Added to spec.md §FR-031: "The 'next `TransportFactory::make(...)` call' includes ANY code path that calls `make()` — FSM-driven reconnect attempts, operator-driven `Session::open` with `transport_factory_override`, and any future acceptor-side `make()` after the rotation. All callers read the same atomic slot via `cert_source_snapshot()` at `make()`-time."
- [x] CHK015 Is "atomic STORE point is `TransportFactory::reload_credentials(...)`" (§A.6) clear about pre-conditions — must the swap happen BEFORE the call returns, or may an internal worker defer? [Clarity, Spec §A.6] — PASS: A.6 says "executes synchronously on the operator call." FR-033 confirms "performs the `store(new_source)` synchronously." The store completes BEFORE `reload_credentials` returns. No internal worker deferral. Specified.

## Scenario Coverage

- [x] CHK023 Are requirements covered for rotation during `AwaitingResend` (recovery in-flight)? Spec covers in-flight handshake (FR-033) but not in-flight recovery. [Coverage, Gap] — PASS: During AwaitingResend, the session is ACTIVE on an existing Transport — NO new TLS handshake is in progress (the connection is established). `reload_credentials` atomically stores the new cert_source; the Active session's existing TLS session is unaffected (FR-031). The new cert_source is observed at the NEXT `make()` call (next reconnect attempt). Rotation during AwaitingResend behaves exactly like rotation during any Active state — no special case needed.
- [x] CHK024 Are requirements covered for rotation interleaved with `ReconnectPolicy` (peer drops, FSM walks the schedule, operator rotates BETWEEN attempts) — which attempt observes the new cert? [Coverage, Spec §FR-031, Gap] — PASS: FR-031 says "next `TransportFactory::make(...)` call observes the new cert." If the operator rotates BETWEEN reconnect attempts (after attempt N's `make()` returned and before attempt N+1's `make()` is called), attempt N+1 reads the new snapshot. The atomic slot guarantees this — no race condition between the `store()` on the operator thread and the `load()` on the session strand at the next `make()` entry.
- [x] CHK025 Are requirements covered for multiple concurrent `reload_credentials` calls — last-write-wins via atomic store, or operator-MUST-serialise per FR-033? [Coverage, Spec §FR-033, Gap] — PASS: Covered by CHK003 DD-DECIDED: `std::atomic<std::shared_ptr>::store()` is thread-safe; concurrent calls are last-write-wins without operator serialization requirement.
- [x] CHK026 Are requirements covered for an initiator vs. acceptor concurrent rotation (operator rotates one role's cert while the other role's session is active on the SAME factory) — given "factory is the symmetric authority" (plan §item 6)? [Coverage, Spec §FR-030, Gap] — SPEC-FIXED: FR-030 says the factory is the symmetric authority but doesn't address concurrent same-factory rotation from two sessions. Added to spec.md §FR-030: "If multiple sessions share the SAME `TransportFactory*` instance (which the spec discourages — see `SessionConfig::transport_factory_override` ownership note on use_count()==1), a single `reload_credentials()` call atomically updates the shared slot; all subsequent `make()` calls across all sessions sharing that factory read the new cert_source. Concurrent rotation of the same factory by multiple sessions' operator-facing code is safe via the atomic slot (last-write-wins per CHK003 DD-DECIDED)."

## Edge Case Coverage

- [x] CHK027 Are requirements specified for a `reload_credentials(new)` where `new`'s SHA-256 matches the current `cert_source` (true no-op rotation) — emit `credentials_rotated` event, or suppress? [Edge Case, Spec §FR-032, Gap] — PASS: Covered by events.md CHK027 SPEC-FIXED and the FR-032 amendment: a no-op rotation (matching SHA-256) still emits `credentials_rotated{old_sha256=X, new_sha256=X}`. Specified.
- [x] CHK028 Are requirements specified for `reload_credentials` called concurrent with `Session::open` (the Session is not yet Active, the factory is being built) — defer, race, or reject? [Edge Case, Gap] — PASS: `Session::open` calls `factory->make()` which reads `cert_source_snapshot()` via an atomic `load()`. `reload_credentials` calls `cert_source_slot_.store()`. These are two thread-safe atomic operations on the same slot. If `store()` happens before `load()`, the new cert is used for the session being opened. If `load()` happens before `store()`, the old cert is used and the NEXT reconnect observes the new cert (FR-031). No defer, no reject, no race — the atomic guarantees a clean ordering. Covered by FR-031 + FR-033.
- [x] CHK029 Are requirements specified for the OpenSSL `OPENSSL_init` / `OPENSSL_cleanup` boundary — can `reload_credentials` safely build a new SSL_CTX after OpenSSL teardown begins (process shutdown)? [Edge Case, Gap] — SPEC-FIXED: Added to spec.md §FR-033: "Calling `reload_credentials` after `OPENSSL_cleanup` begins (process shutdown) is UNDEFINED BEHAVIOUR — the same constraint that applies to all OpenSSL operations. The operator MUST ensure all `reload_credentials` calls complete before process shutdown initiates OpenSSL teardown. No fixpp-level guard is provided for this boundary."
- [x] CHK030 Are requirements specified for `reload_credentials` AFTER `Listener::cancel` (acceptor torn down, factory may outlive listener) — does the swap still succeed but the next `make()` never happen? [Edge Case, Spec §Edge Cases, Gap] — PASS: `reload_credentials` is an atomic store on the factory's slot; it succeeds regardless of the Listener's lifecycle (the factory may outlive the listener). After `Listener::cancel`, no new `make()` calls are made by the acceptor path — the swap succeeds but is never consumed by the now-cancelled listener. This is well-defined: the factory's slot is updated, but the next `make()` simply doesn't happen. FR-031 covers this: "next `make()` observes the new cert" — if no `make()` happens, the stored cert is unused. No special handling needed.

## Non-Functional Requirements

- [x] CHK031 Are zero-allocation requirements specified for the atomic-swap hot path — `std::atomic<shared_ptr>` store on operator-thread + load on FSM-thread should not allocate beyond reference-counting? [Completeness, plan §Constraints] — PASS: The `std::atomic<std::shared_ptr<T>>::store()` operation modifies reference counts on the existing control block — no new allocation. The `load()` acquires a strong reference (may increment/decrement ref-count but no allocation). The `cert_source_snapshot()` call returns a copy of the `shared_ptr` by value (copies the strong-ref, no allocation beyond ref-count increment). Zero global `new`/`delete` on the atomic-swap hot path. Covered by the C++ standard semantics; no spec annotation needed.
- [x] CHK032 Are security requirements specified for `cert_source` memory lifetime — a captured `shared_ptr` keeps the cert_source's PEM bytes (potentially containing private-key material) alive longer than expected; is there a documented zeroisation requirement? [Completeness, Security, Gap] — SPEC-FIXED: Added to spec.md §FR-033: "Security note on cert_source memory lifetime: a captured `std::shared_ptr<cert_source>` holds the cert_source — including any private-key material in PEM bytes — alive until the last strong-ref is released. In v1.0, no explicit zeroisation of cert_source memory is performed by fixpp; the private key material lives for the shared_ptr lifetime. Operators with strict zeroisation requirements MUST implement a custom `cert_source` whose destructor overwrites its internal PEM buffer before freeing. A future feature MAY add a fixpp-managed zeroisation guarantee."
- [x] CHK033 Are cancellation requirements specified for `reload_credentials` — does the call honour `cancellation_type::total` (per `[const §XI.2]`), or is it strand-free and not cancellable? [Completeness, Spec §FR-033, Gap] — SPEC-FIXED: Added to spec.md §FR-033: "`TransportFactory::reload_credentials(new_source)` is NOT cancellable — it is a synchronous, instantaneous `std::atomic::store()` on the operator's thread. It has no asio awaitable, no coroutine suspension point, and no cancellation slot. It is strand-free (callable from any thread). Per `[const §XI.2]`, only asio-awaitable operations participate in the cancellation protocol; `reload_credentials` is not such an operation."
