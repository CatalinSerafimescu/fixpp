## Requirement Completeness

- [x] CHK002 Is the `CompIdAuthorizationPolicy` mutation model specified — frozen-at-open per `[arch §5.6]`, or operator-mutable mid-session, and via which entry point? - [x] CHK004 Are "matching" semantics for a principal value precisely specified — exact byte compare, case-insensitive (DNS-style), trimmed, NFC-normalised, IDNA-encoded? [Clarity, Gap] — SPEC-FIXED: FR-022 was silent on comparison semantics. - [x] CHK007 Are requirements specified for a peer cert with CN populated AND multiple SAN-DNS entries — does FR-022's "first non-empty wins" extract the CN, or iterate through SAN-DNS values? - [x] CHK008 Are requirements for the empty-cert / no-cert TLS-handshake case specified at the binding layer — does it bypass binding (already rejected at TLS layer per 011 `SecurityProfile::mtls_pinned`) or pass through with empty principal? [Coverage, Spec §FR-019, Gap] — PASS: The no-cert case is already handled by 011's `SecurityProfile::mtls_pinned` at the TLS layer — the handshake fails with `error::tls_handshake_failed` before any `handshake_result` is produced. - [x] CHK009 Are principal-to-compid-set cardinality requirements defined — must each principal map to ≥1 compid? Can the same compid appear in multiple principal sets (overlap permitted)? [Completeness, Gap] — SPEC-FIXED: FR-023 was silent on cardinality constraints. ## Requirement Clarity

- [x] CHK011 Is "asserted `SenderCompID`" (FR-019) precise about timing — only the first Logon, or any subsequent message? Can mid-session CompID re-assertion be rejected? [Clarity, Spec §FR-019] — SPEC-FIXED: FR-019 was silent on whether binding applies to subsequent Logons (re-Logon across reconnect) or mid-session non-Logon messages. Added to spec.md §FR-019: "The binding check runs ONCE per Logon message — the inbound `MsgType=A (Logon)` message is the ONLY trigger for `CompIdAuthorizationPolicy::authorize()`. Mid-session messages are NOT re-authorized per message. On reconnect, the new Logon drives a fresh binding check (the FSM runs FR-019 again with the new Logon's SenderCompID and the new `handshake_result.peer_id`). A mid-session SenderCompID change via a non-Logon message is not possible in standard FIX sessions — SenderCompID is set at session establishment and remains constant."
- [x] CHK012 Is "default-deny" (FR-023) clear for the boundary case of a populated policy that lists OTHER principals but not the connecting peer's — is this still `session_compid_unauthorized` rather than "no policy entry, allow"? [Clarity, Spec §FR-023] — PASS: FR-023 is explicit: "unmatched principal OR unmatched principal→compid pair returns `error::session_compid_unauthorized` (FR-021)." A populated policy that lists other principals but NOT the connecting peer's principal triggers the "unmatched principal" branch → `session_compid_unauthorized`. No "allow" escape. US2 AC6 confirms: "empty policy rejects ALL Logons." The non-empty-but-not-matching case is covered by the same rule.
- [x] CHK013 Is FR-022's "extraction order is invariant and not operator-overridable in v1.0" clear about whether per-binding-entry overrides are **deferred to a future feature** or **explicitly banned**? [Clarity, Spec §FR-022] — PASS: FR-022 says "a future feature MAY introduce per-binding-entry overrides if reference-engine industry pattern emerges." This is unambiguous: deferred to a future feature (not eternally banned). The v1.0 restriction is time-bounded, not categorical.
- [x] CHK014 Is the term "principal" defined precisely — the string value (e.g., `"ACME-PROD-01"`) or the `(source, value)` pair? Does `peer_identity_bound::principal_source` survive the policy lookup? [Clarity, Spec §FR-020, §FR-022] — PASS: FR-022 says "The resolved principal value is what `CompIdAuthorizationPolicy` keys against" — the key is the STRING VALUE only, not the (source, value) pair. `bound_principal` struct (contract) carries BOTH `value: std::string_view` AND `from: bound_principal::source` — the source field IS carried through the policy lookup and surfaced in `session_event_peer_identity_bound::principal_source` (contract session_event.hpp line 50). The principal is the string value for lookup purposes; the source is carried for audit purposes. Specified.

## Scenario Coverage

- [x] CHK022 Are requirements covered for an initiator-side rebinding when the peer's server cert rotates mid-session (we reconnect and observe a different `peer_identity` for the same compid)? [Coverage, Gap] — PASS: FR-019 runs on every Logon (per CHK011 SPEC-FIXED). On reconnect, a new `handshake_result.peer_id` is produced by the fresh TLS handshake; FR-019 runs the binding check with the new `peer_identity` and the new Logon's compid. If the new cert's principal maps to the same compid in the policy, the session proceeds normally. If not, `session_compid_unauthorized` fires. Covered by FR-019 + reconnect FSM semantics.
- [x] CHK023 Are requirements specified for the binding-policy-empty-AND-TLS-validation-succeeded case — is this an always-reject deployment (operator misconfiguration), or could it be a valid "open" deployment where binding is intentionally not used? [Coverage, Spec §FR-023] — PASS: FR-023 + A.4 + US2 AC6 are explicit: empty policy = default-deny = EVERY Logon rejected with `session_compid_unauthorized`. There is no "intentional open" mode — allow-list only means an empty allow-list is the closed configuration. Operators who want no binding must set a policy that accepts all expected CompIDs.
- [x] CHK024 Are requirements covered for FIX 4.2 vs FIX 4.4+ — does the CompID extraction protocol-version interact (e.g., `SenderSubID(50)` cross-check, `OnBehalfOfCompID(115)`, `DeliverToCompID(128)`)? [Coverage, Gap] — PASS: FR-019 binds the TLS cert principal to `SenderCompID(49)` ONLY; sub-comp IDs (`SenderSubID(50)`, `OnBehalfOfCompID(115)`, `DeliverToCompID(128)`) are outside the binding scope per FR-019. The binding is protocol-version independent — it operates on the cert identity, not FIX session-level sub-comp IDs. Out of scope by design for v1.0.
- [x] CHK025 Are requirements specified for a peer that succeeds binding but later attempts a `SenderCompID` change mid-session (relogon with different CompID across the same TLS session)? [Coverage, Gap] — PASS: Per CHK011 SPEC-FIXED, binding runs ONCE per Logon. A mid-session relogon (reconnect) triggers a new Logon with the new SenderCompID — FR-019 runs again with the new asserted CompID and the same (or new) `peer_identity`. If the new CompID is not in the authorized set, `session_compid_unauthorized` fires. Standard FIX does not permit mid-session CompID changes without a Logout/Logon cycle; the reconnect FSM always enforces a new Logon.

## Edge Case Coverage

- [x] CHK026 Are requirements specified for a peer chain with multiple end-entity certs (rare but valid mTLS) — which end-entity drives principal extraction? [Edge Case, Gap] — DD-DECIDED: 011's `verify_peer` produces exactly ONE `peer_identity` from the verified leaf cert of the peer's certificate chain. Multiple end-entity certs in a single TLS handshake are not supported by TLS 1.3 or standard X.509 mTLS; this case cannot arise with OpenSSL's standard `SSL_VERIFY_PEER`. Out of scope for v1.0 by precondition (011 contract).
- [x] CHK027 Are requirements specified for a SAN-URI with scheme variations (e.g., `spiffe://…` vs `urn:…`) — must the operator encode the exact URI byte-for-byte? [Edge Case, Gap] — PASS: Covered by CHK004/CHK007 SPEC-FIXED edits to spec.md §FR-022: SAN-URI matching is exact byte-for-byte comparison; no URI normalization. The operator MUST encode the exact URI as it appears in the cert (byte-for-byte).
- [x] CHK028 Are requirements specified for a CompID containing non-printable or UTF-8 bytes — rare-but-permitted under FIX 4.4 — and for the principal-key normalisation? [Edge Case, Gap] — PASS: Covered by CHK004 SPEC-FIXED (exact byte comparison, no NFC normalization) and CHK009 SPEC-FIXED / CHK023 text (exact byte CompID matching). No special treatment for non-printable bytes.
- [x] CHK029 Are requirements specified for the case where all of CN, SAN-DNS, SAN-URI are empty AND the fingerprint is the principal — operator MUST enumerate `(sha256_hex, compid_set)` bindings? [Edge Case, Spec §FR-022] — PASS: Covered by CHK006 SPEC-FIXED added to spec.md §FR-022: when SHA256_FINGERPRINT is the source, `bound_principal.value` is the 64-char lowercase hex fingerprint; the operator MUST supply `add_binding(hex_fingerprint, compid)`. Specified.

## Ambiguities & Conflicts

- [x] CHK036 Are "deny-list / hybrid modes are deferred" requirements (FR-023) backed by an explicitly-reserved surface (e.g., `enum class CompIdAuthorizationMode { allow_list_only }` with future-mode placeholders), or merely text-only? - [x] CHK038 Is the conflict between "no reference engine implements CompID↔cert binding" (Clarifications Q2/Q3 sweep finding) and "we set the default-deny precedent" resolved with a documented escape hatch — what does the operator do during a v1.0→v1.x migration if reference precedent emerges? [Conflict, Spec §A.4, Gap] — DD-DECIDED §Q3=A: FR-023 explicitly documents the one-way restriction ("adding modes is backward-compatible, removing the allow-list semantic is not") and that deny-list / hybrid modes are deferred to a later feature. The invariant "allow-list only" cannot be silently changed to "allow-all" without operator action. This is the appropriate design for a security-default surface per `[const §VI]`.
