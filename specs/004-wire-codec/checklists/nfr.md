## Allocation Discipline

- [x] CHK001 - Is the zero-allocation window bounded by a single, precisely-defined start and end point used identically across FR-012, SC-002, and the three-arena model? [Consistency, Spec FR-012/SC-002] — **PASS**: spec FR-012 "between the start of parse and the return of the simulated `fromApp`"; SC-002 "between the start of parse and the return of `fromApp`"; data-model PMR accounting "Global heap between parse and `fromApp`: 0"; plan.md §VIII.5 row "Zero `new`/`delete` between parse and `fromApp`"; `[2b §6.6]` same. Window identically bounded.
- [x] CHK002 - Is "between the start of parse and the return of `fromApp`" defined unambiguously (what event is "start of parse"; whose `fromApp`)? [Clarity, Spec FR-012] — **DD-DECIDED `[2b §6.6]` + spec Assumptions + arch §5.1**: `[2b §6.6]` "the session FSM ensures rotation happens **after** `fromApp` returns"; spec Assumptions binds "The per-message arena (`SessionConfig::message_arena`, `[arch §5.2]`) is provided by the caller/config and reset after `fromApp`"; the session-FSM-driven `fromApp` is the user `Application::fromApp` callback owned by the session module (FIX-FSM Phase-4 spec / `[arch §5.1]`). "Start of parse" = `Parser::parse` entry; "return of `fromApp`" = the user callback's return. Defined at the design-doc + architecture level (Phase-1 split: spec carries the contract; precise call-site semantics live at the design doc / session-FSM boundary owned by 2d/005).
- [x] CHK003 - Are the three arenas' lifetimes (per-message / session / writer-scratch) each specified with an explicit owner and reset trigger, with no arena left ambiguous? [Completeness, Spec Key Entities / Plan Constraints] — **PASS**: data-model State/lifetime table + `[2b §8]` PMR recap explicitly bind owner + lifetime + reset trigger per arena: `SessionConfig::message_arena` / per-message / session FSM after `fromApp`; `SessionConfig::framer_carry_arena` / session / session destruction; `Writer::scratch_mr` / one outbound build turn / caller after `commit()`. Explicit.
- [x] CHK004 - Is the requirement that allocation-bearing trait specializations use the supplied arena (not heap) stated as a testable obligation rather than guidance? [Measurability, Spec FR-012] — **PASS**: spec FR-012 "allocation-bearing trait specializations MUST use the per-message arena supplied by the wire layer"; data-model PMR accounting "Global heap between parse and `fromApp`: 0 — verified by `tools/check_alloc.py` under `mallocnesia`"; plan Test-seam #10 binds the allocation-guard test. Testable.
- [x] CHK005 - Is "Iter mode is zero-allocation end-to-end" stated as a distinct, separately-verifiable requirement from the Index-path arena bound? [Completeness, Spec FR-003/Plan] — **DD-DECIDED `[2b §6.6]` + data-model PMR accounting + plan.md**: data-model PMR accounting "**Iter path:** 0 allocations end-to-end"; `[2b §6.6]` "Iter mode is zero-allocation end-to-end (no offset table; no validator; no writer in the typical Iter consumer path)"; plan.md "Iter mode is zero-allocation end-to-end". Distinct from Index-path arena bound (which is bounded by §1.2 caps, not zero). Anchored at design-doc + data-model per Phase-1 split (spec FR-003 binds the compile-time mode selection requirement; zero-alloc invariant for Iter is the design-doc consequence).
- [x] CHK006 - Are the worst-case arena footprint figures (e.g. ≈80 KiB at the 4096-entry cap; validator ≤~600 B) specified with their derivation basis so they are auditable? [Measurability, Plan PMR accounting] — **PASS**: data-model PMR accounting "OffsetTable `entry[]` + hash overlay from per-message arena; ≤ §1.2 caps (worst-case ≈ 80 KiB at the 4096-entry cap)"; validator "≤ ~600 B from `scratch_mr`"; `[2b §1.2]` derivation "4096-entry table is `4096 × 12 = 48 KiB` of arena (§4.4) plus a `8192-slot` open-address pointer overlay (32 KiB on a 4-byte slot). At the cap the offset table consumes ~80 KiB"; `[2b §6.5]` validator scratch "A `seen[]` bitmap sized to `default_max_offset_entries / 8` ≈ 512 B ... required_remaining ≈ 10–50 B ... Total scratch per validate(): ~600 B worst case at the §1.2 cap". Derivation explicit.

## DoS / Capacity Bounds

- [x] CHK007 - Are all four DoS caps (frame size, offset-table occurrences, group entries/instance, tag range) each specified with a default value AND a distinct error code for the exceed path? [Completeness, Spec FR-015] — **PASS**: spec FR-015 enumerates all four: frame size 256 KiB → `wire_frame_too_large` (30); offset-table 4096 → `wire_offset_table_full` (35); group entries 4096 → `wire_group_too_large` (36); tag range `uint16_t` 0..65535 → `wire_tag_out_of_range` (37). Default + error per cap.
- [x] CHK008 - Is each cap's value stated once as a single source of truth (no drift between spec, plan, data-model)? [Consistency, Spec FR-015 / Plan / data-model] — **PASS**: spec FR-015 = data-model E2/E5 = `[2b §1.2]` = plan.md Constraints (`default_max_frame_bytes = 256 KiB`, `default_max_offset_entries = 4096` occurrence-space, `default_max_group_entries_per_instance = 4096`, `uint16_t` tag range). Single source of truth across artifacts.
- [x] CHK009 - Is "occurrence space" vs "distinct-tag space" for the offset-table cap defined explicitly so 4096 is unambiguous? [Ambiguity, Spec FR-002/FR-015] — **PASS**: spec FR-002 "each repeated-tag / repeating-group occurrence independently addressable"; data-model E5 "One entry per field **occurrence**, not per distinct tag"; `[2b §1.2]` "v0.1 conflated the two; v0.2 caps in occurrence space" + dedicated normative paragraph; design-doc Appendix C Root cause #1 records the v0.1→v0.2 correction. Unambiguous (this was the Gate A r1 RC#1 reconciliation).
- [x] CHK010 - Is the per-group-instance cap explicitly scoped as per-instance (not aggregate) in the requirement text? [Clarity, Spec Edge Cases] — **PASS**: spec FR-015 "maximum group entries per instance (default 4096 → `wire_group_too_large`)"; Edge Cases "the per-group-instance entry cap (`default_max_group_entries_per_instance`, 4096) is enforced per instance, not aggregate"; `[2b §1.2]` "Per-instance, not aggregate (a `NewOrderList` with 100 orders × 50 legs each is allowed ...)". Explicit.
- [x] CHK011 - Is "bounded memory and no crash when exceeded" stated as an objectively verifiable acceptance condition? [Measurability, Spec FR-015/SC-003] — **PASS**: spec FR-015 "with bounded memory and no crash when exceeded"; SC-003 "rejected with the defined wire error and bounded memory — zero crashes, zero unbounded allocation, zero out-of-bounds access (clean under sanitizers and fuzzing)". Triple-zero predicate is objectively verifiable.
- [x] CHK012 - Are the caps documented as caller-tunable bounds (not FIX-spec invariants), including the explicit "rejects conformant venue traffic on day one" consequence? [Completeness, Spec Assumptions] — **PASS**: spec Assumptions "The DoS caps are caller-tunable bounds for memory/DoS protection, not FIX-spec invariants; defaults target FX/equities. Per `[2b §1.2]` these defaults **reject conformant venue traffic on day one** for options/derivatives (e.g. a 1000-strike-option-chain MDIR ≈ 200 KiB is past the 256 KiB frame cap; CME/CBOE SPX `SecurityList` ≈ 3000–5000 strikes exceeds the 4096-occurrence offset cap) — those venues MUST raise the caps ... this is the explicit, testable design-doc tuning claim, not a silent overflow". Explicit.

## Lifetime & Flyweight Safety

- [x] CHK013 - Is the flyweight lifetime contract (view lifetime ⊆ originating buffer) stated as a requirement, not only an entity description? [Completeness, Spec FR-016/Key Entities] — **PASS**: spec FR-016 "the flyweight lifetime contract: `[[clang::lifetimebound]]` markers on view-producing surfaces ... and a debug-build generation-counter trap on use-after-buffer-reuse"; Key Entities "View (flyweight base): zero-copy, non-owning; lifetime is the underlying buffer's; carries a debug-only generation token to detect use-after-reuse"; data-model E1 "lifetime ⊆ originating frame buffer". Both requirement + entity description.
- [x] CHK014 - Are the debug-trap behaviour and the release-strip behaviour of the generation token specified as two distinct, separately-testable requirements? [Clarity, Spec FR-016] — **PASS**: spec FR-016 "a debug-build generation-counter trap on use-after-buffer-reuse, with the counter compiled out in release builds"; data-model E1 "Trivially copyable in release. ... `check_alive()` traps in debug if pool generation rotated past `gen_`"; plan Test-seam #7 + tasks.md T015 bind the lifetime-trap test (debug trap + release no-trap). Distinct + separately verifiable.
- [x] CHK015 - Is the `[[clang::lifetimebound]]` obligation specified with its accepted enforcement gap (MSVC) so the requirement is not over-claimed? [Consistency, Spec FR-016/Assumptions] — **PASS**: spec FR-016 "(best-effort on Clang/GCC, accepted gap on MSVC per `[const §IX.4]`)"; spec Assumptions "MSVC lifetime-annotation enforcement is a known, accepted gap (`[const §IX.4]`); Clang is the primary enforcement target, GCC best-effort"; `[2b §6.4]` confirms. Gap explicit, not over-claimed.
- [x] CHK016 - Is "capturing a view past `fromApp`" classified with a defined outcome for both release (UB) and debug (trap)? [Coverage, Spec Key Entities / data-model] — **PASS**: data-model E4 "capturing past `fromApp` is UB in release / debug-trap"; `[2b §6.4]` "Outliving that buffer is undefined behavior in release; debug builds trap"; `[2b §6.6]` "Capturing a `MessageView` past `fromApp` return is undefined in release; debug builds trap via the §6.4 generation-counter mechanism". Both outcomes defined.
