## Scratch-Arena Bound

- [x] CHK009 - Is the whole-message entry point specified to take an explicit caller-supplied scratch arena (`validate(msg, scratch_mr)`)? [Clarity, Spec FR-011 / data-model E7] — **PASS**: spec FR-011 "Its whole-message entry point MUST take an explicit scratch arena — `validate(msg, scratch_mr)` per `[2b §4.6]`/`[2b §6.6]`"; data-model E7 "`validate(msg, scratch_mr)`"; contracts/validator.hpp signature "`validate(MessageView<...> const& msg, std::pmr::memory_resource* scratch_mr)`". Explicit.
- [x] CHK010 - Is the working-set bound (~600 B: `seen[]` bitmap + `required_remaining`) specified with its composition so it is auditable? [Measurability, Spec FR-011 / data-model E7] — **PASS**: spec FR-011 "its ≤ ~600 B working set (`seen[]` bitmap + `required_remaining` list)"; data-model E7 "`seen[]` bitmap (~512 B at cap) + `required_remaining` sorted `pmr::vector<uint16_t>` (~10–50 B); ≤ ~600 B worst-case from `scratch_mr`"; `[2b §6.5]` derivation paragraph "A `seen[]` bitmap sized to `default_max_offset_entries / 8` ≈ 512 B ... A `required_remaining` set ... ⇒ 10–50 B ... Total scratch per validate(): ~600 B worst case at the §1.2 cap". Composition + derivation auditable.
- [x] CHK011 - Is `validate_field` specified as allocation-free distinctly from the arena-bound whole-message path? [Completeness, data-model E7] — **PASS**: data-model E7 "`validate_field` allocation-free"; data-model PMR accounting "**Validator.validate:** ≤ ~600 B from `scratch_mr`. `validate_field`: 0"; `[2b §6.5]` "`Validator::validate_field(tag, value)` is allocation-free; it consults `dict::table_view`'s field-type rule and applies the type's validator directly to the byte span". Two-line distinction explicit.
- [x] CHK012 - Is the validator's zero-`new`/`delete` claim traced onto FR-012/SC-002 so the allocation guarantee covers the validator path? [Traceability, Spec FR-011/FR-012] — **PASS**: spec FR-011 "so the zero-heap-allocation claim (SC-002) is FR-traceable onto the validator path (no `new`/`delete`; allocation is confined to the named caller-supplied arena, `[const §VIII.5]`)"; FR-012 "The system MUST NOT perform any heap allocation (`new`/`delete`) between the start of parse and the return of the simulated `fromApp` (`[const §VIII.5]`)"; SC-002 measures the full parse+serialize path; data-model PMR accounting "Global heap between parse and `fromApp`: 0 — verified by `tools/check_alloc.py` under `mallocnesia` (seam #10)". The validator path is FR-traceable onto SC-002 (FR-011 binds the trace explicitly).
