## Encoding & Framing Fidelity

- [x] CHK006 - Are the Tag=Value/SOH encoding rules (W-001) specified precisely enough that ASCII-digit tag, `=` separator, and SOH delimiter are unambiguous? [Clarity, Spec FR-001] — **DD-DECIDED `[2b §4.2]` + `[2b §6.1]` + `[FIX50SP2 §3]`**: spec.md FR-001 names "Tag=Value SOH-delimited FIX messages (W-001)"; the design doc §4.2 + §6.1 specifies the exact byte algorithm (locate `8=`, parse `9=BodyLength|`, byte ranges, SOH delimiter). `[FIX50SP2 §3]` is the cited normative reference. The combination is unambiguous; precise byte-level grammar belongs in the design doc per the Phase-1 split.
- [x] CHK007 - Are the standard header (W-002) and trailer (W-003) mandatory fields and their ordering requirements stated, including the out-of-order/duplicated-header outcomes? [Completeness, Spec FR-001/Edge Cases] — **DD-DECIDED `[2b §6.5 rule 1]` + spec.md Edge Cases**: spec FR-001 binds W-002/W-003 surface; Edge Cases enumerates "duplicated standard header fields, and out-of-order mandatory header fields"; the design doc §6.5 rule 1 maps the outcome to `wire_header_out_of_order` (slot 39, data-model Error mapping). Outcomes are anchored.
- [x] CHK008 - Is `BodyLength(9)` computation specified by exact byte range (field after BodyLength through byte before CheckSum) and rendering (digit-only, no space padding)? [Clarity, Spec FR-007 / research D-5] — **PASS**: spec.md FR-007 + US2 acceptance scenario 1 ("`BodyLength(9)` equals the byte count from the field after `BodyLength` through the byte before `CheckSum`"); research D-5 ("digit-only BodyLength rendered with a `memmove` backpatch at `commit()` (no space padding)"); `[2b §4.5]` algorithm steps 1–4 + `[FIX50SP2 §3.3]` `Length` data-type rule (no padding) is the binding rationale. Edge.md CHK017 mirrors the rejection-side requirement. Specified precisely.
- [x] CHK009 - Is `CheckSum(10)` specified as unsigned byte-sum mod 256, exactly 3 zero-padded ASCII digits, with XOR explicitly excluded? [Clarity, Spec FR-007 / research D-5] — **PASS**: spec.md US2 acceptance scenario 1 ("`CheckSum(10)` equals the unsigned sum of all preceding bytes modulo 256, formatted as exactly 3 zero-padded ASCII digits"); research D-5 ("byte-sum, *not* XOR — Codex P1 #2"); `[2b §4.5]` step 5 + `[2b §6.1]` step 5 + `[2b §App-C]` Codex P1 #2 ("XOR sum mod 256 vs FIX byte-sum mod 256 → §6.1 step 5 + §4.5 commit algorithm rewritten"). XOR explicitly excluded as a documented anti-pattern that test seam #12 regression-tests.
- [x] CHK010 - Is pipelined multi-message framing (W-010) specified with the partial-carry and pre-parser verification obligations, not just "frame a stream"? [Completeness, Spec FR-009] — **PASS**: spec FR-009 ("emitting zero or more complete frames per feed, carrying partial trailing bytes over to the next feed, and verifying `BodyLength` and `CheckSum` before any parser is exposed to a frame"); spec Key Entities ("Framer carry buffer"); `[2b §4.2]`/`[2b §6.1]` step 4 carry algorithm; plan Test-seam #4 partial-read test. Pre-parser verification obligation is explicit.

## Structural Fidelity

- [x] CHK011 - Are repeating-group (W-006) and nested-group (W-007) requirements specified distinctly, including delimiter/first-field rules driven by the dictionary? [Completeness, Spec FR-004] — **PASS**: spec FR-004 ("decode/encode repeating groups including nested groups (W-006, W-007)"); Edge Cases ("Nested repeating groups: groups within groups (W-007) index and round-trip correctly"); `[2b §4.7]` + `[2b §7.2]` (`group_first_field` dictionary rule, per `[FIX50SP2 §3]`). Validator FR-011 names `group_first_field` as one of the 5 pure-virtuals. Edge.md CHK004 mirrors distinctness.
- [x] CHK012 - Is the `Length`+`Data` (W-008) requirement specified with the Index-vs-Iter scope boundary (runtime dict vs static FIX-5.0-SP2 table), not left as "handle Data fields"? [Coverage, Spec FR-005 / research D-11] — **PASS**: spec FR-005 explicitly "Scope boundary (`[2b §4.3]`, design §10 Q5): Index mode handles all dialect-introduced `Length`+`Data` pairs via the runtime dictionary; Iter mode uses a static `constexpr` table of FIX-5.0-SP2-standard pairs and does **not** cover dialect-introduced *new* BLOB pairs for v1.0 (those need Index mode or a 2c static-table specialization — deferred per research D-11)". Boundary unambiguous.
- [x] CHK013 - Is the W-009 field-data-type set enumerated (the spec lists the full type set) so "all field data types" is bounded, with decode/encode delegated to 2a/2c traits (no wire-side decoding)? [Clarity, Spec FR-006] — **DD-DECIDED `[FIX50SP2 §3.3]` + `[2b §7.1]` + `[2b §7.2]` + spec FR-006**: spec FR-006 explicitly delegates to "the field-representation traits owned by 2a (`decimal<T>`) and 2c (`dict::field_traits<...>`); the wire layer MUST NOT re-implement field decoding". The full FIX type set is normatively enumerated in `[FIX50SP2 §3.3]` (the cited authority); ownership lives in 2a (decimal) and 2c (everything else) per the Phase-1 ownership split. Wire's spec is bounded by delegation — the type set is closed-by-reference at the cited spec, not re-enumerated here.
- [x] CHK014 - Is the zero-copy requirement (W-011) stated as a non-owning, alias-the-buffer obligation with a measurable acceptance (zero copies / zero alloc)? [Measurability, Spec FR-001/SC-002] — **PASS**: spec FR-001 ("non-owning, zero-copy view whose lifetime is the caller-owned buffer's"); FR-012 + SC-002 ("Zero heap allocations occur between the start of parse and the return of `fromApp`, verified by an allocation-counting harness"); Key Entities "View (flyweight base): zero-copy, non-owning". Measurable via the `mallocnesia` `tools/check_alloc.py` seam #10.
- [x] CHK015 - Is the offset-table O(1)-by-tag requirement (W-012) specified with occurrence-level addressability (not distinct-tag), consistent with FR-002? [Consistency, Spec FR-002] — **PASS**: spec FR-002 ("O(1)-by-tag field lookup (W-012), with each repeated-tag / repeating-group occurrence independently addressable in document order"); data-model E5 ("One entry per field **occurrence**, not per distinct tag"); `[2b §1.2]` explicitly corrected v0.1's wrong-dimension model — "occurrence space" is the binding dimension. Consistent throughout spec / data-model / design-doc.
- [x] CHK016 - Are the serializer (W-013) and validator (W-014) conformance obligations each traced to a distinct FR and SC, not folded into a generic statement? [Traceability, Spec FR-007/FR-010] — **PASS**: W-013 → FR-007 (Writer auto BodyLength/CheckSum) + SC-001 (round-trip) + US2; W-014 → FR-010 (full per-version default validator) + FR-011 (exactly 5 pure-virtual) + SC-005 (zero false accept) + SC-007 (no virtual wire→dict edge) + US4. Distinct FR/SC anchors per row.
