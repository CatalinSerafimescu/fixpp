# Contract: type-erased lock + awaitable-header cleanliness

**Feature**: `046-atomic-shared-ptr` | Replaces the (rejected) Article XI §3 amendment. **No constitution change.**

## Goal

Keep `atomic_shared_ptr.hpp` free of `std::mutex` (and the FR-014 six banned mutex types) on **every** standard library, so the two awaitable consumers that include it (`async_mutex.hpp`, `engine.hpp`) never breach Article XI §3 / XV §9 — without amending the constitution.

## Header/`.cpp` boundary

- **Header (`include/fixpp/core/sync/detail/atomic_shared_ptr.hpp`)** — under `detail/` ⇒ physically installed (public headers depend on it) but **excluded from the supported API / Doxygen stability surface** per [arch §9.1] (not public API):
  - Native path: `using atomic_shared_ptr = std::atomic<std::shared_ptr<T>>;` (no lock at all).
  - Fallback path: the `atomic_shared_ptr<T>` class with `load`/`store`/`exchange`/`compare_exchange` whose bodies acquire `fixpp::sync::detail::shard_guard g(this);` (RAII) instead of `std::lock_guard<std::mutex>`.
  - **MUST NOT** `#include <mutex>` or name any of the six banned mutex types.
  - Declares `namespace detail { class shard_guard { public: explicit shard_guard(const void* self) noexcept; ~shard_guard(); shard_guard(const shard_guard&) = delete; shard_guard& operator=(const shard_guard&) = delete; shard_guard(shard_guard&&) = delete; shard_guard& operator=(shard_guard&&) = delete; private: std::size_t shard_index_; }; }`.
  - **State layout (Codex #9)**: the single header-visible member is `std::size_t shard_index_` — a plain integer, **emphatically not** a `std::mutex*`, `std::unique_lock`, or any `<mutex>`-adjacent type (that would re-introduce a banned token into the header). The ctor computes the index from `self` and locks the corresponding shard (in the `.cpp`); `shard_index_` records which shard the dtor must unlock. The guard is non-copyable **and non-movable** (it owns a held lock for its scope). Size/alignment = `sizeof(std::size_t)`; no other members.
  - **`noexcept` contract (New-C — DELIBERATE)**: `shard_guard`'s ctor is declared `noexcept`. Its out-of-line body calls `std::mutex::lock()`, which is **not** standard-`noexcept` (may throw `std::system_error`); a throw across the `noexcept` boundary therefore `std::terminate`s. This is **intentional and recorded** — it matches `std::atomic`'s no-throw operation contract (P0718 ops are `noexcept`), and a shard-lock failure here is an unrecoverable resource-exhaustion fault, not a recoverable error. The ctor does **not** catch (catching would only let an op proceed without the lock = a data race). See spec Clarifications 2026-06-21. (This is the catalogued [[feedback_noexcept_boundary_user_callback_terminate]] class, here resolved by *keeping* `noexcept` + documenting terminate-on-lock-failure, not by silencing it.)
- **TU (`src/core/sync/atomic_shared_ptr.cpp`)** — **always compiled** into the promoted `fixpp_sync` STATIC/OBJECT target on **every** mode (native and fallback alike); see the always-ship-guard decision in **CT-4** / research D-9:
  - Defines the 128-`std::mutex` function-local-static shard table + the address-hash (murmur finalizer).
  - Defines `shard_guard::shard_guard(const void*)` (hash `self` → `shard_index_` → lock) and `~shard_guard()` (unlock `shard_index_`).
  - This is the **only** project TU that names `std::mutex` for this primitive.
  - **Zero native overhead despite always-compiling**: the shard table is a function-local-static, so on a native build the `shard_guard` symbols are present-but-never-called (the native `atomic_shared_ptr` is a pure alias whose `load`/`store` never construct a `shard_guard`) → the lazy-init never fires, there is no call-site codegen change, and SC-005 (zero Tier-1 regression) holds. The shipped symbols are `fixpp::sync::detail::` internal, not public ABI.

## Behavioral equivalence to the harness

- Same sharding (128, address-hash with high-bit mixing), same lock discipline (one shard lock per op, released on return), same CAS-equivalence and memory-order behavior. The lock is held only across a synchronous `shared_ptr` op; **never across a `co_await`**.

## Acceptance

- **CT-1** (the load-bearing no-amendment check — must be **falsifiable on the libc++ leg**, the only path where it could fail):
  - **CT-1a (script fail-closed + `-stdlib` forwarding, New-A/Codex #1/#2)**: `tools/check_no_std_mutex_in_awaitable_headers.sh` MUST be edited (this is a listed Project-Structure edit, plan.md):
    1. **Fail on any preprocessing (`-E`) error** — the current `|| true` swallow (script L171) is removed so a missing dep / broken include path / compile error RED-fails instead of silently passing with empty output. Safe to apply globally (the Tier-1 toolchain is known-good).
    2. **Recognize and forward `-stdlib=*`** to the compiler flags. **Source-verified defect (round 2)**: the current flag parser (L67–78) accepts only `-I`/`-Ipath`/`-D*`/`--std=*`/`-std=*`; `-stdlib=libc++` falls into the `else` branch (L77) and is appended to `HEADERS`, then at L160 hits `[[ ! -f "$HEADER" ]]` and emits a `WARNING: header not found` (**not** an `-E` error) before `continue` — so CT-1a's fail-closed never fires and the real headers preprocess under the host-default libstdc++ (clang++ default on this host). The parser MUST add a branch matching `-stdlib=*` (and forward it into `INCLUDE_FLAGS`).
    3. **Use the preset's configured clang** for the libc++ leg (so the `-stdlib=libc++` flag is honored by the same compiler the `linux-clang-libc++` preset builds with), not merely the first compiler found on `PATH` — pass `CXX`/the preset compiler explicitly.
  - **CT-1b (Tier-1 leg unchanged)**: the existing `check_no_std_mutex_corpus` ctest (`tests/sync/CMakeLists.txt`) stays green under the default libstdc++ toolchain with its **current membership unchanged** — `engine.hpp` and every transitive includer are **already registered** (039 US4); **no header is added**.
  - **CT-1c (libc++ leg, NEW — the actual proof, with a `_LIBCPP_VERSION`-active assertion)**: a **new** ctest, registered **only in the `linux-clang-libc++` preset** (NOT mutating the existing corpus test), runs the gate with `-stdlib=libc++` + the libc++ include path over `core/sync/async_mutex.hpp` + `session/engine.hpp`, and **asserts each supplied header emitted the `asio/awaitable.hpp` marker** (so a libc++ misconfig → empty output → RED, never silent-pass). **AND** it MUST positively assert **libc++ is actually active** (closing Codex #1's "vacuous PASS under libstdc++" hole): a concrete probe — preprocess a one-line TU (`#include <version>`) with the same `-stdlib=libc++ <preset-clang>` invocation and `-dM`, then **grep the macro dump for `_LIBCPP_VERSION`; RED-fail if it is absent** (proving the leg ran under libc++, not the host default). Only this combined run proves the header is mutex-free *on the path where the fallback compiles in*.
  - **CT-1d (mutation fixture — both legs once CT-1a lands, New-P3-1)**: a fixture in which a project-local **transitive** include introduces a banned mutex type into an awaitable header → the gate MUST fire (proves CT-1 discriminates, not just passes vacuously). The fixture MUST run on **both** the libstdc++ leg (file-attribution discrimination) **and** — once CT-1a's `-stdlib` forwarding lands — the **libc++ leg**, so the discrimination proof and the no-amendment proof (CT-1c) live on the same path (the only path where the real fallback `std::mutex` could leak).
- **CT-2**: a `static_assert`/grep confirms `core/sync/detail/atomic_shared_ptr.hpp` does not `#include <mutex>` nor name a banned mutex type.
- **CT-3 (enumerate the re-validated harness tests)**: the type-erased guard MUST re-pass the integrated inventory rows that exercise the lock path — specifically plan "Integrated test inventory" rows **4** (contention TSan + ASan/UBSan), **5** (CAS equivalence), **6** (publish/acquire ordering TSan), **7** (linearizability + allocator-pressure), **3** (refcount integrity), and **10** (30s randomized stress) — run against the out-of-line `shard_guard` shape (not the harness's inline `lock_guard`). Passing these re-establishes that the structural lock-path adaptation preserved the harness semantics.
- **CT-4 (mode contract — PINNED: always-ship-the-guard, Codex #3/#4)**: the library's fallback-vs-native mode MUST be a **single target-level contract**, not a per-TU accident. CMake applies exactly one selector (`-DFIXPP_FORCE_ATOMIC_SHARED_PTR_FALLBACK` / `_NATIVE`, or the auto-detected default) **consistently to the `fixpp_sync` implementation and every consumer target** in a build. **Decision (pinned at Gate A round 2 — no longer deferred to `/implement` or tasks)**: `src/core/sync/atomic_shared_ptr.cpp` (the `shard_guard` lock/unlock bodies + the 128-`std::mutex` shard table) is **always compiled into `fixpp_sync` on every mode** (native and fallback), so the guard symbols are **always present at link time**; the *header* conditionally **uses** them (only the fallback `atomic_shared_ptr<T>` class constructs a `shard_guard`). This closes the failure Codex #3 named — an auto-detected *native* library has no exported selector to communicate its resolved mode downstream, so a downstream `FIXPP_FORCE_ATOMIC_SHARED_PTR_FALLBACK` define selects the fallback class; under always-ship that define **always finds its guard symbols**, so there is no mixed-mode link failure to guard against. **Native zero-overhead is preserved** (see the TU bullet above: the always-compiled symbols are never *called* on native — function-local-static lazy-init never fires — so SC-005 holds; `fixpp_sync` promotes INTERFACE→STATIC **unconditionally**, not per-config). The forced-fallback **link tests** (inventory row +B: `tls/transport/session_forced_fallback_link`) build the whole configuration in fallback mode and assert the guard symbols resolve. (The rejected alternative — exporting a resolved-mode compile definition + a compile-time mismatch check covering auto-detected builds — is more complex for no benefit once symbols always ship; not chosen.)
