## User Scenarios & Testing *(mandatory)*

### User Story 1 — A downstream C++ project consumes fixpp via `find_package` (Priority: P1)

An integrator wants to use fixpp in their own CMake project. They install a fixpp package, write `find_package(fixpp REQUIRED)` and `target_link_libraries(app PRIVATE fixpp::fixpp)`, include a core header, and build. Everything — include paths, compile features, transitive third-party dependencies — arrives through the imported target. They never hand-add an include directory and never guess a link line.

**Why this priority**: This is the entire point of a `-dev` package. Today a consumer must hand-add the include directory because there is no config package at all, which makes fixpp effectively un-consumable by normal CMake projects. Every other story in this feature is packaging *around* this capability. It is also the 078 follow-up that B-10 explicitly folds in.

**Independent Test**: Extend the existing `fixpp::consumer::install-witness` ctest (`CMakeLists.txt:289-311`, driven by `tests/consumer/run_consumer_witness.cmake`) to stage-install the build, then configure the standalone consumer project against the staged prefix using `find_package(fixpp)` + `fixpp::fixpp` rather than a hand-added include path. **This is not a discovery-only change**: the witness links four archives by hand today (`tests/consumer/CMakeLists.txt:56`), and `fixpp::fixpp` pulls the full closure plus OpenSSL, asio and Crc32c — so the minimal tier acquires a link surface it does not have today (Assumption 7). Green witness = Story 1's *resolution and link-closure* half delivered; it does not cover the operator-environment half (SC-016) or the live-session half (SC-011).

**Acceptance Scenarios**:

1. **Given** a staged install prefix produced from any in-scope configuration, **When** a standalone CMake project calls `find_package(fixpp REQUIRED)`, **Then** configuration succeeds and `fixpp::fixpp` is defined as an imported target.
2. **Given** that consumer project, **When** it links only `fixpp::fixpp` and includes a public core header, **Then** it compiles and links with no manually specified include directory and no manually specified library path.
3. **Given** a consumer built in a configuration different from the installed package, **When** it configures, **Then** it either resolves correctly or fails with a clear diagnostic — never with an undefined-symbol error at link time.
4. **Given** an installed package, **When** the consumer's `find_package` runs, **Then** every third-party dependency required by the exported targets is located transitively without the consumer naming it.
5. **Given** the installed include tree, **When** a consumer attempts to include a typed-builder `Args` header, **Then** the header is absent — confirming the 078 export-scope boundary holds.
6. **Given** an installed package, **When** a **real FIX client program** — one that establishes sessions, sends and receives application messages over a transport, and is already used to benchmark fixpp against a third-party engine — is built against it, **Then** it compiles, links, and runs against a live counterparty.
7. **Given** that real client, **When** it is built, **Then** it names only the installed package and its own dependencies — it does not reach into the fixpp source tree, its private header roots, or its test-support headers. *(Genuinely delivered as of Gate B round 1, finding F1: the initial `/speckit-implement` pass satisfied the driver's dictionary-helper include by COPYING `tests/support/minimal_dictionary.hpp` — a private test-support header — into the scratch project, recorded only as a `tasks.md` note and never reconciled with this scenario. Fixed with a witness-local shim (`tests/packaging/real_client/shim/support/minimal_dictionary.hpp`) that loads the **shipped** `FIX42.xml` through the public `XmlLoader::load` API instead, on the same precedent already used for the HdrHistogram stand-in four lines below in `tasks.md`. The driver stays byte-for-byte unmodified — its quoted `"support/minimal_dictionary.hpp"` include now resolves to the shim via the compiler's normal include-path fallback rather than to a copy of the private header — so this scenario's property now genuinely holds, and `run_real_client_witness.cmake` asserts it directly rather than only by the absence of a copy step.)*

**Witness strategy for this story** — **three** tiers, because they fail differently *(corrected at Gate A round 2: this said "two", which survived the round-1 repair that landed the third tier in `plan.md` and `data-model.md`. It is the first thing a task generator reads for this story, so a two-tier heading here can drop SC-016 from a derived task list while every other document says three)*:

- The **minimal** tier (the existing `fixpp::consumer::install-witness`) proves `find_package` resolves and the umbrella target carries include paths — **and, after this feature switches it from four hand-listed archives to `fixpp::fixpp`, that the export closure links** (Assumption 7). It is fast, runs in every configuration, and catches config-package regressions.
- The **real-client** tier proves the export is *sufficient to build a working FIX application*, linked **and run** against a live counterparty. This is the tier that catches an export set that resolves but cannot link a real program.
- The **clean-environment** tier (**SC-016**) is the only one that inherits **nothing** from the producing build — no Conan toolchain, no source-tree path. It is **mandatory**, not optional: the other two are both handed the producer's Conan toolchain (`tests/consumer/CMakeLists.txt:39-44`), so neither can fail on the dependency-provisioning gap, and without this tier they are green against a package no operator can consume (FR-018e, research R13).

The real-client tier is grounded in an existing program rather than a purpose-built one: `perf/fixpp_perf_driver.cpp` already consumes only public `<fixpp/...>` headers (engine, session, application, transport, TLS, parser) and links the session/transport/TLS stack with a documented static-link-order constraint against OpenSSL. It is the fixpp half of the cross-engine benchmark rig — it establishes real sessions over real sockets in both plaintext and TLS, in single-process and split initiator/acceptor topologies — so it is a genuine client by construction, not a mock.

Three adaptations the packaged variant requires, none of which change the program's status as a real client:

- Its one non-public include is a **test-support dictionary helper**; the packaged variant MUST replace it with a runtime dictionary load through the public API, reading a dictionary shipped in the package (FR-018a). *(Delivered as of Gate B round 1, finding F1 — see the scenario 7 note above: `tests/packaging/real_client/shim/support/minimal_dictionary.hpp` loads the shipped `dictionaries/FIX42.xml` via `fixpp::dict::XmlLoader::load` from the staged install prefix. Kept as FIX 4.2, not FIX 4.4 — the driver's use of this helper is version-agnostic, and substituting versions was no part of what this fix required.)*
- Its build **fetches an external histogram library from the network** and adds the source and test directories to its include path. The packaged variant MUST drop all three — the histogram is latency instrumentation irrelevant to a link-and-run witness, and the include paths are exactly what SC-012 forbids.
- It is **disabled by default** behind a build option, so the witness must enable it explicitly rather than assume it is present.

**A standing caution from the benchmark work applies directly here**: this driver is documented as needing an in-tree build so that it links freshly generated libraries rather than a stale prebuilt one. Building it out-of-tree against an installed package is a deliberate inversion of that guidance, and it is safe *only* because the package is produced from the build under test — which is what FR-021a exists to enforce. Treat any relaxation of FR-021a as reintroducing the staleness trap that guidance was written to prevent.

### User Story 2 — An operator installs fixpp from a platform-native package (Priority: P2)

An operator on a supported platform obtains a package artifact for their toolchain and configuration and installs it with their platform's normal tooling. They get public headers, the static libraries, and the CMake package config in standard locations, with package metadata that identifies the product, version, and license.

**Why this priority**: This is B-10's stated business value — "operators need installable artifacts, not just source builds." It ranks below Story 1 because a package whose contents cannot be consumed via `find_package` is a container with no product in it; Story 1 defines the payload, Story 2 distributes it.

> **What this story does and does not promise** *(rewritten at Gate A sign-off; this previously made delivery contingent on choosing a provisioning model)*. The package is **provider-agnostic**: its config resolves each dependency by plain `find_package` against the operator's own `CMAKE_PREFIX_PATH`, from whatever provider they use. `find_dependency` still **locates** rather than **provides**, so the operator must have the six dependencies of `contracts/export-set.md` §4 available — and **two of them, `Crc32c` and `opentelemetry-cpp`, are rarely offered by a platform package manager**, so a typical operator will have to supply those themselves. The package description MUST say this plainly (FR-018e obligation 3) rather than let an operator discover it at `find_package(fixpp)`. SC-016 is the check that keeps it honest.

**Independent Test**: Run the package step on a configured build tree and assert the produced artifacts exist, carry the expected name/version, and — for at least one generator — that extracting them yields the same file set as a direct staged install.

**Acceptance Scenarios**:

1. **Given** a configured and built tree for an in-scope Linux configuration, **When** the package step runs, **Then** DEB, RPM, and TGZ artifacts are produced, each named to encode product, version, platform, toolchain, configuration, **and format** — the three differ only in format, so each must be independently identifiable by name, not merely by directory placement (FR-017).
2. **Given** a configured and built tree for an in-scope Windows configuration, **When** the package step runs, **Then** a ZIP artifact is produced with the same naming scheme.
3. **Given** any produced package, **When** its contents are listed, **Then** they contain the public headers, the exported libraries, and the CMake package-config files — and contain no test executables, no build system scratch, and no denylisted generated sources.
4. **Given** a Debug-configuration package, **When** its libraries are inspected, **Then** debug information is present and usable for symbolication.
5. **Given** a Release-configuration package, **When** its libraries are inspected, **Then** no debug information is present.

### Edge Cases

- **Configuration mismatch between package and consumer.** A dependency resolved for one configuration can leave an imported target with no location for another, producing undefined references at link time rather than a configuration error. The existing witness already documents this exact failure for the private XML-parser dependency (`CMakeLists.txt:299-304`). Must fail loudly at configure time, not silently at link time.
- **A new generated-artifact kind appears under the codegen include root.** The exclusion set at `CMakeLists.txt:349-355` is an allowlist-by-exclusion: anything new is installed by default. A future emitter that adds a directory type would silently leak unexported symbols into the package.
- **A "must be absent" check written from the 078 five-pattern subset.** The exclusion block is **eight** patterns (seven when this was written — see the FR-009 amendment banner); `_dispatch` and `vt11` sit above the 078 five and are excluded on different grounds, and `Manifest.txt` was added below them during implementation. A content gate built from the five would pass a package that leaked the build-tree-private reify bridge or the FIXT.1.1 tree, while looking coherent. **The deeper lesson, learned when `Manifest.txt` was caught: any denylist-shaped content gate is unfalsifiable on a genuinely NEW artifact kind, whatever its length.** Assert the present set exactly instead.
- **An operator installs on a host that does not have every dependency.** `find_dependency` locates rather than provides, so `find_package(fixpp)` fails at **configure** wherever any of the six is unfindable — most likely `Crc32c` or `opentelemetry-cpp`, which few platforms package. The failure is loud and names the missing package, which is the correct behaviour; what must not happen is the operator being surprised by it (FR-018e obligation 3, SC-016).
- **The generated config bakes in a build-host path.** A `fixppConfig.cmake` or `fixppTargets*.cmake` carrying an absolute path under the producing host's package-manager cache configures perfectly on that host and is unusable anywhere else — the provider-agnostic property lost silently, in generated files nobody reads (FR-018e obligation 1).
- **An exported target transitively reaches an unexported one.** Exporting a target whose link interface names `fixpp_builders_<ver>` or `fixpp_validators_<ver>` breaks consumer configuration, because those targets are absent from the export set by design.
- **Debug package size.** Debug archives carry DWARF for every translation unit; the measured Release-to-Debug ratio on a single library is ~17×. Packages must remain producible without exhausting build-host storage.
- **Windows debug information lives outside the library file.** Debug info is emitted to separate symbol files rather than into the static library, so a Windows Debug package built with Linux-shaped install rules would ship undebuggable libraries. There is no Linux counterpart to this rule.
- **Stale export state across a reconfigure.** A tree configured before the export existed, then reconfigured, must not produce a package containing a partially-generated config.
- **A consumer requests an incompatible version.** `find_package(fixpp 1.0 REQUIRED)` against an installed 0.0.1 must fail at configure time with a version diagnostic.

## Requirements *(mandatory)*

### Functional Requirements

#### Package-config export (the 078 follow-up)

- **FR-001**: The build MUST define a single public umbrella target, exported under the `fixpp::` namespace, that a consumer links to obtain the core C++ public API (sessions, transport, wire, dictionaries). Four further export-set members — the C-ABI, TOML-config, tap and service targets — are exported separately, by name, for consumers who deliberately want them instead of the umbrella (`contracts/export-set.md` §1); FR-001's umbrella does not subsume them. A fifth member, `fixpp_log_otlp`, is in the export set only as a `$<LINK_ONLY:>` closure requirement of `fixpp_config_toml` (FR-008a) — it is not a consumer-facing surface and no public header names it.
- **FR-002**: The umbrella target MUST carry the public include directories such that they resolve correctly both from within the build tree and from an installed prefix.
- **FR-002a**: **Every target entering the export set MUST first be given a build-tree/install-tree-discriminated include interface.** No module target has one today — the verified census is zero matches for a generator-expression include interface across `src/`, with every module declaring `PUBLIC "${CMAKE_SOURCE_DIR}/include"` raw. Exporting such a target is not a degraded export; it is a **generate-step hard error**, so this is a precondition of FR-003 rather than a refinement of it. *(This requirement moves `src/*/CMakeLists.txt` inside the feature's touched-file set — see Assumption 11 and `plan.md` → Project Structure. Whether the rewrite is per-module or centralised from the root is a design choice, but both forms touch build files under `src/`.)*
- **FR-002b**: The feature MUST fix an explicit disposition for `fixpp_transport`'s `PUBLIC FILE_SET HEADERS` (`src/transport/CMakeLists.txt:53-60`, the repository's only file set) and record the choice with its consequence. `install(TARGETS … EXPORT …)` is a hard error unless a target's interface file sets are also installed, and `fixpp_transport` is an unavoidable export-set member. The candidate dispositions — install the file set (which duplicates headers already installed by `CMakeLists.txt:321-324` and needs a non-conflicting `FILE_SET HEADERS DESTINATION`), demote it to `PRIVATE`, or drop it — have different footprints and two of the three touch `src/**` again.
- **FR-003**: The build MUST install an export set and generate a package-config file plus a version file, placing them where `find_package(fixpp)` locates them without consumer-side hints. **The installed imported-target names MUST match the `fixpp::` aliases the in-tree targets already carry** (e.g. `fixpp::capi`, not `fixpp::fixpp_capi`) — `install(EXPORT … NAMESPACE fixpp::)` derives each imported name from the **target** name, and `add_library(fixpp::X ALIAS …)` does **not** carry into an export, so this requires `EXPORT_NAME` to be set explicitly on every aliased export-set member (`contracts/export-set.md` §1). Left unset, the package publishes `fixpp::fixpp_capi` while `.specify/architecture.md:503` — the ground D1 Option A was decided on — names `fixpp::capi`.
- **FR-004**: The package-config file MUST resolve every third-party dependency that the exported targets require, so a consumer never names those dependencies itself. **Symmetrically, it MUST NOT `find_dependency` a package no export-set member actually links** — a spurious dependency requirement is as much a packaging defect as a missing one, and is why the set is produced by FR-010c's derivation rule rather than a hand-written enumeration (an earlier hand-written list both omitted a real dependency and named two the library does not use).
- **FR-005**: The version file MUST derive its version from the project version declared in the build system (currently `0.0.1`) — never from a separately maintained literal.
- **FR-006**: The version file MUST reject an incompatible requested version at configure time with a version-specific diagnostic.
- **FR-007**: The precompiled per-version builder and validator libraries MUST remain outside the export set. *(Settled by 078 Gate B P1 — install-scope coherence. Not open for relitigation.)*
- **FR-008**: No target in the export set may expose a link-interface dependency on a target outside the export set. **Where export-set membership is determined by reading `target_link_libraries` rather than by an executed `install(TARGETS … EXPORT …)` + generate run, the closure MUST be re-verified by an executed run before the feature is treated as complete** — a member list produced by reading alone is not sufficient evidence of FR-008, because the identical method has previously missed members across a multi-level cascade (`contracts/export-set.md` §2a records the standing obligation and the members it applies to).
- **FR-008a**: The closure in FR-008 MUST be computed over the **`$<LINK_ONLY:>`-expanded** link interface, not over declared `PUBLIC` dependencies alone. ## Assumptions

Recorded because the feature description did not fully specify them. Each is a reasonable default, not a discovered fact.

1. **One package per configuration, dev-shaped** (user decision). Each package carries headers + static libraries + CMake package config. There is **no separate binary-only runtime package** before v1.0. Rationale: the anchor doc defines the runtime package as "shared libs, no headers", but the `add_library` census shows **at most one** SHARED target in the entire project — `fixpp_capi_shared` — and it is gated on `FIXPP_BUILD_TESTS` (`src/capi/CMakeLists.txt:47-48`), so a packaging build with tests OFF has **zero**. Either way such a package would contain one library or none. *(Census corrected at Gate A round 1: the earlier "exactly one SHARED target" ignored the `FIXPP_BUILD_TESTS` gate, the OBJECT target `fixpp_capi_objects`, and the INTERFACE targets. The correction **strengthens** this assumption's conclusion.)* The alternative (adding shared variants of the core C++ targets) is ruled out above, on the freeze-mechanism ground.

2. **Both Release and Debug packages are produced and archived as CI artifacts; none are published as release artifacts.** *(Clarified 2026-07-31.)* Constitution Article V §5 keeps a "Work in progress — NOT for production use" disclaimer in force until publishing is unblocked, so this feature produces distributable artifacts without establishing a distribution channel. Packages are downloadable from CI runs for maintainer use. Publication is REMAINING-WORK item 13's decision at GA, and this feature MUST NOT pre-empt it.

3. **Package version is the project version, `0.0.1`, and this feature does not change it.** *(Clarified 2026-07-31; rationale corrected at Gate A round 1.)* The GA version string is REMAINING-WORK item 13's decision. Because FR-005 binds the package version to the declared project version rather than to a packaging-local literal, a later bump propagates with no change to any packaging rule.

    **Two independent version spaces — do not conflate them.** `0.0.1` is the **project** version (`CMakeLists.txt:5`), which is what the package and its `fixppConfigVersion.cmake` carry. `1.5.0` is the **C-ABI** version (`FIXPP_C_ABI_VERSION_MAJOR`), GA-frozen via PR #160 (`REMAINING-WORK.md:7`). The earlier rationale here — that a `1.x` package name "would imply an ABI stability the project is not claiming" — was doubly wrong: it borrowed a *C-ABI* fact to justify a *project-version* choice, and the fact itself was stale (the C ABI **is** claiming exactly that stability). The decision is unchanged; its surviving ground is Assumption 2 — nothing is published, so no version string is being committed to any consumer.

4. **In-scope packages are built OTel-ON**, consistent with all four existing Linux legs (`FIXPP_BUILD_OTEL:BOOL=ON` verified in three existing caches). Descoping the *requirement* that OTel-ON builds feed packages does not license producing an OTel-OFF package for one leg only — that would make the gcc Debug package the sole one missing the OTel targets. Building dependencies with OTel disabled is acceptable **only** as a development accelerator while the packaging logic is being written (it reduces the gcc-Debug from-source dependency build from 9 packages to 3), never for a shipped artifact.

5. **The build matrix is exercised one configuration at a time**, deleting each build tree before the next. Measured basis: a Debug tree is ~22 GB, of which ~11 GB is test executables and ~4.5 GB is object files; the installable payload is ~4.6 GB of archives.

   **The budget is the whole volume, not the tree.** Corrected at Gate A round 1: the earlier claim that "peak single-configuration footprint is well within the available build storage" counted only the transient build tree. Three things share the one 64 GB volume (`quickstart.md` §0): the build tree (22–25 GB in Debug), a 20 GB ccache, **and** the artifact directory — which FR-021 deliberately preserves *past* the deletion cycle and which FR-015 fills with **three redundant Linux formats** (DEB, RPM, TGZ) carrying the same ~4.6 GB payload, across four Linux configurations. Nothing in this feature bounds that directory, and FR-021a exists precisely *because* it accumulates. SC-008 therefore asserts the **whole-volume high-water mark**, not the tree's, and the feature MUST either state a measured artifact-directory budget with a retention rule or place `artifacts/` on different storage.

   **Ordering starts with gcc Release** — the only configuration that is cheap on *both* axes: a 3.4 GB tree and zero third-party dependencies to build (Assumption 9). The smallest-tree configuration is clang Release, but it carries 5 dependency builds, so "smallest" and "fastest to first package" are different configurations here. Validating the export and packaging logic on gcc Release means the first end-to-end run is bounded by fixpp's own compile time and nothing else.

6. **Windows packaging is produced in a separate build sandbox** on different storage from the Linux matrix, so the Windows configurations do not consume the Linux build-storage budget.

7. **The existing consumer witness is extended, not replaced — but its link surface grows substantially.** `fixpp::consumer::install-witness` already stage-installs, configures a standalone project against the staged prefix, and inherits the build configuration; that harness is reused. *(Corrected at Gate A round 1: this previously said "only its discovery mechanism changes". That understates it.)* Today the witness links exactly **four** archives — `fixpp_dictionary`, `fixpp_wire`, `fixpp_dict_dispatch_bridge`, `fixpp_core` (`tests/consumer/CMakeLists.txt:56`) — inside a hand-written `-Wl,--start-group`, plus `pugixml` resolved by its own `find_package`. After the change it links `fixpp::fixpp`, i.e. the **entire export closure** plus OpenSSL, asio and Crc32c. Two consequences: the minimal tier acquires the ability to fail for **link-interface** reasons that this spec elsewhere attributes exclusively to the real-client tier, and it becomes the first place a missing `find_dependency` (FR-010c) or the `FILE_SET` blocker (FR-002b) surfaces. Good for detection; it means the minimal witness is no longer a cheap discovery-only check, and the two-tier framing must say so.

   **What still distinguishes the tiers**: the minimal tier exercises the link *interface* but links a header-shaped consumer against a staged prefix in the producer's environment; the real-client tier links a working FIX application and runs it against a live counterparty. And neither tier covers the operator environment — that is SC-016's job.

8. **Dependency resolution for the new gcc Debug configuration adds a *tracked* `conan/profiles/linux-gcc-debug`** — a `build_type=Debug` sibling of `conan/profiles/linux-gcc-release` — rather than reusing the release profile with a command-line configuration override.

    *(Corrected at Gate A round 2. This previously read "reuses the existing dependency profile with the configuration overridden, rather than introducing a separate profile", which was the **only** surviving site of a position the rest of the bundle had already abandoned: research R5 decides the tracked profile explicitly and rejects the `-s build_type=Debug` override by name, and `plan.md`'s Article III §3 row and Project Structure both already commit to `conan/profiles/linux-gcc-debug  # NEW`.)*

    **Two independent grounds.** *(i) Discipline*: `conan/profiles/` is a tracked in-repo directory; an untracked override leaves the configuration unreproducible and outside the Article III §2 "declared, pinned" rule. Adding a profile needs no Article XX amendment — Article III §3's enumeration is already non-exhaustive (four in-repo libc++ profiles are absent from it), so this follows established practice (research R5). *(ii) Measured — precisely what was executed, and no more*: the orchestrator's round-1 measurement ran `quickstart.md`'s documented untracked-profile invocation (`-pr:a=gcc13 -s build_type=Release -b missing`) and it **fails outright**, with Conan writing into the source root and colliding with the tracked `CMakePresets.json` for want of `-of build/<preset>`. That establishes two things directly: the profile it named (`~/.conan2/profiles/gcc13`) **is not in the repository** — `conan/profiles/` holds 14 tracked profiles and no `gcc13` — and the documented form does not run. It does **not** establish anything about a `-s build_type=Debug` override specifically; that form was never executed, and Assumption 8 rests on ground (i) for it. The working invocation is the tracked-profile one CI uses (`.github/workflows/tier1.yml:411-414`); `quickstart.md` §1 now documents exactly that.

9. **Third-party dependency availability is uneven across the in-scope configurations, and the gap is time, not storage.** Resolved 2026-07-31 against the local dependency cache: clang Debug and gcc Release need **nothing** built; clang Release needs **5** packages built from source; gcc Debug needs **9**. In both deficient cases the cost is dominated by the telemetry SDK and its transitive chain. Ordering should account for this — the nominally "cheapest" configuration by disk is not the cheapest by wall-clock — and the dependency build is a one-time cost per (toolchain, configuration) pair that persists in the shared cache. This shared cache lives on different storage from the build matrix and is unaffected by the build-tree deletion cycle in Assumption 5.

10. **Packages ship the vendored dictionaries with full attribution — and this feature discharges the mechanical obligations only.** *(Clarified 2026-07-31.)* Shipping them keeps the package self-sufficient: the same package exposes a runtime dictionary-loading API that reads files from disk, and omitting the data would ship an API with no inputs. The attribution obligations this feature acts on are **two**, not one: the upstream license text must be reproduced in the distribution (satisfied by shipping it), *and* a specific acknowledgment sentence must appear in end-user documentation, which the `NOTICE` file this feature creates carries.

    **How the second is discharged, stated precisely** *(softened at Gate A round 1)*: upstream clause 3 is **conditional** — *"The end-user documentation included with the redistribution, **if any**, must include the following acknowledgment"* — and offers an explicit alternative: *"Alternately, this acknowledgment may appear in the software itself, if and wherever such third-party acknowledgments normally appear."* A `NOTICE` file is a **sound and conservative** discharge of that clause, and it is the one this feature implements. It is not the *only* reading, and the earlier flat assertion that shipping the license file "does not discharge" obligation 2 stated one reading of a conditional clause as fact — in a feature that elsewhere correctly disclaims legal clearance. The conservative choice stands; the certainty does not.

    **The full clause set is five, not two.** Clause 1 (source-form redistribution retains notice + conditions + disclaimer) applies — the packages ship the dictionary XML, which *is* the redistributed material in source form — and is discharged by the same shipped license file. Clause 4 (no endorsement) is discharged by FR-018c. Clause 5 (derived products may not be called "QuickFIX" nor carry it in their name) is discharged by the product name `fixpp` (FR-017). The complete clause-to-discharge table is in `contracts/package-layout.md` §4.

    **Explicit limit — this feature does not close REMAINING-WORK item 15d.** That item's open question is whether the upstream's advertising-style acknowledgment clause constitutes an additional restriction incompatible with the project's own license, and it is pending counsel review. Choosing to ship the dictionaries makes that question *live* rather than hypothetical; it does not answer it. This feature implements the mechanical attribution correctly and MUST NOT be read as legal clearance. Item 15d remains open and gates publishing (constitution Article V §5), which is consistent with Assumption 2 — nothing here is published as a release artifact.

11. **The verification matrix is derived from touched trees — and this feature's touched set is now known to include build files under `src/`.** The verification gate buckets a change by the paths it touches: library sources and public headers trigger the full C++ preset matrix; the C-ABI surface triggers the ABI gates; the Python bindings trigger their own matrix; a change confined to specifications and documentation triggers none.

    **Corrected at Gate A round 1 — the premise changed.** This assumption previously read "this feature touches build configuration, shared build modules, the preset set, the consumer witness, and packaging metadata — none of which is a library source or public header", and concluded the full preset matrix and coverage gate were *expected* N/A. FR-002a and FR-002b make that false as stated: giving the export-set members a build/install-discriminated include interface, and dispositioning `fixpp_transport`'s file set, land in `src/*/CMakeLists.txt`. **No `.cpp`/`.hpp` under `src/` or `include/` is touched — only CMake files inside those trees.** Whether the coverage and preset buckets key on a *path prefix* (`src/**`, which now matches) or on *compiled-source file type* (which still does not) is **not resolved here and MUST NOT be assumed either way**; it is derived from the real diff against the gate's own taxonomy at verification time.

    **The taxonomy gap is now expected, not hypothetical.** The bucket set has **no explicit bucket for a build-system-only change** — such a change is neither a source change nor strictly documentation-only — and this feature will certainly produce one. That gap MUST be recorded explicitly in the verification record rather than silently resolved as documentation-only. Any preset that is skipped MUST be skipped through the gate's own waiver mechanism, which requires a paired recorded rationale; an unpaired skip is a failure by design.

12. **Excluding the alternate-standard-library configuration from verification requires replacing the coverage it provides, not merely noting its absence.** That configuration is the only one built with telemetry disabled. Consequently it is the only one that would expose a config package which unconditionally requires the telemetry dependency — a defect that would break **every** consumer of a telemetry-disabled build, and which no telemetry-enabled configuration can detect. Since that configuration is descoped from packaging (user decision, 2026-07-31) and is expected to be out of the verification matrix per Assumption 11, this feature MUST instead verify the underlying risk directly: the generated package config MUST be exercised against a telemetry-disabled build and MUST resolve. This is materially cheaper than building that configuration (its tree measures ~8 GB) and it tests the actual hazard rather than a proxy for it. **Dropping the configuration without this substitute check is not acceptable** — it would remove the only existing coverage of a real packaging defect class.

Commercial consumers wanting *dynamic* isolation under Article IV §2 remain unserved; un-gating that target and resolving the `WINDOWS_EXPORT_ALL_SYMBOLS ON` symbol-surface problem (`:70`, which the header-hash freeze does not cover) is a decision for a feature that also builds the mechanism to hold it. **The whole `include/fixpp/service/` row follows from A**: `fixpp_service`'s only link edge is `fixpp_capi` (`src/service/CMakeLists.txt:15`), now a member.

**The original framing, retained because the decision was made against it.** The defect is verified, the remedy was a decision. `include/fix/c_api.h` and `include/fix/c_api/` (12 files) exist, and the header install rule at `CMakeLists.txt:321-324` installs the **entire** `include/` tree. Packages therefore ship the C-ABI header **with no library behind it** — structurally the same defect FR-018a fixes for the dictionaries, and it exists in the current install rules independent of this feature.

**This is one row of the FR-012a class, not a standalone question.** `include/fixpp/config/`, `include/fixpp/tap/` and `include/fixpp/service/` exhibit the same defect. D1 is separated out only because the C ABI carries a constitutional weight the others do not — Article IV §2 makes it *"the legal isolation boundary for AGPL/commercial dual licensing"*, and a commercial consumer links that surface, not `fixpp::fixpp`. Note `include/fixpp/service/` is **bound to this decision**: `fixpp_service` links `fixpp_capi` (`src/service/CMakeLists.txt:15`), so its disposition cannot be settled independently. Three C-ABI targets exist: `fixpp_capi` (STATIC), `fixpp_capi_objects` (OBJECT), `fixpp_capi_shared` (SHARED).

**Binding evidence that must be on the table before this is decided** *(added at Gate A round 1)*. `.specify/architecture.md` §7.4 already specifies this exact surface, and root `CMakeLists.txt:319` names it as the authority for this exact work — the header above the install rules reads *"CMake package export (`fixpp::` namespace per [arch §7.4])"*.

- `architecture.md:502` — `fixpp` is *"the **C++ public umbrella** … `INTERFACE_INCLUDE_DIRECTORIES = include/`, **exposing `<fix/c_api.h>`** and the entire `<fixpp/...>` C++ surface."*
- `architecture.md:503` — `fixpp::capi` is *"the **C-ABI consumer target** … `INTERFACE_INCLUDE_DIRECTORIES = include/fix/` only. **C-ABI consumers link this.**"*
- `architecture.md:504` — a `fixpp::service-iface` INTERFACE target exposing `include/fixpp/service/`.
- `architecture.md:523`, `:526` (§8) — `fixppd` links `fixpp::capi` and `fixpp::service-iface`; the AGPL isolation boundary is **structural**, enforced by target visibility and the `tools/check_layers.py` lint.

**Counterweight — §7.4 is itself partly stale** (FR-024a): `:500` describes the module targets as OBJECT libraries combined into a final `fixpp` shared/static (all are STATIC; no combined `fixpp` target exists), `:504`'s `fixpp::service-iface` does not exist, and `:501`'s `fixpp::capi-objects` has no namespaced alias. §7.4 is evidence to weigh, not an answer to defer to — but it is evidence the decision cannot be made without.

| Option | Answer | Implications |
|---|---|---|
| A | Export the static C-ABI library so the shipped header has a library | Smallest coherent fix — removes the API-without-substance defect without touching the shared library. Consistent with `architecture.md:503` (`fixpp::capi` as the C-ABI consumer target). Commercial consumers needing dynamic isolation are still unserved. Drags `fixpp_capi_objects` and the whole C++ closure into the export set (`src/capi/CMakeLists.txt:28-41`) — **including `fixpp_tap`** (`:36`), which is itself one of the FR-012a open rows, so choosing A settles that row as a side effect. Verify against FR-008a before choosing. |
| B | Export the static **and** shared C-ABI libraries | Serves the Article IV §2 isolation boundary properly, and the shared library is the one place a binary-only runtime package would have real content. **Risk framing corrected at Gate A round 1**: this is *not* "closer to an ABI commitment than the project is ready for" — the C ABI is **already GA-frozen at `1.5.0`** (`REMAINING-WORK.md:7`, PR #160), with a header-hash baseline (`tools/capi_freeze.sha256`) and a POSIX version script restricting exports to `fixpp_*` per `[const §X.2]` (`src/capi/CMakeLists.txt:73`). B is therefore *"ship an already-frozen, already-gated C ABI"* — materially lower risk than previously stated, and arguably what Article IV §2 asks for. **Two real constraints remain, and they are the ones to weigh**: (i) `fixpp_capi_shared` exists **only under `FIXPP_BUILD_TESTS`** (`src/capi/CMakeLists.txt:47-48`), so B requires un-gating it from a test-only option; (ii) on Windows it is built `WINDOWS_EXPORT_ALL_SYMBOLS ON` (`:70`) — deliberately **not** the `[const §X.2]` "only `fixpp_*`" surface the POSIX version script enforces, because the comment at `:64-68` records it as test-only with no shipped Windows consumer. Shipping it would export every C++ internal symbol on Windows — an Article X §2 problem the header-hash freeze does **not** cover. |
| C | Exclude `include/fix/` from the package; state C-ABI packaging as a non-goal | Internally consistent as a packaging choice, but it **contradicts `architecture.md:502` and `:503`** — §7.4 names `<fix/c_api.h>` as part of the umbrella's exposed surface and `fixpp::capi` as the target C-ABI consumers link — and it would delete the structural half of the §8 licensing boundary. It also **removes a header that ships today**, a regression in delivered content. If C is chosen it requires an **Article XX-visible architecture amendment**, not merely a spec non-goal. |

**Decided at sign-off — Option A.** The Gate A verdict at round 1 was *do not decide it yet*, not until §7.4/§8 had been weighed and the stale freeze premise had been corrected within the bundle. Both preconditions were met at round 3, and the user decided at sign-off on 2026-08-01. Deciding on the pre-correction evidence would have risked selecting Option C — the one option that contradicts `architecture.md:502`/`:503` — on a risk model that was a month stale. The unacceptable outcome, a header shipping with no library and no recorded decision, does not occur.
