## Requirement Completeness — serialization domains

- [x] CHK001 Are requirements defined for **both** serialization domains (per-session AND engine control-plane), with each domain's protected state enumerated rather than left as "engine-global state"? [Completeness, Spec §FR-001/§FR-011] — PASS: FR-001 enumerates the per-session domain (establishment, handshake, read-pump, dispatch, send, teardown closes); FR-011 enumerates the control-plane domain (registry, stopped, listeners, endpoint tables, counters, per-session-handle publication) with no residual "engine-global state" weasel words. Both domains fully specified. refs: spec.md §FR-001, §FR-011.
- [x] CHK002 Is the **complete set** of per-session work that must run in the session domain enumerated (establishment, handshake, read/framing, dispatch, send, BOTH teardown closes), or could a reader omit one? [Completeness, Spec §FR-001/§FR-002] — PASS: FR-001 explicitly lists "connection establishment, TLS handshake, inbound read/framing, inbound message dispatch, outbound send, and teardown (i.e. the entire engine-owned per-session role loop plus its shutdown close)"; FR-002 separately calls out both the transport close (before join) and terminal Session::close (after join + send-drain). - [x] CHK003 Is the **complete set** of control-plane state enumerated (registry, stopping flag, listener table, endpoint table, counters, per-session-handle publication), so no fifth structure silently escapes the domain? [Completeness, Spec §FR-011; research R4 half-restructure] — PASS: FR-011 lists "the session registry, the stopping flag, the listener and endpoint tables, the in-flight counters, and the publication of per-session handles that the shutdown path reads" — matching exactly the full set in research D0/data-model E-0 (adds `accept_scope_signals_` which is an implementation detail of the listener table). - [x] CHK004 Are requirements stated for **every cross-thread entry point** (any-thread send, shutdown, and the synchronous public readers), or only for send/stop? [Completeness, Spec §FR-012/§FR-014] — PASS: FR-012 covers any-thread send (registry/stopped read inside the control-plane domain, hand-off to session domain) and engine shutdown (snapshot/cancel/drain/clear inside the control domain); FR-014 covers the synchronous public readers (lookup/acceptor_bound_endpoint via atomic snapshot, any thread, no domain entry). - [x] CHK005 Is the publication of the per-session handles the shutdown path reads (`session`/`live_transport`) specified as a requirement, including its ordering relative to the read pump? ## Requirement Clarity — vague terms quantified

- [x] CHK007 Is "**serialization domain**" defined precisely enough (one boundary, no two operations overlap) to be objectively checkable, rather than an abstract synonym for "strand"? [Clarity, Spec §Key Entities] — PASS: spec.md §Key Entities defines "Engine control-plane domain" as "a single engine-wide serialization boundary inside which all engine-global bookkeeping…is read and mutated; every cross-thread engine entry point routes through it" and "Session serialization domain" as "the per-session boundary inside which all of one session's operations are ordered so none overlap; the unit of serialization is a single session." Both definitions state the invariant (no overlap) and scope, not just "strand." Objectively checkable via TSan. refs: spec.md §Key Entities.
- [x] CHK008 Is "**non-blocking handoff**" defined (a post that never occupies/blocks a domain) so FR-006's deadlock-freedom claim is testable, not just asserted? [Clarity, Spec §FR-006] — PASS: FR-006 states "Every cross-domain handoff MUST be a non-blocking handoff (never a synchronous wait that occupies a serialization domain), so a callback-issued send cannot deadlock the domain it runs on." The parenthetical "(never a synchronous wait that occupies a serialization domain)" is the concrete definition: it names the prohibited pattern (synchronous wait while holding the domain) rather than leaving "non-blocking" abstract. The Assumptions also state "every handoff between them…is a non-blocking post" as the mechanism. refs: spec.md §FR-006, §Assumptions.
- [x] CHK009 Is the `stopped_` "**defined cross-thread access discipline**" stated concretely (atomic acquire/release OR control-domain read), not left as "must not remain a plain flag"? [Clarity, Spec §FR-013] — PASS: FR-013 states the discipline concretely: "read within the control-plane domain, or via an atomic with acquire/release ordering — it MUST NOT remain a plain non-atomic flag justified by single-thread confinement." Both valid access patterns are named. refs: spec.md §FR-013.
- [x] CHK010 Is the snapshot-read cost characterization precise — does the spec avoid an absolute "lock-free" guarantee and instead state the bounded "wait-free where the STL makes it lock-free, else non-`std::mutex` STL-internal" property it can actually hold? [Clarity, Spec §FR-014] — PASS: FR-014 states precisely "the standard `std::atomic<std::shared_ptr<…>>` primitive, wait-free where the STL makes it lock-free and otherwise STL-internal non-`std::mutex` synchronization, not an absolute lock-free guarantee." This matches the realized property and avoids over-claiming. refs: spec.md §FR-014.
- [x] CHK011 Is "**bounded handle**" defined with its exact validity boundary (valid across `stop()`/registry-clear *while the Engine is alive*; NOT past `~Engine`), so the precondition is unambiguous to a caller? [Clarity, Spec §FR-008/§FR-014] — PASS: FR-008 states "it is valid only while the `Engine` is alive — because `Session` borrows the engine's runtime config, the caller MUST NOT let a `lookup()`/snapshot handle outlive the `Engine`" and "It is NOT a general keepalive past `~Engine`." FR-014 repeats and elaborates (UAF reasoning: Session borrows const EngineConfig& engine_, same hazard as send path at engine.cpp:726-730; debug lease assert). The exact boundary (`while the Engine is alive`) is unambiguous. refs: spec.md §FR-008, §FR-014.

## Requirement Consistency

- [x] CHK012 Does FR-011's "all control-plane state … mutated only within the control domain" stay consistent with FR-014's "readers read an immutable snapshot off any thread" — i.e. is the mutate-on-strand / read-via-snapshot split stated without contradiction? [Consistency, Spec §FR-011↔§FR-014] — PASS: FR-011 states mutations MUST happen only within the control domain AND that reads happen either (a) within the control domain or (b) via the atomically-published immutable snapshot (FR-014). FR-014 then specifies the snapshot mechanism. The split is explicit: "Engine-global state is **read** either (a) within the control-plane domain, or (b)…from an atomically-published immutable snapshot." No contradiction; the two requirements are complementary halves of a consistent design. refs: spec.md §FR-011, §FR-014.
- [x] CHK013 Is the single permitted public change (`lookup() → shared_ptr<Session>`) described **identically** wherever it appears (FR-008, SC-004, Out of Scope, US3), with no second public change implied anywhere? [Consistency, Spec §FR-008/§SC-004/§Out-of-Scope] — PASS: FR-008 names the sole change ("sole permitted signature change is `Engine::lookup()` returning a shared-ownership handle"); SC-004 repeats it ("exactly one intended, recorded signature change — `Engine::lookup()` returns `std::shared_ptr<Session>` instead of a raw `Session*`"); Out-of-Scope states "Any change to the public engine or session API surface beyond the single recorded `lookup()` return-type safening"; US3 AS-2 refers to "the single recorded `lookup()` return-type safening (FR-008/SC-004)." All four occurrences are identical; no second change is implied anywhere. refs: spec.md §FR-008, §SC-004, §Out of Scope, §US3.
- [x] CHK014 Is `stopped()`'s discipline consistently attributed to the atomic flag (FR-013) and explicitly **excluded** from the snapshot (FR-014), so the two readers' mechanisms don't blur? [Consistency, Spec §FR-013↔§FR-014] — PASS: FR-014 ends with "`stopped()` is covered separately by the atomic stopping flag (FR-013)." The last sentence of FR-014 is a direct exclusion statement. FR-013 independently defines the atomic acquire/release discipline. No ambiguity about which mechanism covers stopped(). refs: spec.md §FR-013, §FR-014 (last sentence).
- [x] CHK015 Do the two lifetime mechanisms (send-path keepalive/drain vs the `lookup()` bounded-handle debug assert) stay **distinct** in the requirements, or could they be read as one unified keepalive? [Consistency, Conflict risk — research R7; not pinned in an FR] — DD-DECIDED research R7/C-8: The spec's FR-008 states the `lookup()` handle "is NOT a general keepalive past `~Engine`" and FR-014 specifies the lease mechanism is debug-only with no `stop()` drain. The send-path keepalive is addressed by FR-012 ("any-thread outbound send MUST resolve the registry…inside the control-plane domain" — the send_counter_ barrier that FR-012's control-domain routing preserves). The separation is maintained by FR-012 (send drain as a control-domain operation) vs FR-014 (lease as a debug assert + caller obligation only). Research R7 explicitly warns implementers to keep them separate; contracts C-8 and C-6 each describe their respective mechanisms without overlap. The requirements as written do not conflate the two. refs: spec.md §FR-008, §FR-012, §FR-014; research.md R7; contracts C-6/C-8.

## Acceptance Criteria Quality — measurability

- [x] CHK016 Is the SC-002 deterministic-witness standard stated as an objectively decidable bar (a one-sided park → TSan race on **every** pre-change run, GREEN 100% post-change) rather than "deterministic" left undefined? [Measurability, Spec §SC-002] — PASS: SC-002 defines the bar objectively: "a test-only delay that parks one thread inside / immediately adjacent to an unsynchronized listener/endpoint-table access…while shutdown clears those tables from another thread, with no happens-before edge between the two racing accesses…The park window is wide enough that the conflicting access reliably lands inside it, so the thread-sanitizer reports the race on **every** pre-change run (reliable RED) and the witness passes **100%** of runs on the post-change engine." Both the pre-change and post-change bars have quantified pass criteria. refs: spec.md §SC-002.
- [x] CHK017 Does SC-002 explicitly **forbid** the self-defeating reproducer (a bidirectional latch that creates a happens-before edge and suppresses the race), so the criterion can't be met by a witness that proves nothing? [Measurability, Spec §SC-002; research D6] — PASS: SC-002 explicitly states "a bidirectional latch is forbidden — it would synchronize the accesses and suppress the very race the thread-sanitizer must report." The prohibition is explicit and the reason is given. refs: spec.md §SC-002.
- [x] CHK018 Is SC-004's "no unintended API/ABI change" measurable via a named diff tool expectation (exactly one recorded `lookup()` diff, no other), not a subjective "no surprising change"? The named tools (`abidiff`/`nm`) and the exact expected output (one diff, nothing else) make this objectively decidable. refs: spec.md §SC-004.
- [x] CHK019 Is SC-001's "**across repeated runs**" quantified (a minimum repetition count) or does it leave "repeated" to interpretation? [Measurability, Spec §SC-001 — Ambiguity] — DD-DECIDED tasks.md T015/C-7 V-2: SC-001 in spec.md says "zero…findings and zero crashes across repeated runs" without a numeric count. This is a DD-DECIDED against the tasks and contract anchor; the spec's "repeated runs" is intentionally left to the implementation guide rather than hard-coding a number in the acceptance criterion itself. refs: tasks.md T015; contracts C-7 V-2; spec.md §SC-001.

## Scenario Coverage — concurrency scenario classes

- [x] CHK021 Are **steady-state** MT requirements covered (round-trip + ordering correct, no two same-session ops overlap)? [Coverage, Primary — Spec §US1 AS-2/§FR-005] — PASS: US1 AS-2 states "message handling and delivery ordering are correct and no two operations for the same session run simultaneously." FR-005 requires inbound message ordering and exactly-once in-order delivery under MT. FR-001 requires all per-session work to execute within a single serialization domain so no two operations for the same session run concurrently. SC-001 requires zero sanitizer findings across repeated runs. Steady-state fully covered. refs: spec.md §US1/AS-2, §FR-001, §FR-005, §SC-001.
- [x] CHK022 Are **teardown-vs-in-flight-read** requirements covered (close serialized with the completing read)? [Coverage, Exception — Spec §Edge Cases/§FR-002] — PASS: FR-002 requires teardown to occur "inside that session's serialization domain, so teardown never runs concurrently with that session's in-flight read or write completion." The Edge Cases section lists "Teardown vs. in-flight read: shutdown closes a session's connection at the same moment…Must be serialized within the session's domain." US1 AS-1 directly tests this scenario. refs: spec.md §FR-002, §Edge Cases, §US1/AS-1.
- [x] CHK023 Are **teardown-vs-in-flight-send** requirements covered (shutdown overlapping an outbound send for the same session)? [Coverage, Exception — Spec §Edge Cases] — PASS: The Edge Cases section explicitly lists "Teardown vs. in-flight send: shutdown overlaps an outbound send still in progress for the same session. Must be serialized within the session's domain." FR-001 and FR-002 require all session work (including outbound send) to run within the session's domain. refs: spec.md §Edge Cases, §FR-001, §FR-002.
- [x] CHK024 Are **re-entrant send** requirements covered, including the post-`stop()` clean-fast-fail disposition (not only the no-deadlock happy path)? [Coverage, Recovery — Spec §Edge Cases/§FR-006] — PASS: FR-006 requires re-entrant sends to "complete without deadlock" and requires "a non-blocking handoff (never a synchronous wait)." The Edge Cases section states "Re-entrant send: must not deadlock and must not race." The post-stop fast-fail is covered by FR-012: the send "MUST resolve the registry/stopping flag inside the control-plane domain before handing off" — if stopping_, the control-domain read of stopped_ returns true and the send fails cleanly without racing a half-cleared registry. Contract V-9 adds "fails cleanly (stopped/session_invalid_state_for_send), never races a half-cleared registry." refs: spec.md §FR-006, §FR-012, §Edge Cases; contracts V-9.
- [x] CHK025 Are **cross-session parallelism** requirements covered as an explicit non-guarantee (unrelated sessions still progress; serialization is per-session, not engine-global)? [Coverage, Spec §FR-004] — PASS: FR-004 explicitly states "Cross-session parallelism MUST be preserved — unrelated sessions MAY continue to make progress on different threads concurrently; the serialization guarantee is per-session, not engine-global." The Edge Cases section states "Many concurrent sessions: distinct sessions may legitimately run in parallel on different threads; the feature serializes within a session, not across unrelated sessions." refs: spec.md §FR-004, §Edge Cases.
- [x] CHK026 Are **shutdown-vs-connection-accept** control-plane requirements covered (registry/listener clear vs accept-loop publish)? [Coverage, Exception — Spec §Edge Cases/§FR-011] — PASS: FR-011 requires all control-plane mutations including "the publication of per-session handles that the shutdown path reads" to occur only within the control-plane domain. The Edge Cases section covers "Shutdown vs. connection accept: shutdown clears the registry/listener tables on one thread while an accept loop is publishing a newly accepted session into those tables on another. Must be serialized within the control-plane domain." refs: spec.md §FR-011, §Edge Cases.
- [x] CHK027 Are **any-thread-send-vs-shutdown** requirements covered (resolve registry inside the domain, fail cleanly if shutdown began, never read a half-cleared registry)? [Coverage, Exception — Spec §Edge Cases/§FR-012] — PASS: FR-012 requires "an any-thread outbound send MUST resolve the registry/stopping flag inside the control-plane domain before handing off." The Edge Cases section states "Any-thread send vs. shutdown: The send must resolve the registry inside the control-plane domain (and fail cleanly if shutdown has begun), never read a half-cleared registry." All three requirements stated. refs: spec.md §FR-012, §Edge Cases.
- [x] CHK028 Are **synchronous-reader-vs-shutdown** requirements covered (consistent immutable snapshot; a handle taken just before clear keeps its session alive)? [Coverage, Exception — Spec §Edge Cases/§FR-014] — PASS: FR-014 requires readers to "atomically load the current snapshot" so they never observe "a control-plane structure mutated in place." The Edge Cases section states "the reader must observe a consistent immutable snapshot (never an in-place-mutating structure), and a `lookup()` handle obtained just before `registry_.clear()` must keep its session alive (shared ownership) for as long as the `Engine` is alive (bounded handle)." FR-008 defines the bounded handle validity. refs: spec.md §FR-014, §FR-008, §Edge Cases.
- [x] CHK029 Are **idle-established-session-at-shutdown** requirements covered (close-to-wake preserved, now inside the session domain)? [Coverage, Edge Case — Spec §Edge Cases/§FR-002] — PASS: The Edge Cases section states "Idle established session at shutdown: a session blocked on an inbound read with no peer traffic must still be unblocked and torn down (the close-to-wake behavior is preserved, now performed inside the session's domain)." FR-002 requires teardown to occur inside the session domain. The Clarifications round-1 confirms transport close must run on the session strand before the join. refs: spec.md §Edge Cases, §FR-002, §Clarifications r1 (Gate A round-1).

## Memory-Model & Lifetime Requirements

- [x] CHK034 Does the spec state the memory-ordering requirement for the stopping flag (acquire/release) rather than leaving ordering implicit? [Completeness, Spec §FR-013] — PASS: FR-013 explicitly states "MUST have a defined cross-thread access discipline (read within the control-plane domain, or via an atomic with acquire/release ordering) — it MUST NOT remain a plain non-atomic flag justified by single-thread confinement." The acquire/release ordering is named explicitly; implicit ordering is explicitly prohibited. refs: spec.md §FR-013.
- [x] CHK035 Is the `lookup()`-handle-vs-`~Engine` UAF hazard documented as a requirement (the handle borrows engine-owned config; must not outlive the Engine), with a debug-assert obligation? [Completeness, Spec §FR-008/§FR-014] — PASS: FR-008 states the UAF precondition ("it is valid only while the `Engine` is alive — because `Session` borrows the engine's runtime config, the caller MUST NOT let a `lookup()`/snapshot handle outlive the `Engine`") with the UAF reason given. FR-014 adds "This precondition MUST be debug-asserted at `~Engine` via a realizable lease-control-block mechanism." Both the requirement and the debug-assert obligation are explicit. refs: spec.md §FR-008, §FR-014.
- [x] CHK036 Is the debug `~Engine` zero-outstanding-handle check specified at the level of *what property it proves* (no outstanding returned handle) rather than a mechanism that cannot hold it (a bare snapshot `use_count()`)? [Clarity, Spec §FR-014; research round-4/5 lease correctness] — PASS: FR-014 specifies the correct mechanism (the lease control block — ctor increments an engine-owned `std::atomic<uint64_t>`, dtor at last-copy destruction decrements, `~Engine` asserts zero) AND explicitly states why `use_count()` is insufficient: "(A bare `use_count()` on the published snapshot is insufficient — a caller can copy the `Session` handle out and drop the snapshot, so the snapshot's count would never observe it.)" The prohibition of the broken alternative is explicit. refs: spec.md §FR-014.
- [x] CHK037 Are the two lifetime mechanisms' **release-build** behaviors specified (lease/counter compiled out; bounded-handle contract then by caller obligation), so there's no implied release-mode overhead or enforcement? [Completeness, Spec §FR-014] — PASS: FR-014 states "In release builds the handle is a plain `std::shared_ptr<Session>` with no lease/counter overhead; the bounded-handle contract then holds by caller obligation." Both the absence of overhead (plain handle) and the shifted enforcement model (caller obligation) are stated. refs: spec.md §FR-014.
