## Cancellation contract

- [x] CHK009 - Are both sub-cases specified with their exact outcomes — cancel at/before mutex-acquire → `store_cancelled` + zero state change + no syscall; cancel after the child is issued (mid-syscall) → durable success, never `store_cancelled`? Both sub-cases with exact outcomes are present.
- [x] CHK010 - Is the "syscall on a worker thread is not an asio suspension point and cannot be interrupted mid-call" assumption stated as the basis for run-to-durable-completion, so the linearisation reasoning is auditable? [Clarity, Spec §Assumptions / FR-004] — PASS: spec.md §Assumptions states "Cancellation cannot interrupt a syscall mid-flight. ## Mid-walk-reset / generation guard

- [x] CHK014 - Is the mid-walk-reset hazard specified as a LOGICAL stale-snapshot window (retrieve releases the index mutex then suspends at each `on_frame` co_await, during which a reset may swap/truncate the log), distinct from any physical fd race? [Clarity, Spec §US3 / FR-006] — PASS: spec.md §US3 (User Story 3) prose states the hazard precisely: "`retrieve()` snapshots the index under the writer mutex but releases it before walking frames (**FR-017**), and the walk suspends at each `visitor.on_frame()` `co_await`; a `reset()` can run during that suspension and replace/truncate the log, leaving the snapshot's offsets **stale**. Reading against a stale snapshot is the defect to guard". The same section states "pool threads execute only raw syscalls … so a `reset()`'s live-handle swap (also strand-confined) can never **physically** overlap a read — there is no fd race. The residual hazard is **logical**". The logical-vs-physical distinction is explicit.
- [x] CHK015 - Is the detection mechanism specified concretely (a `generation_` counter bumped by reset on the strand, snapshotted by retrieve under the mutex, re-checked before each per-frame read) with the clean-failure outcome (`store_io_failure`)? [Completeness, data-model §4 / FR-006] — PASS: data-model.md §4 provides a code-pseudocode specification of the guard: `g0 := generation_` sampled inside the mutex, `if generation_ != g0: return store_io_failure` checked before each `pread`. spec.md §FR-006 states "retrieve() MUST detect a mid-walk reset() (e.g., a store-generation guard checked on each resume) and either continue reading a coherent pre-reset frame or fail cleanly with a defined error". The mechanism and the outcome are both concrete. CodeGraph: `generation_` ABSENT from `src/session/file_store.cpp` (confirms it is a new field to be added, not an existing one being repurposed — the spec's "add" claim is accurate).
- [x] CHK016 - Is the atomicity requirement between the generation re-check and the following `pread` stated (no `co_await` between them, the only suspension is the post-read `on_frame`), so the guard cannot be defeated by an inserted suspension point? [Clarity, data-model §4] — PASS: data-model.md §4 states "The `generation_` re-check and the `pread` that follows it are **atomic on the session strand** — there is **no `co_await` between them**, so a `reset()` cannot land in that gap (the only suspension point is the `visitor.on_frame()` `co_await` *after* the read). An implementer MUST NOT insert a suspension point between the re-check and the read." The atomicity requirement and the prohibition on a suspension-insertion are explicit. The guard is not defeasible by the stated class of attack.
- [x] CHK017 - Is the discriminating requirement specified (reset-race → `store_io_failure` (56); FR-017 logical gap → `store_seqnum_gap` (57)), so a reset-race cannot masquerade as a never-persisted gap? [Consistency, data-model §5] — PASS: data-model.md §5 states the clean-failure value is "`store_io_failure` (56)" and "deliberately **not** `store_seqnum_gap` (57), so a reset-race cannot masquerade as a logical never-persisted gap (which would mask a real gap bug). The discriminating test asserts: reset-race → `store_io_failure`; FR-017 logical gap → `store_seqnum_gap`." The values 56 (`store_io_failure`) and 57 (`store_seqnum_gap`) are confirmed correct against `include/fixpp/core/error.hpp:190/194`. The discriminating requirement is present and the variant values are accurate.
