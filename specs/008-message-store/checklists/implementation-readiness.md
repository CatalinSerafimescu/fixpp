## Durability & Crash-Safety Requirements

- [x] CHK001 - Is the on-disk byte ordering (little-endian vs big-endian) of the 16-byte record header fields (`record_kind`, `dir`, `reserved`, `seq`, `len`, `crc32`) explicitly specified? [Gap, Spec §FR-009] — **DD-DECIDED data-model.md E4 + FR-009**: exact byte layout explicitly delegated to T-impl ("exact byte layout T-impl, must align to 8-byte boundary"); v1.0 Tier-1 (Linux/Clang/x86_64) + Tier-2 (Windows/MSVC on x86_64/ARM64) per `[const §II.3]` are all little-endian, so host-order is the implicit T-impl choice. No cross-arch portability claimed in v1.0; future BE port would bump the sentinel `version` field per the §6.3.1 mechanism.
- [x] CHK002 - Is the algorithm computing `session_triple_hash` in the sentinel record defined (input string format, hash function, truncation width)? [Gap, Spec §FR-009] — **DD-DECIDED §10 Q7 + data-model.md E4**: design doc `[2e §10 Q7]` names only the field purpose ("re-open verifies, returns `store_factory_failed` on mismatch") + the sentinel byte composition; hash algorithm + width are explicit T-impl latitude (same "exact byte layout T-impl" delegation as CHK001). The only normative contract is mismatch → `store_factory_failed`.
- [x] CHK003 - Is the data-loss window for `commit_batched(N)` and `commit_interval(ms)` quantified as a normative requirement (not just "documented in the per-policy block-comment")? [Measurability, Spec §FR-011 / §SC-002] — **DD-DECIDED data-model.md E10 + Spec §FR-011 + Spec §SC-002**: the window IS normatively quantified at the data-model behavioural-oracle layer (E10 lines 279–281: `commit_per_message` = 0% loss; `commit_batched(N)` = up to N-1 records; `commit_interval(ms)` = ms-bounded). Spec §SC-002 binds the contract ("loss MUST be bounded by the per-policy documented window — no surprise loss outside the window") and §FR-011 defers the verbatim numbers to the per-policy block-comment, where they ARE pinned (contracts/file_store.hpp lines 37–40). The split is the Phase-1 oracle convention: spec.md = abstract requirement; data-model.md = concrete normative numbers.
- [x] CHK004 - Are escaping/validation rules specified for `sender_comp_id` and `target_comp_id` strings that compose the `<sender>__<target>.log` filename (path separators, non-ASCII, length limits)? [Gap, Spec §FR-008 / §FR-009] — **WAIVED**: FIX CompIDs are alphanumeric per FIX-SL convention; sender/target are caller-controlled fields in `SessionConfig` (not external untrusted input — the cfg_loader reads them from a trusted operator-supplied `.cfg`). Filesystem-safety validation belongs at the SessionConfig / cfg_loader layer (out-of-scope for the 2e store contract). The store contract treats CompIDs as opaque strings; downstream readers should note that path-traversal hygiene is the caller's obligation, not the store's.
- [x] CHK005 - Is the recovery contract specified for a torn **sentinel** record (first record corrupted, not just a tail record)? [Edge Case, Gap, Spec §FR-009 / §FR-012] — **DD-DECIDED §6.3.2 step 3**: "Verify the sentinel record; if invalid → return `store_factory_failed` (the directory holds a foreign file or a corrupted earlier session; recovery is operator's choice)". A torn sentinel is "invalid sentinel" and surfaces identically to sentinel-mismatch / foreign-file. Recovery is operator-driven (manual investigation), not auto-recovered — by design.
- [x] CHK006 - Is the contract for a partial `pwrite` return (short write to disk-full or signal-interrupted I/O) specified — retry, fail with `store_io_failure`, or treat as torn write? [Gap, Spec §FR-011] — **WAIVED**: partial-pwrite handling is T-impl per standard POSIX/Win32 hygiene (impl loops on short return; -1+errno surfaces). The normative contract is FR-011's "MUST call `fdatasync` ... before completing the awaitable with success" — i.e., the full record must be persisted before success-return; how the impl achieves that (loop on partial returns, syscall retry on EINTR) is unconstrained. A pwrite that cannot complete (disk full mid-write) surfaces as `store_io_failure` per the §6.1.2 trap_throw routing. Future readers: this is a recognised T-impl latitude.
- [x] CHK007 - Is the durability scope of `MOVEFILE_WRITE_THROUGH` explicitly tied to power-loss (not just SIGKILL) survival, matching what Linux parent-dir `fsync` guarantees? [Consistency, Spec §FR-010 / §SC-002 / §SC-003] — **DD-DECIDED §6.3 + §6.3.5 + round-3 C-R3-P1-2**: design-doc §6.3 lines 1063 names the contract explicitly — "Durability of the rename — i.e., 'after a crash, will the rename still be visible?' — is **not** automatic on either platform: on Linux, the parent-directory `fsync` after the rename is **mandatory** ... on Windows, the `MOVEFILE_WRITE_THROUGH` flag ... is **mandatory** per Win32 semantics (NTFS metadata journaling commits the rename to the journal but the journal itself is buffered)". Both primitives target host-crash including power-loss; SIGKILL is the easier sub-case used in SC-002/SC-003 as the testable representative. Consistency holds.
- [x] CHK008 - Are requirements specified for `flock` / `LockFileEx` behaviour on network filesystems (NFS, SMB) where advisory locking is documented-unreliable — supported, rejected, or undefined? [Gap, Spec §FR-013] — **WAIVED**: v1.0 deployment target is local NVMe/SSD per `[2e §1.2]` per-session 10⁴ frames/s throughput target and `[const §VIII.5]` hot-path discipline; NFS/SMB advisory-lock semantics are out-of-scope. Post-v1.0 network-filesystem support would require explicit FR + a different locking strategy (likely a manifest-file lock with leases); recorded here as forward-compat note.
- [x] CHK009 - Is the forward-compatibility invariant prohibiting cross-filesystem `.reset.tmp` written as a normative FR (not just an Edge Case discussion), so future implementations cannot regress it? [Gap, Spec §EC / §FR-010] — **DD-DECIDED Spec §EC (Cross-filesystem `.reset.tmp`)**: spec.md §EC carries the constraint as a normative `MUST` — "a future implementation that admits an external temp directory MUST reject cross-filesystem paths instead of falling back to copy". Edge Cases section is normative per the Spec-Kit template convention (`*(mandatory)*` enclosing block at spec.md §User Scenarios & Testing). Same invariant mirrored at design-doc §6.3 Cross-filesystem note (line 998).
- [x] CHK010 - Are the side-channel distinctions between sentinel-mismatch failure modes (foreign file vs. version drift vs. corrupted sentinel CRC) specified so the operator can choose recovery, given §EC says "recovery is the operator's choice"? [Clarity, Spec §EC / §FR-009] — **DD-DECIDED §6.3.2 step 3 + Spec §Observability (owed to 2k)**: by-design a single `store_factory_failed` variant covers all sentinel-invalidation modes; v1.0 does not claim auto-recovery and the operator's recovery path is uniform (manual investigation). Distinguishing failure-mode side-channels (foreign file vs. version drift vs. CRC-corrupted sentinel) is a 2k structured-log concern per design-doc §7.5 line 1163 ("All observability is implemented through 2k's Logger / Sink / TracerProvider interfaces"), explicitly deferred per Spec §Observability — owed to 2k. The single-variant + 2k-deferred-observability shape is the v1.0 contract.
- [x] CHK011 - Is `reset()`'s linearisation-vs-durability ordering unambiguous when SIGKILL occurs **between the `rename` returning success and the parent-dir `fsync` returning success** — does FR-020's "after linearisation must be durable" align with FR-010's "cannot return success until durability primitive returns"? [Consistency, Spec §FR-010 / §FR-020] — **DD-DECIDED §6.3.4 step 5 + §6.1.4 Linearisation-as-durability footnote (round-3 N3-P3-1)**: the footnote at design-doc:963 pins explicitly — "Linearisation point for FileStore methods means 'the point at which the on-disk state per §6.3 transitions to the new value AND the durability primitive ... has returned success'". §6.3.4 step 5 + Property paragraph at lines 1040–1047 confirm: SIGKILL between `rename` and parent-dir `fsync` (Linux) → durability primitive did not complete → linearisation point not reached → `reset()` did NOT return success → FSM retries on next open. FR-010 + FR-020 are consistent under this footnote.

## Concurrency, Cancellation & Strand Requirements

- [x] CHK012 - Is the invariant "concurrent calls on the same instance from the same session strand cannot occur" stated explicitly as the v1.0 single-serialisation-domain assumption that FR-016's FIFO-fairness defence-in-depth backstops? [Clarity, Spec §FR-015 / §FR-016] — **DD-DECIDED Spec §FR-024 + §FR-016**: FR-024 binds the single-strand invariant explicitly ("Every MessageStore async method MUST be invoked on the session strand via `session_executor` per `[2d §4.8]`"); FR-016's FIFO-fair `async_mutex` is the defense-in-depth backstop for the off-spec case where concurrent callers arrive from outside the session serialisation domain. The two-layer split is the v1.0 contract per `[2d §4.8]` single-session-serialisation-domain discipline + `[2f §4.3.2]` fast-path CAS-acquire.
- [x] CHK013 - Is the state of `store_arena` (post-FR-019 deep-copy) under "cancelled before linearisation point" defined — does the arena retain the copy (memory waste), or is it required to roll back? [Ambiguity, Spec §FR-019 / §FR-020] — **DD-DECIDED §6.1.4 Idempotency-under-cancellation footnote (design-doc:967)**: "no state change" in the cancellation table refers to *observable* state; pre-linearisation mutations to internal slab/arena are by-construction unobservable (`MemoryStore` does not insert into its index until the slab memcpy and entry write are complete; `FileStore` treats partial writes as torn writes truncated on next open). The deep copy in store_arena prior to linearisation is therefore not a "state change" for the cancellation-result contract; subsequent calls may reuse the slot (T-impl detail — bounded by `max_frame_bytes` per slot).
- [x] CHK014 - For `retrieve` cancelled between two `on_frame` invocations, is the contract for already-yielded frames specified (delivered? rollback semantics? side-effects observable to the visitor)? [Gap, Spec §FR-017 / §FR-020] — **DD-DECIDED §6.1.4 retrieve row + Spec §FR-020 retrieve clause**: design-doc cancellation table row for `retrieve` explicitly defines both branches — "before any visitor invocation → `expected_t::unexpected{store_cancelled}`"; "Visitor invocation in progress: cancellation propagates through the visitor's awaitable per root cause #2; the next visitor frame is not invoked; `retrieve()` completes with `store_cancelled`". Already-yielded frames are delivered (the visitor saw them); no rollback semantics (a read path has no state to roll back); side-effects of completed `on_frame` calls are the visitor's own concern, not the store's.
- [x] CHK015 - For mid-traversal mutation appending sequential seqnums in-range (e.g., snapshot ended at 42, store advances to 43 before the next `on_frame`), is the visitor's visibility of seqnum 43 defined — "already-visited frames are not re-visited" covers 42 but not 43? [Ambiguity, Spec §FR-017] — **DD-DECIDED Spec §FR-017 (already pinned)**: spec.md FR-017 explicitly says "iteration stops at the original `end`". The snapshot taken under the writer-mutex bounds the iteration; seqnum 43 appended after the snapshot is NOT visited on this retrieve call (it falls outside the original `[begin, end]`). Same applies to `end == 0` (snapshot resolves "to current tail" at snapshot time, not dynamically). This was a misread on my part — the spec is unambiguous.
- [x] CHK016 - Is the contract for `Session::close(terminal)` racing with an in-flight `FileStore::store` whose work is mid-flight on `file_io_executor` specified — does the rebind-to-strand surface a defined error, or is the awaitable abandoned? [Gap, Spec §FR-024 / §FR-028] — **DD-DECIDED §6.2.1 step 2 + data-model.md I-22**: design-doc §6.2.1 step 2 specifies "cancel → drain → destroy `unique_ptr<MessageStore>` → release `session_arena` → `~Session`". I-22 binds the test contract: "100 in-flight outstanding calls all complete (with `store_cancelled` for those whose linearisation point was not reached); no UAF on `session_arena`; `~MessageStore` runs before `session_arena` release". `cancellable_dispatch` per `[2d §6.5]` handles the `file_io_executor → session-strand` rebind under cancellation; the awaitable surfaces `store_cancelled`, not abandoned. Seam 18 verifies under TSan + ASan.
- [x] CHK017 - Are linearisation-point requirements stated symmetrically for **all four methods** (FR-020 lists store/next_seqnum/reset/retrieve) — is `retrieve`'s "per-frame, each visitor invocation has its own linearisation boundary" measurable in the same way the others are? [Measurability, Spec §FR-020] — **DD-DECIDED §6.1.4 linearisation-point list line 961**: `retrieve`'s per-frame linearisation boundary is precisely defined as "the visitor's awaitable resumes" — measurable per `on_frame` invocation by cancellation-vs-resumption timing. The four methods are symmetric in shape (each has a defined linearisation point that the cancellation table queries); `retrieve`'s split into per-frame boundaries reflects the per-frame visitor awaitable design (root cause #2), not a measurability defect. Seam 6 verifies per-method cancellation-result contract including `retrieve`'s per-frame variant.
- [x] CHK018 - Are latency requirements specified for `next_seqnum(_, false)` **under writer-mutex contention** (SC-008's ≤75 ns is "warm cache, uncontended")? [Coverage, Spec §SC-008 / §FR-015] — **WAIVED**: v1.0 single-strand discipline per FR-024 + `[2d §4.8]` makes mutex contention an off-design path; the FIFO-fair `async_mutex` per FR-016 is defense-in-depth for off-spec callers. No SLO is defined under contention because the contended path is by-construction off-design; the uncontended `[2f §4.3.2]` fast-path CAS-acquire is the v1.0 hot-path budget the SC-008 ceiling targets. Future readers: if v2.0 admits multi-strand store sharing, that's a post-v1.0 design surface (`[SYN §3.2 Q6b]`) and would re-open the latency-under-contention question.
- [x] CHK019 - Is the cancellation contract for `flush_for_session_close()` defined — FR-028 says it MUST NOT surface `store_cancelled` under graceful close, but is the behaviour under a root-total cancellation propagated from the engine specified? [Gap, Spec §FR-028] — **DD-DECIDED §6.2.1 step 1 (round-3 C-R3-P1-3)**: "The cancellation case is forced shutdown (`Session::close(terminal)` per step 2 / `cancellation_type::total` per `[2d §6.5]`), under which the hook is short-circuited and may leave the on-disk log in an unflushed state — recovery on next session open truncates the last incomplete record per the §6.3.4 startup contract; the user accepts that data-loss window." Under root-total cancellation the hook is short-circuited (not invoked at all); the §6.3.4 restart contract handles the unflushed tail.
- [x] CHK020 - Is the FIFO-fairness ordering specified as observable to the caller (i.e., is it just an internal property, or must `expected_t<void>{}` completions appear to the caller in arrival order)? [Clarity, Spec §FR-016 / §SC-005] — **DD-DECIDED Spec §SC-005 + design-doc §6.4**: SC-005 binds the observable contract explicitly — "Two coroutines concurrently invoking `store()` on the same instance from an `asio::thread_pool` MUST both complete with `expected_t<void>{}` in FIFO-arrival order". Under mutex serialisation, completion order = arrival order, observable by the calling coroutines.

## Allocator & PMR Discipline Requirements

- [x] CHK021 - Is the failure contract specified when `store_arena`'s PMR throws during FR-019's deep-copy (post-mutex-acquire, pre-pwrite) — `store_io_failure`, `store_capacity_exhausted`, or `store_visitor_aborted`? [Gap, Spec §FR-019 / §EC] — **DD-DECIDED §6.1.2 (round-2 Opus N2-P2-1)**: PMR allocation throw paths route through `fixpp::core::detail::trap_throw` per `[2a §4.2]` → `expected_t::unexpected{store_io_failure}` on FileStore disk-side; `expected_t::unexpected{store_capacity_exhausted}` on MemoryStore under `bounded` policy (unreachable under FR-007's zero-allocator-calls discipline); `expected_t::unexpected{store_io_failure}` on MemoryStore under `unbounded` policy where the throw is the only failure path. The mutex is released cleanly via RAII in all branches.
- [x] CHK022 - Is FR-007's "zero allocator calls under `bounded` after construction" reconcilable with FR-027's HALO-fallback to `session_arena` — does a HALO-elision-miss for the awaitable promise frame count as an allocator call that violates FR-007? [Conflict, Spec §FR-007 / §FR-027] — **DD-DECIDED §6.1.1 + Spec §SC-007**: scopes are disjoint. FR-007 + SC-007's "zero allocator calls" measures the `store_arena` tracking-PMR (MemoryStore's own per-call hot path); FR-027's HALO fallback is on `session_arena` (engine PMR), targeting the awaitable's coroutine promise frame on HALO-elision miss. Two different PMR resources, two different allocation domains — no conflict. Design-doc §6.1.1 confirms: "**`MemoryStore::store` performs zero allocator calls** ... `store()` is memcpy + index increment" (scope: MemoryStore-side). Coroutine promise allocation on `session_arena` is the engine's HALO fallback, not the store's.
- [x] CHK023 - Is the upstream `memory_resource` of the engine-provided default `monotonic_buffer_resource` (FR-026 fallback when `MemoryStore::Config::store_resource == nullptr`) constrained so a buffer grow cannot reach global `new` and violate FR-027? [Gap, Spec §FR-026 / §FR-027] — **DD-DECIDED §6.1.1 + data-model.md I-10 + FR-014 / I-11**: I-10 binds "one PMR allocation at construction for slot+slab combined", sized by the FR-014 / I-11 storage-DoS guard (overflow-safe checked arithmetic against `EngineConfig::max_store_memory_per_session`). Under bounded sizing the slab is allocated once at construction and never grows; subsequent `store()` calls are memcpy + index increment with zero allocator calls (FR-007). If the construction-time allocation exceeds the cap, `MemoryStoreFactory::make()` rejects with `store_factory_failed` before the upstream is touched. Upstream growth is unreachable by construction.
- [x] CHK024 - Does SC-007 extend the zero-global-allocation contract to **`FileStore::store`** under all three policies, or only to `MemoryStore::store`? [Coverage, Spec §SC-007 / §FR-027] — **DD-DECIDED Spec §FR-027 + §SC-007**: FR-027 applies to "`store(...)`" — i.e., all `MessageStore::store` implementations, not just MemoryStore. SC-007's `tools/check_alloc.py` post-link symbol scan + 10⁴-message session under `mallocnesia` covers the entire session run (both stores). The narrower zero-allocator-calls property (tracking-PMR counter unchanged) is MemoryStore-specific per FR-007 because FileStore necessarily uses `store_arena` for `pwrite` buffer scratch (FR-019 deep-copy lands there); FileStore's contract is no-global-new-but-may-use-store_arena. Both stores satisfy FR-027 collectively.
- [x] CHK025 - Is the lifetime of the `mr` parameter passed to `MessageStoreFactory::make()` (and its relationship to `store_resource`) specified — caller-owned, engine-owned, ownership-transferred? [Gap, Spec §FR-005 / §FR-026] — **DD-DECIDED §6.2.1 step 2 + I-22 + design-doc §4.4**: `mr` is the per-session PMR resource (typically pointing at `session_arena` per `[2d §4.5]`); lifetime is bound by the Session's ownership chain — I-22 binds "`~MessageStore` runs before `session_arena` release", so `mr`'s pointee outlives the store. Standard PMR convention (caller-owned, non-owning pointer); the engine holds the `session_arena` and threads its address into `make()`. No ownership transfer.
- [x] CHK026 - Is PMR-poison routing through `trap_throw` defined for both the visitor's caller-supplied resource (EC) AND the store-side `store_arena` (during deep-copy)? [Coverage, Spec §EC / §FR-019] — **DD-DECIDED §6.1.2 + data-model.md I-21**: routing is defined for both sides but to **different** variants. Visitor's caller-supplied resource throwing on the recovery path → `trap_throw` → `expected_t::unexpected{store_visitor_aborted}` (I-21 / Spec §EC PMR-poison-on-recovery-path). Store-side `store_arena` throwing during FR-019 deep-copy → `trap_throw` → `store_io_failure` (FileStore) or `store_capacity_exhausted` (MemoryStore bounded — unreachable) / `store_io_failure` (MemoryStore unbounded) per §6.1.2. Coverage is complete; the variant-side asymmetry reflects which surface owns the failure.
- [x] CHK027 - Is the `MemoryStore::Config::store_resource` lifetime contract specified — must outlive the store; what is the engine's obligation when it provides the default resource and the store is destroyed? [Gap, Spec §FR-026] — **DD-DECIDED Spec §FR-026**: engine-provided case is explicit — "the engine MUST provide a dedicated `std::pmr::monotonic_buffer_resource` whose lifetime matches the store instance" (so the engine owns it and destroys it after `~MemoryStore`). Caller-supplied case is PMR convention (`memory_resource*` is a non-owning pointer; caller must keep the resource alive for the store's lifetime), consistent with `mr` lifetime in CHK025. The two surfaces compose correctly.

- [x] CHK030 - Is the `unique_ptr<MessageStore>` deleter shape specified — default `delete`, custom deleter for PMR-allocated impls, or impl-defined?
