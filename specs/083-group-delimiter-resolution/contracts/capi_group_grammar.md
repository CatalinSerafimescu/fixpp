**Feature**: `083-group-delimiter-resolution` | Satisfies FR-018, FR-018a, FR-018b, FR-019, **FR-019a**, **FR-019b**, **FR-022 (path 3)**, SC-009, SC-012

**Created**: 2026-07-30 (Gate A round 1) — the 2026-07-30 clarification widened scope onto the C-ABI construction path, and that surface had a research paragraph, no contract and no test artifact while carrying a **disclosed behaviour change through a GA-frozen ABI**.

## Why this needs a contract, not a paragraph

`[const §X.1]` (`.specify/constitution.md:220`) makes the C ABI a versioned contract, frozen at 1.5.0; `[const §X.6]` (`:225`) makes an ABI-affecting feature trigger all four mandatory controls. FR-019/FR-019a (`spec.md`) already admit a **disclosed C-ABI construction-side behaviour change** in three classes — two of them regressions (a client that today builds an affected group opening with the old delimiter gets `FIXPP_ERR_TYPE_MISMATCH` afterwards) and one a widening. *(Generalised 2026-07-31, `/speckit-analyze` re-run F2 — this background paragraph still said "five groups whose delimiter moves" after C-9.6/C-9.7 below were widened to three classes.)* `[const §VII.4]` ("no code without a test") applied to a disclosed ABI-visible regression means SC-012 needs a witness, and it had none.

## Current behaviour

`validate_group_grammar` is **file-static** at `src/capi/message_write.cpp:710-730` and already recurses through nested instances (`:724-726`). Its delimiter leg is:

```cpp
if (dict) {
    uint16_t delim = dict->group_first_field(e.tag);      // :719 — context-FREE
    if (delim != 0 && inst.fields[0].tag != delim) {
        return FIXPP_ERR_TYPE_MISMATCH;                    // :721
    }
}
```

`group_first_field(e.tag)` is the dictionary-**global**, first-seen delimiter — the same value inbound validation is being moved off. So construction and validation apply two different rules to the same message today.

Separately, three sites use the same global as an *is-this-a-group* **predicate**, not as a delimiter: `src/capi/message_write.cpp:157`, `:812`, `:923`. Those are D-10's concern, not this contract's; they are named here so the two uses are not conflated during implementation.

## Contract

**C-9.1 — One rule, two paths.** The construction-side delimiter check resolves through the per-context delimiter (`group_ctx_delims.md` Entity 2, via `table_view::group_first_field(msg_type, parent_path, no_tag)`), the identical rule inbound validation applies. A message the builder accepts is never rejected by the engine's own validation on delimiter grounds, and vice versa.

**C-9.2 — Context is threaded through the existing recursion; nothing new is plumbed across the boundary.** `validate_group_grammar` already descends per nested instance, and the accumulator already carries the message type at both commit call sites (`src/capi/message_write.cpp:762`, `:781`). The change is (a) an added `std::string_view msg_type` and an ancestor-path parameter on the file-static function, and (b) pushing `e.tag` onto that path at the `:725` recursion. Both are internal.

**C-9.2a — The route from the C-ABI handle to Entity 2, named** *(added Gate A round 2, 2026-07-31 — Codex #3. This was the contract's central mechanical gap.)*

`validate_group_grammar` receives a `const fixpp::dict::Dictionary*` (`src/capi/message_write.cpp:710-711`). `Dictionary`'s only `group_first_field` is the **bare** overload (`include/fixpp/dict/dictionary.hpp:109-111`); the context-keyed overload lives on `table_view` (`include/fixpp/dict/table_view.hpp:349-365`). So a route must be named, and the obvious one is **banned, not merely slow**:

- ✗ **`dict->as_table_view()` at the call site.** It compiles (`as_table_view()` is public, `dictionary.hpp:212`) but rebuilds the whole table view per message and per field run, and both its declaration and its definition carry `[const §XV.1]` — *"construction only at config-time; the returned `table_view` is immutable and must not be rebuilt on the per-message hot path"* (`include/fixpp/dict/dictionary.hpp:210-212`) / *"called once at session/validator setup; must not be called on the per-message hot path"* (`src/dictionary/dictionary.cpp:357-358`). `validate_group_grammar` runs inside `fixpp_msg_commit` (`src/capi/message_write.cpp:755`) — the per-message path. Naming this route would put a constitution violation in front of `/speckit-tasks`.

**✓ Chosen route — a session-cached `table_view`, mirroring how `dict_` already propagates.** `fixpp_session` today holds only `std::shared_ptr<const Dictionary> dict_` — declared at `src/capi/capi_internal.hpp:493` and **cached at `fixpp_session_open` time by the assignment at `src/capi/session.cpp:109-111`**. Add, beside it, one `table_view` built **once at that same config-time point** from that dictionary — the identical pattern `fixpp::session::Session` already uses for `inbound_tv_` (`src/session/session.cpp:992`) and that `fixpp_msg` already uses for its clone-owned `owned_tv_` (`src/capi/capi_internal.hpp:285`, with its documented destruction-order note at `:277-284`). `fixpp_msg_create_outbound` copies a **non-owning pointer** to it into the handle exactly as **the statement at `src/capi/message_write.cpp:289-291`** already copies `dict_` into the member declared at `capi_internal.hpp:261-266`, and `validate_group_grammar` takes that pointer alongside the `Dictionary*` it takes today.

*(Citations sharpened 2026-07-31, Gate A round 3, Codex #1: the round-2 text cited `capi_internal.hpp:261-266` — the destination member's declaration and comment — for the **copy**. That comment is not stale (`:262` reads *"Copied from the session's `dict_` at create\_outbound time"*), so this was imprecision rather than a wrong pointer; the two copy **statements** are now cited where the clause is about copying, and `:261-266` is retained below where the clause is about the member's lifetime and null semantics. `:493` is kept as-is — it is the exact declaration line, and the reviewer's proposed `:489-493` would replace a precise citation with its comment block.)*

**Allocation / lifetime disposition** — the leg that makes this checkable:

- **Allocation**: exactly **one** `as_table_view()` per opened session, at `fixpp_session_open`. Zero per message, zero per field run. `[const §XV.1]` and C-6.5's "no hot-path effect" both hold.
- **Ownership**: the `table_view` is **owned by `fixpp_session`**, not by the message handle. The message stores a raw `table_view const*` into it, valid for the dispatch/build window the session already bounds for `dict_`. It is **not** stored in the session arena, for the same reason `dict_` is not (`capi_internal.hpp:261-266`): the container destructors must not depend on arena lifetime.
- **Which member commit reads**: **the session-cached view**, always — never `owned_tv_`. `owned_tv_` is the *clone-inbound membership copy* (`capi_internal.hpp:267-285`), populated only when a cloned handle's source `MessageView` was dict-backed; it is not a construction-side artifact and the two must not be conflated. If a future change wants commit to consult `owned_tv_`, that is a separate decision requiring its own witness.
- **Absent-view disposition, and why it does not disturb C-9.4**: `fixpp_msg::dict_` is `nullptr` for inbound dispatch-window handles (`capi_internal.hpp:261-266`), and the cached view is absent on exactly the same handles, from the same source. The two are therefore **always** present or absent together — a session with no dictionary caches no view. When the pointer is null, commit performs the empty-instance check only and **no delimiter check**, byte-for-byte C-9.4's existing disposition. A handle with a `Dictionary` but a null view is not a reachable state; if the implementation cannot make that structural, it MUST fail the commit closed rather than silently fall back to the bare `dict->group_first_field(e.tag)`, which would reinstate exactly the global first-seen defect FR-001 removes (`group_ctx_delims.md` C-3.4's first refused fallback).
- **Exported surface**: unchanged. `fixpp_session` and `fixpp_msg` are internal `struct`s in `src/capi/capi_internal.hpp`, not part of the C header; adding a member changes no `fixpp_*` declaration and no client-visible layout. C-9.3 holds byte-for-byte.

**C-9.3 — No exported signature changes (FR-018a).** `validate_group_grammar` is `static`; it is not an exported symbol and carries no ABI. No `fixpp_*` declaration, no enum value, no struct layout, and no `FIXPP_C_ABI_VERSION_*` constant moves. The 1.5.0 freeze holds byte-for-byte on the exported surface.

**C-9.4 — The `dict == nullptr` disposition is unchanged.** A handle with no dictionary performs the empty-instance check only (`:716`) and no delimiter check, exactly as today. This feature does not make the C ABI stricter for dict-free handles.

**C-9.5 — The predicate sites are NOT converted.** `:157`, `:812` and `:923` keep asking the bare global "is this tag a group". They are answered by D-10's repopulated projection. Converting them to a context-keyed query would make `group_begin` reject a group whose context the caller has not yet established, which is a total regression through the frozen ABI — the failure mode D-10 exists to prevent.

**C-9.6 — The behaviour change is enumerated, not merely disclosed — and it is THREE classes, not one.** FR-019's `spec/behaviors-and-limitations.md` B&L row (this repo's release-note artifact — there is no `CHANGELOG.md`) enumerates **FR-019a's classes (a), (b) and (c)**, so an integrator can diff their builder against a list rather than against prose. Per fixpp#208's suggested-scope item 4, a client building with the old opening tag receives `FIXPP_ERR_TYPE_MISMATCH` after this change.

*(Widened 2026-07-31, Gate A checklist audit.* As written through Gate A this clause named only the **five** cause-2 groups. That set is the answer to *"whose global value moves"* — but the construction check's change is that it stops reading the **global** value at all (C-9.1/C-9.2), so the enumeration must be taken over *"whose resolved value moves"*. Two classes fall outside the five:

- **class (b)** — the cause-1 tags. Their global value is **unchanged**, which is precisely why enumerating against the global lookup misses them; their *per-context* value differs in the divergent contexts, so a client building there is accepted today and rejected after — **the same severity as class (a)**, and the reason SC-007's exception cannot be stated as "five groups".
- **class (c)** — the three unregistered groups plus their six nested children. Verified at source: `src/capi/message_write.cpp:812` and `:923` reject a group whose `group_first_field` is 0 with `FIXPP_ERR_TYPE_MISMATCH`, so today these are **unbuildable through the C ABI**, and the commit-time check never runs for them either (`:720` guards on `delim != 0`). Registration makes them buildable — a **widening**, disclosed but not an SC-007 exception.

Witness coverage was already adequate and is unchanged: **W-11** runs on a divergent context and therefore pins class (b); **W-12** pins class (a). The defect was in the *enumeration*, not the pins — which is why this is a disclosure fix and adds no test.)*

**C-9.7 — Relation to SC-007.** SC-007 ("no schema-valid message accepted before is rejected after") is not violated: the newly-rejected construction orders are not schema-valid under declaration order. C-9.6's enumeration is what lets the SC-007 audit distinguish an **intended** new rejection from a regression — without it the audit has no discriminator. *(2026-07-31, Gate A checklist audit: the discriminator is only as wide as the enumeration. With C-9.6 scoped to the five cause-2 groups, a class-(b) rejection — same mechanism, same severity — would have presented to the SC-007 audit as an **unenumerated** new rejection, i.e. as a regression, or been waved through as "the disclosed change" without ever being listed. Classes (a) and (b) are both SC-007 exceptions; class (c) is a widening and is not.)*

## Witnesses

New file `tests/capi/capi_group_delimiter_ctx_test.cpp`:

**W-11 — `CapiGroupDelimiterCtx.ConstructionAcceptsIffValidationAccepts`** (SC-012 / **C-9.2a**). For a divergent context — one where the global first-seen delimiter and the context delimiter differ — build the group through the C ABI and validate the same bytes through inbound validation; assert the two verdicts agree. Run for both the accepting and the rejecting delimiter placement, so agreement is proven in both directions rather than by a single accept. **The divergence is what pins the route**: a commit that still resolved through `dict->group_first_field(e.tag)` would answer with the global value and disagree with validation, so this case fails if C-9.2a's session-cached `table_view` is not the source. Use a **nested** group (non-empty ancestor path) so the path threaded at `:725` is exercised rather than defaulted.

**W-11a — `CapiGroupDelimiterCtx.CommitDoesNotRebuildTableViewPerMessage`** (C-9.2a / `[const §XV.1]`). Assert the config-time-only construction directly: open a session, commit **N > 1** messages carrying groups, and assert `as_table_view()` was entered **once**. Without this, the banned `dict->as_table_view()` route passes W-11 and W-12 identically — it is *correct*, just constitutionally forbidden — so no other witness in this feature can tell the two routes apart. The counter is a test seam of the same *kind* as `fixpp_capi::detail`'s existing live-state counter (`src/capi/capi_internal.hpp:496-500`), but it cannot live in that namespace: `as_table_view()` is defined in `src/dictionary/dictionary.cpp`, a different module with no existing `detail`-namespace instrumentation to extend (checked — none found). **Route named** *(added at checklist audit, 2026-07-31; header choice tightened by the orchestrator in the same pass)*: a `fixpp::dict::detail::as_table_view_call_count()` counter, incremented in `Dictionary::as_table_view()`'s body in `src/dictionary/dictionary.cpp` and declared in **`src/dictionary/dictionary_internal.hpp`** — the internal header this feature already edits for Entity 2 — **not** in the public `include/fixpp/dict/dictionary.hpp`. This mirrors the `fixpp_capi::detail` precedent *exactly*: that counter is declared in `src/capi/capi_internal.hpp` (`:496-503`), an **internal** header, and `tests/capi/` already includes internal headers directly (`message_write_test.cpp`, `public_roundtrip_test.cpp`, `send_recv_test.cpp` and others), so the witness can reach it without the seam entering installed public surface. The first drafting of this clause placed it in the public header, which would have been a *stricter* change than the precedent it cites — a test-only seam in an installed header — for no gain in observability.

**W-11b — `CapiGroupDelimiterCtx.DictFreeHandleStillSkipsDelimiterCheck`** (C-9.4 / C-9.2a). A handle whose session carries no dictionary — and therefore no cached view — commits a group and receives the pre-083 disposition: empty-instance check only, no delimiter check, no new rejection. Pins that C-9.2a's added member did not make the C ABI stricter for dict-free handles, and that "no dictionary" and "no view" are the same state.

**W-12 — `CapiGroupDelimiterCtx.DisclosedDelimiterMoveRejectsOldOrder`** (FR-019 / C-9.6 / **C-9.2a**). For one of the five named groups, build with the **old** opening tag and assert `FIXPP_ERR_TYPE_MISMATCH`; build with the new one and assert `FIXPP_ERR_OK`. This is the disclosed regression, pinned rather than described — and it is a second consumer of the C-9.2a route, since the old tag *is* the global first-seen value for those groups, so a commit still reading the bare global would accept it and fail this case.

**W-13 — `CapiGroupDelimiterCtx.GroupBeginStillAcceptsEveryRegisteredGroup`** (C-9.5 / D-10). Over all ten dictionaries, every registered `no_tag` still answers the bare predicate non-zero. This is the direct pin for the total-regression scenario D-10 identifies — a scenario whose whole hazard is that it would otherwise be caught only by a C-ABI client, after release.

**W-14 — No exported-surface change** (FR-018a / `[const §X.1]`). The existing ABI hygiene gate must show no delta; recorded as evidence in Phase 5 rather than as a new test. **The gate is `nm`-based exported-symbol comparison only** — `abidiff` was retired 2026-06-22 (`.github/workflows/abi-golden.yml`: libabigail 2.4.0 asserts/core-dumps on debug-info-less archives, and `nm` gives the same check); abidiff artifacts are retained solely as an upgrade hook. Do not treat Article IX §5's `abidiff` wording as describing the live gate — that is a pre-existing constitution/artifact drift outside this feature's scope.
