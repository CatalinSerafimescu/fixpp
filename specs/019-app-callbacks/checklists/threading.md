# Threading / Lifetime Requirements Quality Checklist: Application Callback Layer (Phase-5, slice 1)

**Purpose**: Validate that the concurrency/lifetime requirements (per-session-strand serialization, no-concurrent-callbacks, drain-before-destroy, any-thread `Engine::send` post + keepalive, re-entrant-send non-deadlock, throw→terminal-close at every site) are complete, clear, consistent, and measurable — BEFORE implementation. "Unit tests for the requirements," not for the code.
**Created**: 2026-06-04
**Feature**: [spec.md](../spec.md)
**Domain**: Threading / lifetime (Gate A trigger). Audience: reviewer / `/speckit-checklist-audit` gate (step 9).

## Requirement Completeness

- [x] CHK001 Is the per-session-strand serialization requirement stated for EVERY callback (the 4 message hooks + the 3 lifecycle hooks), not only in aggregate? [Completeness, Spec §FR-010] — PASS: FR-010 states "All `Application` callbacks for a given session MUST execute on that session's serialized executor" covering all 7 callbacks; data-model INV-2 cross-references the `exec_` strand as the real guarantee; contracts/application-interface.md method table lists "session strand" threading for every callback row. Refs: spec.md §FR-010, data-model.md INV-2, contracts/application-interface.md method table.
- [x] CHK002 Is the drain-before-destroy requirement (`stop()` → `close(terminal)` + join-before-registry-clear, so no callback runs against a freed session) captured, including the detached outbound write originated by a callback? [Completeness, Spec §FR-012/§Edge Cases] — PASS: FR-012 is explicit — "drain all dispatched `Application` callback work — and any detached outbound write originated by a callback — before destroying a session"; the `[L-015-4]` contract citation (`stop()` → `close(terminal)` + join-before-registry-clear) and the detached-write keepalive (014 class) are both named. The Edge Cases section reinforces it. Refs: spec.md §FR-012, §Edge Cases, data-model.md INV-3, research.md D3/D6.
- [x] CHK003 Is the any-thread `Engine::send` post-keepalive requirement stated — that the registry lookup captures a strong/owning session reference outliving the posted work, and `stop()` drains posted-but-not-yet-run sends? [Completeness, Spec §FR-006/§FR-012] — PASS: FR-006 explicitly requires "post MUST preserve … the `[L-015-4]` keepalive"; FR-012 states the registry lookup "MUST capture a strong/owning reference to the target session … that outlives the posted work" and "`stop()`'s join MUST drain posted-but-not-yet-run sends before the registry clear". research.md D6 names the exact UAF class. Refs: spec.md §FR-006, §FR-012, research.md D6.
- [x] CHK004 Is the re-entrant-send case (a `send` issued from inside an on-strand callback is enqueued behind the current dispatch, no deadlock/recursion) captured as a requirement, conditional on the post-only/awaited model? [Completeness, Spec §FR-006/§Edge Cases] — PASS: FR-006 states "a re-entrant call from inside an on-strand callback MUST NOT deadlock (the entry point posts and does not synchronously block the strand on its own completion)"; the Edge Cases §Re-entrant send section elaborates the conditional guarantee with the post-only model and the MUST-NOT-synchronously-block constraint. Refs: spec.md §FR-006, §Edge Cases.
- [x] CHK005 Is the throw→terminal-close disposition required at EVERY callback site (inbound/outbound/lifecycle), with the re-entrancy guard cleared on unwind, rather than at a single site? [Completeness, Spec §FR-011] — PASS: FR-011 says "at every callback site (inbound, outbound, lifecycle) the engine MUST catch it at the dispatch boundary, log it, clear the re-entrancy guard, and terminate the session via terminal close"; research D5 explains that the `dispatch_guard` RAII already clears `in_dispatch_` on unwind; tasks T007/T018 pin that all 7 sites are covered. Refs: spec.md §FR-011, §Edge Cases, research.md D5, tasks.md T018.
- [x] CHK006 Is the `onCreate` execution domain pinned (fires after `Session::open()` initializes `exec_`, so it is genuinely on-strand — not at pre-`open()` construction when `executor()` is invalid)? [Gap, Spec §FR-009/§US3] — PASS: FR-009 explicitly states "after a session is created and its executor is initialized by `open()`"; US3 AC1 repeats "after `Session::open()` initializes its executor"; data-model.md and contracts/application-interface.md `onCreate` row both list "session strand (post-`open()`)" as the pre-condition. The firing point is unambiguously pinned. Refs: spec.md §FR-009, §US3 AC1, data-model.md onCreate row, contracts/application-interface.md method table.

## Requirement Clarity

- [x] CHK007 Is "on the session's serialized executor" defined against a concrete mechanism (the `exec_` strand) rather than an abstract "serialized" adjective, and is the debug-only nature of the `dispatch_guard` re-entrancy check distinguished from the strand (the real guarantee)? [Clarity, Spec §FR-010, data-model INV-2] — PASS: data-model INV-2 explicitly states "The serialization guarantee is the `exec_` strand (`make_strand`); `dispatch_guard` is a **debug-only (`#ifndef NDEBUG`) invariant check**" — the distinction is unambiguous and measurable. Verified in live code: `session.hpp` line 321 shows `#ifndef NDEBUG` guard on the `dispatch_guard` struct. Refs: data-model.md INV-2, spec.md §FR-010, session.hpp:321.
- [x] CHK008 Is the inbound invocation model (direct synchronous on-strand, NOT an `asio::post` queue) stated unambiguously, so "delivered on the executor" cannot be misread as buffering/queueing? [Ambiguity, Spec §Assumptions/research D3] — PASS: spec.md Assumptions §Wiring point explicitly states "callbacks execute **on** the session's serialized executor; the inbound … callbacks are invoked **directly** at the existing on-strand sites (no per-message `asio::post`, preserving zero-alloc §VIII.5 and no-drop §XV.15)"; research.md D3 is the detailed design decision with the same statement; plan.md Summary reiterates "callbacks run **directly on the per-session strand**". The word "directly" is used authoritatively. Refs: spec.md §Assumptions, research.md D3, plan.md Summary.
- [x] CHK009 Is "exactly once" for each lifecycle callback (`onCreate`/`onLogon`/`onLogout`) expressed as an objectively-testable once-per-session criterion pinned to a single transition edge, given `onLogout` has three converging exit paths (graceful / terminal / callback-threw)? [Clarity, Spec §FR-009, data-model INV-7] — PASS: FR-009 states `onLogout` fires "**exactly once** when a session leaves the established state — pinned to the single idempotent `Active → !Active` state-transition edge (fire-once-per-session guard) so the graceful-close, terminal-close, and callback-threw-teardown exit paths cannot double-fire or miss it"; data-model INV-7 repeats this verbatim and names `record_state_transition_` as the pin-point; tasks T015 mandates one test cell per exit path. Refs: spec.md §FR-009, data-model.md INV-7, tasks.md T015.

## Requirement Consistency

- [x] CHK010 Is the no-message-drop guarantee (`[const §XV.15]`) consistent across the inbound path (no post-queue — natural backpressure on the read-pump) AND the outbound `Engine::send` path (awaitable result = backpressure, no unbounded silent-drop queue)? [Consistency, Spec §FR-006, plan §XV.15] — PASS: FR-006 explicitly states the awaitable model "carries veto/store/write outcome truthfully and the await gives natural backpressure (no unbounded silent-drop outbound queue)"; spec §Assumptions Wiring point covers inbound ("no per-message `asio::post`"); plan.md Constitution Check row §XV.15 notes both paths. research.md D3 (inbound) and D6 (outbound) are consistent on the same principle. Refs: spec.md §FR-006, §Assumptions, research.md D3/D6, plan.md §XV.15.
- [x] CHK011 Is the `[L-015-4]` drain contract reused consistently (no second executor, no change to the session threading model) rather than re-specified divergently? [Consistency, Spec §Assumptions/§FR-012] — PASS: FR-012 cites `[L-015-4]` by name; spec §Assumptions last bullet explicitly states "This feature adds the public `Application` surface and its engine wiring; it does not introduce a second executor or change the session threading model"; research D3 confirms the same under "Alternatives rejected". No divergent restatement: the feature is explicitly defined as an extension on top of the existing drain contract. Refs: spec.md §FR-012, §Assumptions §Wiring point, research.md D3.
- [x] CHK012 Are the no-Application (`application==nullptr`) zero-behavioral-delta requirement (FR-002/FR-014) and the strand/drain requirements consistent — i.e. with no Application registered, none of the strand/drain machinery changes observable behavior? [Consistency, Spec §FR-002/§FR-014/§SC-006] — PASS: FR-002 requires `application==nullptr` to produce "behaviour identical to the pre-019 engine (no callback invocation, no behavioral change)"; FR-014 reinforces "MUST NOT regress any existing session/engine behavior when no `Application` is registered"; data-model INV-1 states the firing order collapses to the pre-019 path with zero invocations; SC-006 makes it measurable. The D8 admin/app classifier change is explicitly gated: the app-accept branch that suppresses `Reject(35=3)` applies only "when an `Application` is registered" (research D8), preserving byte-identity when `application==nullptr`. Refs: spec.md §FR-002/§FR-014/§SC-006, data-model.md INV-1, research.md D8.
