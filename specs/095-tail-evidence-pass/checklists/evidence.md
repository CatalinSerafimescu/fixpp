# Evidence Checklist: Typed app-message tail — offline witnesses, the walk, the census and every RED arm

**Purpose**: Requirements-quality review, for the Gate B reviewer, of the offline evidence the 12 tail rows close on. It covers the closure-required rule and the runtime dictionary walk, the 23 witnesses (intent list, bidirectional readback, required-presence check), the census, the non-circular known positives and every RED arm and mutant of contracts W1–W8, the N-002/N-003 registry pins and routing cell, FR-014's selection check as an instrument, and the evidence-file / verify-record rule. In scope: FR-001 to FR-008, FR-014 (instrument half), FR-020, US1, US2, SC-001, SC-002, SC-005. Must-have: the repo's #1 defect class, an instrument that reports clean because it could not report anything else, gets an explicit item for every check the bundle relies on.

## Witness requirements (intent list, build, parse, readback)

- [ ] CHK013 Is the relation between a witness's intent list and its `Args` setters specified precisely enough for the mutants to be realisable? W2 says Args "are populated from the literals of the intent list", yet Mutants B, D, E and H delete one side and keep the other. If setters read their value from the intent entry, Mutant D (delete the entry, keep the setter) may not compile and Mutant H (delete the setter, keep the entry) is trivially true. Is the required code shape stated? [Ambiguity, Contracts §W2, Contracts §W6 (Mutants B, D, E, H)]
- [ ] CHK014 Is the value-mismatch arm defined so that it can fire? Contracts W6 says "a literal changed after the build"; T027 adds "(or its intent literal changed)". If the Args are populated from the same intent literal, changing that literal before the build changes both sides and the comparison stays green. Is the arm restricted to a post-build change of the frame bytes or of the expected side only? [Conflict, Contracts §W6 (value-mismatch row), Tasks §T027]
- [ ] CHK015 Is "the tags the test's framing writes" enumerated or derived by a stated rule, so the set removed from both sides of W4 cannot silently swallow a body field that shares a tag with the framing? Is it stated what happens if a tail message's closure-required set contains such a tag? [Clarity, Edge Case, Spec §FR-003, Contracts §W4]
- [ ] CHK016 Does data-model §C's literal scheme make instance order checkable for every group? Enum fields take their first declared value and ints their tag number, so in a group whose members are all non-string, every instance carries identical literals: an instance swap or a misattribution between instances cannot fail W4's multiset comparison. Is a distinguishing literal required per instance in that case, or the limit stated? [Edge Case, Gap, Data-model §C, Contracts §W4 ("Instance order is checked by the per-instance literals")]
- [ ] CHK017 Is attribution "to the outermost required group whose extent contains it" defined for an entry inside an OPTIONAL group the witness happens to set, and for a message-level field written after a group (trailing member)? Does the path grammar cover them? [Coverage, Contracts §W4, Research §R-4]
- [ ] CHK018 Is "at least two fields in total" (FR-002) the same quantity as "the intent list holds at least two entries" (FR-003, W4)? Count fields are intent entries, so a witness with one group of two instances could meet the second without setting two fields. Which one is the requirement? [Consistency, Spec §FR-002, Spec §FR-003]
- [ ] CHK019 Is the independence of the parse stated as a checkable property (no builder table, generated header or Args type reachable from the parse path), rather than only as the statement "the parse does not use the typed builder's code or tables"? [Measurability, Spec §Terminology (Offline witness), Contracts §W3]
- [ ] CHK020 Is the "build MUST succeed" requirement paired with what a refused build means for the evidence (a stop, never an arm's RED), and is the same said for a refused parse of a witness frame, not only of a deficient frame? [Completeness, Contracts §W2, Tasks §Execution rules (Stop rules)]
- [ ] CHK021 Is FR-006/W8 measurable as written ("byte-unchanged; its tests still pass") with a stated command for both halves, and does it say whether the 077 tests' count in the binary may change (the new TU shares the executable)? [Measurability, Spec §FR-006, Contracts §W8, Tasks §T024]
