## The C ABI and Python (FR-007, `[const §X.7]`)

- [ ] CHK001 FR-007 says the C ABI is unchanged because it exposes none of the changed types. Article X §7 also counts as breaking a call that returns a result other than the one documented. `fixpp_dict_load_from_xml_with_overlay` documents `FIXPP_ERR_DICT_LIMIT_EXCEEDED` by pointing at the cause list in `xml_loader.hpp`, which D8 amends. An overlay whose only fault was the side-table fit now returns `FIXPP_ERR_OK`. Is that C-observable change stated, and is it dispositioned as BREAKING or additive? [Conflict, Spec §FR-007, contract preamble, `[const §X.7]`, research D8]
- [ ] CHK002 `fixpp_dict_load_from_xml` wraps `load_any`. On an Orchestra document with a component or group id above 65535 it used to return `FIXPP_ERR_CAPI_CONFIG_INVALID`, and now returns `FIXPP_ERR_OK` (B-102-3). Is that change dispositioned for the C ABI, and for the Python `dict_load_from_xml` that wraps it? [Gap, Spec §FR-007, contract §2, `[const §X.7]`]
- [ ] CHK003 Is it stated whether the C-ABI version in `version.h` moves? If it does not, is it stated why the changes CHK001 and CHK002 ask about do not require a move? [Clarity, Spec §FR-007, `[const §X.7]`]

## MultiCharValue types (contract §4, B-102-2)

- [ ] CHK013 Contract §1 sorts every change into "fails to compile" or "compiles and changes silently"; contract §4 sorts none. Is each MultiCharValue change classified that way? Examples: a `char` assignment, `switch (*acc)`, a comparison with a `char` literal, and `auto v = *acc;`. [Completeness, contract §4, contract §1]
- [ ] CHK014 A view accessor that returned `expected_t<char>` by value now returns a `std::string_view` into the message buffer (lifetimebound, research D3). A caller that kept the value after the message was gone compiled and was correct before; now it compiles and dangles. The same holds for an owning (reified) object that is moved or destroyed. Is this silent break stated in contract §4? Research D4 rejects lifetime cells because "its lifetime contract is not new to 102". That is true of the emitted text but not of a caller migrating from `char`. [Gap, contract §4, research D3, research D4 "#621"]
- [ ] CHK015 A builder `Args` member becomes `std::optional<std::string_view>`, so assigning a temporary `std::string` compiles and dangles until the build call. Is the caller's lifetime obligation stated in the migration, as it is for MultipleStringValue members? [Gap, contract §4, Spec §FR-005]
- [ ] CHK016 The contract says "The precompiled builder libraries' C++ ABI changes accordingly". Is it stated what a consumer of a prebuilt builder library must do, and whether any package or library version records the change? [Clarity, contract §4, Spec §Assumptions]
- [ ] CHK017 Is the set of affected generated symbols stated by re-derivation, as every accessor, `Args` member and group-entry setter of a MultiCharValue field in `fixpp::v50sp2` and `fixpp::vlatest`? Today only the example `exec_inst` identifies it. [Completeness, contract §4, research Survey "Codegen"]
- [ ] CHK018 Is it stated that `fixpp::v42`, `fixpp::v44` and `fixpp::vt11` have no MultiCharValue symbol to change, so their typed C++ API changes only through `Fields.hpp`'s row? [Coverage, Spec §US2.4, contract §5]
