## Side tables and the record fields (FR-001, FR-002)

- [ ] CHK001 FR-001 exempts three classes from the 32-bit rule: a FIX tag, a group index, and a member no loader writes (`condition_index`, `enum_table_index`). T029 may leave XML `GroupDef`'s 16-bit `first_field_index` and `field_count` in place as "unwritten pre-existing members". Is that member in one of FR-001's classes, or does FR-001's "no start or count" require it widened? [Consistency, Spec §FR-001, tasks T029, tasks "Bundle findings" 2]
- [ ] CHK002 Is "every vendored base" (US1.2, FR-002, SC-001) defined by a re-derivation, such as every dictionary file under `dictionaries/` and `dictionaries/orchestra/`? Otherwise the set is whatever the existing equivalence rows happen to list. FIX50SP1 is not a codegen target, yet SC-001 names it. [Clarity, Spec §US1.2, Spec §SC-001, tasks T009]
- [ ] CHK003 FR-002 says "with and without an overlay". Is the overlay set defined: each base's existing equivalence overlays, an overlay that adds definitions as in US1.3, or both? [Clarity, Spec §FR-002, Spec §US1.3]
- [ ] CHK004 The threshold reads "more than 65,535" components or entries in Context, contract §2 and B-102-3, and "more than 65,536 components" in US1.4 and FR-002. A base of exactly 65,536 components is the first whose one-based id wraps at `$P` (research Survey "Component identity"). Is that case required correct by a stated requirement and reached by a fixture? [Consistency, Spec §US1.4, Spec §FR-002, contract §2, research Survey]
- [ ] CHK005 FR-002 requires `Dictionary::component` to return each component's own "name offset". `name_offset` has no public reader, and no `src/` reader uses it (research Survey). Is the requirement stated as research D4's oracle states it, "the pool slice at `name_offset` equals the name", so that "own name offset" has a checkable meaning? [Clarity, Spec §FR-002, research D4 "name offset"]
- [ ] CHK006 Group starts and counts widen, but the group index stays 16-bit because NumInGroup tags (1..65535, first seen wins) bound it. Is that bound stated as a condition in the spec as well as in research Survey and data-model, so a reviewer can see that the group index falls within FR-001's "group index" exemption? [Completeness, Spec §FR-001, data-model `GroupRef`, research Survey "Group identity"]
- [ ] CHK007 Data-model defines `component_id` as the "0-based declaration index" and `FieldRef::component_index` as "the component's index + 1". Is it stated that, for an Orchestra base, `component_id` is the declaration index and not the document's `fixr:component id`? Otherwise US1.4's "its own" identity does not mean the same thing for both formats. [Clarity, data-model `ComponentRef`, Spec §US1.4]

## Component identity (FR-001a)

- [ ] CHK008 FR-001a names the holders by class ("every loader-internal counter, map and one-based cast that carries it"). Is its scope stated to include the readers of those maps too? These are the `component_index_by_name_` and `component_index_by_xml_id_` lookups in `collect_header_tags` and 100's `collect_section_groups`, which the orchestrator's 2026-11-13 ruling added. [Completeness, Spec §FR-001a, tasks "Census manifest" "D1 identity readers", tasks "Bundle findings" 15]
- [ ] CHK009 The one-based encoding is kept: 0 means "not in a component" and "top level". Is it stated as a requirement that both loaders write the same encoding, and that 0 is never a valid one-based value below 2^32 components? [Consistency, Spec §FR-001a, data-model `FieldRef`, data-model `ComponentRef`]
- [ ] CHK010 The edge case reads "a child component whose parent sits at index 65,535 or beyond". Is a parent at exactly index 65,535 required? Its one-based value, 65,536, is the first to wrap, and "or beyond" alone lets a fixture place every parent past it. [Edge Case, Spec §Edge Cases, tasks T008]
- [ ] CHK011 FR-001a states the boundary at exactly 2^32 components in detail. Is it also stated whether a caller can observe that a dictionary is in L-102-1 (c)'s region? If there is no error and every value is in bounds, is the absence of any signal stated explicitly? [Clarity, Spec §FR-001a, Spec §Out of Scope]
- [ ] CHK012 Is "No component count is refused" stated as removing only the width-driven failures? A large base can still meet other refusals: a repeated or empty name in `collect_components`, an allocation failure, and B86's later budget. [Consistency, Spec §FR-001a, research D2 "The component identity"]

## Orchestra surrogate ids (FR-001b)

- [ ] CHK013 FR-001b reads component, group and ref ids "in the schema's `fixr:id_t` domain". That domain is `xs:positiveInteger` and excludes 0, yet the edge case keeps id 0 admitted. Is the admitted domain stated exactly (0..2147483647), with the departure from the schema named? [Conflict, Spec §FR-001b, Spec §Edge Cases, research Survey "Orchestra surrogate ids"]
- [ ] CHK014 Is "malformed" defined for the 32-bit surrogate parse? It could mean today's lexical rule, the tag parse's, or the schema's: `xs:positiveInteger` admits a leading `+`, leading zeros and surrounding whitespace. Data-model says only "above it, or malformed, `orchestra_parse_error` as today". [Ambiguity, data-model "Loader behaviour", research D1b]
- [ ] CHK015 FR-001b says "the loader, the overlay merge and the code generator alike". Is it stated that the three end the same way on the same out-of-domain id (2147483648, `-1`, malformed)? Today they differ: the loader refuses with `orchestra_parse_error`, the code generator's misses are "defensive only, continue" (research D1b), and the overlay keys skip silently. [Gap, Spec §FR-001b, Spec §US1.5, research D1b]
- [ ] CHK016 US1.5 requires that "when the code generator reads it … every reference resolves to the definition it names". Is the generator's input domain stated? Either generating code from a non-vendored Orchestra document is a supported use, or the requirement is only that the generator's walk agrees with the loader's. [Clarity, Spec §US1.5, research D4 "Codegen"]
- [ ] CHK017 The kind split keeps the FIX tag ids 16-bit: `<fixr:field id>`, `fieldRef`, `lengthId` and `numInGroup`. Is it a stated requirement that their refusal is unchanged, with the same exception and the same message? Without it, row (g)'s message pin only characterizes today's behaviour. [Clarity, Spec §FR-001b, research D4 (g)]
- [ ] CHK018 The section ids 1024 and 1025 (the header and trailer components) become surrogate ids in the header lookup and in `collect_section_groups`. Is it stated that a document may declare a component or group whose id is 1024 or 1025 plus a multiple of 65,536, and that the widening does not mistake it for the header or the trailer? [Edge Case, research D1b, tasks T032]
- [ ] CHK019 Is it stated whether a component id and a group id may be equal in one Orchestra document? If they can, is it stated that every widened container keeps the two id spaces apart, including 100's oracle once T034a re-keys it by (kind, id)? [Clarity, research D1b, tasks T015b, tasks T034a]
