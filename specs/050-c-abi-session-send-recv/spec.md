# Feature Specification: C ABI engine surface — Feature B (session lifecycle, message send, receive callback)

**Feature Branch**: `050-c-abi-session-send-recv`
**Created**: 2026-06-23
**Status**: Draft
**Input**: User description: "C ABI engine surface — Feature B: session lifecycle + message send + receive callback (CA-005, CA-006, CA-007)."

> **Workstream context.** This is the second of three C-ABI features (A.2 in the v1.0 tracker), following Feature A (049 — handle catalogue, error surface, version accessors; merged PR #146). Feature B makes the opaque handles introduced by Feature A *operable*: a C consumer can, for the first time, create an engine, open and close a session, send a message, and receive inbound messages via a registered callback. The signatures are **net-new and authored here** — both `[2i §7.9]` and `[2j:54]` explicitly disclaim ownership of the actual signatures/behaviour (they pin only the *shape*: opaque-handle plumbing, error-translation, reentrancy annotation, version-binding) and assign the signatures + FSM-wrapping behaviour to "the session-module Phase-4 spec" — i.e. **this feature**. The gRPC control-plane doc `[2j]` is a downstream *consumer* of these symbols, not part of this feature. Feature C (CA-008..010: field accessors / repeating groups) follows; Python bindings (PY-001..005) remain blocked until Feature C merges. Authoritative shape contract: `.specify/2i-capi.md` ([2i]); ABI policy: `.specify/constitution.md` Article X.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create an engine and drive a session lifecycle from C (Priority: P1)

A developer integrating fixpp from a C program (or a binding author building on the C ABI) needs to create an engine, open a session against a configured peer, and later close it — entirely through `extern "C"` calls, with every fallible step reporting a stable numeric code and never letting a C++ exception cross the boundary.

**Why this priority**: Session lifecycle is the precondition for send and receive — without an open session there is nothing to send to or receive from. It is also where the consumer's ABI minor version is recorded (`fixpp_engine_create`), which makes Feature A's forward-compatibility downgrade *live* (discharges L-049-1).

**Independent Test**: A pure-C program creates an engine, opens a session against a loopback peer, observes a successful open, closes the session, and confirms the session handle is invalidated and the engine destroys idempotently — all without linking any C++ header and with zero exceptions escaping the boundary.

**Acceptance Scenarios**:

1. **Given** a C consumer compiled against the published header, **When** it creates an engine with a valid configuration, **Then** it receives a non-null owning engine handle and the consumer's ABI minor version is recorded against that engine for later error downgrade.
2. **Given** an engine handle, **When** the consumer opens a session with a valid configuration, **Then** it receives a non-null **non-owning** session handle that becomes valid (resolvable) on success — open **registers a session identity** (`register_session`); the **transport is NOT yet bound** (open ≠ connected). Transport binding happens only after `fixpp_engine_start` and successful async establishment, observed via `fixpp_session_is_established` (FR-021/FR-022). On a configuration failure it receives a null handle and a domain-appropriate configuration error code (no exception crosses the boundary).
3. **Given** an open session, **When** the consumer closes it, **Then** the close signals the engine's native cancellation path and tears down the live transport, and the session handle is invalidated once close returns (there is no separate session-destroy call).
4. **Given** an engine handle, **When** the consumer destroys it (including twice, or with a null pointer), **Then** the destroy is idempotent, null-safe, and never throws.

---

### User Story 2 - Send a message over an open session (Priority: P1)

A C consumer holding an open session and a constructed outbound message needs to send it and learn the outcome as a stable numeric code, with the engine's durable-before-transmit guarantee honoured.

**Why this priority**: Sending is the primary outbound action a consumer performs; together with US1 it forms the minimum viable outbound path. It is independently demonstrable once a session is open.

**Independent Test**: With an open session to a loopback peer, the consumer sends a message and observes a success code; the peer receives the wire bytes; a send on a session whose outbound seqnum counter is at its maximum surfaces as the published **store-domain** error code (`FIXPP_ERR_STORE_RUNTIME`, from `store_seqnum_overflow`) rather than a silent transmit; cancellation of an in-flight send surfaces as the uniform cancellation code. (Note: a store *I/O persistence* failure on the send path is **not** observable — the engine's durable-before-transmit store is logged-then-proceed by the inherited I-07 invariant; see **L-050-3**.)

**Acceptance Scenarios**:

1. **Given** an open session and a valid outbound message, **When** the consumer sends it, **Then** the message is durably stored before transmit and a success code is returned.
2. **Given** an open session, **When** a send is cancelled (engine teardown / total cancellation), **Then** the outcome is reported as the uniform cancellation code, not a partial or undefined state.
3. **Given** a send on a session whose outbound seqnum counter is at `seqnum_max`, **When** the consumer sends, **Then** the published **store-domain** code `FIXPP_ERR_STORE_RUNTIME` is returned (from `store_seqnum_overflow`, not the opaque "unknown" sentinel), so the consumer can react. (`store_seqnum_overflow` slot 60 is mapped by Feature A's `translate()`, `error.cpp:109-112`; injectable via a session restored with the outbound counter at `seqnum_max`. A store *I/O persistence* failure is **not** surfaced here — durable-before-transmit is I-07 logged-then-proceed; **L-050-3**.)

---

### User Story 3 - Receive inbound messages via a registered callback (Priority: P1)

A C consumer needs to register a callback (plus an opaque user-data pointer) that the engine invokes when an inbound application message arrives, with the inbound message handle valid only for the duration of the dispatch.

**Why this priority**: Receiving closes the round-trip; an engine that can only send is not usable for a real FIX session. It depends on US1 (an open session) but is otherwise independent of US2.

**Independent Test**: The consumer registers a callback, a loopback peer sends a message, and the callback fires with a readable inbound message handle and the registered user-data; the consumer confirms it must not retain the inbound handle past the callback return.

**Acceptance Scenarios**:

1. **Given** an open session, **When** the consumer registers a receive callback with a user-data pointer, **Then** subsequent inbound application messages invoke the callback with an inbound message handle and that same user-data pointer.
2. **Given** a callback invocation, **When** the callback returns, **Then** the inbound message handle is no longer valid (its lifetime is bounded by the dispatch window); the consumer must copy out anything it needs before returning.
3. **Given** a registered callback, **When** the session closes, **Then** no further callbacks fire for that session.

---

### Edge Cases

- **Null / invalid handle** passed to any new handle-taking function → the documented null-handle code (for null) or invalid-handle code (for a destroyed/corrupted handle), reusing Feature A's distinct codes; never undefined behaviour.
- **Open against bad configuration** → null session handle + a domain-appropriate configuration error code, set via the construction-time thunk path (catch → translate, no abort, no exception escape).
- **Send on a closed / closing session** → `FIXPP_ERR_THREAD_SESSION_LIFECYCLE` (existing-published) for `session_already_closed`, or `FIXPP_ERR_UNKNOWN` for the deferred session/app arms (the published session/app block is deferred — L-050-4); never a silent success and never a crash.
- **Cancellation mid-send / mid-close** → uniformly reported as the cancellation code per `[2i §4.9]`; close must break a blocked idle read by closing the socket, not merely signalling total cancellation.
- **Forward-compat downgrade now live**: a session/engine call on an engine created by an older-minor consumer that would surface a code introduced after that minor is downgraded to the "unknown" sentinel on the return path (Feature A's pure `translate_for_consumer`, now fed a real recorded `consumer_minor`).
- **Steady-state invariant violation**: an exception escaping the steady-state send thunk is treated as an invariant violation → fatal log + abort, **not** translated to a code.
- **New exported symbols** must appear in the nm symbol-golden and leak zero C++ symbols.
- **Blocking C-ABI call from inside the receive callback** → forbidden by contract (would deadlock: the callback runs on the session strand and a blocking `send`/`close`/`destroy` thunk posts onto that same strand and waits — the strand can't progress until the callback returns). The consumer copies out and sends/closes from a non-callback thread. (FR-013a / research D-10.)

## Requirements *(mandatory)*

### Functional Requirements

**Session lifecycle (CA-005)**

- **FR-001**: The C ABI MUST provide an engine-creation entry point that takes the engine configuration and the consumer's compiled C-ABI version, returns an **owning** `fixpp_engine_t` handle on success, and on a configuration failure returns a null handle plus a domain-appropriate configuration error code. It is a **construction-time** thunk per `[2i §5.2]`: it catches `std::exception` and translates to `FIXPP_ERR_*_CONFIG` / `FIXPP_ERR_CAPI_CONFIG_INVALID`; no exception crosses the boundary.
- **FR-002**: The engine-creation entry point MUST record the consumer's **ABI minor** version against the engine so that every fallible C-ABI call on that engine applies Feature A's forward-compatibility downgrade (`translate_for_consumer`) on the return path. This discharges the named limitation **L-049-1** and makes CA-004's downgrade live.
- **FR-003**: The C ABI MUST provide an engine-destroy entry point that is idempotent, null-safe, and never throws (null / already-destroyed → no-op), per the `[2i §4.2.1]` destroy discipline already documented in `handles.h`. This includes a **created-but-never-started** engine (e.g. `create` → `session_open` fails → `destroy`): destroy MUST drive `Engine::stop()` **unconditionally** before deleting the engine, because `~Engine` asserts `stopped()` (inits false, `engine.hpp:406`) and `stop()` is idempotent from any state (`engine.hpp:199`) — a conditional "if started" guard would `std::abort` on the never-started path, violating never-throws.
- **FR-004**: The C ABI MUST provide a session-open entry point taking the engine handle, a session configuration (delivered via the FR-014 builder), and an error-out parameter; it **registers** the session with the engine (the real `Engine::register_session`, `engine.cpp:206`) and returns a **non-owning** `fixpp_session_t` handle keyed by the derived `SessionId`. Because the real engine is register-then-start, the handle is valid (resolvable) but the session is **not yet connected** — establishment is asynchronous after `fixpp_engine_start` (FR-021). The configuration is frozen for the session lifetime (`[2i §3.4]`). Session-open MUST be called **before** `fixpp_engine_start`; calling it after the engine has started MUST return a domain error (the C-ABI enforces the register-before-start order even though the C++ layer leaves a late registration inert). It is a **construction-time** thunk (catch-and-translate). On failure the session handle is null and the error-out carries the reason.
- **FR-005**: The C ABI MUST provide a session-close entry point that drives the engine's per-session graceful/forceful close (`Session::close`, posted onto the session's serialisation domain by the thunk since the v1.0 `Session::close` precondition is on-strand invocation), using the engine's **ASIO native cancellation** mechanism per `[const §XI.2]` (the per-session `cancellation_signal` / total-cancellation that closes the transport so a blocked idle read is broken — not a separate stop_token). The `fixpp_session_t` handle MUST be invalidated once close returns; there is **no** separate session-destroy (the store handle invalidates with the session per `[2i §4.2.1]`).
- **FR-006**: Every new handle-taking function MUST distinguish a null handle (null-handle code) from a previously-valid-but-destroyed/corrupted handle (invalid-handle code), reusing the distinct codes published by Feature A, per `[2i §4.2.1]`.
- **FR-007**: The CA-005 entry-point **names** MUST follow the `[2i]`/`[2j]` contract — `fixpp_engine_create` / `fixpp_session_open` / `fixpp_session_close` — and MUST NOT introduce separate `connect` / `disconnect` / `session_destroy` symbols, because the session handle is non-owning (the row-title shorthand "create / connect / disconnect / destroy" is reconciled to these contract names, mirroring Feature A's `FixSession` → `fixpp_session_t`). *(Resolved — Clarifications 2026-06-23.)*
- **FR-021**: The C ABI MUST provide an engine-start entry point (`fixpp_engine_start(engine)`) mapping to `Engine::start()` (`engine.hpp:277`) — called **once**, after all sessions are registered via FR-004. It co_spawns the role loops; sessions then establish asynchronously. It is a construction-time-flavoured thunk (validates config — e.g. null clock → config error — and returns a domain error without an exception escaping). Because the real C-ABI engine owns its own event loop, `fixpp_engine_create` MUST stand up an internal io_context + worker thread(s) and `fixpp_engine_start` drives loop spawning on that executor (the C++ `Engine` "owns NO worker threads", `engine.hpp:222`). *(Added plan-time — Clarifications 2026-06-24.)*
- **FR-022**: The C ABI MUST provide a session-establishment poll accessor (`fixpp_session_is_established(session) → bool` via an out-param + `fixpp_error_t`) mapping to `Engine::lookup(id) != nullptr && Session::is_open()` (any-thread-safe, `engine.hpp:301` / `session.hpp:196`), so a consumer can wait for logon before sending (SC-001). Richer `onLogon`/`onLogout` lifecycle callbacks are a documented follow-up (**L-050-x**), out of scope here. Reentrancy class `FIXPP_THREAD_SAFE`. *(Added plan-time — Clarifications 2026-06-24.)*

**Message send (CA-006)**

- **FR-008**: The C ABI MUST provide a send entry point taking a session handle and a **committed wire-frame byte span** (`const` bytes + length) and returning a `fixpp_error_t`, mapping to `Engine::send(SessionId, std::span<const std::byte>)` (`engine.hpp:266`). Per `[2i §10]` the consumer obtains the serialised span from Feature C's `fixpp_msg_commit` (or hand-rolls a frame); send does **not** take a `fixpp_msg_t` (the `fixpp_msg_t` handle is the **inbound** callback type — FR-011 — and the **outbound construction** surface is Feature C). It is a **steady-state** thunk per `[2i §5.2]`: an exception escaping it is an invariant violation → fatal log + `std::abort`, **not** translated to a code.
- **FR-009**: Send MUST honour the engine's **durable-before-transmit** invariant (`[2e §6.1.4]` — the store-linearises-before-`async_write` contract), honoured **by reference** (the C-ABI calls `Engine::send` → `Session::send` → `store_then_emit`; it adds nothing). *(The earlier `[2j:975]` pointer was imprecise — line 975 is about the per-session arena / store-factory selection, not the send path; it does reference `[2e §6.1.4]` as the invariant, which is the correct anchor used here.)*
- **FR-010**: Any cancellation outcome on the send path (e.g. total cancellation at engine teardown) MUST be reported uniformly as the single cancellation code per `[2i §4.9]`.

**Message receive callback (CA-007)**

- **FR-011**: The C ABI MUST provide a callback-registration entry point taking a session handle, a function pointer, and an opaque user-data pointer, returning a `fixpp_error_t`. On a subsequent inbound application message the engine invokes the registered function with an inbound `fixpp_msg_t` handle and the registered user-data. This entry point MUST be called **before** `fixpp_engine_start`; calling it after the engine has started MUST return a domain configuration error (`FIXPP_ERR_CAPI_CONFIG_INVALID`) via the construction-time thunk path (no exception escapes, no abort). This enforcement mirrors FR-004 for `fixpp_session_open` and is required because the `CapiApplication` callback map is read on the session strand without a mutex (Article XV §9) — a post-start registration would race the `fromApp` on-strand read. *(Clarity fix — CHK022 audit, 2026-06-24.)*
- **FR-012**: The inbound `fixpp_msg_t` handle passed to the callback MUST be valid **only** for the duration of the dispatch (the lifetime block of `[2i §4.6]`); the consumer must not retain the pointer or destroy the inbound message — it is engine-destroyed at parse-window close. After the session closes, no further callbacks fire for that session.
- **FR-013**: The receive-callback dispatch model MUST be **synchronous on-strand**: the engine invokes the registered callback directly on the session strand (mirroring the C++ `fromApp` dispatch per `[2d §7.6]`). There is **no** `fixpp_session_poll`-style drain symbol. The callback executes within the session's serialisation domain, so its reentrancy class is `FIXPP_REQUIRES_SESSION_LOCK` and it inherits the zero-allocation hot-path discipline (`[const §VIII.5]`); the consumer MUST copy out anything it needs before returning. *(Resolved — Clarifications 2026-06-23.)*
- **FR-013a**: The receive callback MUST NOT make a **blocking** C-ABI call on its own engine/session (`fixpp_session_send` / `fixpp_session_close` / `fixpp_engine_destroy`) — doing so deadlocks (the callback holds the session strand; the blocking thunk posts onto the same strand and waits). The documented "receive → send reply" pattern is **copy-out-then-send-from-a-non-callback-thread**. This MUST be stated in the header doc-block for `fixpp_session_register_callback` and witnessed by the **supported positive-path proof** (copy-out-then-send-from-a-drain-thread completing end-to-end — D-11/T030); a hang-watchdog "prove it deadlocks" test is deliberately NOT used (fragile wedged-thread risk, marginal benefit with no real clients yet — the completing supported path IS the discriminating proof the contract holds). A callback-safe non-blocking send is a v1.x follow-up (**L-050**). *(Added — research D-10, Gate-A pre-empt.)*

**Session configuration delivery (cross-cutting CA-005 input)**

- **FR-014**: Session and engine configuration MUST be delivered across the C boundary via an **opaque builder family** — `fixpp_session_config_t` (`fixpp_session_config_create` / `fixpp_session_config_set_*` / `fixpp_session_config_destroy`) and a parallel engine-config builder — per the `[2j:813]` shape. The builder handles are opaque (no struct layout exposed) so that a future configuration field is added as a new setter rather than a layout change, honouring the Article X ABI-stability rule; the flat config-by-value PoD and the TOML-path-reuse alternatives were rejected (ABI-fragile / file-bound respectively). The config builder is consumed at open and the resulting configuration is frozen for the session lifetime (`[2i §3.4]`). The specific setter field set is a plan/data-model detail; each builder symbol is subject to the same thunk-split (FR-016), reentrancy (FR-017), symbol-golden (FR-018), and no-exception-escape (FR-019) controls as the lifecycle symbols. *(Resolved — Clarifications 2026-06-23.)*

**Error surface extension — DEFERRED (L-050-4; L-049-2 stays open)**

- **FR-015 [DEFERRED — L-050-4]**: The plan to publish a session/app C-ABI error block and re-point the reachable `session_*`/`app_*` arms off `FIXPP_ERR_UNKNOWN` is **deferred**. Implement-time source contact found that `[2i §4.3]` (the master C-ABI error layout) has **NO published session/app error block** — `session_*`/`app_*` are the *unpublished* `FIXPP_ERR_UNKNOWN` bucket (`error.h:51`); the design uses **coalesced remediation-class groups** (not per-variant codes); and the occupancy gate (`tools/check_capi_occupancy.sh`) has a **hardcoded `EXPECTED` map** derived from the `[2i §4.3]` master. Publishing 5 per-variant codes (`FIXPP_ERR_SESSION_INVALID_ARGUMENT`/`_INVALID_STATE`, `FIXPP_ERR_APP_DO_NOT_SEND`/`_CALLBACK_THREW`/`_PAYLOAD_MALFORMED`) would therefore require **editing the signed-off `[2i]`** — out of scope for Feature B and contradicting the Gate-A LEAVE decision / CHK030 (`[2i]` not reopened). **User decision 2026-06-24: DESCOPE** (treat exactly like the L-050-1 dictionary descope). The 5 reachable session/app arms (`session_invalid_argument` 119, `session_invalid_state_for_send` 77, `app_do_not_send` 129, `app_callback_threw` 130, `app_payload_malformed` 131) **remain `FIXPP_ERR_UNKNOWN`**: no new `error.h` codes, no `translate()` re-point, no `error_codes_v1.txt` append, no occupancy-gate delta (the gate stays green unchanged). The published session/app block is deferred to a dedicated `[2i §4.3]` amendment (**L-050-4**); **L-049-2 stays open** (un-discharged). The existing-published send arms (`wire_frame_too_large`→`FIXPP_ERR_WIRE_LIMIT_EXCEEDED`, `store_seqnum_overflow`→`FIXPP_ERR_STORE_RUNTIME`, `session_already_closed`→`FIXPP_ERR_THREAD_SESSION_LIFECYCLE`, cancellation→`FIXPP_ERR_CANCELLED`) are **unchanged** — they were always existing-published, never part of the deferred block.

**Cross-cutting ABI controls**

- **FR-016**: Each new public C-ABI symbol MUST be placed on exactly one side of the construction-vs-steady thunk split per `[2i §5.2]` (engine-create + session-open = construction-time catch→`*_CONFIG`; send = steady-state abort-on-escape; close and callback-registration classified explicitly in design).
- **FR-017**: Each new public C-ABI symbol MUST carry exactly one reentrancy class — thread-safe / single-thread / requires-session-lock — verified by the CI gate `tools/check_capi_reentrancy.sh`, per `[const §X.5]` / `[2i §4.10]`. Pinned classifications: `fixpp_session_send` = `FIXPP_THREAD_SAFE` (backed by the any-thread `Engine::send` contract, `engine.hpp:241-267`; callable from any consumer thread **except** from within the receive callback, where the blocking wrapper deadlocks — FR-013a/D-10. This is a **recorded Gate-A deviation** from `[2i §4.10]`'s `FIXPP_REQUIRES_SESSION_LOCK` send example, which is stale — see plan `## Gate A`); the blocking `fixpp_session_close` = `FIXPP_SINGLE_THREAD` with a "non-callback / non-session-strand caller only; no concurrent close on the same handle" restriction (the thunk posts onto the session domain and blocks; a callback/strand caller is the deadlock case); the **receive-callback** (its on-strand dispatch per FR-013) stays = `FIXPP_REQUIRES_SESSION_LOCK` (it genuinely runs on the strand); `fixpp_engine_create` and the config-builder mutators (one-time, not reentrant) = `FIXPP_SINGLE_THREAD`; `fixpp_session_is_established` = `FIXPP_THREAD_SAFE`; the remaining lifecycle symbols classified in design. No public symbol may be left unannotated.
- **FR-018**: No C++ symbol MUST leak through the C ABI; only `extern "C"` `fixpp_*` symbols are exported (verified by `nm` / `fixpp_capi.map`), and **every new exported symbol** MUST be appended to the nm symbol-golden `tests/abi/golden/fixpp_capi_symbols.txt` in the same change, per constitution Article X §2 and the superseding nm symbol-set gate (the abidiff approach is retired — D-note carried from Feature A).
- **FR-019**: No exception MUST cross the `extern "C"` boundary from any new thunk (construction-time translate, steady-state abort), per `[2i §4.2.3]` / `[2i §5.2]`.
- **FR-020**: The published C-ABI version MUST receive an additive **MINOR** bump (from the current `0.2.0`) reflecting the **21 new exported symbols**; the `0 → 1` major freeze remains deferred to GA, per `remaining-work/release-engineering.md` Task 2. (The bump is justified by the new symbols alone — the session/app error block is deferred, L-050-4, and ships no new codes.)

### Key Entities

- **Engine handle (`fixpp_engine_t`)**: owning; created with the consumer's recorded ABI minor; destroyed idempotently. Owns the session(s).
- **Session handle (`fixpp_session_t`)**: non-owning observer of an engine-owned `Session`; valid from a successful open until close returns, then invalidated.
- **Inbound message handle (`fixpp_msg_t`)**: engine-owned, valid only inside the receive-callback dispatch window; never destroyed by the consumer. (`fixpp_msg_t` appears in Feature B **only** as this inbound callback type — send takes a committed byte span, not a `fixpp_msg_t`, FR-008; the outbound message-construction surface that produces those bytes is Feature C.)
- **Receive callback + user-data**: a C function pointer and opaque pointer registered per session and invoked **synchronously on the session strand** on inbound application messages (FR-013).
- **Session/engine config builder (`fixpp_session_config_t` + engine-config builder)**: opaque builder handles (create / set_* / destroy) that carry configuration across the boundary without exposing a struct layout; consumed at open, frozen for the session lifetime (FR-014).
- **Session-domain error block [DEFERRED — L-050-4]**: a published `[2i §4.3]` session/app code block is **not** introduced by Feature B (no such block exists in `[2i §4.3]`; publishing requires an `[2i]` amendment, out of scope). The reachable session/app arms that `session_open` / `session_send` can return stay `FIXPP_ERR_UNKNOWN`; L-049-2 stays open.

## Limitations

- **L-050-1 — round-trip dictionary blocked on Feature C**: see Out of Scope. SC-001 is satisfied only with a test-supplied dictionary in Feature B.
- **L-050-2 — `fork()` after `fixpp_engine_create` is unsupported**: `fixpp_engine_create` stands up an internal `io_context` + worker thread (research D-2). POSIX `fork()` copies **only the calling thread**, so a child process holding a live `fixpp_engine_t` has a dead worker — its `io_context` never runs and every session op hangs / the destroy join deadlocks (`feedback_fork_inherited_asio_pool_deadlock`). **Do not `fork()` a process holding a live `fixpp_engine_t`; create the engine in the child after fork.** (research D-12.)
- **L-050-3 — a store *I/O persistence* failure on the send path does not surface as a send error**: the engine's durable-before-transmit store on `Session::send` is **logged-then-proceed** (the inherited I-07 invariant, shared with 007/024/029/032 — `store_then_emit` swallows store errors at `session.cpp:4790`, propagating only `operation_aborted` as `dispatch_aborted`). A C consumer therefore cannot observe a store I/O failure as a distinct `fixpp_session_send` return; the only store-domain code reachable on `send` is `store_seqnum_overflow` (outbound counter at `seqnum_max`) → `FIXPP_ERR_STORE_RUNTIME`. This is an inherited engine behaviour, not introduced by Feature B; surfacing store I/O failures across the C ABI would require a wider engine change (out of scope). (data-model E-4; Gate A round 3 corrected the round-1 mislabel of `store_io_failure` as send-reachable.)
- **L-050-4 — published session/app C-ABI error block deferred to a dedicated `[2i §4.3]` amendment**: `[2i §4.3]` (the master C-ABI error layout) has **no published session/app block** — `session_*`/`app_*` are the unpublished `FIXPP_ERR_UNKNOWN` bucket (`error.h:51`); the design uses coalesced remediation-class groups (not per-variant codes); and `tools/check_capi_occupancy.sh` has a hardcoded `EXPECTED` map derived from the `[2i §4.3]` master. Publishing the 5 per-variant session/app codes would require editing the signed-off `[2i]`, which the Gate-A LEAVE decision / CHK030 forbids (`[2i]` not reopened). **User decision 2026-06-24: DESCOPE** (deferred, treated exactly like the L-050-1 dictionary descope). Consequently the reachable session/app arms (`session_invalid_argument` 119, `session_invalid_state_for_send` 77, `app_do_not_send` 129, `app_callback_threw` 130, `app_payload_malformed` 131) **remain `FIXPP_ERR_UNKNOWN`**, and **L-049-2 stays open** (un-discharged). Publishing the block is a dedicated future `[2i §4.3]` amendment. (Drops FR-015 + SC-005 from Feature B; the existing-published send arms and the L-049-1 downgrade mechanism are unaffected.)
