# Implementation Plan: Acceptor inbound-Logon SendingTime guard + session/reconnect hardening riders

**Branch**: `038-acceptor-sendingtime-guard` | **Date**: 2026-06-14 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/038-acceptor-sendingtime-guard/spec.md`

## Summary

Close the session-scoped subset of the Fable **F-f** tail — three cleanly-separated, independently witnessable groups:

- **GROUP 1 (primary, P1) — Acceptor first-Logon SendingTime(52) latency guard.** fixpp validates inbound `SendingTime(52)` latency at exactly two sites: the steady-state Q3 guard (`session.cpp:2381`, reached only for an *already-established* session) and the initiator's Logon-ack Guard-3 (`session.cpp:3415`). The **acceptor's `NotConnected` first-Logon arm** (`session.cpp:~1793-2300`) establishes the session via `interpret_logon` — which **explicitly skips tags 34/52/98** (`admin_messages.cpp:226`) — and never reaches the Q3 guard, so a Logon with an absent/empty, malformed, or hours-stale `52` establishes unchecked. Fix: insert a SendingTime check in the first-Logon arm **after `ensure_hydrated_` (`session.cpp:1925`, read-only outbound/inbound seed) but BEFORE `reset_on_logon` (`:1927`) and `check_inbound` (`:1936`)** — so the Reject carries the hydrated durable outbound seq while inbound is seeded-not-advanced and no durable reset fires — and therefore before the FIXT `1137` validation (`:2102`) and `authorize_logon(553/554)` (`:2155`). The order becomes `interpret_logon → ensure_hydrated_ → SendingTime(52) [NEW] → reset_on_logon → check_inbound → 1137 → authorize_logon → establish`. The guard reuses the **emit shape** proven by the in-arm `1137` reject sibling (`session.cpp:2102-2136`): **`build_reject` (≥512B stack buffer; build-fail → FAIL CLOSED `Disconnected`) → `Reject(35=3, RefTagID=52, SessionRejectReason=10)` → `assign_outbound` → `fire_to_admin_` → `store_then_emit` → `record_state_transition_(Disconnected)` — NO Logout** (the in-arm `1137` reject emits no Logout; the established-Q3 Logout is a *live-session* teardown, not applicable pre-establishment). **FR-004 stays strong**: because the guard precedes `check_inbound`, a rejected first-Logon does NOT advance the in-memory inbound counter (it is seeded-not-advanced: memory store → `seqnum_min`, persistent store → the seeded durable `D`) and does NOT touch the durable inbound counter or fire a durable reset. Only the OUTBOUND counter advances (via the Reject's `assign_outbound`) — and because the guard runs AFTER `ensure_hydrated_` (which seeds outbound unconditionally), that Reject carries the **hydrated durable outbound seq `N`**, NOT the construction counter 1, so on a persistent-store reconnect it is in-sequence on the wire and the store accepts it. Per Clarifications, absent/empty, malformed, AND stale all share the single `reason=10` disposition (mirrors established-Q3's reason code, which already maps empty `52` → reason=10). Grounded against QuickFIX-cpp (`Session::next` → `isGoodTime` → `doBadTime`, role-agnostic on the Logon) and QFJ (`isGoodTime`/`doBadTime`), not symmetry-derived — the *MUST-reject* fact from QF, the *frame shape* from fixpp's in-arm `1137` precedent. Amends catalogue **S-019** (`[FIX-SL §4.2.3]`) via the **S-033 / §4.5.4** reject taxonomy.

- **GROUP 2 (rider, P2) — Reconnect `credentials_rotated` callback-seam exception containment.** `reconnect_fsm.cpp:200` invokes the `emit_credentials_rotated_(...)` callback bare inside the `noexcept` `drive_reconnect_attempt` coroutine. This is **not** a `std::terminate` defect (an exception escaping a coroutine body is delivered to the promise, not to `terminate` — distinct from the noexcept-*method* class of `[[feedback_noexcept_boundary_user_callback_terminate]]`); it is a graceful-degradation gap — a throwing callback abandons the in-flight reconnect attempt. **Production reachability:** in the live `Session` path this callback is engine-owned — `Session::open()` injects a `noexcept` lambda (`:1108-1109`) calling the `noexcept` `emit_event` (`:255-260`, ring-buffer write, no user code), so the throw is **unreachable in production today**; the only throw-surface is the standalone-`ReconnectFsm` injection seam. G2 hardens that callback-boundary seam — NOT a reachable operator-callback guarantee (stated plainly so it is not an over-claimed arm, the 025 trap). Fix: wrap the single callback invocation in `try/catch` matching the established `authorize_logon` callback-guard shape so a throw is contained and the attempt proceeds per policy. Relates to **T-040** / 014 (`session_event_credentials_rotated`). Unit-test-backed only; SC-free by design.

- **GROUP 3 (rider, test-only, P3) — FIXT `DefaultApplVerID(1137)` reject witness.** The existing acceptor `1137` reject arms (`session.cpp:2070-2128`: absent → `Reject 373=1`; non-conformant → `Reject 373=5`, both `RefTagID=1137`, then Disconnected) are fail-closed by code-read but have **zero session-level negative witnesses** (031's analogous reject arms got three). Add negative witness(es) asserting the on-wire `Reject(371=1137)` + its `toAdmin` observation + the disconnect. **No production change** (FR-009).

### Why one feature, not three

All three live on the same acceptor-establishment / reconnect surface and ship as one Gate-A/Gate-B unit, but they are kept as three independent FR groups (each with its own witness and SC disposition) so review can judge each on its own — the primary Group-1 scrutiny is not diluted by the two small riders. Group 3 is pure test addition; Group 2 is a one-site `try/catch`; only Group 1 changes establishment control flow.

## Phase 0 — Research

See [research.md](./research.md). Key decisions:

1. **Reference-engine ground truth (Group 1)** — both QFcpp (`Session::next` → `isGoodTime` → `doBadTime`, `Session.cpp:996`) and QFJ (`Session.java:1821`) validate inbound SendingTime latency **role-agnostically on the Logon**, BEFORE message-type routing; on failure: `Reject(SessionRejectReason=10 SendingTimeAccuracy)` + `generateLogout()` + disconnect, and `next()` returns false (processing halted, session NOT established). fixpp takes the *MUST-reject* fact + reason=10 from this, but the *frame shape* from its own in-arm `1137` reject (Reject + disconnect, **no Logout** — D-3), not QF's added Logout. Verified, not symmetry-derived.
2. **Missing-`52` is NOT caught upstream (Group 1)** — `interpret_logon` (`admin_messages.cpp:226`) explicitly skips tags 34/52/98, and the steady-state Q3 guard is not reached on the establishment path; so absent/empty `52` is currently unvalidated at the acceptor first-Logon. Per Clarifications 2026-06-14: absent/empty, malformed, AND stale all share one `reason=10` disposition mirroring established-Q3 (which already maps empty `52` → reason=10). Accepted, documented divergence from QFcpp/QFJ (which use `RequiredTagMissing=1` for absent) in favour of internal consistency.
3. **Scaffold on the in-arm `1137` reject; inline, not extract-a-helper (Group 1 design choice)** — the closest precedent is the FIXT `1137` reject in the SAME `NotConnected` first-Logon arm (`:2102-2136`): `Reject(35=3, 371=…)` → `assign_outbound` → `fire_to_admin_` → `store_then_emit` → `Disconnected`, **no Logout**. This is the correct pre-establishment shape (the established-Q3 Logout is a live-session teardown) and it proves the outbound-seqnum + observation machinery works before establishment. Inline-replicate that block with `371=52`/`373=10`; do NOT extract a shared helper (a single new caller does not justify the abstraction — `[const §XV]` simplicity; Karpathy #2 — and extracting would re-point the merged path, the seam-reorder trap `[[feedback_seam_removal_profile_gate_ordering]]`). Leave both the `1137` reject and established-Q3 untouched.
4. **No inbound advance OR persist on reject; Reject carries hydrated outbound N (Group 1)** — because the guard precedes `check_inbound`, a rejected first-Logon does NOT advance the in-memory inbound counter (seeded-not-advanced: memory store → `seqnum_min`, persistent store → seeded durable `D`), does NOT touch the durable inbound counter, does NOT fire a durable reset (it precedes `reset_on_logon`), and must NOT call `persist_inbound_advance_` (`[[feedback_unconditional_persist_at_multiexit_gate_breaks_lowerbound]]`). The strong "not advanced" claim comes from this placement before `check_inbound`, NOT from the `1137` sibling — the `1137` reject runs AFTER `check_inbound`, so it leaves the in-memory inbound ALREADY advanced (it only proved "no durable persist"). Only the OUTBOUND counter advances (one `assign_outbound` for the Reject) — and because the guard runs AFTER `ensure_hydrated_` (which seeds outbound unconditionally), that Reject carries the **hydrated durable outbound seq `N`**, NOT the construction counter 1, so on a persistent-store reconnect the Reject is in-sequence and the store accepts it; `store_then_emit` persists that outbound frame. See research D-4 / data-model INV-4.
5. **Guard ordering (Group 1)** — the SendingTime check fires AFTER `ensure_hydrated_` (`:1925`, read-only outbound/inbound seed) but BEFORE `reset_on_logon` (`:1927`) and `check_inbound` (`:1936`), and therefore before the FIXT `1137` validation and `authorize_logon`. Order: `interpret_logon → ensure_hydrated_ → SendingTime(52) → reset_on_logon → check_inbound → 1137 → authorize_logon → establish`. Placing it before `check_inbound` is what keeps FR-004's "not advanced" strong (a guard after `check_inbound` would leave the in-memory inbound counter advanced); placing it AFTER `ensure_hydrated_` makes the Reject's `assign_outbound` stamp the hydrated outbound seq `N` (not construction-1), fixing the persistent-reconnect wrong-seq Reject; placing it before `reset_on_logon` means a Logon we then reject fires no durable seqnum reset. SendingTime-before-seqnum is MORE faithful to QFcpp's `next()`; CompID-before-SendingTime is the one divergence (forced by `interpret_logon`'s structure). A `52`-bad Logon pre-empts the seqnum/`1137`/credential gates — see data-model "simultaneous-bad ordering". (The old "mirrors established-Q3 Guard-2→Guard-3" rationale was false and is dropped — see research D-5.)
6. **Group 2 mechanism + reachability** — an exception escaping `drive_reconnect_attempt` (a `noexcept` coroutine) is delivered to the coroutine promise's `unhandled_exception`, NOT to `std::terminate`. The `try/catch` is graceful-degradation containment matching `authorize_logon`, distinct from the noexcept-*method* `terminate` class. **Production reachability:** the live `Session`-path callback is engine-owned `noexcept` (→ `noexcept` `emit_event` ring-buffer write, no user code), so the throw is unreachable in prod today; G2 hardens the standalone-`ReconnectFsm` injection seam, NOT a reachable operator-callback guarantee. SC-free. See research D-6.
7. **Scope non-expansions** — (a) only the acceptor first-Logon arm changes; initiator + established paths untouched; (b) no new config knob (reuse `sending_time_threshold`); (c) Group 3 adds zero production code; (d) the other F-f tail items (wire-parser overflow, C-ABI sentinel, coverage waivers, §XV.9 corpus gate, the **001-014** B&L back-fill) stay out of scope — but 038's OWN B-038-1/L-038-1 rows + S-019/S-025 catalogue/coverage-index amendments are IN scope (see research D-8).

## Phase 1 — Design & Contracts
