- [x] CHK003 Is the inverse render helper requirement (`application_version → wire 1137 string`) documented, including that it is **absent today** and must cover divergent values (e.g. `v50`→`"7"`)? [Completeness, Spec §research R3 / data-model E3] — PASS: R3 states the helper is "ABSENT today" (grep-confirmed 2026-06-12), enumerates divergent examples (`v50`→`"7"`, `v40`→`"2"`), and data-model E3 repeats the same; tasks T004/T005 add it as a deliverable. - [x] CHK004 Are requirements defined for recording **and** exposing the negotiated version (`negotiated_version_profile()` reachable via `Engine::lookup`)? [Completeness, Spec §FR-005/C3] — PASS: FR-005 specifies "record the negotiated application version and expose it as the default application `version_profile`"; C3 specifies the accessor `Session::negotiated_version_profile()` reachable via `Engine::lookup(SessionId)→shared_ptr<Session>` (verified at engine.hpp:294); data-model E2 specifies the exposure contract; W5/SC-006 make it measurable. - [x] CHK005 Is the `1128`-on-application-message tolerance requirement specified for the **established** session state (not just establishment)? [Completeness, Spec §FR-010/C9] — PASS: FR-010 explicitly says "on application messages of an **established** FIXT session"; C9 clause header is "Given an **established** FIXT session"; INV-FIXT-3 scopes to the session layer's dict-free delivery; data-model E1 note covers established-session behaviour. Established-state scope is unambiguous.

## Requirement Clarity

- [x] CHK006 Is "serviceable application version" defined by an objective criterion (`version_registry::get(resolved) ≠ dict_no_dictionary_for_application_version`, plus unparseable `1137`)? [Clarity, Spec §FR-004a / research R2] — PASS: FR-004a states "no application dictionary registered for the peer-advertised `ApplVerID` in the version registry"; R2 pins the exact criterion: "`resolve_*` fails (unparseable `1137` value) OR `get()` returns `dict_no_dictionary_for_application_version`"; C5 mirrors this. `version_registry::get()` is confirmed to return `core::expected_t<Dictionary const*>` with `dict_no_dictionary_for_application_version` on miss (version_registry.hpp:51-58). Objective criterion is present and measurable.
- [x] CHK007 Is FR-003 unambiguous that the session **records/exposes** the negotiated version and delivers app messages **dict-free**, rather than the session selecting/applying a dictionary? [Clarity, Spec §FR-003/FR-005] — PASS: FR-003 explicitly reads "The session layer itself delivers inbound application messages dict-free (identical to FIX.4.x) and does not select/apply a dictionary — it records and exposes the version (FR-005), it does not add a per-message reify gate (research R4)." The word "dict-free" appears verbatim; the session selection claim is negated. `parse_and_dispatch_` confirmed at session.cpp:238-265 using `wire::Parser<access_mode::Index>` — no dictionary. Unambiguous post B1 reword.
- [x] CHK008 Is "version-general / no `FIX.5.0SP2` hardcoding" stated as a measurable property (selection driven solely by configured/negotiated `ApplVerID`)? [Measurability, Spec §FR-006/SC-006] — PASS: FR-006 states "MUST accept any `ApplVerID` value (no `FIX.5.0SP2` hardcoding)"; SC-006 says "demonstrated by establishing at least two distinct application versions (5.0SP2 and 4.4-over-FIXT) with no version-specific establishment code path"; W5's discriminating assertion on `negotiated_version_profile().default_appl` per cell makes it measurable (not a proxy). Objectively verifiable.
- [x] CHK009 Is the FIXT predicate `is_fixt()` defined precisely (`begin_string=="FIXT.1.1" && default_appl_ver_id.has_value()`)? [Clarity, data-model E3] — PASS: data-model E3 states "FIXT predicate: `is_fixt() := (begin_string == "FIXT.1.1") && default_appl_ver_id.has_value()`"; contracts reference "FIXT session ⇔ `SessionConfig::is_fixt()`" at the top; task T003 adds it to `session_config.hpp`. Precise definition present.
