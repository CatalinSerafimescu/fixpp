## Requirement Completeness — Trace Correlation

- [x] CHK001 Are all three context tiers specified with distinct, named macros (`FIXPP_SLOG` session, `FIXPP_ELOG` engine, `FIXPP_LOG0` zeroed)? [Completeness, Spec §FR-013/§SC-004] — PASS: FR-013: "Three macros MUST provide the three context tiers without any `thread_local`: `FIXPP_SLOG(lvl, tc, cat, fmt, ...)` (session strand...), `FIXPP_ELOG(lvl, engine, cat, fmt, ...)` (engine scope...), `FIXPP_LOG0(lvl, cat, fmt, ...)` (zeroed context)"; anchor §4.3 gives the full macro definitions; data-model confirms all three. Complete.
- [x] CHK002 Is the "no `thread_local` on any correlation path" constraint stated as an enforceable requirement (grep-gate), not just prose? [Clarity, Spec §FR-013, `[const §XIII.3]`] — PASS: FR-013: "without any `thread_local`"; plan.md Constitution Check: "`[const §XIII.3]`... grep-gate for `thread_local`"; tasks.md T047: "grep-gate confirms **zero** `thread_local` on any log/macro path (`[const §XIII.3]`)"; quickstart.md validation gates: "grep-gate confirms zero `thread_local`". The grep-gate is an explicit enforceable verification step.
- [x] CHK003 Is the source of each tier's context specified — session macro takes explicit `tc = session.get_trace_context()`; engine macro reads an atomic engine-snapshot? [Completeness, Spec §FR-013] — PASS: FR-013 specifies each tier's source inline: `FIXPP_SLOG` "caller passes an explicit `tc = session.get_trace_context()`"; `FIXPP_ELOG` "reads an atomic engine trace-context snapshot"; anchor §4.3 and contracts/log-core.md both restate this. Complete.
- [x] CHK004 Is every `Record`'s carriage of `trace_id` (16 B) / `span_id` (8 B) as plain fields with no extra allocation stated as a requirement? [Completeness, Spec §FR-012] — PASS: FR-012: "Every `Record` MUST carry `trace_id` (16 bytes) and `span_id` (8 bytes) as plain fields, with no additional allocation for correlation"; data-model §Record layout confirms 16-B `trace_id` + 8-B `span_id` in the 48-B header; `static_assert(sizeof(Record)==256)` enforces the size. - [x] CHK005 Is the context-free behavior specified as all-zeros with no UB/panic (not merely "uncorrelated")? [Clarity, Spec §FR-013, Edge Case] — PASS: FR-013 specifies `FIXPP_LOG0` produces "zeroed context"; spec Edge Cases: "Context-free log site → all-zero trace/span, treated as uncorrelated"; US2 AS3: "record carries all-zero `trace_id`/`span_id` with no panic or undefined behavior"; TS-7 tests specifically under ASan; anchor §6.4 Tier 3: "No panic, no undefined behaviour." Explicitly "no UB/panic" — not merely "uncorrelated".

## Edge Case & Failure Coverage

- [x] CHK017 Are OTLP export-failure requirements complete — bounded retries with a **quantified cap**, then drop with an export-failure counter, no retry storm? [Completeness, Ambiguity, Spec §FR-019, Edge Case] — PASS: FR-019: "OTLP export retries MUST be capped"; data-model §OtlpLogSink: "`max_export_retries=3`" (quantified default); contracts/log-sinks.md: "Retries capped (no storm; `otel_export_failed` core slot 127... on give-up)"; anchor §6.5: "Retries are capped at `max_export_retries` (default 3)... no retry storm". The cap is quantified as a `max_export_retries` config field with a default of 3.
- [x] CHK018 Is the retry cap actually quantified in the requirements (FR-019 says "capped" — is the number specified, or deferred to tasks)? [Gap, Spec §FR-019] — PASS: FR-019's "capped" is backed by `OtlpLogSinkConfig::max_export_retries=3` in data-model and contracts. The cap is an operator-configurable parameter (not a magic constant) with a default of 3; the requirement is both quantified via the default and operator-controllable. Not deferred to tasks — present in contracts and data-model.
- [x] CHK019 Is the no-op-provider fallback on provider-init failure specified as observable behavior (engine continues, metric/span ops are silent, `otel_provider_init_failed` surfaced)? [Completeness, Spec §FR-019, Edge Case] — PASS: FR-019: "on provider-init failure the engine substitutes a no-op provider and continues"; data-model §TracerProvider/MeterProvider: "On provider-init failure ⇒ no-op provider (`otel_provider_init_failed`), engine continues"; contracts/error-block.md: `otel_provider_init_failed` (128) "returned via `expected_t<void>`; no-op provider fallback"; tasks.md T040 adds the negative test asserting the engine does not throw/crash + no-op behavior. Observable + error code + engine-continues all specified.
- [x] CHK020 Are requirements defined for a sink-level OTLP failure vs a provider-init failure as distinct paths (different counters/errors)? [Clarity, Spec §FR-019, Edge Case] — PASS: data-model error block table distinguishes: `otel_export_failed` (127) = "OTLP batch export failure counter; engine continues" (internal counter via `OtlpLogSink`'s `sink_error_count` + eventual `export_failed` event); `otel_provider_init_failed` (128) = "provider ctor failure; returned via `expected_t<void>`"; contracts/error-block.md row-by-row; contracts/log-sinks.md §OtlpLogSink: "retries capped... `otel_export_failed` core slot 127... on give-up". Two distinct error codes for two distinct failure paths.
