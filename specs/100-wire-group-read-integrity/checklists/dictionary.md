## The predicate's arms

- [ ] CHK001 Arm 3 requires "no context key in any context". Does that consult only the bitset, which `group_ctx_` keys set, or also the arm-1 store's keys and the section store? Section records explicitly do not set the bitset. [Ambiguity, research D2 "The predicate", data-model "table_view registration"]
- [ ] CHK002 Is arm 3's answer stated for a tag that only section records register, such as a header group whose count tag has no `group_ctx_` key anywhere? Can arm 3 then fire for that tag in the body of every message? [Coverage, research D2]
- [ ] CHK003 Is arm 1's key set (every `(msg_type, parent_path, no_tag)` the expansion reaches) stated as one set with a hand-built table's `group_ctx_` keys? That would define the accessor's answer for a hand-built table that has no delimiter records. [Clarity, research D2 "The predicate"]
- [ ] CHK004 The lookup runs the `group_bit` pre-filter first. Is it stated that every tag holding an arm-1 or section record also has `group_bit` set, so that the pre-filter never hides a record? [Assumption, research D2 "Per-occurrence records"]
- [ ] CHK005 On a key clamped to the outermost `kMaxGroupContextDepth` entries, two different deep paths share one key. Is it stated which record that key holds, and what the predicate answers for the path whose record was not kept? [Edge Case, research D2]
- [ ] CHK006 Clarifications says NoPartySubIDs(802) "is not a group here" at the top level. Research D9 (iv) has a count tag that one message places both nested and at its root, and it reads as a group at the root. Is one rule stated that gives both 802's `TYPE_MISMATCH` and (iv)'s cursor? [Consistency, Spec "Clarifications", research D9]
