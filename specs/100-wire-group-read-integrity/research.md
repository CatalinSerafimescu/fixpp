## Decisions

### D1 — The probe bound is a per-build budget, and exceeding it ends the build (#645)

**Decision:** replace `OffsetTable::build`'s per-insert cap with a per-build probe budget of `kMaxBuildProbe` × `entries_.size()`, counted across the insert loop. When the budget is spent, `status_ = err_offset_table_full(); entries_.clear(); overlay_.clear(); return;`, the shape of every other build-failure arm. An occurrence is one entry of `entries_`, so a repeated tag counts: its insert walks to its first occurrence's slot, and those steps are probes. The overlay indexes first occurrences, so FR-008's "every distinct tag" means each tag's first occurrence. A probe is one step past an occupied slot, the `slot = (slot + 1U) & mask` advance the insert loop counts today. Inspecting the home slot is not a probe, so an insert at an empty home slot costs none. The build fails at the step that takes the running total over the budget. The constant is the same; the worst-case build stays at most `kMaxBuildProbe` probes per occurrence, so it stays linear and the DoS bound is unchanged. `find()` is untouched: its walk is already bounded by `overlay_.size()`, so a tag placed far from its home slot is still found. The refuted comment claims ("only a crafted hostile frame can hit", "normal frames keep clusters far below the cap", "robin-hood overlay") are deleted, keeping only the condition (the project's comment-claims rule: run `.claude/scripts/check-comment-claims.py` on the diff). The same claims in `.specify/2b-wire.md` get "Updated (100-wire-group-read-integrity)" notes in the same change (census), so no copy is left behind.

**Measurement (Gate A round 1, 2026-11-07; figures in the Opus review).** Recipe: replicate `mix()` and `overlay_cap_for()` as `tests/wire/hostile_input_hardening_test.cpp` does; insert n distinct tags in frame order with the build's linear-probe loop; record the longest single-insert probe and the total probes per occurrence; vary n over 20…3276 and the tag draw over 1..1000, 1..2000, 1..9999 and 1..65535, a fresh 32-bit seed per trial. Result, as conditions: consecutive tag runs and sets of up to about 200 distinct tags never reached the per-insert cap; sets of a few hundred or more distinct, non-consecutive tags at overlay load near 0.8 reached it for a small fraction of seeds; every trial's total probe work stayed inside the per-build budget, by the margin the review records (not restated here). The recipe re-runs on demand. The committed re-check is US3.2's cell (tasks T008), a frame that reaches today's per-insert cap and must parse. A crafted window cluster under a known seed (D9) exceeds the budget at every size from 512 entries (a frame of about 4 KB) up, inside both the entry limit and the inbound byte limit.

**Rationale:** one ending a caller already handles: `Parser::parse` fails with `wire_offset_table_full`, the C ABI maps it to `FIXPP_ERR_WIRE_LIMIT_EXCEEDED` (`src/capi/error.cpp`), an inbound session takes 092's late-parse-failure terminal close. With the per-insert cap that ending would also fall on non-crafted frames, and the per-process seed makes the peer's resend close the session again until the process restarts, where QuickFIX parses and delivers the frame. With the per-build budget only a frame crafted against the seed reaches it, so a terminal close is proportionate. The seed is fixed for the life of the process, and the production seed is not weakened (spec Assumptions). So a peer that has crafted a frame against it can close any session of that process, and close it again on every resend, until the process restarts. That residual is accepted: the frame is hostile, and re-seeding is rejected below. No new `core::error` slot, so no `expected_error_map.csv` row. The ending still breaks a published promise for the crafted case, declared in D8.

**Alternatives:**
- Keep the per-insert cap with D1's ending: terminally closes sessions on legitimate traffic (the measurement). Rejected; it would be an owner decision, not a design default.
- A new `wire_index_probe_cap` error: more precise in a log, but a new slot, a CSV row and a C-ABI code mapping for an ending the caller handles identically. Rejected.
- Linear scan on a miss, or re-seeding and rebuilding: the first is the O(occ²) the cap prevents; the second is unbounded retries against an adaptive attacker. Rejected.

### D2 — Group-ness is one context-exact predicate, asked before anything else (#647)

**Decision:** `OffsetTable::group()` evaluates, in order:
1. the dict-free decline (#220), widened to decline when the bundle has no registration callback;
2. locate the count entry; absent → absent (unchanged);
3. `registered(stored context, no_tag)`; false → not a group (`err_required_field_missing`, as today's "absent" answer). `group()` is public. Its result keeps today's conflation: absent and not-a-group both answer `err_required_field_missing`. A caller that needs to tell them apart uses `find(no_tag)`, or `group_slices_status().is_group` (D3);
4. only then the "count field is the last entry" shortcut → present, zero instances;
5. the next field's membership: **not a member → present, zero instances** (`group_index{no_tag, first, 0}`), where today it returns absent;
6. otherwise today's extent walk, unchanged (`consume_group_extent` and the split are untouched). The walk reads the declared count as today: it consumes at most that many instances, and a declared 0 consumes none (its zero-count arm, B-004-7). So a registered count of 0 followed by member fields reads present with zero instances, and a declared n below the instances on the wire reads n.

**The predicate.** This is the one statement of its arms; the spec, the data model and the contract point here.
`registered(ctx, no_tag)` holds when any of these arms holds:
1. **Context arm:** `group_ctx_` has a key for `(msg_type, parent_path, no_tag)`, whatever its record holds: members, a delimiter, or required members only. A record whose delimiter is 0, as a hand-built `add_group_member_ctx` leaves it, still counts. *(Arm 1 is no longer keyed from `group_ctx_` alone; it reads the key set the next sentences define: superseded by Gate A round 4 hand-edit (owner, 2026-11-07).)* The key set is every `(msg_type, parent_path, no_tag)` at which the message's expansion reaches the group. `build_table_view`'s context loop keys one parent per count tag (`immediate_parent` over the de-duplicated `message_fields` run), so a count tag reached at two parent paths in one message has a `group_ctx_` key at one of them only. Arm 1 therefore reads the arm-1 store, a registration-only key set that `build_table_view` fills from the message's delimiter records (`msg_group_ctx_delims`), which the loader captures at every occurrence with its full path, together with the `group_ctx_` keys of a hand-built table. The set creates no `group_ctx_` key, so the validator is unchanged (FR-009). Each key the set fills from the delimiter records carries that occurrence's record, which the wire membership and delimiter lambdas read ("Per-occurrence records" below). *(The sentence read "so the validator and the membership hook are unchanged": superseded by Gate A round 5 → hand-edit 3 (owner, 2026-11-07).)*
2. **Section arm:** `table_view` holds a section-group record for `(parent_path, no_tag)` (its delimiter and direct members, "Per-occurrence records" below): the dictionary declares a group with count tag `no_tag` under `parent_path` inside its header or its trailer, whatever the message type (QuickFIX C++ `_header_` / `_trailer_`; QuickFIX/J `HEADER_ID` for the header). *(The parenthesis read "QuickFIX/J `HEADER_ID`" as if it covered the trailer: superseded by Gate A round 4 hand-edit (owner, 2026-11-07).)* `is_header_tag` and `group_bit` are not consulted. *(Supersedes round 2's header arm, `parent_path` empty ∧ `is_header_tag` ∧ `group_bit`, which is not a section registration: superseded by Gate A round 3 hand-edit (owner, 2026-11-07).)*
3. **Bare-only arm:** `no_tag` has no context key in any context, and `group_bit(no_tag)` is set (a bare-only registration). "Context key" here means a `group_ctx_` key, read through the "has a context key" bitset ("It is backed by" below). Arm-1 store keys and section records do not set the bitset. So a tag that only section records register (no `group_ctx_` key anywhere) satisfies arm 3 in every context, body included, once its `group_bit` is set. That is the answer the bare fallback gives it today. The loaders record header and trailer groups per declared message (survey, membership hook), so such a tag needs a dictionary whose declared messages never reach that section group.

Arm 1 holds when `(msg_type, parent_path, no_tag)` is in the union of the arm-1 store and `group_ctx_`'s keys. A hand-built table has no delimiter records, so for it `group_ctx_`'s keys are the whole set.

Otherwise the tag is not registered. The count's value never decides group-ness. Steps 1 to 5 never read it, and there is no strict-zero parser. Step 6's unchanged extent walk reads it, as today.

**Clamped keys.** A key clamps only for a path deeper than `kMaxGroupContextDepth`. That constant mirrors the wire's `kMaxGroupDepth`, beyond which the extent walk fails `wire_group_too_large` (FR-011). At an arm-1 key, two distinct paths that clamp to one key are refused at load: `flush_group_ctx_delims` reports the clash and both loaders throw their parse error (#264). The section walk keys the same header and trailer paths that each declared message's expansion captures, because both loaders expand the header and the trailer inline per message: XML through `header_node_` / `trailer_node_`, Orchestra through the components 1024 and 1025 that each message's structure references. So in a dictionary that declares such a message, a section clamp collision is refused by the same check. Outside that case the section key keeps the first walked path's record, the rule of a shared section key ("Not fixed, and not pre-existing in its ending" below).

The arms follow QuickFIX's lookup keys. C++ `2ce8a60` `DataDictionary::getGroup(msg, field, …)` (`DataDictionary.h`) requires a `(field, msg)` entry for a body group. Header and trailer fields are parsed with `setGroup("_header_", …)` and `setGroup("_trailer_", …)` (C++ `Message::setString`; the groups are loaded by `addXMLGroup(…, "_header_"/"_trailer_", …)`), keys that do not depend on MsgType. QuickFIX/J does the same for the header (`DataDictionary.HEADER_ID`), but its `parseTrailer` forms no groups. For trailer groups the engines differ, and the section arm follows QuickFIX C++: it is also today's ending (FR-009) and fixpp's ending in a declared message type. *(The previous sentence named only `_header_` and `HEADER_ID`: superseded by Gate A round 4 hand-edit (owner, 2026-11-07).)* fixpp's loader records header or trailer groups, at any depth, per declared message (survey, membership hook), so without arm 2 a header or trailer group, at any depth, in an undeclared MsgType would stop reading as a group.

Baseline: a scratch probe on today's tree (Gate A round 4, 2026-11-07, not committed) showed that a count ≥ 1 group read ignores where the dictionary declares the group and that every count-0 group reads `TYPE_MISMATCH` on the flat getter (the nested getter's `OK`/0 for a registered zero-count nested group stays a control, US1.3); the exact predicate departs from that baseline, so a count ≥ 1 read outside the declared context becomes `TYPE_MISMATCH` where the dictionary does not register the tag there (contract "Changes from 1.14"), and the RED run on `fa778a8e` stays the witness.

The records are filled by walks beside the ones that fill `header_tags_` (`collect_header_tags` in both loaders), over the header and the trailer (XML `<header>` and `<trailer>`; Orchestra components 1024 and 1025, a `fixr:groupRef` inside them being a nested section group). Each walk carries the enclosing path and visits a component or group definition once per (definition, enclosing path), not once per definition: `collect_header_tags`' `walked` and `walked_groups` sets serve the flat tag set and must not gate the records. A definition already on the current path is skipped, which ends a cycle. A group is recorded once for every path of section groups that encloses it, never through a body context. The key is clamped as `make_group_ctx_key` clamps it (the outermost `kMaxGroupContextDepth` entries). *(Round 3's text, "the walks that fill `header_tags_` … extended … to carry each group's parent path", which visits each definition once and so records one path: superseded by Gate A round 4 hand-edit (owner, 2026-11-07).)* *(Round 2's five "Conditions arm 2 rests on" are deleted: the record is structural, so none is needed. **Per-occurrence records (Gate A round 5 → hand-edit 3, owner, 2026-11-07).** Registration says that a key is a group, not where its instances end. On a `group_ctx_` miss, `table_view::group_member_tags(msg_type, parent_path, no_tag)` and `group_first_field(…)` answer from the bare store, which holds one definition per count tag. Its members come from the `GroupDef` node recorded at the first `expand_field_list` call that reaches the tag (`group_index_by_no_tag_`, first-seen; the component- and group-cache expansions record it too). Its delimiter is the first-seen projection of the delimiter pool, in pool order. The two can come from different occurrences. Step 5 then turns the membership miss on the next field into "present, zero instances".   4. the bare store.

  Arm 1 comes before the section record, so a declared message never resolves through a section record at the same `(parent_path, no_tag)`. The `group_bit` pre-filter hides no record as long as every count tag that holds an arm-1 or a section record has `group_bit` set. `as_table_view` sets it for every group the message expansion reaches, and the expansion reaches every section group through each declared message's header and trailer. ### D4 — C-ABI getters: one ordered table of endings (#541, #644, #647)

**Decision:** both getters answer from the one ordered table in `contracts/capi-group-getters.md` (first condition that holds): argument errors; absent → `TAG_NOT_FOUND`; read could not complete → `WIRE_LIMIT_EXCEEDED`; not registered → `TYPE_MISMATCH`; registered, zero instances read → `OK`/0, `*out` null; n instances → `OK`, cursor. The table is true for both getters because a failed read means a present, registered tag (the invariant is stated in data-model `nested_slices_result`; D11 establishes it). So the nested getter may test the status before its presence probe and still match the table.

- Flat getter: `find` (allocation-free) → absent; `group_slices_status`: status ≠ ok → `WIRE_LIMIT_EXCEEDED`; `!is_group` → `TYPE_MISMATCH`; empty → `OK`/0; else the cursor.
- Nested getter: checks its two out-pointers first (`NULL_HANDLE`, outputs untouched, when either is null), then writes null/0 to both before validating `g` and the index (row 0b, as the flat getter does); `nested_group_slices`: status ≠ ok → `WIRE_LIMIT_EXCEEDED`; `!is_group` → its existing presence probe: absent → `TAG_NOT_FOUND`, present → `TYPE_MISMATCH`; empty → `OK`/0; else the cursor.
- The cursor-shell `new_object` sits in `try { … } catch (std::bad_alloc const&) { return FIXPP_ERR_WIRE_LIMIT_EXCEEDED; }` with the out-parameters left null/0. Only `std::bad_alloc` can reach it. The shell's allocation throws what the arena's resource throws: a `monotonic_buffer_resource` whose upstream is `null_memory_resource()` or the heap throws `std::bad_alloc`. `fixpp_group`'s default construction must not throw, which T044 asserts with `static_assert(std::is_nothrow_default_constructible_v<fixpp_group>)`. Every other call on the getters' path is `noexcept`.

**Rationale:** `FIXPP_ERR_WIRE_LIMIT_EXCEEDED` ("Wire-level capacity or size limit exceeded (DoS bound)") is what the nested getter returns today and what `wire_offset_table_full` / `wire_group_too_large` already map to. One code for one cause (FR-007). The code's documentation in `include/fix/c_api/error.h` is not amended: the per-message arena is a fixed capacity bound in that sense (see Alternatives), and 073's nested getter already returns the code for it.

**Alternatives:** a `FIXPP_ERR_OUT_OF_MEMORY`-style code: the arena is a fixed per-message bound, not process memory; and the nested getter's shipped answer would change too. Rejected. Separate ordered tables per getter with "exhausted + absent nested = `WIRE_LIMIT_EXCEEDED`": writes into the contract an ending 073 FR-007 forbids, and one that depends on residual arena bytes. Rejected (D11).

### D5 — A group read stopped by a wire limit is a failed read, with its own status (found at plan)

**Finding:** `OffsetTable::group()` returns `err_group_too_large` when an instance exceeds `max_group_entries_per_instance` or nesting exceeds its depth limit. `group_slices_status` turns that into an empty, not-failed result, so the typed read is empty and the flat getter answers `TYPE_MISMATCH`. Same class as #644 (a present group read as empty); not filed.

**Reachability, as conditions.**
- **Top level: reachable.** A session's root table runs with `Config{.max_offset_entries = inbound_entry_cap_}` and the default per-instance cap (`src/session/session.cpp`). Where the root's entry cap exceeds the per-instance cap, a peer reaches the instance cap with a frame that repeats a member tag past it in one instance, on a validation-off session. The session's root entry cap is `parse_capacity::entry_cap_for(inbound limit)` (`src/session/parse_capacity.hpp`). At `kDefaultInboundLimit` it exceeds `default_max_group_entries_per_instance`, so a session with the shipped defaults reaches the top-level arm. Re-derive from those constants; an advertised MaxMessageSize(383) small enough to bring `entry_cap_for` under the per-instance cap makes the arm unreachable on that session.
- **Nested: defensive.** `build_nested_subview` builds the sub-table with the default `Config`, whose entry cap (`default_max_offset_entries`) equals the per-instance cap (`default_max_group_entries_per_instance`). `consume_group_extent` flags an instance only when it holds more entries than the per-instance cap, so a sub-table that large fails `OffsetTable::build`'s entry-cap check first (D7). The nested walk starts at its stored context's depth and descends the same members with the same bundle as the root walk that produced the parent instance, so a parent read that completed bounds its depth. The one exception is a caller passing a different bundle to the six-argument `nested_group_slices`; the C getter (the four-argument overload, which uses `this->hooks_`) and the generated accessors (`ctx_.hooks`) do not. The status mapping is kept, since it costs nothing, and the RED phase records the arm as unreachable. *(The sentence ended "as contract row 3's malformed-data arm"; that arm is constructible, T012: superseded by orchestrator ruling, 2026-11-07.)*

**Decision:** the two result structs carry one `std::uint8_t`-based enum `group_read_status { ok, alloc_failed, limit_exceeded }` (field `status`) in place of `bool alloc_failed`. `alloc_failed` is set for a caught `bad_alloc` (slices, the cache row of a group with instances (D10), the sub-table shell or its cache row, a sub-build `out_of_memory`). `limit_exceeded` is set for `wire_group_too_large` and for a sub-build `wire_offset_table_full` (D7). `group_view` keeps `alloc_failed()` (`status == alloc_failed`, its documented meaning unchanged) and gains `read_failed()` (`status != ok`); its doc tells typed readers to check `read_failed()`. Constructors:
- both `bool` constructors are kept as they are (`true` → `alloc_failed`);
- two status constructors are added **without** a default argument, so `group_view{inst, ctx}` still selects the `bool` overload unambiguously;
- `MessageView::group<>()` (D6) and the emitter pass `r.status`.

The C ABI maps any `status != ok` to `FIXPP_ERR_WIRE_LIMIT_EXCEEDED`. Renaming the result structs' field is a C++ source change for any reader of it, including a header generated by an older emitter; it is declared in the B&L delta (Phase 6).

**Codegen consequence:** the generated nested accessor passes `r.status` where it passes `r.alloc_failed` today, because the field is renamed. That is one token in `emit_messages.cpp`'s nested accessor line, regenerated text for every nested accessor (the checked-in goldens included, census), and the pinned literal in `accessor_resolution_census_test.cpp`. An `enum class` does not convert to `bool`, so an emitter left on the old field or passing the status to a `bool` parameter is a compile error, not a silent misreport; it needs no mutant of its own.

**Alternatives:** widen `alloc_failed()`'s meaning (the first draft): makes a public accessor lie about hostile structural input. Rejected. Two flags (`alloc_failed`, `limit_exceeded`) that every reader must OR. Rejected. Replace the constructors' `bool` parameter with the status: `group_view{…, true}` in caller source stops compiling, for no gain. Rejected. Leave D5 out and file it: keeps a silent loss on lines this feature rewrites. Rejected.

### D10 — The group cache records only completed reads (FR-007)

This is the one statement of the cache rule; the data model points here.

**Decision, flat cache (`group_index_` in `group_slices_status`).** A row is cached only for a completed read, and a failed read leaves no row.
- **A registered group with n ≥ 1 instances.** The count pass has computed n without allocating, so the row is pushed after the count pass and before the `allocate()`. If the push throws, the read fails `alloc_failed`; on a monotonic resource every repeat fails the same way. If the slice allocation then throws, the row is popped (`pop_back`), so the failed read caches nothing.
- **An answer that needs no slices** (absent, not a group, zero instances read). The push has its own `try`. If it throws, the answer is served uncached: recomputing it allocates nothing and yields the same answer.
- **A limit failure** (`limit_exceeded`) pushes nothing. `group()` allocates nothing, so the failure recurs deterministically.

**Decision, nested cache (`nested_cache_` in `nested_group_slices`).**
- When the call builds a sub-table, its row is pushed **before** the build. A failed push is a failed read, resolved as a null sub-table is (mode (a), through D11's failure rule). The built table, or null, is stored in the pushed row.
- When the call reuses the sub-table of an earlier row for the same slice and bundle, a failed push serves the answer uncached. The repeat finds the same row and the same table.
- A cached row is re-resolved at the cache-hit exit through `resolve_nested_result` (D11), whatever the row holds (a null sub-table, a failed build, a built table). So a repeat answers as the first read did.

So a completed read's repeat fails only where the getter allocates a cursor shell (FR-007).

"Every repeat fails the same way" assumes a monotonic arena, one that returns nothing to its free space before it resets. The session's parse arena is a `monotonic_buffer_resource`, and so is every rig D9 names. `MessageView` accepts any `std::pmr::memory_resource*`, so a caller-supplied resource that reuses freed memory (a vector reallocation inside the read frees its old buffer) can let a repeat complete where the first read failed. FR-007 states the condition.

**Alternatives:**
- Cache the status in `group_span` too and replay it. Workable within 16 bytes, but caching an outcome is what made the first draft's repeat read differ from the first; recomputing has one source of truth. Rejected.
- Push after the slices and serve a materialized result uncached when the push fails (this bundle's round-1 text): the slice bytes stay consumed on the monotonic arena, so the repeat allocates again and can fail. One condition, two endings. Rejected; the same holds for building a sub-table before its row.
- Reserve machinery (a pre-reserved row slot per read): more state than push-then-pop for the same guarantee. Rejected.

### D11 — On the nested path, a failed read means a present, registered tag (FR-004, 073 FR-007)

**Decision:** `resolve_nested_result` receives the instance slice, the call's `ctx` and the caller's `hooks` (those of the `nested_group_slices` call), at both of its exits: the cache-hit exit and the final exit. When any failure mode fires (a, c, D7, or a failed nested cache push (D10)), it decides in this order:
1. **Registration first, because it is the cheaper test.** Ask D2's predicate for `(ctx, nested_no_tag)` through `hooks`' registration callback; it is O(1) and allocates nothing. Not registered → `{empty, ok, !is_group}`. A null registration callback answers not registered (as D2 step 1): `{empty, ok, !is_group}`. The nested getter's existing presence probe then separates `TAG_NOT_FOUND` from `TYPE_MISMATCH`, so the wire layer needs no scan on this branch.
2. **Presence.** Scan the slice for `nested_no_tag` without allocating: a field walk that splits Length+Data through `hooks.data_tag_for_length`, the rule `OffsetTable::build` uses. Absent → `{empty, ok, !is_group}`. "Present" means anywhere in the instance slice, nested instances included. The C getter's `scan_slice_for_tag` walks every field of the slice, and the sub-table indexes every tag in it, as the root table's `find` does for the whole message on the flat getter. So a tag that occurs only inside a deeper nested instance is present here. If it is not registered in this `ctx`, it reads `TYPE_MISMATCH`, not `TAG_NOT_FOUND`.
3. **Present and registered** → the failed status.

It never uses `this->hooks_`, for the registration callback as for the scan: pairing the root table's own bundle with the caller's split would reintroduce the mismatched-pairing defect fixpp#426 closed. (`scan_slice_for_tag` is local to `src/capi/message_read.cpp` and uses `parser.hpp`'s `field_iterator`, which `offset_table.hpp` cannot include, so the wire layer has its own walk.)

**Condition: one (slice, bundle) is read under one `ctx`.** `nested_cache_` rows, and the reuse of an earlier row's sub-table for the same slice, are keyed `(slice_data, hooks.opaque_dict(), nested_no_tag)`, without `ctx`; a sub-table's stored context is seeded once, at its build, and `ctx` is ignored on a warm hit (the `nested_group_slices` doc comment in `include/fixpp/wire/offset_table.hpp`). So a completed nested read answers registration in the context seeded by the first call over that slice and bundle, while this failure branch asks the call's own `ctx`. FR-001's nested context is the call's `ctx` while every caller reads a given (slice, bundle) under one `ctx`.
